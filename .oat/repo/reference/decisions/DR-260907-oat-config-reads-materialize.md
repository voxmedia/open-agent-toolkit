# OAT config reads materialize `__proto__`-named keys as own data properties

## Context

`packages/cli/src/config/json.ts` is the single parse chokepoint for every OAT config read. It used `jsonc-parser`'s `parse`, which fills a plain object by assignment, so a member literally named `__proto__` reached the legacy prototype setter. That produced two defects at once: the key was lost as data, and its value became the parsed object's prototype, after which normalization read the injected members as though they had been configured. Reproduced end-to-end on the wave-6 base: a shared config holding only `{"__proto__":{"git":{"defaultBranch":"INJECTED"}}}` made `oat config get git.defaultBranch` answer `INJECTED`, and `oat config list` and `oat config dump` attributed it to the shared surface. The write path already preserved such siblings (`normalizeOatConfig` builds them with `Object.fromEntries` under a comment naming this hazard), so the read side was the remaining gap, documented as a scope-out in the FR10 write-path test.

## Decision

Read `packages/cli/src/config/json.ts`. `parseJsonConfig` keeps `parseTree` for error collection, then materializes the tree itself with an explicit stack, defining every own key through `Object.defineProperty` (enumerable, writable, configurable). `Object.defineProperty` stores `__proto__` as an ordinary own data property and never invokes the prototype setter, so the key survives while nothing is inherited. The objects are otherwise completely ordinary and keep `Object.prototype`. The obvious alternative, `jsonc-parser`'s own `getNodeValue`, was implemented first and rejected under cross-model review for two measured regressions: it returns null-prototype objects, which made `String(rawDefaultScope)` in the invalid-scope diagnostic at `config/oat-config.ts` throw `TypeError: Cannot convert object to primitive value` where it had produced an actionable `CliError`; and it recurses, capping accepted nesting near 2112 levels where the previous `parse` reached about 4068, turning deep-but-valid documents into a `RangeError` instead of the contracted `SyntaxError`. Materializing iteratively into plain objects avoids both, so no consumer normalization layer is needed. The error contract is unchanged: the same documents are rejected with the same `SyntaxError` message, and empty or whitespace-only content still throws `ValueExpected` rather than returning `undefined`. The alternative close, documenting the limitation and closing the backlog item as will-not-do, was rejected because the defect is not only a lost pathological key but a config-file-driven prototype injection that the resolver reports as real configuration.

## Consequences

The objects `parseJsonConfig` returns are ordinary, so every implicit coercion, prototype method, `JSON.stringify` round-trip and zod `safeParse` on a parsed object behaves byte-identically to before; the parsed result also round-trips through `JSON.stringify` with the `__proto__` key intact, so a read-modify-write cycle no longer erases it. All ten production callers (`config/oat-config.ts`, `config/sync-config.ts`, `config/user-sync-config.ts`, `commands/gate/index.ts`, `commands/config/index.ts`) pass unchanged, and a `__proto__`-keyed config now flows through `oat config get`, `set`, `unset`, `list` and `adopt` without loss.

That equivalence now extends to the maps rebuilt downstream from the parsed objects. `BL-260908-guard-normalized-config-maps` closed the gap this paragraph previously scoped out, under the plan `2026-09-08-harden-normalized-config-maps`. Both normalizers build their maps with `Object.fromEntries` instead of member assignment: `normalizeRecordMap` (`config/oat-config.ts:547-573`), which backs the gate and exec-target maps, and both provider assignment sites in `normalizeDispatchMatrix` (`config/dispatch-matrix.ts:312` for the scalar branch and `:351` for the tier branch — the scalar branch silently dropped the entry rather than installing a prototype, the same data loss by a different route). A key named `__proto__` therefore stays an own data key on those maps, `Object.keys` and `Object.entries` yield it, `'command' in skills` is false, and the map keeps `Object.prototype`.

Because the key is now visible to `Object.entries` for the first time, the same plan closed the sites that change exposed, plus the unguarded user-named lookups the sweep found. The standing rule is that **any lookup on a config-derived map with a user-supplied name is read through `getOwnKey`, and any assignment under such a name is written through `setOwnKey`** (`config/own-keys.ts`); a computed key in an object literal already uses define semantics and is safe. The guarded sites are `mergeExecTargetLayer` and `resolveExecTargetViews` (`config/resolve.ts`), the dispatch-ceiling provider lookup at `commands/config/index.ts:2042`, `applyDispatchMatrixRecommendation` and `effectiveTerminalReviewerNotices` in the same file, and `setExecTarget` at `commands/gate/index.ts:1225`. The repository-wide sweep that plan prescribes found five further sites, all reproduced on the built CLI with a passing control: (A) `mergeEffectiveDispatchMatrix` (`commands/project/dispatch-ceiling/index.ts:2124`), which swallowed the preserved key one layer downstream into the effective matrix; (B) `resolveSelectedExecTarget` (`commands/gate/index.ts:1868`), where a `--target` id of `__proto__` or `constructor` skipped the adjacent `Unknown exec target` rejection and crashed; (C) the provider lookups at `commands/project/dispatch-ceiling/index.ts:2635` and `:2801`, guarded defensively — their map is built with a computed literal key, so it owns the name; (D) the dispatch-report builder (`providers/identity/dispatch-report.ts:381`), whose missing-provider `throw` is a truthiness check that an inherited member passed; and (E) `getCeilingAdapter` (`providers/ceiling/registry.ts:219`), the actual cause of the corrupt `unsupported (undefined)` output for `--provider __proto__`, where a non-nullish `Object.prototype` defeated the documented `??` fallback to the advisory adapter. The gate lookup at `config/resolve.ts:271` was already `hasOwn`-guarded and is now pinned by a test.

Two families were swept and left unchanged. The `pjm.remote` maps in `config/oat-config.ts` and `commands/config/index.ts` iterate constant key lists and catalogued `KEY_ORDER` segments, so no user string reaches their subscripts. The sync-config provider family is inert behind two independent guards: `SyncConfigSchema.providers` is a `z.record`, which drops the key during parsing, and `commands/providers/set/index.ts` rejects any name outside `knownProviders`. The zod guard is pinned by a control so that a future upgrade which stops stripping the key re-opens that classification rather than failing silently.

One further consequence is intended by the plan's Outcome rather than incidental: a `__proto__` key now persists through the user-config write path, which carries unknown fields with `Object.fromEntries` and an object spread (`config/oat-config.ts:1828` and `:1867`) and through the legacy rest-spread at `config/user-sync-config.ts:63-65`. A file written by this CLI and then read by a pre-fix CLI therefore reinstates the original injection, since the old reader still turns the key into a prototype. The FR10 read-write-read test pins the persistence half of that behavior.

Accepted nesting depth returns to within one stack frame of the previous `parse` (a cold bisection at the wave-6 final review measured base accepting 3585 nested arrays and head 3584), rather than to the roughly halved ceiling a recursive materializer imposed. Every depth number here is only meaningful with its measurement regime attached, because the limit is available stack rather than a property of the parser: measured cold in a fresh Vitest worker, `getNodeValue` caps near 2112 while base `parse` reaches about 4068; measured warm, base and head sit at parity within two frames of each other, around 6330. Parity is therefore the honest claim and a guarantee is not available, since `parseTree` still recurses while scanning and the two implementations can differ by a frame or two in either direction. The pinned control is consequently a fixed-document A/B at depth 2400 — above any recursive materializer's ceiling, comfortably inside both parsers' — rather than a search for each one's maximum, because two moving maxima converge once warm and make such a comparison flaky.

Out of scope and unchanged: the write path still drops unknown top-level keys, which is key-name-agnostic normalization behavior owned by `config/oat-config.ts`, not by this decision.
