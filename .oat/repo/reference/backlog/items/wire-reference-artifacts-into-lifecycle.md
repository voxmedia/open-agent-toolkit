## Description

**Needs real discussion before scoping — this is a directional proposal, not a ready-to-implement plan.**

OAT currently treats `.oat/repo/knowledge/` (architecture, stack, structure, conventions, testing, integrations, concerns, project-index — generated by `oat-repo-knowledge-index`) as a load-bearing input to the project lifecycle. Seven core skills read it: `oat-project-discover`, `oat-project-spec`, `oat-project-design`, `oat-project-plan`, `oat-project-progress`, `oat-doctor`, `oat-agent-instructions-analyze`.

By contrast, `.oat/repo/reference/` — the authored institutional memory (`current-state.md`, `decision-record.md`, `project-summaries/`, `roadmap.md`, `backlog/`) — is effectively write-only from the lifecycle's perspective. It's maintained by `oat-pjm-update-repo-reference` and occasionally cited by `oat-wrap-up`, `oat-project-import-plan`, `review-backlog`, and `oat-project-document`, but no core lifecycle skill consults it when starting new work. Users who want the institutional memory to inform discovery/planning/review have to manually direct the agent to read the files every time.

Competitive reference: [EveryInc/compound-engineering-plugin](https://github.com/EveryInc/compound-engineering-plugin) ships a `ce-learnings-researcher` agent as one of six always-on reviewers that searches a `docs/solutions/` directory on every code review. OAT has a stronger write side (dated, structured summaries + ADR file + current-state doc) but no equivalent read path. See `docs/research/compound-engineering-plugin-analysis-opus-4-7.md`.

Proposed change (minimum-viable, for discussion):

- **`oat-project-discover`** — at start, scan `current-state.md` + `decision-record.md` fully, and filter `project-summaries/` by keyword/recency match against the discovery topic. Load hits into context with an explicit token budget.
- **`oat-project-plan`** — read `decision-record.md` for ADRs that constrain planning. Surface matched prior-project summaries as "prior art."
- **`oat-project-review-provide`** — match `project-summaries/` against files/areas touched by the change; surface decision-record entries for cross-cutting concerns.

Explicitly **not** in scope: rewiring `oat-repo-maintainability-review`. That skill is meant to review cold — absence of `reference/` documentation should surface as a finding, not be backfilled from it.

Shared infra to consider: a small reference-reader helper parameterized by topic/file/area, with a token budget. The scanning pattern already exists in `oat-wrap-up` (filter summaries by window); factor and reuse.

## Caveats and open questions

- **Project-management surface is optional per repo.** OAT's workflow doesn't assume `.oat/repo/reference/` exists in every consuming repo — not all installations enable the pjm tools. Any lifecycle-skill change must no-op gracefully when the reference tree is missing. Decide whether missing-reference should be silent, a soft warning, or a strong signal.
- **Token budget governance.** 15+ summaries already exist in this repo alone; a mature OAT user repo could easily have 50+. Naive "read all summaries" would blow context. Need a consistent filter + budget contract (recency window, keyword match, file-path match) and probably a `.oat/config.json` knob for the budget.
- **Overlap with `knowledge/` vs `reference/`.** Worth naming the distinction explicitly in OAT docs: `knowledge/` = generated structural map; `reference/` = authored institutional memory. Different cadences, different consumers.
- **Staleness handling.** `current-state.md` can go stale between `oat-pjm-update-repo-reference` runs. Lifecycle skills that read it should note staleness thresholds (cf. `oat-project-discover`'s existing staleness pattern for `knowledge/`).
- **Relationship to HiLL checkpoints.** Should a reference-aware review surface "prior summaries suggest X" as a HiLL-style checkpoint that requires explicit acknowledgment, or pass it through silently? Likely the former for high-confidence matches, silent otherwise.
- **Matching quality.** Keyword/recency filtering is the floor. Consider whether frontmatter conventions on summaries (tags, affected components, related decision-record entries) would pay off, and whether that work is in scope here or a separate backlog item.

## Acceptance Criteria

- Discovery phase of `oat-project-discover` reads `current-state.md` + `decision-record.md` and surfaces matched `project-summaries/` entries when the reference tree exists.
- `oat-project-plan` reads `decision-record.md` when present and surfaces prior-art summaries matched against the planning topic.
- `oat-project-review-provide` consults `project-summaries/` and `decision-record.md` against the files/areas under review.
- Reading is no-op when `.oat/repo/reference/` is not present in the consuming repo (no user-facing error).
- A documented token-budget contract controls how many reference artifacts feed into each skill run.
- Follow-up docs update names the `knowledge/` vs `reference/` distinction explicitly.
