### Important

- **`gh api` posting example cannot build the inline `comments[]` array** (`.agents/skills/oat-review-provide-remote/SKILL.md:204-209`)
  - Issue: The posting step shows `gh api --method POST ".../reviews" --field event="$VERDICT" --field body="$REVIEW_BODY"` with a trailing prose comment `# plus comments[] entries: { path, line, side, body } per in-diff finding`. The GitHub reviews endpoint requires a JSON body containing a `comments` array of objects, but `gh api`'s `--field`/`-f`/`-F` flags only set top-level scalar (or `@file`) values and cannot express an array of objects. An agent following this example literally will either drop all inline comments or issue a malformed request. Inline-comment line mapping is called out in `design.md` → Error Handling as "the single biggest source of posting failures and must be handled explicitly," so leaving the actual posting mechanism unspecified undercuts Step 5's careful mapping work in Step 7.
  - Fix: Show the working mechanism — build the full payload as JSON and pipe it through `--input -` (e.g., construct `{ "event": "...", "body": "...", "comments": [ { "path": "...", "line": N, "side": "RIGHT", "body": "..." } ] }` and run `gh api --method POST "/repos/{owner}/{repo}/pulls/$PR/reviews" --input -`). Optionally note that an empty/omitted `comments` array is valid for a body-only review. This keeps the documented posting path executable as written.
  - Requirement: design.md → Data Flow step 3 (single `POST .../reviews`) + Error Handling → Inline-comment line mapping; plan.md p02-t03 Step 2 ("posting (`gh api`)").

### Medium

- **`acquireWorktree` failure during `git worktree add` can leak a partial worktree** (`packages/cli/src/review-remote/worktree.ts:58-80`)
  - Issue: `acquireWorktree` calls `mkdtempSync`, then `rmSync` to clear the path, then `execFile('git', ['worktree', 'add', ...])`. If `git worktree add` rejects after partially creating the target directory and/or registering `.git/worktrees/<name>` metadata, the function throws without returning a handle, so the caller's `finally { releaseWorktree(handle) }` never runs — the partial worktree and its git metadata leak. Tests cover success, idempotent release, and release-on-callback-throw, but not acquire-time failure. The SKILL.md's shell flow has the same shape (mktemp → rmdir → `worktree add`) and likewise relies on a later `worktree prune`/`rm -rf` only on the teardown path.
  - Fix: Wrap the `execFile('git', ['worktree', 'add', ...])` in a try/catch that, on failure, best-effort runs `git -C <repoRoot> worktree prune` and `rmSync(worktreePath, { recursive, force })` before rethrowing. Add a test that stubs/forces `worktree add` failure (e.g., point `repoRoot` at a non-repo dir) and asserts no `oat-review-wt-*` dir survives. This is a defensible omission for v1 (the failure window is narrow and `git worktree prune` reclaims dangling entries on the next acquire), so it can also be deferred — but the asymmetry between the leak-proof release path and the unguarded acquire path is worth recording.

- **`--review` posting-flag candidate risks a forward-compat false positive** (`packages/cli/src/review-remote/capability-probe.ts:64-69`)
  - Issue: `POSTING_FLAG_CANDIDATES` includes the generic `--review`. A future `agent-reviews` could add `--review` with an unrelated meaning (e.g., "show a review"), which the probe would report as `supported`, steering the skill toward an `agent-reviews` posting path that does not post. The word-boundary regex correctly avoids matching `--reply`/`--review` substrings, so this is purely a semantic-overlap risk, not a parsing bug.
  - Suggestion: Consider narrowing to the more intent-specific tokens (`--post-review`, `--submit-review`) and dropping the generic `--review`/`--post`, or add a comment noting the false-positive risk is accepted because `gh api` remains the safe fallback even if `agent-reviews` posting is mis-detected.

- **`Write` in `allowed-tools` is vestigial for a no-file-output skill** (`.agents/skills/oat-review-provide-remote/SKILL.md:7`)
  - Issue: The skill declares "No file outputs on this machine" (line 82) and BLOCKS local artifact writes (line 30); the diff-only fallback writes `$DIFF_FILE` via Bash redirection, not the Write tool. `Write` is therefore unused.
  - Suggestion: Acceptable as-is — `allowed-tools: Read, Write, Bash, Glob, Grep, AskUserQuestion` matches the sibling `oat-review-provide` / `oat-review-receive-remote` family convention and the plan prescribed this exact list. No change needed unless tightening tool grants is desired family-wide.

- **Args documented in a `## Arguments` body section rather than an `argument-hint` frontmatter key** (`.agents/skills/oat-review-provide-remote/SKILL.md:72-82`)
  - Issue: The local `oat-review-provide` skill exposes its arg surface via an `argument-hint:` frontmatter field; this skill uses a body section instead.
  - Suggestion: Optional. This matches the named consistency anchor (`oat-review-receive-remote`, which also omits `argument-hint`), and the validator passes, so this is a defensible choice. Could add `argument-hint` for parity with the provide family if desired.
