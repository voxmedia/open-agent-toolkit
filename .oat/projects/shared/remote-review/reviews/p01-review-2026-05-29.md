- **`gh api files` rename handling not surfaced by `parsePullFilesPatch`**
  (`packages/cli/src/review-remote/line-mapper.ts:78`)
  - Issue: The plan (p01-t03, Step 1) calls for handling renamed files "per
    `gh api` `previous_filename` field." `parseUnifiedDiff` correctly records
    `previousFilename` from `rename from`/`rename to` lines, but
    `parsePullFilesPatch` (the `gh api /pulls/<N>/files` path) only parses the
    per-file `patch` text — which does not carry the rename field. The
    `previousFilename` on `HunkRange` is therefore only ever populated on the
    `gh pr diff` (diff-only) path, not the rich-context `gh api files` path.
  - Suggestion: This is defensible for a pure-logic helper — the `gh api files`
    response carries `previous_filename` as a sibling JSON field, so the p02/p04
    caller is the natural place to thread it onto the returned `HunkRange[]`
    (e.g., `parsePullFilesPatch(patch, { previousFilename })`). Recommend a
    one-line code comment on `parsePullFilesPatch` noting that callers supply
    `previousFilename` out-of-band for the `gh api files` rename case, so the
    contract gap is explicit when p02/p04 wire it up. No change to test
    behavior required this phase.

- **`classifyFinding` LEFT-side mapping is untested for the `gh api files`
  patch parser** (`packages/cli/src/review-remote/line-mapper.test.ts:118`)
  - Issue: The LEFT-side (removed-code) classification is exercised only
    against `parseUnifiedDiff` output. `parsePullFilesPatch` ranges are tested

    `HunkRange` shape so the path is logically covered, but there is no direct
    assertion that a `removed: true` finding maps LEFT against patch-field
    ranges.
  - Suggestion: Add one assertion classifying a `removed: true` finding against
    `parsePullFilesPatch(FILE_PATCH)` ranges to lock the LEFT-side behavior on
