## Findings

### Critical

- **The transition can delete a concurrently advanced active ref** (`packages/cli/src/commands/project/sync/git.ts:48`)
  - Issue: The atomic push deletes `:${activeRef}` without a lease, and the non-atomic fallback repeats the same unguarded deletion at `packages/cli/src/commands/project/sync/ref-sync.ts:1102`. The preceding `ls-remote` probe is not part of either mutation, so another collaborator can advance the active ref after the probe. The current push then succeeds, deletes that newer ref, and installs the older bound SHA as the completed ref. A direct Git reproduction confirmed that an active ref advanced from the bound SHA to a newer commit is deleted by the current atomic refspec. This violates the exact source-SHA binding and transaction-safety requirements and can discard the remote reachability root for newer work.
  - Fix: Add an explicit active-ref lease bound to `sourceSha` on both the atomic and fallback deletions (for example, `--force-with-lease=${activeRef}:${sourceSha}`). Also lease the completed-ref expectation so a ref created or changed after the probe cannot be silently fast-forwarded or overwritten. On a lease rejection, re-probe and accept only an already-converged completed-only state at the bound SHA. Add atomic and fallback race tests that advance the active ref between the probe and push and assert that the competing ref remains intact.
  - Requirement: Discovery transaction safety and exact source-ref SHA binding; plan p01-t02 safe, idempotent transition.

### Important

- **Completed-only recovery fails when the terminal commit is not already in the local object database** (`packages/cli/src/commands/project/sync/ref-sync.ts:1182`)
  - Issue: A completed-only retry performs read-only `ls-remote` verification, skips the remote transition, and then creates the local completed ref with `git update-ref`. `update-ref` rejects a SHA whose object is not present locally. This occurs when a parent checkout already existed before another machine retired the project: it can see the later completed ref through `ls-remote` but has never fetched the unrelated synced-project commit. A direct Git reproduction produced `trying to write ref ... with nonexistent object`, so repeated calls do not converge without an out-of-band fetch. The current retry test reuses the checkout that created the project and therefore already owns the object.
  - Fix: Before creating a missing local completed ref, fetch the verified remote completed ref (or otherwise fetch the exact object) without making it an active discovery ref, verify the fetched SHA still equals `sourceSha`, and only then update/reconcile local refs. Add a two-checkout test where the recovery checkout predates completed-ref creation and lacks the object, then assert completed-only recovery succeeds and materializes only the local completed ref.
