## Findings

### Critical

- **The non-atomic fallback can delete the active ref after the completed ref changes** (`packages/cli/src/commands/project/sync/ref-sync.ts:1111`)
  - Issue: After verifying `both`, the fallback deletion pushes only `:${target.ref}` with an active-ref lease. The completed ref is not part of or guarded by that mutation. If another actor changes or deletes the completed ref between the probe at lines 1101-1109 and this push, the active lease still succeeds and removes the bound active ref. The later probe detects the mismatch only after the destructive mutation. Direct isolated-Git probes confirmed that a deletion-only push ignores a completed-ref lease when that ref is not updated, and that a non-atomic two-ref push can partially delete the active ref while rejecting a stale completed-ref update. This still violates the exact-SHA, reachability, and concurrent-change guarantees from the prior Critical finding.
  - Fix: Do not perform the fallback active deletion unless the remote provides a mechanism that jointly conditions the deletion on both the active ref and completed ref remaining at their verified expectations. A plain non-atomic multi-ref push with two leases is insufficient because it may partially update. If no such mechanism is available, fail closed after completed-ref creation/verification, preserve both refs, and return or persist an explicit recoverable `both` transition state rather than claiming retirement. Add a race test that changes or removes the completed ref immediately before fallback deletion and proves the active ref remains at `sourceSha`; success may be accepted only for completed-only state at that SHA.
  - Requirement: Discovery transaction safety, source-commit reachability, and exact source-ref SHA binding; plan p01-t02 safe, idempotent transition.
