## Findings

### Critical

- **The completed-ref lease is optimized out of an atomic both-ref transition** (`packages/cli/src/commands/project/sync/git.ts:49`)
  - Issue: `pushAtomicRefTransition` supplies a completed-ref lease and the refspec `${sourceSha}:${completedRef}`, but when the remote completed ref already resolves to `sourceSha`, Git treats that refspec as up to date and sends no update command for it. A packet-level reproduction with Git 2.54.0 showed `receive-pack` receiving only `sourceSha -> 000000... refs/oat/projects/<slug>`; no completed-ref command was present even when the command line expected either the existing SHA or absence. Consequently `--atomic` covers only the active deletion in this recovery/race state. A collaborator can change or delete the completed ref after advertisement while this push deletes the active ref, and the post-push probe at `ref-sync.ts:1263` detects the problem only after the bound reachability root may be gone. The happy-path both-ref retry at `ref-sync.test.ts:1982` does not inspect the transmitted update set or exercise this race.
  - Fix: Do not treat the current push shape as jointly leasing both refs when the completed update can be a no-op. Use a remote primitive that performs a genuine compare-and-swap over both refs, or fail closed while retaining the active ref whenever the completed ref may already exist; standard `git push --atomic` cannot condition deletion on an unchanged ref that the client omits. Add a deterministic protocol/server race test proving that a completed ref changed or deleted after advertisement cannot coincide with active deletion, and retain the existing fresh, both-ref, wrong-SHA, and retry assertions.
  - Requirement: Discovery transaction safety, source-commit reachability, exact source-ref SHA binding, and plan p01-t02's safe/idempotent transition contract.
