- **Migration `--print-prompt` test stubs the prompt reader instead of asserting bundled content** (`packages/cli/src/commands/pjm/index.test.ts:197`)
  - Issue: The command-level `--print-prompt` test injects `readPjmMigrationPrompt: async () => '# OAT PJM repo-reference migration\n'`, so it verifies wiring but not that the real bundled `assets/migration/pjm-restructure.md` is emitted. The bundle-consistency test (`bundle-consistency.test.ts`) does independently assert the real asset is bundled and contains the `OAT PJM repo-reference migration` marker, so end-to-end coverage exists across two tests rather than one.
  - Suggestion: Optionally add one assertion in `readPjmMigrationPrompt` (or a small integration test) that reads the real asset via `resolveAssetsRoot()` to close the literal "`--print-prompt` emits the bundled prompt" RED-step intent. Not required for correctness.

- **No dedicated idempotency-probe test for a second `--apply` run** (`packages/cli/src/commands/pjm/migrate.test.ts`)
  - Issue: The plan's p02-t02 RED step lists "Test idempotency probe." The suite covers the `already-migrated` short-circuit via a pre-seeded `pjm/` + `reference/decisions/` repo (line 200), but does not run a full legacy-apply followed by a second apply. I reproduced the second-apply path with a throwaway probe: the second run returns `already-migrated`, items are not re-suffixed, and the migrated record is byte-identical. Behavior is correct; only the explicit regression test is absent.
  - Suggestion: Add a test that seeds a legacy repo, applies migration, then applies again and asserts `status === 'already-migrated'` with an unchanged `pjm/backlog/items` listing and record content.

- **`oat pjm migrate` has no `pjm --help` snapshot** (`packages/cli/src/commands/help-snapshots.test.ts`)
  - Issue: The spec success metric states "New command help snapshots include `oat decision`, `oat pjm doctor`, and `oat pjm migrate`." There is no `pjm --help` snapshot in the suite (only root/init/backlog/decision/etc.), so `migrate` is not literally snapshotted. The root `--help` snapshot does include the `pjm` command (line 59), preserving discoverability, and `migrate` behavior is tested in `pjm/index.test.ts`.
  - Suggestion: Optionally add a `pjm --help` inline snapshot listing `init`, `doctor`, and `migrate` to satisfy the metric literally. Low value given existing behavior coverage.

- **Tracked migration asset vs. gitignored assets dir is an undocumented nuance** (`packages/cli/assets/migration/pjm-restructure.md`, `.gitignore:19`)
  - Issue: `packages/cli/assets/` is gitignored, but `migration/pjm-restructure.md` is force-tracked (it and `public-package-versions.json` are the only tracked files under `assets/`). This makes the asset its own source of truth, and the bundle script's temp-copy-before-`rm -rf` dance (lines 10-13, 130-134) correctly preserves it across a default-location rebundle. The behavior is sound and tested, but `implementation.md` (p01 note, lines 254-255) generically states "The assets directory is ignored," which could mislead a future reader into thinking the migration asset is regenerated rather than authored-and-tracked.
  - Suggestion: When updating `implementation.md` for Phase 2, note that the migration prompt is a force-tracked source asset (no canonical home outside `assets/`), unlike templates/skills which are mirrored from `.oat/templates` and `.agents/skills`.
