### High

- **Bare alias evidence still omits valid `availableModels` substitutions** (`packages/cli/src/providers/claude/targets.ts:204`)
  - Issue: The default `sonnet` equivalence class is fixed to Sonnet 5 and Sonnet 4.6, and the default `opus` class is fixed to Opus 5/4.8/4.7/4.6. Claude Code's current `availableModels` contract permits a family alias to resolve to the newest allowed older version, including Sonnet 4.5 in the documented examples and provider tables. Models absent from the effort table do not support effort. The resolver neither reads effective settings nor includes those non-effort substitutions in its equivalence class, so `sonnet/high` is accepted and materialized even when effective settings make the alias land on Sonnet 4.5. That silently changes the supposedly enforced model-plus-effort route and leaves the fail-closed part of prior H1 unresolved.
  - Fix: Resolve effective alias restrictions from the authoritative settings/runtime surface before admitting a bare alias, or fail closed whenever an unseen restriction can alter capability. Do not label a hand-selected subset `documented-substitutions`. Add a control with `availableModels` substituting Sonnet 4.5 that refuses an effort-pinned bare alias, alongside normal Sonnet 5, Claude Platform AWS Sonnet 4.6, Bedrock/Agent Platform Sonnet 4.5, Foundry Sonnet 4.5, and apps-gateway Fable controls.
  - Requirement: p04-t01; SC1, SC2, and the Compatibility and Selection Contract.

- **A recognized family pin ignores an explicit restrictive capability declaration** (`packages/cli/src/providers/claude/targets.ts:123`)
  - Issue: `familyPinCapabilityEvidence` returns built-in generation capabilities as soon as the pinned ID matches a known generation and only reads `_SUPPORTED_CAPABILITIES` for an opaque ID. Claude Code documents that when this variable is set it enables the listed capabilities and disables unlisted ones. With `ANTHROPIC_DEFAULT_OPUS_MODEL=us.anthropic.claude-opus-5` and `ANTHROPIC_DEFAULT_OPUS_MODEL_SUPPORTED_CAPABILITIES=effort`, OAT still accepts `opus/xhigh` and records all five levels, even though the provider declaration omits `xhigh_effort` and `max_effort`. This inflates capability and can turn a managed `xhigh` route into provider fallback rather than the selected target.
  - Fix: When the matching `_SUPPORTED_CAPABILITIES` variable is present on a supported third-party route, treat it as authoritative for recognized and opaque pin IDs. Preserve the recognized generation as supplementary evidence, but derive supported effort levels from the declaration and reject undeclared `xhigh`/`max`. Add positive and negative controls for recognized IDs with `effort`, `effort,xhigh_effort`, and `effort,max_effort`, plus stale-regeneration coverage when only the declaration changes.
  - Requirement: p04-t01; SC1, SC2, and the no-capability-inflation contract.
