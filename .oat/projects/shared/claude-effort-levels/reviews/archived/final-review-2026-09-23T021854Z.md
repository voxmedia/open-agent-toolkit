Both preferred-versus-ceiling comparisons compute `order.indexOf(policy.value)`; with a frontier tier ending in `gpt-6-sol/ultra` that index is `-1`, so each branch skips capping and returns the ceiling target unchanged. Reproduced against the built CLI with a ladder whose frontier tier is `[gpt-6-sol/max, gpt-6-sol/ultra]`: `--role implementer --preferred high` resolves `selectedValue: "ultra"`, `dispatchArgs.variant: "oat-phase-implementer-gpt-6-sol-ultra"`, `capped: false`, `selectionMode: "capped"`. Before this range the `ultra` ladder failed closed with a clear error; now it resolves but discards the caller's cheaper preference and dispatches the most expensive target without any warning or `capped` signal, which inverts the documented "a named ceiling is a maximum; lower candidates remain eligible" semantics for exactly the tier where cost matters most. The new tests exercise only the exact `--candidate-effort ultra` route and the reversed-order rejection, so nothing pins this path.
  - Fix: Use `CODEX_CANDIDATE_EFFORTS` (or a shared ordering derived from it) for the Codex ordering comparisons at `:1894-1910` and `:2669-2688` so `ultra` ranks above `max`; decide explicitly whether `--preferred ultra` should remain rejected by `normalizePreferred` (`:1609-1618`) and keep that consistent with the resolved order.
