### High

- **Alias validation can approve the wrong version and records it as exact resolved-model evidence** (`packages/cli/src/providers/claude/targets.ts:83`)
  - Issue: `builtInAliasGeneration` assigns one generation from provider environment flags and always maps an unpinned `fable` alias to `fable-5-1`. Claude Code's [current model configuration](https://code.claude.com/docs/en/model-config#model-aliases) documents two runtime substitutions that this code cannot see: signed-in Claude apps gateway sessions resolve `fable` to Fable 5, and an `availableModels` or organization restriction can make `sonnet`/`opus` resolve to the newest permitted older family version. The resolver does not read effective Claude settings or runtime/account restrictions, so a default-environment `sonnet/xhigh` is accepted and stamped `resolvedModel: sonnet-5` even when an allowlist can substitute Sonnet 4.6, where `xhigh` falls back. A direct probe also showed that bare `fable` is stamped `fable-5-1`; in an apps gateway session the actual model is Fable 5. Both Fable versions share effort levels, so the Fable case does not break capability selection, but it proves the field is not exact resolved-model evidence. The Sonnet/Opus substitution can change which effort levels are supported and violates p04-t01's fail-closed version-awareness requirement.
  - Fix: Do not present a provider-default inference as an exact resolved model. Resolve the effective Claude model from an authoritative settings/runtime surface that includes alias substitution and account/provider restrictions, or fail closed for version-sensitive alias/effort pairs when that evidence is unavailable. If OAT only needs capability validation, replace `resolvedModel` with a capability evidence object or equivalence class that records source and confidence; keep exact version evidence only for explicit recognized IDs or authoritative runtime resolution. Add controls for apps-gateway `fable`, an allowlist that substitutes Sonnet 4.6, and a normal Sonnet 5 route.
  - Requirement: p04-t01; SC1 and SC2; Compatibility and Selection Contract.

- **Documented custom provider capability pins are rejected before materialization** (`packages/cli/src/providers/claude/targets.ts:156`)
  - Issue: Alias pins are accepted only when their model string contains a recognized generation. Claude Code officially supports arbitrary Bedrock ARNs and custom deployment IDs together with `ANTHROPIC_DEFAULT_<FAMILY>_MODEL_SUPPORTED_CAPABILITIES`; `effort`, `xhigh_effort`, and `max_effort` declare the available effort controls. The implementation ignores those companion variables and rejects the documented pattern. A direct probe with an Opus custom-model ARN plus `effort,xhigh_effort,max_effort` returned `valid: false`, even though Claude Code enables those levels for that pin. This leaves the original final-review failure mode in place for supported provider-native identifiers and conflicts with p04-t01's requirement to accept every documented capability OAT can establish.
  - Fix: Parse the matching `_SUPPORTED_CAPABILITIES` variable for family pins and derive the supported effort set (`effort` for low/medium/high, plus the two optional deeper levels). Preserve the pin string and capability-source provenance instead of fabricating a model generation when the custom ID does not encode one. Continue to reject an arbitrary/custom pin when neither a recognizable version nor a sufficient capability declaration establishes support. Add resolver, materializer, and stale-regeneration controls for Bedrock ARN and Foundry/custom deployment examples, including missing and incomplete declarations.
  - Requirement: p04-t01; SC1 and SC2.

### Medium

- **The launch envelope accepts contradictory resolved-model targets** (`packages/cli/src/providers/claude/dispatch-envelope.ts:106`)
  - Issue: `assertSameTarget` compares only `model` and `effort`, although both resolver target objects now require `resolvedModel`. The remainder of the boundary validates and records only `selection.target.resolvedModel`. A direct production-function probe supplied `provider.target.resolvedModel: sonnet-4-6` and `selection.target.resolvedModel: sonnet-5` with the same `sonnet/high` pair; `acceptClaudeLaunchEnvelope` accepted it and emitted `sonnet-5`. The normal resolver currently duplicates one target, but this boundary exists to reject stale, copied, or inconsistent launch evidence, and p04 explicitly requires exact resolved-model evidence across resolver, materializer, envelope, and record.
  - Fix: Include `resolvedModel` in `assertSameTarget` and add a negative test that mutates either copy while keeping model and effort equal. The definition marker and dispatch record should continue to match the one reconciled value.
  - Requirement: p04-t01; SC1 and SC2.
