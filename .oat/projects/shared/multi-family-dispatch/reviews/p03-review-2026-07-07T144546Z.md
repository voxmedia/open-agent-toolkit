## Findings

### Critical

- **Bundled dispatch-matrix recommendation asset is destroyed by every build** (`packages/cli/scripts/bundle-assets.sh:15`)
  - Issue: p03-t07 (commit `4a3dea73`) committed `packages/cli/assets/config/dispatch-matrix-recommendation.json` directly into the assets directory, but `packages/cli/assets/` is a build-generated tree: `bundle-assets.sh` (invoked by the package's `build` script) runs `rm -rf "${ASSETS}"` and recreates only `skills`, `agents`, `templates`, `scripts`, `docs`, `migration`, and `public-package-versions.json`. It never recreates `config/`, so the first `pnpm build` after the commit deleted the asset — this is exactly the uncommitted ` D packages/cli/assets/config/dispatch-matrix-recommendation.json` currently in the working tree. The deletion is a symptom, not stray user state: `git checkout` alone only fixes it until the next build. Consequences: (a) `oat config adopt dispatch-matrix` fails at runtime with ENOENT in any built/working tree (`loadDispatchMatrixRecommendation` reads `<assetsRoot>/config/dispatch-matrix-recommendation.json`, `packages/cli/src/commands/config/index.ts:983-1004`); (b) a release build would publish the npm package without the asset, shipping a broken adopt command; (c) a later `git add -A` bookkeeping commit would silently delete the asset from history.
  - Fix: Give the recommendation a canonical source location outside the generated assets tree (following the pattern of every other bundled asset, e.g. a source file copied by the bundler, or generation inline in the script), and add a step to `bundle-assets.sh` that creates `${ASSETS}/config/` and copies/generates `dispatch-matrix-recommendation.json` into it. Then restore the working-tree file and verify with `pnpm build && test -f packages/cli/assets/config/dispatch-matrix-recommendation.json`. Note the plan's p03-t07 file-location criterion ("assets bundled into the shipped CLI live under `packages/cli/assets/`") is itself incomplete — it did not account for `assets/` being wiped at build time — so `plan.md` (or at minimum `implementation.md` notes) should record the corrected convention when this is fixed.
  - Requirement: p03-t07

### Medium

- **Matrix cell normalization/traversal logic is quadruplicated across modules** (`packages/cli/src/commands/project/dispatch-ceiling/index.ts:309-410`, `packages/cli/src/config/oat-config.ts:246-355`, `packages/cli/src/commands/config/index.ts:1041-1108`, `packages/cli/src/commands/doctor/index.ts:274-360`)
  - Issue: The bare-value/tier-map/route-cell normalization exists twice in near-identical ~90-line form (`normalizeDispatchProviderValue` et al. in `oat-config.ts` vs `normalizeProjectMatrixProviderValue` et al. in the resolver), and the cell-ref flattening walker exists twice in near-identical form (`collectDispatchMatrixCellRefs`/`addDispatchMatrixCellRefs`/`isRouteTarget` in both `config/index.ts` and `doctor/index.ts`). p05 will change route-cell semantics (escalation selection, `(harness, model, effort)` dispatch), which under the current structure requires coordinated edits in four places and invites silent drift between config-layer and project-layer acceptance rules.
  - Fix: Extract one shared normalizer (exported from `@config/oat-config`, parameterized by the provider enum check) and one shared cell-ref walker (e.g. alongside `@providers/identity/availability`), and consume them from the resolver, config command, and doctor. Behavior-preserving refactor; existing tests should pass unchanged.

### Minor

- **Cursor availability oracle spawns `cursor-agent` per cell with no per-run caching** (`packages/cli/src/providers/identity/availability.ts:138-171`)
  - Issue: `validateCursorCell` runs `cursor-agent models` (and possibly `--list-models`) for every cell independently. Adopt-time validation of the shipped recommendation has 4 cursor cells, and doctor validates every configured cursor cell across three layers — each a fresh subprocess with a 10s timeout, so a slow/hung CLI can add tens of seconds to `oat doctor` or `oat config adopt`.
  - Suggestion: Fetch and parse the cursor catalog once per validation pass (memoize within `validateRecommendationCells` / `createDispatchMatrixDoctorCheck`, or add a catalog cache to the oracle dependencies) and match all cells against it.

- **Doctor check name drifted from the plan label** (`packages/cli/src/commands/doctor/index.ts:378`)
  - Issue: Plan p03-t06 names the check `dispatch:matrix`; the implementation registers `project:dispatch_matrix`. The implemented name is the better choice — it follows the existing `${scope}:check_name` convention used by every other doctor check and the check only runs in project scope — and `implementation.md` documents it. This is stale-artifact alignment, not a code defect.
  - Suggestion: No code change. Update the p03-t06 wording in `plan.md` (or accept the deviation explicitly at review-receive) so downstream phases reference the real check name.
