- **Unknown producer identity removes the previously shipped same-runtime independence floor under the new default** (`packages/cli/src/commands/gate/index.ts:832`)
  - Issue: `listExecTargetCandidates` applies the same-runtime filter only when `avoid === 'same-runtime'` and the family filter only when the producer family is known. With the new default `avoid=same-family` and an unknown/absent producer identity (no `--producer-identity` flag and no matching stamp — i.e., every pre-existing project, every repo without Dispatch Notes stamps, and any final/range review scope), **no avoidance filtering happens at all**: the highest-priority available target wins even if it is the same runtime and model that produced the work. The shipped behavior before this project at least forced a different runtime by default. The behavior is deliberate and tested (`index.test.ts:1449` "does not fall back to same-runtime filtering for unknown producer identity") and is honest — achieved level `unknown-producer` is recorded in metadata and the info log — so it is not the "silent" loss the discovery risk register forbids, but it is a real independence regression for the no-stamp population relative to the pre-change default, surfaced only as an info-level log line (no warning; `diversityFallbackWarning` fires only for degraded/same-family outcomes, not `unknown-producer`).
  - Fix: When `avoid === 'same-family'` and `producerHasKnownFamily(...)` is false, retain the same-runtime filter as a conservative floor (current runtime ≠ candidate runtime), falling back to unfiltered selection only via the existing flagged no-eligible-target fallback; alternatively (minimum), promote the `unknown-producer` outcome to a `logger.warn` stating that no diversity floor was applied. Either keeps intra-Cursor diversity intact for known producers while preserving the old independence guarantee when identity is unknown.
  - Requirement: discovery Key Decision 6 / Risk "Silent loss of gate independence"; design Concern 1 ("degradation is auditable, never silent").

### Minor

- **[Deferred-ledger disposition: accept defer, convert to tracked follow-up] Cursor availability oracle still shells out once per matrix cell** (`packages/cli/src/providers/identity/availability.ts:137`)
  - Issue: Carried from the p03 review ("final follow-up"). Verified at HEAD: no catalog caching or batch API was added. `validateCursorCell` invokes `cursor-agent models` (and `--list-models` on fallback) independently per cell with a 10s timeout each; `oat config adopt dispatch-matrix` validates all 12 recommendation cells and the doctor `project:dispatch_matrix` check validates every configured cell across three layers, so a slow-but-responsive Cursor CLI can add tens of seconds per pass. When `cursor-agent` is absent the failure is fast (ENOENT → `unvalidated`), so the common case is unaffected.
  - Disposition: **Accept the deferral.** Re-evaluated at final scope: the affected commands (adopt, doctor) are explicitly interactive/maintenance surfaces, not dispatch-path hot loops, and correctness is unaffected. Convert to a backlog item (cache the parsed catalog for the duration of one validation pass, or add a batch validation entry point) alongside the consolidation item above.
  - Suggestion: Per-pass catalog cache keyed on env, shared by adopt and doctor loops.

- **Set-time "saving anyway" warning is misleading for closed-enum providers whose invalid values are silently dropped at read time** (`packages/cli/src/commands/config/index.ts:1010`)
  - Issue: `oat config set workflow.dispatchCeiling.providers.claude.high opus-4.8` warns "…was not recognized by the provider availability oracle; **saving anyway**" and writes the value, but `normalizeProviderBareValue` (`packages/cli/src/config/oat-config.ts:262`) drops non-enum codex/claude cell values on every read — so the saved value is inert: the resolver never sees the cell and the doctor drift check (which walks the already-normalized config) can never report it. A user who accepted the warning reasonably believes the cap will apply. Impact is bounded because the closed enums are static (the mistake is caught at set time, and cursor/open-provider cells — the drift-prone ones — are preserved and visible to doctor).
  - Suggestion: For providers with closed value enums (codex/claude), fail the `config set` with the valid-value list instead of warning, or change the warning to state the value will be ignored by the resolver.

- **Producer-stamp lookup is exact single-scope only; final/range gate reviews degrade to `unknown-producer`** (`packages/cli/src/commands/gate/index.ts:645`)
  - Issue: `readStampedProducerIdentity` matches `candidate.scope === scope` against per-phase stamps (`scope=pNN`), so phase gates (`--review-scope "{pNN}"`, as wired in `oat-project-implement`) resolve correctly, but a `final` or range (`p02-p03`) review scope matches no stamp and resolves `unknown-producer` — the design's parenthetical "a gate over p02–p03 diversifies against each phase's producer" (design.md Concern 1) is not implemented as aggregation. The degradation is honest and the docs document the `--producer-identity` escape hatch, so this is a scoped gap, not a defect; note it compounds the Medium above for final-scope gates.
  - Suggestion: Aggregate stamps for all in-range/known scopes and avoid the union of producer families (or at minimum the most recent producers), or document in `workflow-gates.md` that final-scope gates should pass `--producer-identity` explicitly. Alternatively treat as artifact alignment: soften the design's multi-phase parenthetical to match the shipped single-scope + manual-flag behavior.
