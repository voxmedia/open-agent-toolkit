### Medium

- **Failed/blank `observed` record clobbers a valid `declared` identity** (`packages/cli/src/providers/identity/provenance.ts:90-98`)
  - Issue: `normalizeRecord` converts a blank/whitespace value to `'unknown'`, but the declared/observed corroboration logic still treats such a record as a real observation. Empirically verified: `resolveIdentityConfidence([{ value: 'composer-2.5', provenance: 'declared', rejectOnInvalid: true }, { value: '', provenance: 'observed' }])` resolves to `{ value: 'unknown', confidence: 'low', mismatch: true, diversityClaimable: false }` — a failed observation (e.g. an echo that could not be parsed) destroys what design.md defines as a high-confidence declared identity on a reject-on-invalid harness. Symmetrically, a declared record with value `'unknown'` plus a real observed value flags a spurious `mismatch: true`. Design intent ("observed wins — it reflects what actually ran") assumes the observed record actually carries an identity; a value-less record reflects nothing.
  - Fix: Exclude records whose normalized value is `'unknown'` from acting as `declared`/`observed` anchors in the corroboration/mismatch branches (e.g. filter to known-value records before `strongestRecord`, as `strongestKnownRecord` already does for the fallback). A value-less record can neither corroborate nor contradict. Add both edge cases to `provenance.test.ts`.
  - Requirement: p02-t02 (design.md consumption rules — "high-confidence path is `declared` corroborated by `observed`")

- **Classifier maps providerId `cursor` to family `composer`, conflating harness with family** (`packages/cli/src/providers/identity/family.ts:11`)
  - Issue: `PROVIDER_ID_FAMILIES` includes `[/^(cursor|composer)$/i, 'composer']`, and provider-id matching takes precedence over model-value patterns. Empirically verified: `classifyModelFamily({ value: 'gpt-5.5-high', providerId: 'cursor' })` returns `composer`. The project's central invariant is that Cursor is the first harness where runtime ≠ family; the only structured provider-id field live-verified in discovery (Q21) is Codex's `model_provider_id: "openai"` — `cursor` as a model-provider id is speculative. A p04 gate-filtering caller that passes the harness/runtime id as `providerId` would misclassify every Cursor-run model (GPT, Claude, GLM) as `composer`, silently defeating same-family avoidance.
  - Fix: Remove `cursor` from the composer provider-id pattern (keep `composer`), or document on `ClassifyModelFamilyInput.providerId` that it must be a structured model-provider id (e.g. Codex `model_provider_id`) and never a harness/runtime id — preferably both. Add a regression test that `{ value: 'gpt-5.5-high', providerId: 'cursor' }` does not classify as `composer` (or that the misuse is explicitly rejected).
  - Requirement: p02-t01; design.md Family classifier ("never a silent inference") and gate concern ("runtime ≠ family in both directions")
