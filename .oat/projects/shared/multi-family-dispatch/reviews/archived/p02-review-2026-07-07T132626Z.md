### Important

- **Unknown-provenance identities remain diversity-claimable** (`packages/cli/src/providers/identity/provenance.ts:79`)
  - Issue: `diversityClaimable` is derived only from `value !== 'unknown'`, so `resolveIdentityConfidence([{ value: 'gpt-5.5-high', provenance: 'unknown' }])` resolves with `confidence: 'unknown'` but still marks diversity claimable. p02 requires `unknown` identity/provenance to be non-claimable, and this can be reached by malformed or legacy-ish stamp input that preserves `producer=<slug>` while normalizing invalid provenance to `unknown`.
  - Fix: Treat `unknown` provenance/confidence as non-claimable regardless of the concrete value, or normalize the resolved value to `unknown` when provenance is `unknown`. Add a regression test for a concrete value with `provenance: 'unknown'`, and consider a paired stamp-parser test for invalid provenance.
  - Requirement: p02-t02

- **Cursor fallback can bypass catalog exact-match-or-degrade** (`packages/cli/src/commands/internal/cursor-current-target.ts:184`)
  - Issue: `mapThroughCatalog` returns any single-token value when it does not find an exact catalog slug/display-name match. If `cursor-agent models` returns a usable catalog without a current marker, then init-event or `cli-config.json` reports a different single-token value such as `composer-2.5` while the catalog only contains `composer-2.5-fast`, the helper reports `composer-2.5` instead of degrading to `unknown`. That violates the p02/design rule that disagreeing Cursor sources use exact-match-or-degrade and do not auto-normalize slug/variant differences.
  - Fix: When a non-empty catalog is available, return only an exact slug or display-name match; only allow raw single-token fallback when no catalog exists. Add a regression test where catalog entries exist but the cli-config or init-event single-token value does not match any catalog entry.
  - Requirement: p02-t03
