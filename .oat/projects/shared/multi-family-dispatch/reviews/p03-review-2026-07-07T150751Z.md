### Minor

- **Cursor availability oracle shells out once per matrix cell** (`packages/cli/src/providers/identity/availability.ts:137`)
  - Issue: `validateCursorCell` invokes `cursor-agent models` (and `--list-models` on fallback) independently for every cell. Adopt validation loops over every recommendation cell (`packages/cli/src/commands/config/index.ts:1554`) and doctor loops over all configured cells across three layers (`packages/cli/src/commands/doctor/index.ts:387`), so a slow-but-responsive Cursor CLI can add repeated up-to-10s subprocess waits per pass.
  - Suggestion: Cache the parsed Cursor catalog for the duration of a validation pass, or expose a batch API for multi-cell callers.

- **`oat config list` omits dynamically-set dispatch matrix keys** (`packages/cli/src/commands/config/index.ts:1932`)
  - Issue: `runList` iterates only the static `KEY_ORDER` (`packages/cli/src/commands/config/index.ts:162`), which contains just `workflow.dispatchCeiling.providers.codex`/`.claude`. Matrix values set via the new dynamic keys (e.g., `workflow.dispatchCeiling.providers.cursor.high`) resolve correctly through `oat config get` (flattenConfig recurses tier maps) but are invisible in `oat config list` output, hurting discoverability of adopted/pinned matrix state.
  - Suggestion: When building the list, append any `workflow.dispatchCeiling.providers.*` keys discovered in the resolved flattened config that are not already in `KEY_ORDER`.

- **Plan label still says `dispatch:matrix` while code registers `project:dispatch_matrix`** (`.oat/projects/shared/multi-family-dispatch/plan.md:414`)
  - Issue: p03-t06 in `plan.md` names the doctor check `dispatch:matrix`, but the implementation registers `project:dispatch_matrix` (`packages/cli/src/commands/doctor/index.ts:378`). The implemented name is defensible — it follows the scoped doctor-check naming convention and the check runs only in project scope — so this is artifact drift, not a code defect.
