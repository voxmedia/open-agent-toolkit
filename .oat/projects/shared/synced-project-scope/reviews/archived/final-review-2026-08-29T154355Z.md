### Important

- **Local sync skips every localPath when run from a linked worktree nested under the main checkout** (`packages/cli/src/commands/local/sync.ts:110`, `packages/cli/src/commands/local/sync.ts:203`)
  - Issue: `registeredNestedWorktrees` removes only the exact canonical
    `sourceRoot` and `targetRoot` from the `git worktree list --porcelain`
    registry; every other registered path, including the main worktree,
    remains a protected boundary. `pathsOverlap` is then evaluated in both
    directions, so an entry whose source or destination is _inside_ a
    registered worktree counts as overlap. With the default
    `worktrees.root: .worktrees`, a linked worktree is a descendant of the main
    checkout; `oat local sync <peer>` run from that worktree resolves
    `repoRoot`/`sourceRoot` to the linked worktree (`resolveProjectRoot`
    returns the nearest `.git` ancestor), the main root stays in `registered`,
    and every `sourcePath` is within it. Reproduced against the built
    `dist/commands/local/sync.js` with a real repository: from the main root
    `.local-state` is `copied`; from `.worktrees/feat-a` the same call returns
    `{ status: 'skipped', reason: 'nested-worktree' }`, while the identical
    call without `repoRoot` (the pre-`p19-t08` path) copies. Because the
    bootstrap skills invoke `oat local sync "$TARGET_PATH" 2>/dev/null || true`
    and a skip is not an error, `.oat/projects/local/` and other localPaths are
    silently not propagated when an agent bootstraps a worktree from another
    worktree, which regresses the `local`-scope propagation that NFR1 requires
    to stay unchanged.
  - Fix: Exclude from `registered` any worktree that is an ancestor-or-equal
    of the canonical `sourceRoot` or `targetRoot` (they own the roots being
    synced and cannot be "nested" beneath an entry), keeping the two-direction
    overlap check for all remaining registrations. Add a real-Git regression in
    `sync.test.ts` that creates two linked worktrees under `<repo>/.worktrees`,
    calls `syncLocalPaths` with `repoRoot`/`sourceRoot` set to one linked
    worktree and `targetRoot` set to the other, and asserts `copied`; keep the
    existing damaged-marker and registry-failure cases green.
  - Requirement: NFR1, NFR4 (guard intent), FR10 (worktree independence)

### Minor

- **`resolveSyncedTarget` still hand-rolls the remote-absence check that `classifyRemoteRefLookup` now owns** (`packages/cli/src/commands/project/sync/resolve-target.ts:236`)
  - Issue: `p19-t10` introduced `classifyRemoteRefLookup` and uses it inside
    `isStagedPruneDeletion` (`resolve-target.ts:93`) and `pruneSynced`, but the
    adoption branch below it re-implements the same exit-2/empty-output test
    inline with a different error message. Two definitions of "verified
    absent" invite drift the next time the rule is tightened.
  - Fix: Replace the inline `remote.code === 2 && ...` block with
    `classifyRemoteRefLookup(remote, target.remote, target.ref) === 'present'`
    and let the helper throw for transport failures.
  - Requirement: FR11, NFR5
- **Staged-prune recovery issues a network `ls-remote` before checking the cheap local preconditions** (`packages/cli/src/commands/project/sync/resolve-target.ts:68`)
  - Issue: `isStagedPruneDeletion` runs `show-ref`, `ls-remote`, the cached
    diff, and `git show HEAD:<record>` in one `Promise.all`, then calls
    `classifyRemoteRefLookup` before it knows whether a staged deletion exists.
    Any missing-checkout prune resolution therefore performs (and can fail on)
    a remote lookup even when there is no prune transaction to recover, and
    the resulting error names the recovery path rather than the ordinary
    adoption path. Prune needs the network anyway, so this is ordering and
    diagnostics rather than safety.
  - Fix: Evaluate the staged-deletion and prior-record predicates first and
    return `false` early; only then consult `show-ref`/`ls-remote` and
    classify.
  - Requirement: FR11, NFR5
