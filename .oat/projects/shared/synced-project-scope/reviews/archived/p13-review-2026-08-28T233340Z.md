### Important

- **Receipt recovery requires a `project-log.md` seal that the completion contract makes optional** (`.agents/skills/oat-project-complete/scripts/recover-completion-receipts.mjs:530`)
  - Issue: `committedFile(..., 'project-log.md', 'completion log')` throws
    `Recovered pin-source receipt is missing required completion log` when the
    pin-source tree has no log, and `requireCompletionSeal` then requires the
    seal entry. But `SKILL.md` Step 3.7 routes `oat project log check`
    `status: "absent"` to "the feature is inert; proceed without a roll-up or
    seal append", `checkProjectLog` returns `absent` whenever the file does
    not exist (`packages/cli/src/commands/project/log/check.ts:252`), and the
    scaffold honors `--no-project-log` / `workflow.projectLog=false`
    (`packages/cli/src/commands/project/new/index.ts:173-178`). A log-less
    synced project therefore completes Steps 3.7 → 7.5 legitimately, publishes
    its pin source, and on any later interruption the Step 3.65 router calls
    `recoverCompletionReceipts`, which throws; `resolve-completion-retry.mjs`
    exits 1 with `ok: false`, and Step 7.5 forbids falling through to a new
    pin-source publication. Completion is permanently blocked for a supported
    configuration. The new `SKILL.md:672-675` prose codifies the same
    contradiction against Step 3.7, and the negative fixture
    (`completion-transaction.test.ts:882`) asserts the failing behavior rather
    than the contract.
  - Fix: Condition the seal requirement on the log's existence in the
    pin-source tree: when `project-log.md` is absent, accept the receipt
    (matching Step 3.7's `absent` semantics); when present, keep the
    final-entry seal validation exactly as implemented. Update the
    `SKILL.md` receipt-validation bullet to say "when a project log exists",
    replace the `missing required completion log` negative case with a
    log-absent positive case, and keep the active-state and unsealed-log
    negative cases. Bump `oat-project-complete` again in the same PR.
  - Requirement: FR8, NFR5

### Medium

- **Persisted archive identity is matched across the scope-shared `archived/` root without a scope qualifier** (`packages/cli/src/commands/project/archive/archive-utils.ts:543`)
  - Issue: `resolveLocalArchiveProjectPath` places every scope's archive under
    the same `dirname(projectsRoot)/archived/<name>` root (`:345-352`), and
    `ArchiveSnapshotMetadata` carries only `{ projectName, snapshotName }`
    (`:204-207`). `resolvePersistedArchivePath` now `readdir`s that root and
    accepts any directory whose metadata matches those two fields. A shared or
    local project with the same slug archived on the same UTC day writes the
    identical `YYYYMMDD-<slug>` snapshot name, so a synced archive retry either
    finds two matches and throws `refusing an ambiguous retry` (retry blocked)
    or, if the synced archive directory is absent, resolves to the other
    scope's archive, passes `verifyArchiveSnapshotMetadata`, skips the copy,
    and sources the summary/recap/S3 exports from the wrong project. Task
    p13-t04 made same-slug shared/synced isolation an explicit NFR1
    requirement; this reintroduces cross-scope coupling on the retry path.
  - Fix: Record the originating scope (or the exact archive directory basename
    alongside the dated snapshot identity) in the synced record and/or
    `ARCHIVE_SNAPSHOT_METADATA_FILENAME`, and match on it. Add a same-day
    same-slug shared/synced retry test asserting the synced retry resolves to
    its own directory.
  - Requirement: NFR1, FR8

### Minor

- **Synced record persistence now happens after the copy, leaving an orphan archive on record-write failure** (`packages/cli/src/commands/project/archive/archive-utils.ts:1621`)
  - Issue: `writeRecord(recordPath, activeRecord)` moved from before the copy
    to after `copyProjectDirectory` + `writeArchiveSnapshotMetadata`. If the
    record write fails, the retry has no `archiveSnapshot`, computes the same
    same-day identity, takes the `-<suffix>` unique path, and writes a second
    directory with identical metadata; any subsequent retry then hits the
    ambiguous-match error.
  - Suggestion: Persist the identity before the destructive copy, or delete the
    freshly created archive directory in the `catch` block alongside the recap
    export cleanup.
  - Requirement: NFR5

- **Prune still fails on a locked-but-missing registration** (`packages/cli/src/commands/project/sync/ref-sync.ts:974-979`)
  - Issue: `git worktree prune` skips locked worktrees, so a registered
    checkout that is locked and absent (unmounted volume, `git worktree lock`)
    survives prune and `realpath` still throws before the containment check
    can run. The received finding offered "canonicalize registered paths
    without requiring filesystem existence" as the alternative; only the
    prune-first half was taken.
  - Suggestion: Resolve `realpath` with a fallback to `resolve(path)` for
    missing registrations (they cannot host a live checkout, so containment is
    unaffected), or surface a clear `locked stale registration` error naming
    the path.
  - Requirement: FR11

- **Doctor silently emits nothing when the local ref query itself fails** (`packages/cli/src/commands/doctor/synced-projects.ts:218`)
  - Issue: `localQuerySucceeded` accepts only exit 0/1; any other `show-ref`
    failure (for example exit 128) produces neither a `ref_sync` warning nor
    a diagnostic note, unlike the remote transport branch, which records an
    explicit skipped-comparison check.
  - Suggestion: Mirror the remote branch with a `local_ref` pass-level note
    that names the Git error.
  - Requirement: FR13
