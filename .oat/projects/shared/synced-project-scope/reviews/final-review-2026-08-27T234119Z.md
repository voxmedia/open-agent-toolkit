## Findings

### Critical

- **Synced completion cannot finish when archiving is disabled** (`.agents/skills/oat-project-complete/SKILL.md:663`)
  - Issue: `workflow.archiveOnComplete=false` and an interactive "do not archive" answer are both valid (`SKILL.md:90-97`), and Step 8 explicitly skips archive work when `SHOULD_ARCHIVE=false` (`SKILL.md:521-525`). That skipped step is the only synced path that supplies the parent-branch `LIFECYCLE_COMMIT`; Step 10 nevertheless requires it unconditionally at lines 663-665. The completion therefore stops after pushing `state.md` to the project ref, while the tracked discovery record remains `active` because only archive updates it. The selected-recap branch is also built around the absent archive-owned parent commit and export paths. This breaks a valid P0 completion configuration and diverges from shared-scope behavior.
  - Fix: Define and implement an explicit non-archive synced completion transaction. It must durably mark and exact-path commit the discovery record, retain the final project-ref push receipt, and finalize any selected recap against the correct ref/parent evidence without assuming archive exports or parentage. Add executable contract coverage for `archiveOnComplete=false` and an interactive decline, both with and without a selected recap, proving completion, record status, commit containment, ref retention, and recovery. Align docs that currently say completion always archives.
  - Requirement: FR8, NFR1, NFR5

- **Migration follows a tracked project-root symlink and can publish files outside the repository** (`packages/cli/src/commands/project/migrate/index.ts:72`)
  - Issue: The command validates only the lexical direct-child path (`index.ts:72-84`); the migration accepts any clean tracked path (`sync/ref-sync.ts:873-890`) and sends it to `copyDirectory` (`sync/ref-sync.ts:942-945`). `copyDirectory` calls `readdir` on the root (`fs/io.ts:42-50`), which follows a directory symlink. A clean tracked `shared/demo` symlink targeting an external directory can therefore copy and push those external files to `refs/oat/projects/demo`; nested symlink entries are silently omitted instead of preserved or rejected. This violates the fail-closed mutation boundary and can disclose files that were never repository content.
  - Fix: Before creating a ref or worktree, require `lstat(sourcePath).isDirectory()`, reject a symlink root, canonicalize the source and configured shared root, and require the canonical source to remain their direct child. Define and enforce a nested-symlink policy rather than silently dropping entries. Add real-filesystem tests for an external root symlink and nested symlinks, asserting no ref, worktree, record, push, or source mutation occurs.
  - Requirement: FR12, NFR4

- **Forced prune can delete an unrelated registered worktree selected only by its path suffix** (`packages/cli/src/commands/project/sync/ref-sync.ts:789`)
  - Issue: `pruneSynced` selects every registered worktree whose path merely ends in `/synced/<slug>` (`ref-sync.ts:789-793`), then redefines each candidate's `syncedRoot` as that arbitrary path's parent (`ref-sync.ts:795-799`). This makes the later canonical-child assertion self-fulfilling. A same-repository worktree registered at an unrelated path such as `/tmp/synced/demo` can therefore be treated as the OAT checkout and removed by `prune --force`, even though it is outside every configured `.oat/projects/synced/<slug>` boundary.
  - Fix: Derive allowed synced checkout paths from each registered parent worktree root plus the configured scope-relative synced root, canonicalize them, and match only those exact paths. Never derive the trust root from the candidate being validated. Add real-Git tests with an unrelated worktree ending in `/synced/<slug>` and prove both normal and forced prune leave it registered and intact.
  - Requirement: FR11, NFR4

### Important

- **A failed remote-ref deletion aborts the rest of migration rollback** (`packages/cli/src/commands/project/sync/ref-sync.ts:1027`)
  - Issue: Migration rollback awaits remote deletion before invoking local checkout/ref cleanup and local-config restoration. If `git push origin :<ref>` fails, control exits the catch block at lines 1027-1034, so `rollbackCreatedSyncedProject` and any remaining restoration never run. The original source may be restored, but the destination worktree/local ref remain and a retry fails its original preconditions; the error also loses a consolidated account of which compensation steps succeeded.
  - Fix: Run independent compensation steps through `finally`/best-effort aggregation, always attempting local worktree/ref and config restoration even when remote cleanup fails. Preserve the original failure, report every retained resource with exact recovery commands, and add an injected remote-delete failure test that verifies local cleanup and deterministic retry behavior.
  - Requirement: FR12, NFR5

- **Adoption is not idempotently recoverable after the discovery-record commit fails** (`packages/cli/src/commands/project/sync/resolve-target.ts:147`)
  - Issue: Adoption writes the record and returns it as pending before the parent commit (`sync/ref-sync.ts:541-550`; `pull/index.ts:195-209`). If that exact-path commit fails, the record remains uncommitted. On retry, record existence makes `resolveSyncedTarget` set `adopt=false`, so `pullSynced` returns no pending record and both `pull` and `open` can report success without retrying durability. A fresh checkout on the branch still cannot discover the project.
  - Fix: Make adoption recovery own and classify the record transaction. Either roll back only a record created by the failed invocation, or detect an uncommitted/untracked existing record and return it as pending until its exact-path commit succeeds, while preserving explicit `--no-commit`. Add real-Git retry tests for both `project pull` and `project open` with a first commit failure.
  - Requirement: FR4, FR16, NFR5

### Medium

- **The synced-bookkeeping inventory validates anchor presence, not guard semantics or site completeness** (`packages/cli/src/validation/skills.ts:279`)
  - Issue: p04-t06 requires every inventory anchor to still exist **and be guarded**, with completeness preventing future writers from silently bypassing synced durability (`plan.md:2145`). The validator only counts anchor occurrences (lines 279-290). For write entries it then exempts the entire file from completeness once any one write anchor exists (lines 292-308). A future edit can retain an unrelated unique anchor, remove its guard, or add another writer in the same inventoried file without failing. Tests cover only a missing anchor and a wholly uninventoried file (`skills.test.ts:452-492`).
  - Fix: Validate a kind-specific guard or companion guard anchor in the same function/fenced block as each site, and make completeness site-based rather than file-based. Add mutations that preserve the listed anchor while removing its fail-closed scope guard and that add a second unlisted writer to an already inventoried file.
