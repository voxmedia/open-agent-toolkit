### Minor

- **Repair branch is not idempotent when a stray `# END OAT core` precedes the header** (`packages/cli/src/commands/init/managed-block.ts:47`)
  - Issue: The first branch requires `endIndex >= startIndex`
    (`managed-block.ts:34`), so a file whose only end marker sits _before_
    the header falls into the new repair branch every time. The stale end
    marker stays in `prefix`, the freshly written block's own end line is
    then treated as an unmanaged tail line on the next pass, and the file
    grows one `# END OAT core` line per application. Reproduced with
    `applyManagedBlock` on `# END OAT core\nuser1\n# OAT core\n/.oat/a\n`:
    actions `updated,updated,updated`, final tail `# END OAT core` ×3.
    Harmless in `.gitignore` semantics (comment lines) and it needs a
    hand-mangled file, but `action` never settles on `no-change`, so
    `ensureScopedRootGitignore` would report `changed: true` on every
    scaffold. Before `a979f981c` the same input appended a whole new block per
    pass, so this is not a regression. There is no direct
    `managed-block.test.ts`; the repair is covered only through
    `gitignore.test.ts:261-312`.
  - Suggestion: Search for `end` only after `startIndex`
    (`content.indexOf(options.end, startIndex)`), or strip stale end-marker
    lines from `prefix` in the repair branch; add a unit test for this case.
  - Requirement: FR9, NFR5

- **Files already damaged by the pre-fix repair (two headers) still lose the user lines between them on re-apply** (`packages/cli/src/commands/init/managed-block.ts:32`)
  - Issue: `a979f981c` prevents new double-header files, but a `.gitignore`
    that the previous behaviour already left as
    `# OAT core / user / … / # OAT core / … / # END OAT core` (the exact M1
    reproduction in the prior review) still matches the first branch —
    `indexOf(start)` finds the orphan header, `indexOf(end)` the appended
    block's end — and the slice replacement drops everything in between.
    That behaviour exists at `origin/main`, and the precondition is a file
    produced by the old repair, so this is pre-existing and narrow.
  - Suggestion: When the slice between the first `start` and `end` contains
    a second `start`, treat the segment before the second header as
    unmanaged and preserve it (same filter as `preserveUnmanagedTail`).
  - Requirement: FR9

- **Marker matching is substring- and LF-based; the new tail filter inherits it** (`packages/cli/src/commands/init/managed-block.ts:15`)
  - Issue: `indexOf(options.start)` matches mid-line, so a user pattern such
    as `x # OAT core` is split into `x ` plus a managed block (reproduced:
    `x \n# OAT core\n…`). With CRLF endings the orphan header is repaired
    but `preserveUnmanagedTail` splits on `\n` only, so `"/.oat/a\r"` never
    equals the managed entry and survives as a duplicate rule beneath the
    block with mixed line endings (reproduced). Both are pre-existing
    classes (the equality check at `:36` is equally CRLF-blind); OAT writes
    LF, so exposure is limited to hand-edited or Windows-normalized files.
  - Suggestion: Anchor marker detection to whole lines (split once, compare
    trimmed lines) and normalize `\r` when filtering managed entries.
  - Requirement: FR9

- **Restore recommendation literal is duplicated across the annotated and `recorded-invalid` branches** (`packages/cli/src/commands/project/list.ts:274`)
  - Issue: `{ skill: 'none', reason: 'restore invalid record from a trusted
Git revision' }` appears verbatim at `list.ts:274-277` and `:291-294`,
    and the table hint `restore record from Git` is a third place that must
    stay in step. Behaviour is correct and covered by
    `list.integration.test.ts:221-224,257-261`.
  - Suggestion: Hoist one `INVALID_RECORD_RECOMMENDATION` constant.
  - Requirement: FR16

- **`summary.md` still predates Phases 13–17 (carry-forward m8; artifact alignment)** (`.oat/projects/shared/synced-project-scope/summary.md:7`)
  - Issue: `oat_summary_last_task: p12-t01`, `oat_last_updated: 2026-08-28`.
