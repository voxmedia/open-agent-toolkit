## Findings

### Critical

- **Absolute project roots scaffold into a double-prefixed parent path instead of the project checkout** (`packages/cli/src/commands/project/new/scaffold.ts:477`)
  - Issue: When `projects.root` is absolute, `projectPath` is deliberately kept absolute at lines 477-481, but `ensureStructure`, `scaffoldModeTemplates`, and `scaffoldProjectLog` later call `join(repoRoot, projectPath, ...)`. Node path joining therefore turns an intended path such as `/repo/.oat/projects/synced/demo` into `/repo/repo/.oat/projects/synced/demo`. The real nested checkout stays empty while artifacts are written into the parent checkout at an unrelated, normally unignored path; the ref can publish only its empty init tree and the parent can expose agent artifacts. This breaks FR1/FR2 and backward compatibility for the already-supported absolute `OAT_PROJECTS_ROOT`/`projects.root` form.
  - Fix: Carry one canonical absolute project path for filesystem operations and a separately normalized repo-relative path for output/config. Never join `repoRoot` to an already absolute path. Add real scaffold tests for absolute in-repo roots in all three scopes, asserting synced templates are in the nested checkout, the remote ref contains them, and parent status contains only the record.
  - Requirement: FR1, FR2, NFR1, NFR4

### Important

- **Recovery guidance invokes `--continue` when no rebase exists** (`packages/cli/src/commands/project/push/index.ts:73`)
  - Issue: Push uses the same `pull <target> --continue` instruction for `conflict` and `rejected`, while pull uses the same continue/abort instruction for `conflict` and `dirty` (`packages/cli/src/commands/project/pull/index.ts:93`). A non-fast-forward rejection has no rebase in progress and must be recovered with a normal targeted pull; a dirty checkout must be committed/pushed or stashed before pulling. Following the emitted commands causes `git rebase --continue`/`--abort` to fail and does not recover the project.
  - Fix: Render status-specific instructions: conflict -> targeted `--continue`/`--abort`; rejected -> targeted normal pull, then push; dirty -> targeted push or explicit stash/clean guidance. Split the parameterized tests so they prove each emitted command is executable in that state.
  - Requirement: FR3, FR4, NFR5

- **Coordination child failures are silent in human output, and malformed child lists become false success** (`packages/cli/src/commands/project/pull/index.ts:85`)
  - Issue: Human output prints only the successful parent result, then uses child failures solely to set exit code 1. It never prints the failing child slug or the captured `message`, contrary to FR17's per-child reporting contract. In addition, `pullChildren` returns an empty success result when a coordination parent's `oat_children` is absent or not an array (`packages/cli/src/commands/project/sync/ref-sync.ts:439`), silently leaving every child unmaterialized with exit 0.
  - Fix: Print one status line per failed child (slug, status, diagnostic, and targeted retry) in human mode. For `oat_kind: coordination`, reject a missing/non-array `oat_children` field as malformed state instead of treating it as no children; preserve the existing pre-network validation for every slug. Add human-mode partial-failure and malformed-frontmatter tests.
  - Requirement: FR17

- **System and transport failures are collapsed into actionable-user exit code 1** (`packages/cli/src/commands/project/push/index.ts:81`)
  - Issue: New command handlers catch every error and set `process.exitCode = 1`; the same pattern appears in pull, scope, and list. This discards `CliError.exitCode = 2`, contradicting the designed command contract that distinguishes actionable states from system failures. Remote adoption compounds the problem by treating every nonzero `ls-remote` result as “project missing” (`packages/cli/src/commands/project/sync/resolve-target.ts:121`), so authentication, DNS, and remote failures are misreported as absence with exit 1.
  - Fix: Preserve `CliError.exitCode` and classify unknown exceptions as system errors. For `ls-remote --exit-code`, treat only the documented no-match status as absence; surface every other status with the original Git diagnostic and exit 2. Add command-level JSON and process-exit tests for a missing ref, an unreachable origin, and an injected `CliError(..., 2)`.

- **Synced scaffold failures after worktree creation have no compensating rollback or resumable state** (`packages/cli/src/commands/project/new/scaffold.ts:515`)
  - Issue: `createSyncedProject` compensates failures inside its own routine, but `scaffoldProject` performs template rendering, file writes, push, record write, pointer update, and record commit after creation without a surrounding recovery boundary. A template/render/write failure leaves the new worktree and local ref registered (and `.gitignore` possibly modified); a retry then fails the create preflight with “already exists.” Later failures can additionally leave a published ref without a committed discovery record.
  - Fix: Add a staged scaffold transaction/compensation path that tracks exactly what this invocation created. Before publication, remove the new worktree/ref and restore a self-healed gitignore change on failure. After publication, either finish/repair the record deterministically or return explicit resumable instructions without rerunning creation. Test injected failures after worktree creation, template rendering, first push, record write, and record commit.
  - Requirement: FR2, FR5, NFR5

### Medium

- **`--scope` filtering is ignored when remote discovery is requested** (`packages/cli/src/commands/project/list.ts:342`)
  - Issue: Local rows are filtered by `options.scope`, but `appendRemoteRows` is called unconditionally and has no scope input. Consequently `oat project list --scope shared --remote` (and `--scope local --remote`) appends `synced` remote rows, violating the scope filter and making JSON consumers unable to rely on a single-scope result.
  - Fix: Skip remote enumeration when the selected scope excludes `synced`, or pass the filter into `appendRemoteRows` and enforce it there. Add combined `--scope ... --remote` tests for all three values.

- **The new-project JSON contract omits the planned `scaffoldCommit` field** (`packages/cli/src/commands/project/new/index.ts:61`)
  - Issue: p02-t03 and the design API declare `scaffoldCommit`, but the JSON payload exposes only the pre-existing `commitSha` name at line 76. Preserving `commitSha` is defensible for backward compatibility, but the declared additive contract is not implemented and its test checks only a partial object.
  - Fix: Prefer adding `scaffoldCommit: result.commitSha` while retaining `commitSha` as a compatibility alias; alternatively, if `commitSha` is the accepted canonical field, align `plan.md` and `design.md` before closeout. Add an exact JSON-shape assertion.
