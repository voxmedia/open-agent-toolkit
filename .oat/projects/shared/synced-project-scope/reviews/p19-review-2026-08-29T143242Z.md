### Important

- **Marker scanning does not protect a registered worktree with a missing or corrupted `.git` pointer** (`packages/cli/src/commands/local/sync.ts:31`)
  - Issue: `containsNestedGitMarker` only walks the two filesystem trees, and
    the destructive guard at lines 102-105 never queries Git's worktree
    registry. The subsequent `--force` path recursively removes the selected
    destination at line 123. In a real-Git reproduction, I registered a nested
    worktree, removed only its `.git` pointer to simulate corrupted metadata,
    and synced its ancestor with `force: true`: the command returned `copied`,
    deleted the worktree's unsaved sentinel, and
    `git worktree list --porcelain` still listed the same path as a prunable
    registration. This is
    the exact stale/corrupted-registration case that `p19-t02` required in
    addition to marker scanning, so the original destructive-data-loss finding
    remains open for that state.
  - Fix: Give local sync repository/worktree-registry context and, before any
    copy or removal, parse `git worktree list --porcelain`, canonicalize every
    registered path, and reject an entry when either source or destination
    overlaps a registration in either direction. Fail closed on malformed
    registrations or a failed registry query. Add real-Git tests for missing
    and corrupted markers in both sync directions, including the forced
    existing-destination case, and prove the sentinel and registration remain
    untouched.
  - Requirement: NFR1; design local-path sync guard; `p19-t02`

### Medium

- **Archive dry-run still accepts descendants that apply refuses** (`packages/cli/src/commands/project/archive/push-runner.ts:267`)
  - Issue: The apply engine now performs the exact canonical direct-child check,
    including a second pre-mutation assertion, but the command builds the
    dry-run report at lines 312-324 without invoking that validator. A direct
    reproduction against `shared/parent/demo` exited 0 and reported that it
    would archive `demo`; the same apply request is rejected by
    `archiveProjectOnCompletion`. This misses `p19-t01`'s explicit requirement
    to reject before dry-run as well as mutation, and makes the operational
    preview disagree with the action it represents.
  - Fix: Expose one canonical exact-project-root validator and call it before
    archive-target resolution for both dry-run and apply, while retaining the
    mutation-boundary recheck inside the archive engine. Add command-level
    dry-run refusals for shared/local descendants and the synced basename
    collision, plus positive in-repository absolute and symlinked custom-root
    cases.
  - Requirement: FR8, NFR1, NFR4; `p19-t01`

- **Prune recovery treats a remote lookup error as proof that the ref is absent** (`packages/cli/src/commands/project/sync/resolve-target.ts:92`)
  - Issue: `isStagedPruneDeletion` accepts every nonzero `ls-remote` result as
    ref absence, and `pruneSynced` repeats the same `remoteRef.code !== 0`
    condition at `packages/cli/src/commands/project/sync/ref-sync.ts:1055`
    before committing the record deletion and returning `pruned`. A resolver
    reproduction with an exact staged deletion and matching prior record but
    `ls-remote` exit 128 (`network unavailable`) was accepted as a durable
    prune-recovery target. The retry can therefore claim success while the
    remote ref was not authoritatively checked and may still exist. The exact
    prior-record identity and path-limited commit correctly preserve unrelated
    index/worktree changes, but the remote-state predicate is not fail-closed.
  - Fix: In both resolver and executor, accept only Git's verified no-match
    result (exit 2 with the expected empty ref result) as absence; propagate
    transport/auth/configuration failures such as exit 128 without committing
    the staged deletion. Add resolver and public-command retry tests covering
    a remote lookup failure and prove the record deletion remains staged and
    unrelated index/worktree state remains unchanged.
  - Requirement: FR11, NFR5; `p19-t04`
