### Medium

- **Repairing an unterminated `# OAT core` block leaves an orphan header, and the next core re-application silently deletes every user rule beneath it (`p17-t13` residual)** (`packages/cli/src/commands/init/managed-block.ts:22`)
  - Issue: `ensureScopedRootGitignore` now guards its own slice
    (`gitignore.ts:150-155`), but it still delegates the write to
    `applyOatCoreGitignore` → `applyManagedBlock`, which, when `# END OAT
core` is absent, appends a second, terminated block after the existing
    content (`managed-block.ts:36-38`). The scaffold commit therefore ships a
    `.gitignore` with two `# OAT core` headers (reproduced: lines 1 and 6 of
    the committed file). On the next `applyOatCoreGitignore` — `oat init`, or
    any later scaffold that touches a different scope root —
    `content.indexOf(start)` finds the orphan header and `indexOf(end)` the
    appended block's end marker, so the replacement drops everything in
    between. Reproduced under `projects.root: .oat/team-projects` with a
    seeded `# OAT core\nkeep-user-rule\n/.oat/synced/*/\n/.oat/archived/**`:
    `oat project new q --scope synced` exit 0 and the file starts
    `# OAT core / keep-user-rule / … / # OAT core / … / # END OAT core`;
    `applyOatCoreGitignore` then reports `updated` and `keep-user-rule` is
    gone. The new test `repairs an unterminated managed block without
treating its rules as managed` (`gitignore.test.ts:261-301`) asserts only the
    first-run outcome and never re-applies. Precondition is a malformed
    block, so the blast radius is narrow, but the loss is silent and affects
    user content.
  - Fix: Make `applyManagedBlock` (or `ensureScopedRootGitignore` before it)
    terminate or remove the orphan header when `start` exists without `end`
    — e.g. treat "start without end" as "block runs to EOF" only for managed
    rule lines and re-emit user lines outside the new block — and add a
    second-application assertion to the new test.
  - Requirement: FR9 (P0), NFR4
