### Minor

- **WS-authentication phrasing implies cookie-only auth, but the client also resends the key** (`.agents/skills/oat-brainstorm/references/visual-companion.md:49`)
  - Issue: The doc states subsequent same-origin requests, "including the WebSocket upgrade," authenticate "via the cookie without repeating the key in the address bar." In the shipped client (`.agents/skills/oat-brainstorm/scripts/helper.js:32-35`), `websocketUrl()` still appends `?key=<sessionKey>` to the `ws://` URL whenever a session key is present in `sessionStorage` — the WS handshake carries the key redundantly alongside the cookie, it does not rely on the cookie exclusively. The phrase "without repeating the key" is only true of the visible address bar (which never shows the WS connection), not of the WS request itself, so a future doc maintainer skimming this sentence could conclude the key is dropped from the WS URL and be surprised by the actual `server.cjs` `isAuthorized()` check (`.agents/skills/oat-brainstorm/scripts/server.cjs:275-287`), which accepts either the query param or the cookie.
  - Suggestion: Tighten the sentence to something like: "…so the address bar never needs to show the key again; the WebSocket connection re-sends the key as `?key=` from the bootstrapped `sessionStorage` value (falling back to the cookie for plain page/`/files/*` requests)." Low priority — does not affect correctness of the shipped behavior or mislead an agent following the doc operationally, only a documentation-precision nit for future maintainers.
