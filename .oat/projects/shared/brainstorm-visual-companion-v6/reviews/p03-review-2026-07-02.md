### Important

- **"sandboxes /files/ against path traversal and dotfile access" test does not actually verify the traversal/dotfile guard** (`packages/cli/src/integration/visual-companion-smoke.test.ts:417-442`)
  - Issue: The test correctly uses `http.request` with an explicit `path` (`rawHttpGet`) to defeat client-side `..` normalization, so the _request_ reaches the server as a literal `..`/dotfile payload — that part is sound. However, neither assertion actually depends on the server's sandboxing logic in `handleRequest`'s `/files/` branch (`.agents/skills/oat-brainstorm/scripts/server.cjs:354-368`, specifically `path.basename(pathname.slice(7))` and `fileName.startsWith('.')`):
    - The traversal payload `GET /files/../server.cjs?key=<key>` resolves (via `path.basename`) to `CONTENT_DIR/server.cjs`, which never exists in the test's temp content dir — so it 404s regardless of whether `..` is sanitized.
    - The dotfile payload `GET /files/.hidden?key=<key>` targets `CONTENT_DIR/.hidden`, which is never created by the test — so it 404s regardless of whether the `fileName.startsWith('.')` guard exists.
    - I verified this empirically: with `path.basename()` and the `fileName.startsWith('.')` check removed from `server.cjs` (replaced with a raw `fs.existsSync`/`isDirectory` check, `isRegularFileInsideContentDir`'s symlink guard also removed), the full suite was rerun — the "path traversal and dotfile access" test still passed (2589ms, green), while the separate symlink-escape test correctly failed (`expected 200 to be greater than or equal to 400`) as intended. This confirms the traversal/dotfile test does not distinguish a hardened server from a vulnerable one; only the symlink test in this file does. (`server.cjs` was restored byte-for-byte after the experiment; `git status`/`git diff` confirm no residual change.)
    - Root cause note: `plan.md` p03-t01 step 1 literally specifies this weak payload (`GET /files/../server.cjs?key=<key>` "or a dotfile path"), so the implementer followed the plan as written — the gap originates in the plan's suggested payload, not implementer deviation from it. It still needs closing before this counts as real coverage of discovery.md SC#1 ("file server rejects traversal/symlinks/dotfiles").
  - Fix: Mirror the technique the symlink test (`:444-478`) already uses — target real files that traversal/dotfile access would actually reach if unprotected, and assert the response does not leak them:
    - Traversal: write a marker file one level above `CONTENT_DIR` (e.g. `join(projectDir, '.oat', 'brainstorm', <session>, 'sentinel.html')` or, simpler, reuse `info.screen_dir`'s parent) and request `/files/../sentinel.html?key=<key>`; assert 4xx and `body` does not contain the marker content.
    - Dotfile: `writeFileSync(join(info.screen_dir, '.hidden.html'), 'dotfile-should-be-hidden\n')` before the request, then request `/files/.hidden.html?key=<key>`; assert 4xx and `body` does not contain the marker content.
  - Requirement: discovery.md SC#1 ("file server rejects traversal/symlinks/dotfiles"); plan.md p03-t01.

### Minor

- **Restart test only proves port reuse, not key/token reuse** (`packages/cli/src/integration/visual-companion-smoke.test.ts:491`)
  - Issue: discovery.md SC#2 requires "Restart with same `--project-dir` ... reuses port/key so browser tab reconnects." The new restart test (`reuses the recorded port on restart with the same --project-dir (reads .last-port)`) only asserts `second.info.port === first.info.port` and the `.last-port` file contents; it never asserts that `second.info.url`'s `key` matches `first`'s (i.e. that `.last-token` / `BRAINSTORM_TOKEN_FILE` reuse actually keeps the same session key across restart, which is what lets an already-open browser tab's cookie keep validating). No other test in the suite covers token persistence across restart either — this is a genuine coverage gap for that half of SC#2, not just a redundant assertion. `plan.md` p03-t01 also only asked for `.last-port` reuse, so this is a plan-scope narrowing rather than an implementer miss.
  - Suggestion: add `expect(keyFromServerUrl(second.info.url)).toBe(keyFromServerUrl(first.info.url))` (or equivalent `.last-token` file comparison) to the same test.
