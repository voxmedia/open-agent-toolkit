- **The ratchet does not match `../../<skill>/…`, the natural parent-relative
  spelling from a scanned `references/*.md` file**
  (`packages/cli/src/commands/init/tools/shared/skills-bundled-docs-contract.test.ts:79-80`)
  - Issue: `CROSS_SKILL_READ`'s leading lookbehind `(?<![/a-zA-Z0-9_.-])`
    combined with the single `\.\.\/` alternative means a two-level hop is
    silently unmatched. Verified directly against the exported regex:

    ```text
    "Read `../../sibling/SKILL.md`."            => []
    "Read `../../sibling/references/schema.md`." => []
    "Read `../sibling/SKILL.md`."                => ["sibling|SKILL.md"]
    ```

    This is not a hypothetical spelling. `listAuthoredMarkdown` recurses the
    whole skill tree (`:100-113`), so `.agents/skills/x/references/y.md` is in
    the scanned surface — and from that file the correct relative path to a
    sibling skill is exactly `../../<name>/SKILL.md`, not `../<name>/SKILL.md`.
    The matcher's own comment (`:67-77`) claims to cover "`../<name>/…`, a
    parent-relative hop out of the authoring skill directory", so the coverage
    claim overstates what the regex does. Answering the phase's core question
    directly: yes, an executable non-portable read can still slip past. No live
    instance exists today (I grepped `.agents/skills` and `.agents/agents` for
    `\.\./\.\./[a-z]` and found only `../../roadmap.md`, `../../../../docs/...`
    symlink examples, and no cross-skill hop), so this is latent, not a shipped
    defect.

  - Fix: Allow a repeated parent segment in the alternative, e.g. change
    `|\.\.\/)` to `|(?:\.\.\/)+)` (the lookbehind still keeps
    `${SKILL_DIR}/../<name>/…` and `${HOME}/.agents/skills/…` out). Add
    table-driven cases for `../../sibling/SKILL.md` and
