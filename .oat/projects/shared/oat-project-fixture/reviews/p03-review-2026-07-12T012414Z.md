## Findings

### Critical

- **Canonical gate evidence cannot survive the terminal receive lifecycle**
  (`tools/smoke/evidence/collect.mjs:593`)
  - Issue: `normalizeGate()` resolves only the gate JSON's original active
    `artifactPath` with `realpath()`. The normal receive workflow subsequently
    moves that artifact to `reviews/archived/` and updates the terminal plan row
    to the archived path; this repository intentionally ignores that directory.
    Collection therefore fails after a normal receive, before assertions run.
    The path normalization is also inconsistent with the canonical gate
    envelope: lines 616-627 reduce the project to its basename and require
    `artifactProject` or `normalizedArtifactProject` to equal that basename,
    while canonical gate output carries the repo-relative project path.
    `matchingGate()` repeats the basename comparison at
    `tools/smoke/evidence/assertions.mjs:53`. Finally, the durability check at
    lines 91-100 looks only for a commit that touched the current path; it
    neither proves the exact artifact bytes nor models the tracked active
    artifact becoming a local-only archived artifact. The integration tests
    avoid all three production conditions by using an active
    `reviews/<scope>-review.md` path and `oat_project: smoke-fixture`.
  - Fix: Normalize all project identities to the canonical repo-relative
    project path; resolve gate artifact identity across the active-to-archived
    receive transition; and bind the archived bytes to the exact committed
    active artifact blob reachable from outer `HEAD`. Require the terminal
    `passed` row and receive bookkeeping commit on outer `HEAD`. Also
    cross-check `dispatchReport.gateInvocation` against top-level
    `gateInvocation`, corroboration expected/actual invocation, and artifact
    frontmatter. Add an integration test that runs the canonical archive
    transition with `.oat/**/reviews/archived/` ignored.
  - Requirement: p03-t01/p03-t02; design “review/gate rows durable and
    corroborated”

- **Committed-policy recomputation rejects valid Codex configured invocations**
  (`tools/smoke/evidence/assertions.mjs:208`)
  - Issue: The collector flattens each Codex matrix candidate to
    `<model>:<effort>` (`tools/smoke/evidence/collect.mjs:311-319`), then the
    assertion requires the launcher `target` to equal one of those strings and
    requires `modelAxis` to equal `selected:<target>`. A real Codex invocation
    uses a materialized role as the surface-exact target, while its model and
    effort axes remain separate resolver values. Consequently, a valid Codex
    launch under the committed fixture policy cannot pass this assertion. The
    collector-to-report integration test exercises only `cursor-cli`, so the
    required Codex harness is not covered.
  - Fix: Reuse the repository dispatch resolver or preserve structured
    provider candidates through collection. For Codex, compare the materialized
    role target, selected model axis, selected effort axis, candidate tier, and
    ceiling target as separate fields. Add resolver-backed end-to-end evidence
    cases for Codex, Claude, and both Cursor flavors.
  - Requirement: p03-t02; discovery success criterion for exact selected
    provider model or Codex role across all harness targets

### Important

- **Parallel-isolation proof can pass a serial history without merge commits**
  (`tools/smoke/evidence/assertions.mjs:265`)
  - Issue: A phase “merge” is accepted whenever any outer commit lists the
    phase task head as a parent. The code does not require a multi-parent merge
    commit or prove that p01 and p02 originated independently from the common
    baseline. A serial history where p02 starts from the p01 head, followed by a
    normal reconciliation commit before p03, satisfies the current branch-name,
    parent, and ordering checks. In addition, p03 task commits only need to
    include `p03.log`; unlike p01/p02, they may contain unrelated files despite
    the contract's log-only claim.
  - Fix: Record and assert each phase ref's merge base/starting point, reject
    cross-phase ancestry before fan-in, require an outer commit with at least
    two parents for each phase integration, and require every p01/p02/p03 task
    commit to change exactly its phase log.

- **Transition corroboration does not prove the complete lifecycle state**
  (`tools/smoke/evidence/collect.mjs:879`)
  - Issue: `observedLifecycleState()` classifies states from only one state
    field plus one plan field/row, and `corroborateTransitions()` reads only
    `state.md` and `plan.md`. The canonical `implementation-ready` preset also
    requires plan status/template fields, state current-task/phase-status/
    template fields, and `implementation.md` current-task/template fields.
    The current integration test passes without changing `implementation.md`,
    demonstrating that an incoherent transition can be reported as atomic and
    implementation-ready.
  - Fix: Parse parent and commit versions of all three lifecycle artifacts and
    validate the complete preset-defined frontmatter fingerprints for
    pre-review, reviewed, and implementation-ready. Require the expected fields
    to change together in the transition commit and add negative cases for each
    omitted artifact/field.
