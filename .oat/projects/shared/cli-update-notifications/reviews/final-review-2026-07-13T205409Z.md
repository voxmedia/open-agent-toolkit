### Minor

- **`NO_UPDATE_NOTIFIER` honors only the exact value `1`** (`packages/cli/src/app/update-notifier.ts:174`)
  - Issue: Suppression requires `options.env.NO_UPDATE_NOTIFIER === '1'`. The widely adopted `update-notifier` ecosystem convention treats any presence of the variable (e.g. `NO_UPDATE_NOTIFIER=true`) as opt-out. An interactive user who set `NO_UPDATE_NOTIFIER=true` globally for other Node CLIs would still receive OAT notices and guard prompts. This matches the project's own design (`design.md` and all three docs surfaces explicitly document `=1`), so it is artifact-consistent — the finding is an ecosystem-compatibility robustness note, not a contract violation. Residual impact is small because CI/non-interactive contexts are independently suppressed at `update-notifier.ts:161-181`.
  - Suggestion: Either accept truthy values via the existing `isTruthyEnvironmentValue` helper (`update-notifier.ts:129-135`) or presence-based suppression, updating the docs sentence in `packages/cli/README.md:56`, `config-and-local-state.md`, and `tool-packs.md` in the same change; or explicitly record the strict-`1` semantics as intended in a decision note. Bounded either way.

- **PowerShell rerun guidance with embedded double quotes may not round-trip on Windows PowerShell 5.1** (`packages/cli/src/app/tool-bundle-update-guard.ts:102-107`)
  - Issue: `quotePowerShellArgument` single-quotes and doubles embedded `'`, which is correct PowerShell string syntax, and arguments containing a literal `"` (e.g. `'double"quote'`, covered at `tool-bundle-update-guard.test.ts:141`) are passed to native executables correctly under PowerShell 7.3+ default argument passing. Under legacy Windows PowerShell 5.1, embedded double quotes in native-command arguments are re-quoted incorrectly by the shell itself, so the displayed command could reproduce a slightly different argv. The guidance is display-only, explicitly labeled `PowerShell`, and a literal `"` inside an `oat init`/`tools` argument is rare, so practical impact is negligible.
  - Suggestion: No code change required. If desired, escape embedded `"` as `\"` inside the single-quoted form only when a `"` is present, or note "PowerShell 7+" in the label. Bounded to `quotePowerShellArgument` and its two test expectations.

- **A non-abort prompt failure inside the guard aborts the guarded command with a raw error instead of degrading to the decline path** (`packages/cli/src/app/tool-bundle-update-guard.ts:190-193` with `packages/cli/src/commands/shared/shared.prompts.ts:37-44`)
  - Issue: `confirmAction` maps prompt aborts (`ExitPromptError`, force-close) to `false` (decline → warn and continue), but rethrows any other prompt-infrastructure error. Because `guardBundledToolMutation` only wraps `installCli` in try/catch, such an error propagates through the preAction hook and fails the command at exit code 2 via the entrypoint handler (`packages/cli/src/index.ts:104-118`) with a non-actionable message. This is fail-safe (no tool mutation occurs) but lets a best-effort availability feature change the outcome of an otherwise valid command in a rare broken-TTY scenario, whereas registry/cache failures deliberately allow the command (`design.md` Error Handling).
  - Suggestion: Wrap the `dependencies.confirmAction(...)` call in the guard; on a non-abort prompt error, log a warning and treat the result as decline so the requested command continues with the current bundle. Bounded to `guardBundledToolMutation` plus one focused test.
