# Design: Phase-Subagent Evolution of oat-project-implement

## Architecture Overview

A single evolved `oat-project-implement` skill orchestrates phase-level dispatch. A new canonical agent `oat-phase-implementer` carries the phase-execution behavior — loaded as system prompt on native subagent dispatch (Tier 1), read as reference on inline fallback (Tier 2). The existing `oat-reviewer` agent is reused unchanged for phase-end review. `oat-project-subagent-implement` is deleted.

The dispatch model is flat — no nested subagents. For each phase, the main orchestrator dispatches the implementer agent, then the reviewer agent, then runs a bounded fix-loop if the review fails. The main orchestrator's context accumulates only phase-level summaries and verdicts, never per-file reads, per-task writes, or implementation details.

Parallelism is expressed as plan metadata (`oat_plan_parallel_groups` in plan.md frontmatter). When declared, each parallel group runs concurrently — one worktree per phase — and merges back to the orchestration branch in plan order after all phases in the group reach a terminal verdict. Plans without parallelism metadata execute identically to the previous `oat-project-implement` behavior.

## Orchestration Flow

### Startup Sequence

```
[0/N] Resolve active project, read state.md
[1/N] Resumption detection (if prior run entries in implementation.md)
      → identify resume target, detect in-flight phases, detect un-cleaned worktrees
      → prompt user if un-cleaned worktrees found
[2/N] Capability detection and tier selection
      → oat-phase-implementer + oat-reviewer: {available | authorization required | not resolved}
      → Codex authorization required: single user prompt; approve → Tier 1; decline → Tier 2
      → Selected: Tier {1 | 2} — {Subagents | Inline}
      (Tier is locked for the entire run)
[3/N] Read plan.md, invoke oat project validate-plan CLI (Step 2.1)
      → Exit non-zero: STOP, surface validator errors
      → Exit 0: build execution schedule from plan order + parallel groups (Step 2.2)
```

If `--dry-run`: output schedule (tier, phases, groups, worktrees-that-would-be-created) and exit without executing.

### Per-Phase Flow

```
For each phase pNN in the execution schedule:

  ├─ Dispatch oat-phase-implementer (Tier 1 subagent) OR inline per agent reference (Tier 2)
  │     Phase Scope: project path, phase ID, artifact paths, commit convention, workflow mode
  │     Returns: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED + summary
  │
  ├─ Handle implementer status:
  │     DONE              → proceed to review
  │     DONE_WITH_CONCERNS → if correctness-related: fix-dispatch first; else: note and proceed
  │     NEEDS_CONTEXT     → provide context, re-dispatch (counts toward retry limit)
  │     BLOCKED           → STOP, surface to user with phase ID, blocking reason, recommended action
  │
  ├─ Dispatch oat-reviewer with scope = pNN
  │     Reviewer writes reviews/pNN-review-YYYY-MM-DD.md
  │     Returns: verdict (pass | fail) + finding severities
  │
  ├─ If verdict = fail → bounded fix loop (retry limit: default 2, range 0–5):
  │     Re-dispatch implementer in fix mode with review artifact + findings + prior summary
  │     Re-dispatch reviewer with updated commit range
  │     Repeat until pass or retry exhausted
  │     If exhausted:
  │       Sequential mode → STOP, surface to user
  │       Parallel mode   → mark phase excluded, continue group
  │
  ├─ Update implementation.md (append phase outcome row inside orchestration-runs markers)
  ├─ Update plan.md review table row for pNN
  ├─ Update state.md (oat_current_task, oat_last_commit, oat_project_state_updated)
  ├─ Mandatory bookkeeping commit: chore(oat): bookkeeping after pNN {pass|fail}
  └─ HiLL checkpoint check — pause if pNN in oat_plan_hill_phases
```

### Parallel Group Overlay

```
When schedule entry is a parallel group [p02, p03]:

  Tier 2 → degrade entire group to sequential inline (no worktrees)
            log degradation reason in implementation.md Outstanding Items

  Tier 1:
  ├─ Bootstrap worktrees: oat-worktree-bootstrap-auto per phase
  │     Any bootstrap failure → cancel all group worktrees, degrade to sequential inline
  │
  ├─ Concurrent dispatch: per-phase loop (implementer → reviewer → fix-loop) per worktree
  │
  ├─ Wait for all phases to reach terminal verdict (pass | excluded)
  │
  ├─ Fan-in: merge to orchestration branch in plan order for each pass phase:
  │     1. git merge --no-ff
  │     2. On conflict: abort, attempt cherry-pick
  │     3. Cherry-pick conflict: dispatch inline conflict-resolution subagent (Task tool)
  │        - Subagent reads conflicted files + artifacts, resolves, runs verification, commits
  │        - Returns: RESOLVED | UNRESOLVABLE | VERIFICATION_FAILED
  │     4. UNRESOLVABLE or VERIFICATION_FAILED → STOP, surface with phase ID, files, worktree path
  │
  ├─ Post-merge integration verification (pnpm test && pnpm lint && pnpm type-check)
  │     Trivial fix → commit fix; Untractable → revert merge, STOP
  │
  ├─ Worktree cleanup: remove on pass, preserve on excluded (log path in Outstanding Items)
  └─ Bookkeeping commit, HiLL check
```

### Flow Invariants

- Main orchestrator never reads implementation files directly.
- Tier is locked for the run; no silent mid-run downgrades.
- Bookkeeping commits are mandatory after each phase or group.
- HiLL checkpoints fire after the phase (or its group) completes and merges.
- A parallel group with failed phases still merges the passing phases in plan order.
- Never proceed past a broken merge.

## Plan Metadata Format

New frontmatter field in `plan.md`:

```yaml
oat_plan_parallel_groups: [['p02', 'p03'], ['p04', 'p05']]
```

**Semantics:**

- Each inner array is a group of phases that run concurrently in their own worktrees.
- Phases not listed in any group run sequentially in plan order.
- Groups themselves execute sequentially — group[0] completes and merges before group[1] starts.
- Empty or missing field → no parallelism, fully sequential, no worktrees created.

**Validation rules (enforced by `oat project validate-plan` CLI):**

- Every phase ID in the groups must exist in the plan.
- No phase may appear in more than one group.
- Groups must have no internal duplicates.
- Groups must contain at least 2 phases (no singletons).
- Non-array shape → invalid.

**HiLL interaction:** `oat_plan_hill_phases` and `oat_plan_parallel_groups` are orthogonal. A HiLL checkpoint fires after the phase's group completes and merges, not mid-group.

## Tier Selection Model

```
Host: Claude Code
  → Check Task-tool availability for oat-phase-implementer + oat-reviewer
  → Available → Tier 1

Host: Cursor
  → Cursor-native invocation; Available → Tier 1

Host: Codex (multi-agent)
  → Check [features] multi_agent = true
  → Available without auth → Tier 1
  → authorization required → single user prompt at skill start:
      "Delegate phase implementation and review to subagents for this run?
       (Authorizes spawn_agent for oat-phase-implementer and oat-reviewer
       across every phase in this run.)"
      Approved → Tier 1
      Declined → Tier 2

Host: not resolved → Tier 2 (inline fallback)
```

Tier 1: native subagent dispatch. Both implementer and reviewer are dispatched as separate subagents with fresh contexts.

Tier 2: inline fallback. Orchestrator reads `.agents/agents/oat-phase-implementer.md` and `.agents/agents/oat-reviewer.md` as reference and executes the processes in its own context. Parallel groups degrade to sequential since the orchestrator cannot concurrently execute inline.

## Error Handling Architecture

| Error Type                               | Handling                                                  |
| ---------------------------------------- | --------------------------------------------------------- |
| Implementer returns `DONE`               | Proceed to review                                         |
| Implementer returns `DONE_WITH_CONCERNS` | Read concerns; fix if correctness-related before review   |
| Implementer returns `NEEDS_CONTEXT`      | Provide context, re-dispatch (retry count++)              |
| Implementer returns `BLOCKED`            | STOP — legitimate mid-run pause; surface to user          |
| Reviewer returns `fail`                  | Enter bounded fix loop (retry limit 2 by default)         |
| Fix loop exhausted (sequential)          | STOP — surface phase, findings, review path               |
| Fix loop exhausted (parallel)            | Mark phase `excluded`; continue group                     |
| Transient dispatch failure               | Retry once; second failure → treat as fix-loop exhaustion |
| Worktree bootstrap failure               | Degrade entire group to sequential inline                 |
| Merge conflict (merge)                   | Abort, attempt cherry-pick                                |
| Merge conflict (cherry-pick)             | Dispatch inline resolution subagent via Task tool         |
| Subagent: `UNRESOLVABLE`                 | STOP — surface phase ID, files, worktree path, reasoning  |
| Subagent: `VERIFICATION_FAILED`          | STOP — same surface                                       |
| Post-merge integration failure           | Attempt trivial fix; else revert merge + STOP             |
