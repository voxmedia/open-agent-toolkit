### Important

- **Decision promotions are not idempotent across an interrupted writeback** (`.agents/skills/oat-project-retro/references/apply-procedure.md:43`)
  - Issue: The procedure runs `oat decision new` for every eligible decision
    item and treats only the retro item's status as its resume marker. If the
    command creates the record and managed index but execution stops before
    `Status`/`Applied-ref` are written back, the item remains eligible. The
    next run invokes `oat decision new` again, while the CLI explicitly rejects
    an existing same-day/same-slug record
    (`packages/cli/src/commands/decision/new.ts:163`). The claimed resumable,
    idempotent apply contract therefore gets stuck at a realistic interruption
    boundary.
  - Fix: Before creating a decision, perform a date-independent exact-slug
    lookup using the CLI's ID rules. If a matching record exists, verify that
    it represents this proposal and recover by writing its path/ID to
    `Applied-ref`; otherwise create it. Document the same post-side-effect
    recovery rule for every apply type.

- **Non-interactive filing has unresolved mandatory choices** (`.agents/skills/oat-project-retro-file/SKILL.md:121`)
  - Issue: Non-interactive runs must use configured destinations without
    stopping for input, but duplicate handling still requires an explicit
    disposition at lines 153-160, and backlog filing requires confirmed title,
    acceptance criteria, labels, priority, scope, and scope estimate at lines
    194-201. The retro item schema supplies only a title and tracker-ready
    prose, and destination config authorizes a destination rather than these
    missing choices. A configured autonomous backlog run can therefore prompt,
    invent metadata, or stop, while a duplicate can be strengthened, linked,
    skipped, or refiled without a defined non-interactive rule.
  - Fix: Define deterministic non-interactive behavior for duplicate
    candidates and missing backlog metadata. Either extend the artifact schema
    with the required tracker fields or specify bounded defaults and safe
    no-action behavior. State whether configured consent authorizes
    strengthening comments/edits; never prompt or infer broader consent in a
    non-interactive run.

### Medium

- **Rejected apply items require an edit that the same contract forbids** (`.agents/skills/oat-project-retro/references/apply-procedure.md:63`)
  - Issue: Rejection handling says to preserve the reason in item prose, but
    lines 67-69 and the template's mutable-field contract prohibit changing
    proposal bodies and allow only `Status`, `Applied-ref`, and the promotions
    rollup. An agent cannot both retain the reason and obey artifact
    immutability.
  - Fix: Add a dedicated mutable rejection/note field to the canonical item
    schema and both consumers, or remove the reason-write requirement and align
    the design's rejection semantics.

- **Promotion rollup aggregation is not deterministic** (`.oat/templates/project-retro.md:156`)
  - Issue: The template identifies which items contribute to
    `oat_retro_promotions`, but it does not define how combinations of
    `proposed`, `approved`, `applied`, and `rejected` map to `proposed`,
    `partial`, or `complete`. The apply procedure only says to recompute the
    field. Filing provides an exact settled/unsettled aggregation, so different
    agents can legitimately produce different promotion rollups from the same
    register.
  - Fix: Define exact promotion aggregation, including that `approved` remains
    unsettled and whether `rejected` counts as settled, in the template and
    apply reference.

- **Render completion does not validate required artifact provenance** (`.agents/skills/oat-project-retro/SKILL.md:105`)
  - Issue: The template initializes `oat_retro_project` and
    `oat_retro_generated` to `null`, but the render requirements and final
    checks only mandate generated/template marker retirement. A run can satisfy
    the stated completion checklist while leaving source-project and generation
    timestamp null; the checklist also does not explicitly reject unreplaced
    template item placeholders.
  - Fix: Require a non-null project slug and UTC generation timestamp, remove
    all scaffold item examples/placeholders, and add those checks to Step 6
    before `oat_generated: true` is accepted.
