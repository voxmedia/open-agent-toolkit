# Discovery: generated-artifact-gate-hygiene

## Initial Request

Two upstream OAT bugs share one root cause: OAT's own generated or
tool-managed artifacts dirty the working tree, and then trip OAT's own
clean-state gates.

**Bug 1 — dispatch-log append aborts the phase implementer.** During a real
run, a Phase 3 implementer aborted before executing any task. The root
workflow is required to append a project-log entry immediately after a
subagent dispatch is accepted, and the phase implementer is required to abort
unless the worktree is completely clean. In same-checkout (sequential)
execution those two obligations race: the root passes its own pre-dispatch
clean check, dispatches, then dirties the tree with the required log entry,
and the child's preflight sees the dirt and fails closed. No phase code ran.

**Bug 2 — project start prompts on sync-only dirt.** The preflight shared by
the three project-start workflows stops and asks the user how to handle any
non-empty working tree, including the common case where the only dirty path
is output regenerated by `oat sync`. That output carries no user intent, so
the prompt is pure friction and trains users to click through a safety gate.

### Supporting Evidence

Investigation confirmed the mechanism and found the problem is broader than a
race:

- The project log file is tracked in git and covered by no ignore rule.
- No bookkeeping commit in the implementation workflow ever stages it. The
  phase-boundary and closeout bookkeeping commits each stage exactly three
  tracking artifacts and explicitly forbid a repository-wide add. Only the
  summary and completion workflows stage the log, at closeout.
- Consequently the dirt is not transient. Once the first dispatch entry
  lands, the file stays dirty for the rest of the run, so the same blanket
  clean requirement fails at the child's preflight, the child's per-task
  commit verification, the root's pre-dispatch check on every later phase,
  and the root's post-report range validation.
- Parallel-group phases are unaffected, because each worktree is bootstrapped
  from the recorded expected head and never inherits the uncommitted file.
- The project-start preflight decision text is substantively the same across all
  three project-start workflows, but the blocks are **not** byte-identical: only
  `oat-project-quick-start` carries an autonomy branch in Step 0, and it records
  gate `QS-01`, which the other two workflows must not inherit. An initial
  reading of this discovery asserted byte-identity; the plan artifact review
  corrected it.

## Clarifying Questions

### Question 1: Fix shape for the dispatch-acceptance log entry

**Q:** Four options were explored — defer the entry to phase-report return;
keep it at acceptance and whitelist the one path at every clean check;
restructure so the entry is appended and committed before the phase base is
captured; or move dispatch events to a separate gitignored journal. Which?

**A:** Defer it to phase-report return.

**Decision:** The dispatch-acceptance entry is batched with the existing
phase-outcome entry and committed with phase bookkeeping. No clean-state
contract is weakened and no new artifact is introduced. The accepted cost is
losing crash-time evidence of an accepted dispatch when a run dies mid-phase.

### Question 2: Why not simply commit after each log append?

**Q:** If the file is dirty, why not commit it right after appending?

**A:** That works for four of the five append points but not the fifth.

**Decision:** Review-validation, STOP/park, phase-outcome, and merge-result
appends all fire after the child has returned, so committing there is correct
and is adopted. The dispatch-acceptance append is the only one inside a
child-owned window, where committing converts a dirty-file conflict into a
head conflict — it breaks the root's commit-range validation, introduces a
commit that maps to no task, and can make a concurrently running child observe
two commits where its contract requires exactly one. Hence the deferral in
Question 1.

### Question 3: Scope of the sync preflight change

**Q:** Should the sync-only-dirt behavior be folded into this project?

**A:** Yes.

**Decision:** Both bugs ship together as one coherent fix to how OAT treats
its own generated artifacts at clean-state gates.

### Question 4: How is sync ownership proven?

**Q:** Should the preflight read the sync manifest from skill prose, match path
prefixes, or call a CLI primitive that classifies dirty paths?

**A:** A CLI primitive.

**Decision:** The manifest is authoritative but demonstrably under-reports —
this repo reports every Cursor skill view as stray and unmanaged — and asking
an agent to parse JSON and set-match paths from prose is the same class of
fragile instruction that produced Bug 1. A CLI primitive puts classification in
one tested place and lets all three project-start workflows share a single
short instruction. Because the primitive serves one specific call site, it
should report the preflight decision itself rather than only a raw
classification, so the three workflows cannot drift in how they interpret it.

## Solution Space

### Approach 1: Ownership-and-timing correction _(Recommended, chosen)_

**Description:** Treat both bugs as ownership defects rather than check
defects. Every artifact OAT generates must have a workflow step that commits
it, and no artifact write may occur inside a window where a child owns the
repository head. Clean-state checks stay blanket and unweakened.

**When this is the right choice:** When the checks encode a genuine invariant
worth preserving and the writes are the thing out of place.

**Tradeoffs:** Loses crash-time forensic evidence at the dispatch-acceptance
moment, and requires auditing every write site rather than patching one check.

### Approach 2: Narrow allowances at each clean check

**Description:** Keep every write where it is and teach each clean-state check
to tolerate the specific OAT-owned paths.

**When this is the right choice:** When the write timing is genuinely fixed by
an external constraint and forensic evidence at write time is essential.

**Tradeoffs:** Weakens at least four separate contract points instead of one;
each allowance is a place where genuinely unrelated dirt can slip through; the
standing-dirt problem remains unsolved.

### Approach 3: Gitignored journal for dispatch events

**Description:** Move dispatch telemetry out of the tracked project log into a
separate ignored journal artifact.

**When this is the right choice:** When dispatch telemetry has genuinely
different durability requirements from workflow judgments.

**Tradeoffs:** Cleanest invariant, but adds a new artifact and CLI surface,
and the tracked project log is deliberately durable — it feeds roll-up,
summary synthesis, and the roll-up-before-archive gate.

### Chosen Direction

**Approach:** Ownership-and-timing correction.

**Rationale:** It fixes the standing-dirt problem that the other approaches
leave in place, preserves the clean-worktree invariant that makes phase
verification trustworthy, and adds no new artifact surface.

**User validated:** Yes — explicit choice of the deferral option, and explicit
direction to fold in the sync preflight change.

## Key Decisions

1. **Log write timing:** No project-log write may occur while a child owns the
   repository head. The dispatch-acceptance entry moves to phase-report return.
2. **Log commit ownership:** The project log joins the set of artifacts the
   implementation workflow commits at phase boundaries, instead of staying
   dirty until closeout.
3. **Clean-state checks stay strict:** No clean-worktree check is relaxed or
   given a path allowance. Genuinely unrelated dirt must still fail closed.
4. **Sync-only dirt auto-resolves:** When every dirty path is provably owned by
   `oat sync`, the project-start preflight commits it and continues without
   prompting, reporting what it did in one line.
5. **Ownership must be provable:** Auto-commit applies only to paths OAT can
   demonstrate it owns. Anything unproven keeps the existing three-choice
   prompt.
6. **Preflight parity applies to a shared decision core, not the whole block:**
   The classification call and its three branches are byte-identical across the
   three project-start workflows and are delimited so parity can be asserted
   mechanically. Workflow-specific autonomy provenance stays deliberately
   outside that core, so each skill keeps its own mapped gate identifier and no
   workflow inherits another's.
7. **Ownership is proven by a CLI primitive:** A new project-scoped preflight
   command classifies the working tree and reports the resulting decision, so
   the workflows carry a short instruction instead of classification logic.
8. **Ownership proof must survive removals:** Sync deletes a provider path and
   drops its manifest entry in one operation, so the post-sync manifest alone
   cannot prove a deletion was sync-owned. Ownership is established against the
   union of the working and committed-baseline manifests, and unprovable
   evidence degrades to a prompt rather than an assumption of ownership.
   Baseline evidence is required only for claims that need history: a first sync
   with no committed baseline can still auto-commit newly created provider views.
   Extension-generated role files never appear in the manifest at all, but both
   providers record ownership as a marker inside each generated file's content,
   so a deleted one is proved by reading its `HEAD` blob and applying the
   provider's existing managed-role predicate. No new ownership store is needed.
9. **Commit ownership spans every log writer, not just the implementation
   workflow:** `oat gate review` appends a structural entry from CLI code, and
   `oat-project-review-provide` appends in its attempted-reconnaissance branch
   while its bookkeeping commit scope excludes the log. Both are in scope. The
   append-site inventory is pinned by a test with an explicit allowlist, so a
   newly added writer fails until it is consciously given an owner. This scope
   expansion was adopted after the plan review found the original two-bug framing
   too narrow to satisfy the criterion below.
10. **Auto-commit is never reachable from an unmerged path:** Ownership alone
    does not authorize a commit. Any path in a git conflict state resolves to a
    prompt regardless of who owns it, so OAT never resolves a conflict on the
    user's behalf.

## Constraints

- Bundled skill and agent assets count as shipped CLI functionality under repo
  release policy: any change requires the lockstep version bump across all five
  public packages, a frontmatter version bump on each changed skill, and a
  passing `pnpm release:validate`.
- Provider views are generated from canonical sources; edits must be made
  canonically and re-synced, never edited in a provider view.
- The project log's durability, append-only semantics, roll-up behavior, and
  single-writer CLI contract must not change.
- Deferring the dispatch entry must not drop any information the entry
  currently carries; it may only move when that information is written.
- Regression coverage belongs in the existing contract-test harness that
  asserts on skill prose.

## Success Criteria

- A sequential phase implementer no longer aborts its preflight because the
  root appended a dispatch log entry.
- The project log is committed at each phase boundary rather than accumulating
  dirt across an entire run.
- Every path that appends to the project log commits it before returning,
  parking, or stopping — across `oat-project-implement`, the `oat gate review`
  CLI, and `oat-project-review-provide` — including terminal paths that bypass
  the phase boundary.
- A newly introduced project-log writer fails the append-site inventory test
  until it is given an explicit commit owner.
- No path in a git conflict state can ever be auto-committed.
- No project-log write occurs inside a child-owned head window, verified across
  all five append points.
- Every clean-worktree check remains blanket, with no path allowances added.
- Starting a project when the only dirty paths are sync-owned proceeds without
  a prompt and reports the commit it made, including when the dirt consists of
  sync-driven deletions.
- Starting a project with any unproven dirty path still presents the existing
  three-choice prompt.
- The shared preflight decision core is byte-identical across the three
  project-start workflows, and no workflow's autonomy gate identifier appears in
  another's.
- Release mechanics leave no generated version artifact uncommitted or stale.
- Regression tests fail if either sequence regresses.

## Out of Scope

- A separate gitignored dispatch journal.
- Restructuring provider dispatch so handle acceptance can be split from
  payload delivery.
- Adopting or repairing the stray, unmanaged provider entries this repo
  currently reports; that is a pre-existing local condition.
- Any change to project-log roll-up, synthesis, or archive-gate semantics.
- The broader question of which artifacts belong in bookkeeping commits beyond
  the project log.

## Open Questions

- **Untracked sync output:** Resolved during planning — yes. A newly created but
  untracked path auto-commits on the same terms as a modified one, provided the
  manifest proves ownership, since newly materialized provider views are exactly
  the sync-output case.
- **Forensic compensation:** Does losing crash-time dispatch evidence warrant a
  compensating structural entry written before the phase base is captured, or
  is the phase-outcome entry sufficient?

## Assumptions

- The five project-log append points identified in the implementation workflow
  are exhaustive for that workflow.
- Phase-boundary bookkeeping commits are frequent enough that committing the
  project log there keeps the tree clean at every gate that matters.
- No consumer depends on the dispatch-acceptance entry appearing in the log
  before the phase completes.

## Risks

- **Lost crash-time dispatch evidence:** A run that dies mid-phase will no
  longer have a logged record that the dispatch was accepted.
  - **Likelihood:** Medium
  - **Impact:** Low
  - **Mitigation Ideas:** The generic dispatch record still captures
    acceptance; consider a pre-base structural entry if this proves painful.
- **Manifest under-reporting:** If sync-owned path classification is
  incomplete, users keep seeing prompts for output that should auto-resolve.
  - **Likelihood:** Medium
  - **Impact:** Low
  - **Mitigation Ideas:** Failure mode is the status quo prompt, not an
    incorrect commit; prefer a CLI primitive over manifest reading if the gap
    proves material.
- **Prose-contract drift:** These are instructions interpreted by agents, so a
  subtly ambiguous edit can fail closed in a new place.
  - **Likelihood:** Medium
  - **Impact:** Medium
  - **Mitigation Ideas:** Assert the exact contract sentences in the existing
    prose contract tests.
