## Findings

### Critical

- **Post-plan mutation can replace the approved projection and still verify**
  (`packages/cli/src/commands/pjm/remote/providers/linear.ts:1309`)
  - Issue: `validLinearMutationActionEvidence()` checks that the nested digest
    strings agree with one another, but it never recomputes the projection
    digest, preview digest, or action digest from the action's current context,
    identity/provenance, field mask, projection, and postconditions. It also does
    not require projection and postconditions to remain equal. A live probe
    planned and approved a safe title update, replaced both
    `action.intent.projection` and `postconditions` afterward without changing
    any safety/preview/action evidence, supplied matching readback, and
    `verifyLinearMutationObservation()` returned `verified` and
    `authoritative-readback-matched` (`linear.ts:722`). The same validator is
    shared by create, update, transition, and annotation.
  - Impact: A caller can execute or ratify a target, projection, identity,
    provenance, or postcondition that was never safety-checked, previewed, or
    approved. Exact readback of the substituted value does not restore the lost
    authorization boundary.
  - Fix: Canonically validate the complete mutation action before observation
    acceptance: enforce the operation-specific field mask, exact projection /
    postcondition equality, `semanticDigest(projection)` equality with the
    bound safety projection digest, exact outbound-safety evidence, recomputed
    preview digest, and recomputed action digest over every load-bearing input.
    Route both the dedicated verifier and public adapter through that primitive,
    and add post-plan alteration regressions for every mutation class and every
    independently altered context/identity/provenance/evidence field.
  - Requirement: p05-t03, p05-t05, FR8, FR11, FR14, FR15, NFR1, NFR2

- **A stale read action can be retargeted to another UUID and accepted as
  current** (`packages/cli/src/commands/pjm/remote/providers/linear.ts:559`)
  - Issue: `planLinearRead()` records an `actionDigest`, but
    `classifyLinearReadObservation()` never validates or recomputes it. A live
    probe planned a read for UUID A, changed only the action's UUID and stable
    ID to UUID B while retaining the original action digest and step, and
    supplied a same-context observation for B. Classification returned
    `current`, replaced prior evidence, and normalized B as the issue. The
    public `linearAdapter.validateObservation()` also returned `valid: true`
    for the retargeted action (`linear.ts:1027`).
  - Impact: A forged, historical, or mutated semantic action can refresh a
    binding from the wrong Linear issue even when workspace/team capability and
    the observation itself are internally consistent. Persisting that result
    would poison durable identity and reconciliation state.
  - Fix: Add one defensive read-action validator that requires the original
    provider, operation, exact pinned context, canonical workspace/UUID stable
    ID, identifier/step contract, capability digest, result contract, and
    recomputed action digest. Require it in both read classification and public
    adapter validation before considering observation or availability. Add
    wrong UUID/stable ID/step/context/capability plus altered-action-digest
    regressions.
  - Requirement: p05-t02, p05-t04, FR5, FR11, FR13, FR16, NFR2

- **Forged duplicate-search actions can authorize blind retry with a false
  no-match** (`packages/cli/src/commands/pjm/remote/providers/linear.ts:932`)
  - Issue: The duplicate validator checks that `query` and `resultContract` are
    objects and that `maxResults` is bounded, but it never validates the
    planner's complete provenance, reserved-binding, historical-identifier,
    workspace/team, and classification contract. Worse, the zero-result branch
    returns accepted `no-match` before validating any query fields
    (`linear.ts:946`). A live probe supplied a hand-built action whose query was
    `{}`, whose self-consistent query digest matched `{}`, and whose only result
    contract field was `maxResults: 1`; an empty exact-context observation was
    accepted as authoritative `no-match`.
  - Impact: Recovery after an uncertain create can conclude that no duplicate
    exists without ever searching the planned provenance, reservation, or
    historical aliases, allowing the next recovery layer to create a duplicate.
  - Fix: Defensively validate the complete duplicate action before availability
    or result classification: require bounded non-empty provenance and reserved
    binding, unique valid historical identifiers, exact workspace/team query,
    recomputed query digest, exact result-contract flags/classifications, and
    exact capability evidence. Reject incomplete or manually forged actions,
    including zero-result observations, and add direct forged-action and
    wrong-result recovery regressions.
  - Requirement: p05-t08, p05-t09, FR14, FR16, NFR2

### Important

- **The public adapter treats unrelated issue evidence as valid for specialized
  operations** (`packages/cli/src/commands/pjm/remote/providers/linear.ts:1027`)
  - Issue: For `read-discussion` and `search-duplicates`, generic
    `validateObservation()` checks only provider/context plus a nested host
    capability and digest. It does not fail closed because these operations
    require their typed observations and validators. A live probe passed an
    unrelated issue observation for a planned discussion action and received
    `{ valid: true }`; generic `verify()` then returned an empty array
    (`linear.ts:1088`). The empty result does not provide a safe unavailable
    sentinel and can be misread by generic consumers as having no failed fields.
  - Impact: The exported `ProviderAdapter` surface is not closed even though its
    typed helpers are stricter. A provider-neutral lifecycle or conformance
    consumer can validate unrelated evidence without invoking the identity,
    cursor, query, availability, or result-bound checks.
  - Fix: Make generic validation explicitly reject specialized operations and
    generic verification return an unavailable sentinel, directing callers to
    the typed discussion/duplicate validators; or extend the shared contract so
    those typed observations are first-class. Add public-surface regressions for
    unrelated issue evidence and every specialized operation.
  - Requirement: p05-t06, p05-t08, p05-t09, FR16, FR18, NFR2, NFR8

- **Discussion pages accept unbounded item identifiers and bodies**
  (`packages/cli/src/commands/pjm/remote/providers/linear.ts:692`)
  - Issue: The validator bounds item count and cursor length, but it requires
    only a non-empty ID and a string body. It does not bound ID length or UTF-8
    body bytes before copying the item into the returned evidence page
    (`linear.ts:707`). A live exact-context one-item page with a 20,000-byte body
    was accepted as `page` with the body intact. The equivalent mature GitHub
    path enforces concrete ID and body byte limits.
  - Impact: The promised bounded, sanitized, non-persistent evidence surface can
    consume and return arbitrarily large provider-authored text. Non-persistence
    avoids durable leakage but does not satisfy the schema/size boundary or
    protect the live process and downstream prompt surface.
  - Fix: Enforce documented absolute item-count, ID-byte, body-byte, cursor, and
    total-page bounds before suppression/return, using byte length rather than
    JavaScript character count. Add exact-limit, one-byte-over, multibyte,
    oversized-ID, and signaled-body regressions through the typed and public
    surfaces.
  - Requirement: p05-t02, p05-t04, FR12, FR18, NFR1

- **The Phase 5 conformance and lifecycle suites bypass the unsafe Linear paths**
  (`packages/cli/src/commands/pjm/remote/__integration__/linear.test.ts:110`)
  - Issue: The publish/reconcile test calls the generic `LifecycleHarness`, which
    constructs and verifies its own update without using `linearAdapter`,
    `planLinearMutation()`, or `verifyLinearMutationObservation()`. The claimed
    closeout/independent-outcome test only resumes that generic update and
    classifies an archived read (`__integration__/linear.test.ts:179`); it does
    not execute a
    Linear transition, annotation, reviewed independent outcomes, or provider
    persistence boundary. The conformance fixture additionally wraps/overrides
    public planning and validation to manufacture safe observations
    (`providers/linear.conformance.test.ts:109`). This is why all four direct
    bypass probes above coexist with a green focused and full-remote suite.
  - Impact: p05-t06/p05-t07 do not verify the public adapter or the critical
    Linear intake, publish, reconcile, closeout, discussion, duplicate recovery,
    and restart-to-persistence paths required by the plan. Regression protection
    for the phase's P0 safety boundaries is therefore missing.
  - Fix: Drive the real public Linear adapter and typed validators through an
    inspectable lifecycle/store boundary. Persist only after public
    validation/verification; cover all four mutation classes, exact/mismatched
    readback, changed UUID/context/evidence, discussion non-persistence,
    duplicate recovery, archived behavior, crash resumption, and independent
    closeout outcomes. Do not replace the adapter with a fixture wrapper on the
    path under test.
  - Requirement: p05-t06, p05-t07, FR11, FR14, FR15, FR17, NFR2, NFR3, NFR8
