## Findings

### Critical

- **Recreate executes a newly computed create projection outside the approved
  preview** (`packages/cli/src/commands/pjm/remote/service.ts:3822`)
  - Issue: The operator approves the resolution digest created before duplicate
    search, with placeholder projection/safety components
    (`service.ts:789-823`, `:1437-1469`). After a no-match result, production
    computes title, description, and priority, runs the gate, mutates only the
    stored component fields while retaining the old preview digest and approval,
    and immediately emits the create action (`:3822-3891`). The projection also
    always includes the full local description and priority instead of applying
    the effective description and purpose/field policy. The action-level gate is
    real, but its result is not bound to the preview the user approved.
  - Fix: Build the exact effective-policy projection and universal safety result
    before the create approval floor. Persist a new immutable create-substep
    preview whose digest covers target, policy, projection, safety result,
    capability, provenance, and preimage; require fresh matching approval before
    emitting the action. Apply `none`/managed/replace and purpose field directions
    exactly as other production mutations do.
  - Requirement: FR7, FR8, FR14, NFR1, NFR2; p07-t06 and authorized recovery.

- **Ambiguous duplicate search is treated as no match and can create a duplicate**
  (`packages/cli/src/commands/pjm/remote/service.ts:3812`)
  - Issue: The production observation contract represents duplicate search only
    as a generic observed identity or null identity. Any `observed` result with a
    null identity enters the create branch; there is no production representation
    or branch for the planned `ambiguous` outcome. Consequently a host that found
    several candidates cannot return that semantic result without being mistaken
    for no-match. The module helper has the correct four-way union, but production
    bypasses it at the decision point.
  - Fix: Define a bounded provider-neutral duplicate-search outcome schema with
    `found-existing`, `search-unavailable`, `ambiguous`, and `no-match`; bind it to
    the durable search action and validate candidate evidence. Only an explicit
    verified no-match may advance to a newly approved create substep. Exercise all
    four outcomes through `createProductionRemoteRunner()`.
  - Requirement: FR13, FR14, NFR2; p07-t06.

- **An uncertain recreate attempt does not freeze the old binding**
  (`packages/cli/src/commands/pjm/remote/service.ts:3791`)
  - Issue: Unknown/not-committed create observations transition only the operation
    to `uncertain`; production does not change binding metadata or operational
    lifecycle state to blocked. No mutation entry guard treats that uncertain
    resolution operation as a binding freeze. A binding that entered recreate as
    active therefore remains writable after a create that may have committed,
    contrary to the no-blind-retry/frozen-binding contract.
  - Fix: Persist the create attempt before handoff, then atomically mark the old
    binding blocked for any uncertain create result. Reject all further writes and
    create retries until provenance search/read-back reconciles the uncertain
    operation. Add production tests for unknown, rejected, restart, and attempted
    replay states.
  - Requirement: FR11, FR13, FR14, NFR2, NFR3; p07-t06.

- **Relink and recreate complete with stale snapshot/baseline state and an
  unrecoverable split-write window**
  (`packages/cli/src/commands/pjm/remote/service.ts:1521`)
  - Issue: The resolution store bridge updates portable identity and then writes
    only lifecycle fields to the old operational state. It does not update
    `metadataUpdatedAt`, replace the snapshot identity/context, establish the
    required fresh snapshot/baseline, or preserve the old snapshot as resolution
    evidence. A successful relink/recreate therefore causes the production doctor
    to report metadata timestamp/identity divergence. Additionally, a crash after
    metadata update but before state write leaves a split binding while the
    resolution journal still says the transition did not complete; re-application
    then fails preview-preimage validation rather than repairing from the journal.
  - Fix: Model the binding transition as restart-safe durable substeps with a
    retained former snapshot and a fully materialized, sanitized authoritative
    replacement snapshot/baseline. Keep metadata, state, and journal timestamps
    coherent; persist enough pre/post-image evidence to detect and resume either
    side of every crash point. Assert doctor passes immediately after successful
    relink/recreate and that each injected bridge crash is repairable.
  - Requirement: FR5, FR13, FR14, NFR3; p07-t05, p07-t06.

- **Declared P0 cross-provider and lifecycle E2E coverage still does not drive
  production behavior** (`packages/cli/src/e2e/pjm-remote.test.ts:112`)
  - Issue: The E2E lifecycle matrix still returns caller-selected envelopes from
    `envelopeFor()`; only doctor/migration use the production runner. The
    cross-provider suite's production case stops at a GitHub/Linear closeout
    preview, while explicit GitHub-to-Linear/Jira publication, action/observation
    continuation, provider-independent closeout, and no-transitive-mirroring are
    asserted through an in-memory `WorkflowFixture`
    (`remote/__integration__/cross-provider.test.ts:128-279`). Service tests add
    useful happy-path production coverage, but omit found-existing, ambiguous,
    unavailable, uncertain-create, lifecycle crash/restart, and CLI status paths.
    This fails the plan's explicit E2E verification for P0 FR15/FR17 and allowed
    the production defects above to remain green.
  - Fix: Add isolated-repository command/E2E cases that use
    `createProductionRemoteRunner()` for every planned lifecycle family and
    representative GitHub-only, GitHub-to-Linear, and GitHub-to-Jira workflow.
    Drive real provider-neutral actions and observations, including partial and
    uncertain results, and assert persisted postconditions plus human/JSON
    exit-status parity. Keep the fixture-only safety test bounded to declared
    synthetic values.
  - Requirement: FR1, FR15, FR17, NFR3, NFR6, NFR7; p07-t08, p07-t10.

### Important

- **The production discussion action omits its page limit and cannot continue a
  cursor** (`packages/cli/src/commands/pjm/remote/service.ts:619`)
  - Issue: The durable `read-discussion` action includes only `stableId`; the
    requested limit is stored in the operation but is not provided to the host.
    Continuation hard-codes `maxPages: 1` and completes the operation even when a
    non-null cursor reports more evidence. The local result is safely sliced and
    marked truncated, but the host cannot honor the requested fetch bound and the
    command cannot fetch a subsequent bounded page, so production does not
    implement the planned pagination/page-limit contract.
  - Fix: Add bounded `limit` and optional `cursor` to the provider-neutral action,
    bind them to the operation preview, and provide a restart-safe next-page
    continuation that preserves the overall page/item cap without persisting item
    bodies. Add production exact-limit, next-cursor, page-cap, and unavailable
    tests.
  - Requirement: FR12, FR18; p07-t04.

- **Closeout asks for approval without exposing the exact reviewed substep**
  (`packages/cli/src/commands/pjm/remote/service.ts:556`)
  - Issue: The step digest now covers the action and safety evidence, but the
    approval preview rendered to authority validation contains only the word
    `annotate` or `transition`, with null description/priority, and uses aggregate
    operation projection/safety components. The prepare response exposes only a
    digest-bearing recovery sentence, not the annotation body, target transition,
    or exact per-step projection hashes. An operator cannot inspect what the
    fresh approval authorizes even though the stored action is cryptographically
    pinned.
  - Fix: Persist and return one inspectable reviewed-batch preview with each
    ordered substep's target, normalized rendered fields or concise hashes,
    capability, policy, projection, and safety digests. Validate the approval
    against those exact per-step component digests before action handoff.
  - Requirement: FR15, NFR6; p07-t01, p07-t02.
