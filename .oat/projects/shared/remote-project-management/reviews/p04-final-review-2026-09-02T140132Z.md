## Findings

### Critical

- **Duplicate recovery accepts a candidate from a different GitHub host and
  account** (`packages/cli/src/commands/pjm/remote/providers/github.ts:906`)
  - Issue: Candidate context validation checks only whether the candidate's
    current `repositoryId` equals the planned repository ID or its unsourced
    `historicalRepositoryIds` array contains that ID. It does not require the
    candidate host/account to equal the action, does not validate current
    owner/name for a same-repository match, does not bind transfer evidence, and
    does not ensure the returned stable ID belongs to the planned GitHub host. A
    live post-image probe supplied a candidate from `evil.example`, account
    `attacker`, owner `evil`, and name `other` with the planned repository ID;
    the validator returned `accepted: true`, `one-verified-match`, and the evil
    stable ID. The same result occurred when only the historical repository list
    contained the planned ID.
  - Impact: Uncertain-create recovery can relink a local binding to a record from
    another GitHub instance/account or accept an unproved transfer. This is a P0
    wrong-binding path despite exact outer observation/query/capability evidence.
  - Fix: Require candidate host and account equality with the planned action and
    validate the stable-ID host namespace. For a current-repository match,
    require exact repository ID, owner, and name. For a moved candidate, require
    structured transfer evidence bound to the planned repository/context,
    candidate current context and stable identity, capability digest, query
    digest, and observation time; do not treat `contextVerified: true` plus an
    arbitrary historical-ID list as sufficient. Add wrong-host, wrong-account,
    wrong-owner/name, forged-history, and valid-transfer regressions.
  - Requirement: p04-t09, p04-t10, FR14, FR16, NFR2

### Important

- **The generic adapter validates unrelated issue observations for search and
  discussion actions**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:1218`)
  - Issue: `githubAdapter.validateObservation()` has exact branches only for
    mutations and reads. After capability checks, `search-duplicates` and
    `read-discussion` fall through to `{valid: true}` without checking their
    operation-specific observation contract. A live probe paired a bounded
    duplicate-search action with an unrelated issue observation and received
    `{valid: true, reasons: []}`. `verify()` similarly produces an empty result
    for non-mutations, so the shared provider surface does not identify the
    operation as unsupported by that observation type.
  - Impact: A generic `ProviderAdapter` consumer can treat an unrelated issue
    observation as validated evidence for a search/discussion action instead of
    being forced through the dedicated validator. Current integration helpers
    avoid this path, but the provider-neutral public interface is not fail
    closed.
  - Fix: Explicitly reject specialized search/discussion actions in
    `validateObservation()`, `verificationFields()`, and `verify()` unless the
    shared p03 interface can represent their typed observations without change;
    direct callers to the existing operation-specific validators. Add public
    adapter regressions proving these operations never return generic success
    for issue observations.
  - Requirement: p04-t06, p04-t09, p04-t10, p04-t11, FR14, FR16, FR18, NFR2,
    NFR8

### Medium

- **Unavailable search/discussion results are classified before their evidence
  is attributed to the planned action**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:838`)
  - Issue: Duplicate validation returns `unavailable` before comparing the
    observation provider/context/capability/query, and discussion validation
    returns `rate-limited` or `permission-denied` before comparing
    provider/context/capability/stable identity/cursor (`github.ts:1003`). A live
    wrong-repository, wrong-issue, wrong-capability, wrong-cursor discussion
    observation was reported as `rate-limited` rather than invalid.
  - Impact: No content is returned or marked persistable, so this does not create
    the Critical wrong-binding path, but a failure from another action can be
    attributed to the current operation and recorded with a misleading recovery
    reason.
  - Fix: Validate provider, action context, capability digest, query/stable
    identity, and cursor before branching on availability; only then classify a
    matching observation as unavailable, rate-limited, or permission-denied.
    Add mismatched unavailable-result regressions for both operations.
