## Findings

### Critical

- **Repository transfer changes the durable GitHub issue identity**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:272`)
  - Issue: `stableId` includes the current `repositoryId`. A verified repository
    transfer therefore changes the stable ID even when the immutable issue node
    ID is unchanged. The unit test described as covering moved aliases changes
    only owner/name (`github.test.ts:105`), while the integration transfer does
    change `repositoryId` but never asserts stable-ID continuity
    (`__integration__/github.test.ts:86`). A direct synthetic reproduction
    produced `github:github.example:repo_old:node_42` before transfer and
    `github:github.example:repo_new:node_42` afterward.
  - Impact: Existing bindings can appear to point at a different record after a
    legitimate transfer, breaking retained identity, alias history, refresh,
    duplicate recovery, and explicit anomaly resolution.
  - Fix: Derive the durable key from the GitHub instance plus immutable issue
    node/database identity; keep current and historical repository IDs in
    context/extension evidence rather than the stable key. Add a regression that
    changes repository ID, owner, name, number, and URL together while requiring
    an unchanged stable ID and both historical/current aliases. If the design's
    wording at `design.md:651` intended repository ID to be part of the durable
    key, align that stale wording with FR13's durable-move requirement.
  - Requirement: FR5, FR13, NFR5

- **The public adapter can plan and verify mutations without a normalized
  projection or universal safety evidence**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:780`)
  - Issue: `planGitHubMutation()` enforces a closed create/update projection and
    exact universal safety digests, but `githubAdapter.plan()` accepts arbitrary
    intent for every operation and never calls it. Transition and annotation
    tests use that generic bypass (`github.conformance.test.ts:96`), and the
    mutation verifier accepts those actions without checking any projection or
    safety evidence (`github.ts:430`). `verificationFields()` and `verify()` also
    return empty arrays (`github.ts:806`). A direct reproduction planned a
    transition containing only `stableId` and `postconditions`, then classified
    it `verified` after readback. For creates, the safe planner emits
    `stableId: null` (`github.ts:417`), and verification skips durable-identity
    comparison entirely (`github.ts:482`).
  - Impact: Create, update, transition, or annotation callers can bypass the P0
    pre-write gate and its preview/approval/action hashes; a create can report
    success without verifying the newly created durable identity or provenance.
  - Fix: Make the adapter's mutation planning path operation-discriminated and
    reject incomplete generic intents. Require the exact normalized projection,
    field mask, universal safety result/digests, stable identity or create
    provenance, and exact postconditions for all four mutation classes. Route
    `verificationFields()`/`verify()` through the same contract, and require
    verified create identity/provenance before success. Add missing, blocked,
    stale, mismatched, and altered-projection regressions for every mutation
    operation.
  - Requirement: FR6, FR11, FR14, FR15, NFR1, NFR2

- **GitHub publication safety is advisory and is not bound into preview,
  approval, action, or readback**
  (`packages/cli/src/commands/pjm/remote/providers/github-publication-safety.ts:47`)
  - Issue: `assessGitHubPublicationSafety()` returns a result, but no required
    consumer validates that result or carries its digest into a GitHub mutation
    plan. The mutation action retains only the universal safety digests
    (`github.ts:422`). The integration fixture manually checks the verdict and
    then calls the shared harness, which independently recreates universal
    safety and never receives the GitHub publication result
    (`__integration__/github.test.ts:113`). Visibility evidence is also accepted
    as any non-empty string rather than normalized evidence bound to the exact
    provider, repository context, capability, and observation time.
  - Impact: A caller can ignore the additional public-target verdict, substitute
    unrelated visibility evidence, or execute an action whose approved hashes
    contain no proof that the GitHub public/ambiguous-public policy passed.
  - Fix: Define a bounded normalized repository-visibility observation tied to
    exact GitHub context and pinned capability evidence. Add a required
    `requireCurrentGitHubPublicationSafety()` boundary and bind its result digest,
    visibility evidence digest, and the exact universal safety digests through
    preview, approval, semantic action, and readback verification. Add tests that
    execution cannot be constructed when this evidence is absent, stale,
    mismatched, failed, blocked, or from another repository.
  - Requirement: NFR1, NFR2, FR16, FR18

- **Read classification accepts an observation from an unpinned capability and
  does not validate the observation's declared stable identity**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:373`)
  - Issue: Read classification validates a separately supplied host-capability
    object, then directly normalizes the observation. It never compares
    `observation.capabilityEvidenceDigest` to the pinned capability, never
    validates the observation context against a transfer-aware planned identity,
    and only compares the optional action node ID to `fields.nodeId`; the
    observation's `identity.stableId` may contradict it. The generic read planner
    does not require either node identity or capability digest. A direct
    reproduction supplied `identity.stableId: "wrong_identity"` and
    `capabilityEvidenceDigest: "sha256:other-surface"`; classification still
    returned `current`.
  - Impact: Stale or misattributed read evidence can replace the normalized
    snapshot, manufacture a rename/transfer, or become the authoritative pre-read
    for a later mutation.
  - Fix: Require every read plan to carry the immutable expected identity and
    pinned capability digest. Before normalization, validate provider, exact
    account/context rules, observation capability digest, consistency between
    declared stable identity and GitHub node/database fields, and structured
    transfer/deletion evidence. Return incomplete/unavailable evidence instead of
    a normalized issue on any mismatch. Add adversarial mismatched-identity,
    wrong-surface, wrong-account, transfer, and deletion-evidence tests.
  - Requirement: FR11, FR13, FR16, NFR2

- **Duplicate and discussion validators are not bound to the action's capability,
  query evidence, or target identity**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:584`)
  - Issue: Duplicate planning records a capability digest, provenance token, and
    reserved binding ID, but validation compares the observation only with a
    newly supplied host-capability object, not the digest stored in the action.
    A candidate marked `matchedBy: "provenance"` contains no matched token or
    query digest, so it is accepted without proving a match to the planned
    provenance/reservation. A direct reproduction planned with capability A,
    validated with capability B, and accepted an unrelated candidate as
    `one-verified-match`. Discussion validation has the same planned-capability
    omission (`github.ts:724`), and its observation model contains no target
    stable identity at all (`github.ts:194`); a page for another issue in the
    same repository is therefore accepted.
  - Impact: Uncertain-create recovery can relink a local binding to the wrong
    GitHub issue, and on-demand discussion evidence can be attributed to the wrong
    record. Both violate exact evidence validation; the duplicate path is a P0
    recovery boundary.
  - Fix: Compare observation evidence to the capability digest and query contract
    stored in the action, not merely to a caller-supplied current capability.
    Require bounded proof of the exact matched provenance token, reserved binding
    ID, or planned alias plus verified stable/context identity. Include target
    stable identity in discussion observations and require equality with the
    action before accepting a page. Add stale-capability, wrong-query,
    wrong-reservation, and wrong-issue discussion regressions.
  - Requirement: FR14, FR16, FR18, NFR2

### Important

  persistence outcomes instead of exercising the GitHub safety path**
  (`packages/cli/src/commands/pjm/remote/__integration__/github.test.ts:237`)
  - Issue: The discussion fixture reports `journalUnchanged: true` as a literal,
    transfer history is manually appended
    (`__integration__/github.test.ts:104`), and publication
    uses the generic shared harness rather than a GitHub mutation plan. The
    conformance fixture explicitly expects no verification fields
    (`github.conformance.test.ts:72`) and checks transition/annotation only for
    provider/operation/context shape. These tests remain green while all five
    blocking reproductions above succeed.
  - Impact: The reported 53/53 result does not prove p04-t06/p04-t07/p04-t11's
    mutation safety, transfer persistence, readback identity, or discussion
    non-persistence requirements and will not fail on plausible regressions.
  - Fix: Drive create/update/transition/annotation through the safe GitHub adapter
    and the generic external-action/lifecycle boundary with inspectable store
    spies. Assert the same projection/safety/publication digests at preview,
    approval, action, observation, and readback; assert durable transfer alias
    history and stable identity; and prove discussion data is absent from actual
    snapshot/journal writes. Add mutation-style negative fixtures for every
    mismatch identified above.
