## Summary

Phase 3 has useful provider-neutral primitives, but the shipped command family
does not invoke them: every real `oat pjm remote` command reaches a placeholder
runner that claims persistence without reading or writing any remote state.
The disconnected lifecycle and create helpers also leave authority, action and
observation validation, authoritative create read-back, and shared-storage
approval freshness below the approved P0 safety contract. The canonical host
skill additionally remains absent from its managed Claude provider view.

Findings: 5 critical, 2 important, 0 medium, 0 minor

## Findings

### Critical

- **The installed command family is a non-persisting placeholder** (`packages/cli/src/commands/pjm/remote/index.ts:65`)
  - Issue: `DEFAULT_DEPENDENCIES.run` always returns `status: pending` and
    `persisted: true`, without opening a store, loading a binding, invoking the
    lifecycle services, accepting stdin, or emitting an action. This is the
    production dependency used by `createPjmCommand`; the tests replace it with
    another stub and therefore only verify argument forwarding. A live check
    with a nonexistent binding returned a persisted pending result instead of
    reporting that the binding does not exist. Intake, refresh, publish,
    reconcile, storage apply, and operation continuation are consequently not
    implemented through the public CLI.
  - Fix: Replace the default runner with a real service composition over the
    storage locator/store, policy and preview modules, host-execution selection,
    lifecycle/create-binding helpers, and stdin observation parser. Give
    continuation its own `operationId` request field, load the durable operation
    and current step, and return envelopes derived only from the persisted
    transition. Add default-dependency CLI integration tests against a temporary
    adopted repository; do not satisfy them by injecting `run`.
  - Requirement: FR4, FR5, FR16, NFR3, NFR7

- **The action/observation boundary accepts native and unexpected sensitive content** (`packages/cli/src/commands/pjm/remote/external-action.ts:127`)
  - Issue: `buildExternalAction` copies an arbitrary `Record<string, unknown>`
    into `intent` without a closed semantic schema, size bound, or sanitization.
    `acceptExternalObservation` similarly validates `outcome.fields` as an
    arbitrary scalar record but never checks `expectedObservation.fields`,
    `requireIdentity`, sensitive-content suppression, or diagnostic/alias
    safety. A direct reproduction accepted both an action containing
    `nativeRequest: {command: ...}` and an unexpected observation field holding
    a synthetic token signal. `createAndBindRemoteIssue` then passes the entire
    accepted field record to `materialize`.
  - Fix: Introduce closed, operation-discriminated normalized intent and
    observation schemas with byte/depth limits. Reject unknown action fields and
    native invocation shapes. On observations, enforce the exact planned field
    allowlist and identity contract, apply conservative whole-field suppression
    to allowed inbound text before persistence, and reject or ignore all extra
    fields without retaining their values. Add regression tests using generic
    forbidden keys and synthetic signals, without adding provider-native
    schemas or a credential-value parser.
  - Requirement: FR12, FR16, NFR1, NFR2, NFR8

- **Mutation authority and freshness are caller-self-attested** (`packages/cli/src/commands/pjm/remote/lifecycle.ts:353`)
  - Issue: `assertAuthority` accepts `user-authorized` when two digests supplied
    in the same input equal each other, and accepts autonomous authority from an
    input boolean. It does not resolve the p02 effective policy, load durable
    approval evidence, validate approval age/source, or compare workflow ID and
    revision with an authoritative active workflow. The write path also reuses
    the caller-supplied safety result and never re-probes/pins host capability or
    recomputes the projection and gate after its pre-read. Once the command stub
    is replaced, a caller could manufacture its own authority evidence and
    proceed with stale execution evidence.
  - Fix: Remove self-validating authority fields. Derive the expected
    instruction/workflow evidence from the current invocation and durable
    operation, resolve policy through the p02 authority module, validate fresh
    approval with the p02 preview validator, and persist that exact evidence.
    After pre-read, recompute the normalized projection and safety result, select
    and pin a current matching host capability, and reject any policy,
    capability, workflow, revision, projection, or digest drift before an
    attempt can start.
  - Requirement: FR8, FR9, FR11, FR16, NFR1, NFR2, NFR3

- **Initial create materializes from the mutation observation without authoritative read-back** (`packages/cli/src/commands/pjm/remote/create-binding.ts:104`)
  - Issue: Continuation accepts the caller-provided action rather than loading
    the action recorded by `recordAction`, so a self-consistent fabricated
    action/observation pair can pass. More fundamentally, one `observed`
    mutation response is compared with the projection and immediately used to
    materialize the binding and association. No separate provider-neutral read
    action is emitted and no pinned authoritative read-back occurs, despite the
    design and p03-t12 requiring create read-back before materialization. A
    provider-generated success-shaped response can therefore become a false
    verified binding.
  - Fix: Load and validate the durable current action/step by operation ID and
    reject any caller-supplied action that is not byte/digest-equivalent. Treat
    the create observation only as attempt evidence, transition to
    `verification-pending`, and emit a separate semantic read action through the
    pinned execution context. Materialize metadata/state and write the compact
    association only after that read-back verifies durable identity, context,
    requested fields, revision, and the original projection/safety digests.
  - Requirement: FR11, FR14, NFR2, NFR3

- **Shared-storage approval has no freshness or future-time check** (`packages/cli/src/commands/pjm/remote/shared-storage.ts:45`)
  - Issue: Apply accepts any matching approval timestamp that is not before the
    preview. There is no current time, maximum age, finite-time validation, or
    future-approval rejection, so an approval can be replayed indefinitely (or
    dated arbitrarily far in the future) to opt privacy-sensitive operational
    records into tracked Git storage. This does not satisfy p03-t11's fresh
    previewed approval boundary.
  - Fix: Reuse the common preview-approval validator or inject `now` and a
    bounded maximum age, validate finite preview/approval/current timestamps,
    reject future and expired approvals, and retain bounded non-secret
    actor/source evidence. Add future, expired, malformed-time, and replay
    tests.
  - Requirement: FR12, NFR1, NFR3

### Important

- **The new host skill is missing from the managed provider view** (`.agents/skills/oat-pjm-remote/SKILL.md:1`)
  - Issue: `oat status --scope project --json` reports the canonical skill's
    `.claude/skills/oat-pjm-remote` view as `missing` (88 in sync, 1 missing) and
    exits 1. The skill is the Phase 3 host-executor bridge, so leaving its
    managed view absent makes the feature unavailable to that configured host
    and triggers the repository's managed-view hook warning. This is an
    in-scope p03-t09 packaging defect, not a Phase 8 release-version concern.
  - Fix: Run `pnpm run cli -- sync --scope project`, review and commit only the
    generated provider view/manifest changes for this canonical skill, then
    require project status to report no missing or drifted managed views.

- **Remote-core tests still encode the retired provider CLI dialect** (`packages/cli/src/commands/pjm/remote/schema.test.ts:202`)
  - Issue: Current schema, snapshot, store, doctor, and config tests still use
    the literal `gh` transport and, in places, catalog fingerprints or
    transport-shaped helpers. Some legacy record-shape coverage is required,
    but it does not require a real provider executable name; several current
    tests also enter through the compatibility parser instead of exercising the
    schema-v2 path. This violates the approved no-provider-CLI-dialect rule for
    tests and weakens direct coverage of the new provider-neutral model.
  - Fix: Convert current fixtures to `surfaceKind`, semantic capabilities, and
    evidence digests. Keep a narrowly named legacy-migration fixture only where
    compatibility parsing is under test, use a generic value such as
    `legacy-native-surface` instead of a provider executable/dialect, and retain
    assertions that migrated evidence is degraded and non-authoritative.
