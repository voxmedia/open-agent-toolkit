## Findings

### Critical

- **The public adapter validates and verifies matching fields from the wrong
  GitHub issue**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:1054`)
  - Issue: `githubAdapter.validateObservation()` validates only the nested host
    capability and optional capability digest. It does not compare the
    observation provider/context/stable identity, mutation execution evidence,
    or create provenance with the planned action. `githubAdapter.verify()` then
    validates action-internal hashes but compares only postcondition values
    (`github.ts:1085`). A direct post-image reproduction built a fully gated
    update for `expected_node`, supplied an observation for `wrong_node` in the
    same repository, and received `{valid: true}` followed by a verified title
    field.
  - Impact: Any lifecycle or conformance consumer using the immutable
    `ProviderAdapter` contract rather than the dedicated verifier can report a
    mutation successful from another issue's matching fields. This defeats
    authoritative readback identity and can advance the wrong binding.
  - Fix: Make mutation `validateObservation()` enforce exact provider/context,
    planned stable identity, capability digest, execution-evidence equality, and
    create provenance before returning valid. Make `verify()` return unavailable
    for an issue whose provider, context, or stable identity differs from the
    action, or route both methods through one shared exact mutation-verification
    primitive. Add conformance regressions that call the public pair with wrong
    node, repository, capability, mutation evidence, and create provenance.
  - Requirement: p04-t05, FR11, FR14, NFR2, NFR8

- **The public adapter still bypasses the bounded duplicate-search and discussion
  planners**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:1025`)
  - Issue: `githubAdapter.plan()` routes four mutation operations through their
    safe planner and validates reads, but every other operation falls through to
    an arbitrary `{context, ...intent}` action. A caller can therefore create a
    search action with a forged query digest and `maxResults: 1000000`; the
    duplicate validator checks only that the bound is an integer and accepted a
    supplied matching candidate as `one-verified-match`. The same bypass creates
    a discussion action with `maxItems: 1000000`, which the validator accepts
    because it never independently enforces the absolute 100-item contract.
  - Impact: Uncertain-create recovery can use an action that never passed the
    exact provenance/reservation/alias query planner, and discussion reads can
    exceed the declared provider bound. The duplicate path is a P0 wrong-binding
    boundary even though the dedicated planner itself is correct.
  - Fix: Route `search-duplicates` and `read-discussion` through
    `planDuplicateSearch()` and `planDiscussionRead()` with complete typed inputs,
    just as mutations are routed. Also make both validators defensively recompute
    the planned query/result contract and enforce absolute item/result/cursor
    limits so a manually constructed `SemanticAction` cannot bypass the bound.
    Add public-adapter and direct-forged-action regressions.
  - Requirement: p04-t09, p04-t10, p04-t11, FR14, FR16, FR18, NFR2, NFR8

- **Arbitrarily stale deletion evidence is accepted as authoritative for the
  current read**
  (`packages/cli/src/commands/pjm/remote/providers/github.ts:1490`)
  - Issue: `validDeletionEvidence()` verifies provider, stable identity, context,
    capability digest, timestamp syntax, and self-digest, but it never relates
    `value.observedAt` to the current `GitHubReadObservationInput.observedAt`, the
    current action/step, or a freshness window. A direct reproduction passed a
    correctly self-digested deletion observation from
    `2020-01-01T00:00:00Z` into a 2026 not-found read and received
    `classification: "deleted"` with `authoritative-deletion`.
  - Impact: Old evidence can convert an ambiguous current absence into a
    definitive deletion, weakening the required preservation and explicit
    resolution behavior for missing/inaccessible records.
  - Fix: Bind deletion evidence to the exact current read action/step digest and
    require its observed time to equal, or fall within a documented tight bound
    of, the current read observation without allowing future timestamps. Add
    stale, future, wrong-action, wrong-step, and current-evidence regressions;
    ambiguous evidence must remain `inaccessible` and preserve prior state.
  - Requirement: p04-t03, FR13, NFR2

### Important

- **The revised conformance/integration coverage still misses the public adapter
  and persistence paths that remain unsafe**
  (`packages/cli/src/commands/pjm/remote/providers/github.conformance.test.ts:113`)
  - Issue: The conformance wrapper substitutes a safe update planner but the
    immutable harness checks only `verificationFields()`, never
    `githubAdapter.verify()`. It also uses dedicated duplicate/discussion planners
    exclusively. The integration fixture writes most snapshots/journal entries
    manually after calling the dedicated verifier
    (`__integration__/github.test.ts:494`) rather than exercising a public adapter
    validation/verification persistence path. Consequently, the live 76/76 suite
    passes while all three Critical reproductions succeed.
  - Impact: The suite does not yet prove that the actual public adapter contract
    fails closed on wrong-issue readback or that all semantic operations must pass
    their bounded planner before persistence.
  - Fix: Extend conformance to invoke `validateObservation()` and `verify()` as a
    pair on exact and mismatched identities. Exercise duplicate/discussion through
    `githubAdapter.plan()`, add forged-action bounds, and use an inspectable
    lifecycle/store boundary that performs persistence only after public adapter
    validation. Add the stale-deletion reproduction to the read lifecycle suite.
