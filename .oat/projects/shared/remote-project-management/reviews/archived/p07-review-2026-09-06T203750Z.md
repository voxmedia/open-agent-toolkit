## Findings

### Critical

- **Closeout can bypass approval and purpose intersection, yet production
  cannot complete the operation**
  (`packages/cli/src/commands/pjm/remote/closeout.ts:128`)
  - Issue: `resumeCloseoutOperation()` executes every non-blocked pending
    substep without receiving or validating an approval, even when the durable
    substep says `fresh-approval` or `explicit-instruction`. A direct check
    executed a `user-approved` annotation once and returned `verified` with no
    approval supplied. `buildCloseoutJournal()` also admits annotation when
    _either_ source or planning is present and transition whenever planning is
    present (`:209-223`), rather than applying the design's lifecycle-policy
    intersection; a delivery/reference combination can therefore gain an
    operation removed by one purpose. In production, the preview contains no
    normalized annotation/transition intent or safety result, emits no external
    action (`service.ts:218-292`), has no approved-batch apply route, and
    `operation continue` has no closeout branch. The recovery store bridge also
    returns without persisting every update to an existing operation
    (`service.ts:200-203`), so it cannot journal substep progress even if wired.
  - Fix: Compose closeout operations by strict purpose intersection; bind each
    exact normalized substep projection and universal safety result into the
    composite preview; require and validate the exact approval/instruction and
    pinned live capability before execution; emit/continue provider-neutral
    actions with authoritative read-back; transition existing operation and
    batch records atomically on every substep. Add production apply and crash
    recovery tests, including mixed-purpose denial and approval mismatch.
  - Requirement: FR3, FR8, FR11, FR15, NFR1, NFR2, NFR3; p07-t02, p07-t03,
    authorized recovery.

- **Resolution apply is a no-op and restart journals are not bound to the
  requested resolution**
  (`packages/cli/src/commands/pjm/remote/service.ts:347`)
  - Issue: Supplying `--apply-preview` only reloads the preview and returns the
    same `needs-review` envelope (`:347-357`). Production never calls
    `relinkBinding()`, `detachBinding()`, or `recreateBinding()`, never obtains
    verified replacement/duplicate-search evidence, and never durably updates
    the binding or compact association. Independently, each helper trusts any
    existing journal for the supplied operation ID without checking its kind,
    binding ID, or preview digest (`resolution.ts:90-94`, `:139-143`,
    `:212-223`). A direct restart check created a partially completed detach
    journal, then resumed it through `relinkBinding()` under a different
    approved preview; it completed the detach association and returned a
    tombstoned binding while the caller requested relink.
  - Fix: Implement the production resolution state machine and `RemoteSyncStore`
    bridge. Bind preview, approval, operation kind, binding, provider context,
    requested replacement, capability evidence, action, and read-back through
    every restart. Reject any journal/request mismatch before a write. Exercise
    relink, detach, found-existing, create, uncertain-create, crash, and replay
    paths through the real production runner.
  - Requirement: FR8, FR11, FR13, FR14, NFR2, NFR3; p07-t05, p07-t06,
    authorized recovery.

- **The production discussion command is permanently unavailable**
  (`packages/cli/src/commands/pjm/remote/service.ts:301`)
  - Issue: `prepareDiscussion()` always passes `null` as its discussion source
    and then unconditionally returns `blocked` with no external action
    (`:301-335`). A live host capability can never be selected, no bounded read
    can be requested or continued, and sanitized non-persisted evidence can
    never reach the caller. This implements only the unavailable-provider case,
    not the Phase 7 feature.
  - Fix: Persist/emit a provider-neutral bounded discussion-read action using
    current live capability evidence, accept its sanitized bounded observation,
    run whole-field suppression, and return the items without writing them to
    snapshots, journals, or tracked artifacts. Retain the current explicit
    unavailable result when no matching live capability exists.
  - Requirement: FR12, FR16, FR18; p07-t04, authorized recovery.

- **The required cross-provider and end-to-end tests do not exercise production
  workflows**
  (`packages/cli/src/e2e/pjm-remote.test.ts:41`)
  - Issue: The nominal E2E suite replaces the production runner with a callback
    that returns the status requested by the test (`:41-47`, `:136-149`), so it
    proves only Commander forwarding and rendering. The cross-provider suite
    similarly uses a self-contained `WorkflowFixture` that appends bindings to
    arrays (`remote/__integration__/cross-provider.test.ts:21-44`) instead of
    exercising intake, publish, provider adapters, persistence, or production
    closeout. The smoke safety test constructs already-sanitized literal output
    objects (`tools/smoke/pjm-remote/no-secret-output.test.mjs:6-19`) instead of
    driving declared production outputs. These tests therefore cannot verify
    the P0 workflows or detect the production dead ends above.
  - Fix: Replace or supplement the fixtures with production-runner/CLI tests
    over isolated repositories and provider-neutral action/observation
    continuations. Cover GitHub-only, GitHub-to-Linear, GitHub-to-Jira, explicit
    publication, no transitive mirroring, independent closeout, resolution,
    discussion, doctor, migration, every status/exit row, and fixture-owned
    safety surfaces without inspecting unrelated files.
  - Requirement: FR1, FR2, FR17, NFR1, NFR3, NFR6, NFR7; p07-t08, p07-t09,
    p07-t10.

- **Reviewed batch outcomes can regress after reaching a terminal state**
  (`packages/cli/src/commands/pjm/remote/batch.ts:80`)
  - Issue: `reduceReviewedBatchOutcomes()` blindly overwrites every prior member
    outcome (`:80-88`). A direct check changed a one-member batch from
    `verified`/`complete` back to `planned`/`pending`. Stale replay or restart
    reduction can therefore erase a verified outcome despite the immutable
    reviewed-membership and terminal-state requirements.
  - Fix: Define and enforce monotonic member transition rules, reject any
    terminal-to-nonterminal or incompatible terminal rewrite, and test stale
    replay after verified, blocked, uncertain, and partial outcomes.
  - Requirement: FR10, NFR3; p07-t01.

### Important

- **Production doctor omits the evidence required by its new checks**
  (`packages/cli/src/commands/pjm/remote/service.ts:436`)
  - Issue: The production bridge passes only record directories, policy, and
    current time. It supplies no associated binding IDs, stale threshold,
    retention findings, or current host-capability availability, although the
    Phase 7 doctor accepts those inputs (`doctor.ts:20-28`) and the task requires
    those diagnostics. With the default infinite stale threshold, even old
    verified records are never reported stale; compact-link, retention, and
    capability checks silently pass from absent evidence.
  - Fix: Derive bounded association/target and retention evidence from declared
    PJM surfaces, define the documented staleness policy, accept sanitized live
    capability availability from the host when present, and report unavailable
    evidence without claiming the checks passed.

- **Migration cannot discover legacy association-only candidates**
  (`packages/cli/src/commands/pjm/remote/service.ts:464`)
  - Issue: Candidate paths are derived exclusively from existing remote binding
    metadata (`:464-474`). A legacy backlog item containing only the supported
    scalar or `{type, ref}` association has no binding metadata, so `migrate
--check` reports zero inspected targets and can never propose its migration.
    The recovery test avoids this case by creating binding metadata before
    running migration (`service.test.ts:226-241`).
  - Fix: Enumerate only the declared bounded PJM backlog/project surfaces using
    existing local loaders, identify legacy association candidates there, and
    keep the check/apply digest bound to exact file paths and pre-images. Add a
    no-binding legacy fixture and an idempotent second check.

- **A Phase 7 test hard-codes provider-native schema and behavior**
  (`packages/cli/src/commands/pjm/remote/__integration__/cross-provider.test.ts:121`)
  - Issue: The test embeds Jira's native `issueType` field and branches on Jira
    to impose a transition authority (`:121-149`). The approved contract forbids
    native provider schemas and provider action mappings in OAT tests; provider
    differences must arrive as semantic capability/policy fixtures discovered
    at the host boundary.
  - Fix: Use opaque allowlisted extension evidence and inject semantic
    capabilities/effective policy independently of provider identity. Assert
    extension preservation and unsupported/degraded behavior without naming a
    native field or assuming provider-specific authority.
