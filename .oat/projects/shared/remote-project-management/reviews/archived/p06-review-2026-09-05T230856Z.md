## Findings

### Critical

- **Managed-description actions are allowed without a structural-write capability**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:478`)
  - Issue: `previewJiraMutation()` checks only the generic `update` operation;
    it does not require `description-adf` or any semantic evidence that the
    selected surface can preserve ADF. Although planning validates caller-held
    before/after documents, `planJiraMutation()` emits only the normalized
    description string and ADF hashes (`jira.ts:518`-`560`), not an executable
    codec result or capability-bound structural operation. A direct probe with
    `observableFields: []` successfully planned a description write; the
    resulting action contained no before/after ADF document. The host action
    protocol forbids reconstructing or reinterpreting the exact projection, so
    post-write readback can detect damage but cannot prevent the unsafe effect.
  - Impact: A connector/CLI surface that cannot structurally preserve Jira ADF
    can still receive a mutation attempt. This violates the design's explicit
    rule that managed-section update is unsupported unless the execution
    surface demonstrates structural preservation and breaks FR7/NFR2 before
    authoritative readback can help.
  - Fix: Model a bounded semantic structural-description write capability and
    require it during preview. Ensure the emitted provider-neutral action gives
    the executor one non-reconstructive, codec-produced operation whose exact
    writable representation and digests were gated/approved, or block the
    description write before attempt. Add a regression where `update` exists
    but structural ADF preservation does not.
  - Requirement: FR7, FR11, FR16, NFR2, NFR5; p06-t02, p06-t04, p06-t06

- **Mutation verification ignores current capability and metadata semantics**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:835`)
  - Issue: `verifyJiraMutationObservation()` compares only the supplied
    capability/metadata digest strings and capability timestamp
    (`jira.ts:835`-`847`). It never calls `validateJiraHostCapability()` on the
    current `input.hostCapability` and never rechecks the current
    `writableFields` or `transitions`. A direct probe changed the current
    capability to `authorization-required` with no operations and changed the
    current metadata to no writable fields/transitions while retaining the
    opaque labels; a matching transition readback still returned
    `classification: verified`. The existing test named "rejects metadata
    drift" changes only the digest (`jira.test.ts:1061`-`1079`) and misses this
    semantic drift.
  - Impact: Authorization loss, operation loss, or tenant transition/schema
    drift can be reported as a successful write. That is a false success at the
    mutation boundary and defeats the required live re-check and fail-closed
    metadata behavior.
  - Fix: Revalidate the current capability object for the exact operation and
    context during verification, bind or recompute normalized metadata content
    rather than trusting a caller-provided label, and rerun the exact field/
    transition support predicate before accepting readback. Add same-label
    authorization-loss, missing-operation, removed-field, and removed-transition
    regressions.
  - Requirement: FR11, FR15, FR16, NFR2, NFR5, NFR8; p06-t04, p06-t06, p06-t08

### Important

- **The public moved-issue verifier accepts unbound capability evidence**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:1279`)
  - Issue: Exact-context public verification compares the normalized issue's
    capability digest to the planned action, but the project-move branch calls
    `isNormalizedJiraProjectMove()` instead. That helper requires only a
    nonempty digest (`jira.ts:1342`-`1354`), with no validated new-project
    capability, timestamp, or equality to evidence accepted by the classifier.
    A direct probe supplied the correct stable ID and old-project history with
    `capabilityEvidenceDigest: "sha256:forged"`; `jiraAdapter.verify()` returned
    `stable-identity: verified`.
  - Impact: Callers of the public adapter can persist a moved Jira binding as
    verified from a normalized issue whose new-project authority was never
    established, diverging from the stricter typed classifier and
    `validateObservation()` behavior.
  - Fix: Make public verification consume the validated move result/evidence,
    including the new-project capability digest and freshness, or return
    unavailable for moved contexts unless that evidence is present in a closed
    normalized extension. Add a forged-digest public-verifier regression.
  - Requirement: FR5, FR13, FR16, NFR2, NFR8; p06-t01, p06-t05, p06-t08
