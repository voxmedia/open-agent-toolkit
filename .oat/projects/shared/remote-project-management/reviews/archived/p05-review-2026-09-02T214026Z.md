## Findings

### Critical

- **Public read validation accepts a different Linear UUID and exposes no
  failed verification field**
  (`packages/cli/src/commands/pjm/remote/providers/linear.ts:1125`)
  - Issue: `validateObservation()` defensively validates the read action and
    capability/context evidence, but the identity comparison is inside the
    mutation-only branch. A live probe kept a valid read action for UUID A and
    supplied a same-context, same-capability observation for UUID B. Public
    validation returned `{ valid: true }`, normalization produced B's stable
    ID, and both `verificationFields()` and `verify()` returned empty arrays.
    The typed `classifyLinearReadObservation()` is stricter, but the exported
    `ProviderAdapter` contract remains independently unsafe.
  - Impact: A provider-neutral consumer that relies on the public observation
    gate can replace a binding snapshot with a different issue while receiving
    no invalid or unavailable verification signal. This violates the P0 exact
    identity and lifecycle-preservation boundary.
  - Fix: For read actions, normalize only after schema validation and require
    the observation UUID and canonical workspace/UUID stable ID to equal the
    action intent before returning valid. Either make public read verification
    return an explicit unavailable/mismatch field or document and enforce the
    typed classifier as the sole public read gate. Add an intact-action,
    wrong-observation UUID regression through the public adapter and lifecycle
    persistence boundary.
  - Requirement: p05-t02, p05-t04, p05-t06, p05-t07, FR5, FR11, FR13, FR16,
    NFR2

### Important

- **The public mutation selector can disagree with the planned operation**
  (`packages/cli/src/commands/pjm/remote/providers/linear.ts:1045`)
  - Issue: `linearAdapter.plan()` branches on its `operation` argument but
    `isCompleteLinearMutationInput()` accepts any string in `input.operation`.
    It then delegates to `planLinearMutation(input)` without requiring the two
    values to match. A live probe called `plan('update', createInput)` and
    received a fully formed `create` action.
  - Impact: The public adapter does not preserve the operation class selected
    by a provider-neutral caller. Since policy and approval are resolved per
    mutation class, accepting contradictory public inputs creates a future
    authorization and audit integration hazard even though the returned
    action's internal create preview remains self-consistent.
  - Fix: Require `input.operation === operation` before mutation planning and
    reject all cross-class combinations. Add a public conformance matrix for
    every selector/input mismatch.
  - Requirement: p05-t03, p05-t06, FR8, FR11, FR15, FR16, NFR2, NFR8

- **Public create validation does not bind readback provenance**
  (`packages/cli/src/commands/pjm/remote/providers/linear.ts:1137`)
  - Issue: The public validation branch checks mutation execution evidence and
    normalizes the observation, but its identity check is deliberately skipped
    for create and it never compares `fields.createProvenance` with the planned
    provenance. A live probe changed only the observed provenance origin and
    received `{ valid: true }`. The subsequent generic and typed verifiers do
    fail closed, so this is not a terminal-success bypass, but the public
    validation result itself is false evidence.
  - Impact: A generic lifecycle can record an observation as valid before the
    mandatory provenance attribution has been established. That weakens the
    public adapter contract and makes validation-stage persistence unsafe.
  - Fix: Require exact create provenance in public observation validation (or
    return an explicit typed-verifier-required result for create) before
    reporting valid. Add forged origin, binding, missing provenance, and
    misattributed result regressions through the public adapter.
  - Requirement: p05-t03, p05-t05, p05-t06, p05-t07, FR11, FR14, FR16, NFR2
