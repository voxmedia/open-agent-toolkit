## Findings

### Critical

- **ADF description writes can lose all remote-owned structure and still verify**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:848`)
  - Issue: Mutation preview/action evidence binds only the string projection and
    generic digests (`jira.ts:477`-`535`). Verification compares that string to
    normalized `descriptionText` (`jira.ts:848`-`860`) and never calls
    `verifyJiraAdfReplacement()` or binds the original/expected surrounding ADF
    digest. A direct probe planned an approved description update, returned an
    empty ADF document with matching `descriptionText`, and received
    `classification: verified`. Normalization also copies `descriptionAdf`
    without invoking the codec or its byte/shape checks (`jira.ts:301`), while
    anchor discovery scans only top-level nodes and treats a nested existing
    OAT panel as absent (`jira-adf.ts:125`-`145`), allowing a duplicate anchor
    to be inserted.
  - Impact: Jira can silently replace or corrupt remote-owned rich content while
    OAT records authoritative success. This breaks the non-negotiable
    managed-section and fail-closed lossiness boundary.
  - Fix: Make description mutation planning consume a validated before-ADF and
    codec-produced after-ADF, bind canonical before/after/surrounding digests
    through safety, preview, approval, action, and readback, and require
    `verifyJiraAdfReplacement()` before success. Recursively detect every OAT
    anchor, validate/bound normalized ADF before use, and add loss, nested-anchor,
    malformed, oversized, rich-mark, and exact-surrounding readback regressions.
  - Requirement: p06-t02, p06-t04, p06-t06, p06-t08, FR7, FR11, NFR2, NFR5

- **Stable issue identity is rejected when Jira moves the issue to another project**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:605`)
  - Issue: The read classifier requires exact equality between the old planned
    project context and the returned observation before normalization
    (`jira.ts:573`-`615`). Its only `moved` path recognizes a changed key that
    appears in `historicalKeys` (`jira.ts:627`-`632`); it never consumes
    `historicalProjectIds` or lifecycle evidence. A direct probe read the same
    `jira:<site>:<issue-id>` after a verified old-project to new-project move,
    with the old project recorded in history, and received `inaccessible` with
    `observation-attribution-mismatch`.
  - Impact: The immutable issue ID does not actually preserve binding identity
    across the project moves Phase 6 explicitly promises. Refresh and recovery
    freeze a valid moved issue instead of updating project/key aliases, and the
    lifecycle value retained by normalization cannot affect classification.
  - Fix: Add a separately validated move path that requires the same provider,
    account/site, immutable issue ID, trustworthy capability evidence for the
    new project, and explicit old-project/key history before returning `moved`.
    Keep exact-context rejection for unrelated issues, classify archived and
    other lifecycle states explicitly, and add public classifier/adapter tests
    for valid and forged moves.
  - Requirement: p06-t01, p06-t05, p06-t08, FR5, FR13, NFR2, NFR5

- **Post-plan mutation intents can add an unapproved native request and still verify**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:1470`)
  - Issue: `validJiraMutationAction()` recomputes the action digest over the
    residual `baseIntent`, including arbitrary extra keys, rather than requiring
    the exact closed operation-specific intent (`jira.ts:1470`-`1497`). A direct
    probe appended `nativeRequest: {method: "PUT", path: "/rest/api/3/issue/100"}`
    after preview/approval, recomputed the unkeyed semantic digest and matching
    execution evidence, and both `jiraAdapter.validateObservation()` and
    `jiraAdapter.verify()` accepted the action as valid/verified.
  - Impact: The provider-neutral action boundary can carry invocation material
    that was absent from the normalized projection, safety result, preview, and
    approval. Matching readback cannot retroactively authorize the injected
    request, and accepting it contradicts the explicit no-native-dialect
    contract.
  - Fix: Define a closed runtime schema for every Jira action and reconstruct
    the exact expected intent from approved fields only. Reject unknown keys;
    bind the exact action envelope, projection, postconditions, metadata,
    capability, preview, approval, and readback contract; route public
    validation and verification through that one validator. Add alteration and
    unknown-key regressions for create/update/transition/annotation.
  - Requirement: p06-t04, p06-t06, FR11, FR16, NFR1, NFR2, NFR8

### Important

- **Read and metadata validators accept rewritten semantic contracts**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:1556`)
  - Issue: Non-mutation actions are checked only by
    `validJiraActionDigest()`, which hashes whatever fields are currently
    present and validates no operation-specific shape (`jira.ts:1556`-`1569`).
    The public read path and typed metadata validator rely on it
    (`jira.ts:561`-`568`, `643`-`698`). A direct probe replaced a planned
    transition-metadata result contract with `{nativeQuery: "status = Done"}`,
    recomputed the public semantic digest, and
    `validateJiraMetadataObservation()`returned`valid: true`.
  - Impact: A stale or forged planner result can change the requested/read
    contract, issue selector, bounds, or provider-native content while still
    being accepted as planned evidence.
  - Fix: Add exact closed validators for issue-read and metadata-read actions,
    including canonical stable ID/issue ID, step, purpose, result contract,
    capability digest, context, and action digest. Reject extra/missing fields
    before processing observations and add post-plan mutation regressions.
  - Requirement: p06-t03, p06-t05, FR11, FR16, NFR2, NFR8

- **Discussion evidence is accepted after capability or authorization is lost**
  (`packages/cli/src/commands/pjm/remote/providers/jira.ts:725`)
  - Issue: The typed discussion validator compares context, stable ID, cursor,
    and digest but never validates the current `hostCapability`, its
    availability, required `read-discussion` operation, or the exact bounded
    action contract (`jira.ts:725`-`768`). A direct probe planned with an
    available capability, then supplied `authorization-required` with no
    operations and the same evidence digest; the result was accepted as a
    normal page.
  - Impact: Jira discussion content can enter the live evidence/prompt surface
    after permission or semantic capability is no longer established. The
    byte limits and whole-field suppression do not repair missing authority and
    provenance.
  - Fix: Add an exact `validJiraDiscussionAction()` and require
    `validateJiraHostCapability('read-discussion', ...)` against the supplied
    current capability before availability or page processing. Bind freshness
    evidence and add lost-auth, missing-operation, altered-limit/contract,
    wrong-stable-ID, and stale-digest regressions.
  - Requirement: p06-t03, p06-t05, FR12, FR16, FR18, NFR1, NFR2

- **The conformance and lifecycle suites do not exercise the claimed persistence contract**
  (`packages/cli/src/commands/pjm/remote/providers/jira.conformance.test.ts:113`)
  - Issue: The only invocation of the immutable conformance harness asserts
    that it throws instead of producing a passing Jira conformance result
    (`jira.conformance.test.ts:113`-`125`). The lifecycle file substitutes an
    in-memory `Set`/`Map` counter (`__integration__/jira.test.ts:100`-`104`) and
    invokes adapter helpers directly; it never uses the shared lifecycle
    harness/service/store to persist intents, receipts, verification handoff,
    snapshots/baselines, crash recovery, or independent binding outcomes. The
    green suite therefore does not traverse the ADF, move, or forged-action
    failures above.
  - Impact: p06-t07/p06-t08 do not supply the P0 regression evidence declared
    by the plan, so the 42/42 and 586/586 passes overstate Jira conformance and
    restart-safe lifecycle coverage.
  - Fix: Supply a real Jira facade/fixture that passes the immutable shared
    conformance assertions without weakening action safety. Drive the real
    public adapter and typed validators through an inspectable lifecycle/store
    boundary for intake, refresh, publish, reconcile, closeout, discussion,
    duplicate recovery, verification persistence, and restart; include every
    finding above as a negative integration case.
  - Requirement: p06-t07, p06-t08, FR1, FR11, FR14, FR15, FR17, NFR2, NFR3, NFR8
