## Findings

### Critical

- **Production mutation authority is still self-issued and two authority modes are unreachable from the CLI** (`packages/cli/src/commands/pjm/remote/service.ts:63`)
  - Issue: The default `currentInvocation` copies the runner's own
    `expectedEvidenceDigest` into an `interactive` claim, so every
    `user-authorized` publish is accepted without durable evidence of the exact
    user instruction. Conversely, the public command builds no
    `mutationApproval` and exposes no active-workflow ID/revision input
    (`packages/cli/src/commands/pjm/remote/index.ts:198`), so
    `user-approved` and `autonomous` policy cannot succeed without test-only
    dependency injection. The same synthesized invocation is rechecked after
    pre-read, which only proves equality with itself rather than freshness of
    caller authority.
  - Fix: Make the command/host boundary supply a closed current-invocation
    record. Persist exact non-secret instruction evidence for
    `user-authorized`, accept and validate a preview-bound approval for
    `user-approved`, and accept authoritative active-workflow ID/revision
    evidence for `autonomous`. Re-read that authoritative evidence after the
    pre-read. Add default-command temporary-repository tests for all four modes
    and every drift case; do not satisfy them by overriding
    `currentInvocation`.
  - Requirement: FR8, FR9, FR11, NFR2, NFR3

- **Transition and annotation actions can carry content different from the gated projection** (`packages/cli/src/commands/pjm/remote/external-action.ts:258`)
  - Issue: Canonical equality is enforced only for `create` and `update`.
    `transition` and `annotate` still require a safety result, but their
    `intent.transition` and `intent.body` are never compared with the
    projection's `status` and `annotation`. A direct reproduction gated
    `{annotation: "approved-safe"}` and successfully emitted an annotation
    intent whose body was `different token payload`. This breaks the universal
    pre-write gate as soon as the later lifecycle phases use these already
    declared Phase 3 action types.
  - Fix: Define one operation-discriminated mapping from the exact writable
    intent value to the normalized projection for every mutation operation.
    Require canonical equality before the action digest is computed and add
    mismatch/sensitive-value regressions for transition and annotation.
  - Requirement: FR15, FR16, NFR1, NFR2, NFR8

- **A sensitive-content signal in a create stable identity is accepted and later persisted** (`packages/cli/src/commands/pjm/remote/external-action.ts:364`)
  - Issue: Observation ingress checks aliases and diagnostic codes, but not
    `identity.stableId`. A create action with no prior identity accepted the
    stable ID `Authorization Bearer private-tail`; the production continuation
    then uses that value in the read action and, if repeated by read-back,
    writes it to portable metadata. This is durable identity evidence, not an
    allowlisted inbound ticket text field, so whole-field ticket suppression is
    not the right recovery and the value must be rejected before journaling or
    materialization.
  - Fix: Validate every bounded identity/context evidence string with the
    non-ticket evidence safety rule before acceptance. Reject the complete
    observation without retaining the value and add create/intake regressions
    for unsafe stable IDs and context evidence.
  - Requirement: FR5, FR12, NFR1, NFR2

- **Public publish/reconcile bypasses purpose, description, and three-way reconciliation policy** (`packages/cli/src/commands/pjm/remote/service.ts:649`)
  - Issue: Both public commands enter the same `prepareMutation()` path. It
    projects title, full local description, and priority unconditionally
    (`service.ts:684`) and never calls the Phase 2 purpose composer,
    reconciliation engine, or managed-content codec. A `source`, `delivery`,
    or `reference` binding can therefore reach an outbound update whenever its
    authority policy allows it; description mode `none` does not remove the
    description; and `reconcile` never classifies or blocks same-field
    conflicts. After verified update read-back, only the operation journal is
    changed—the binding snapshot and baseline are not advanced.
  - Fix: Compose the production runner through the provider-neutral lifecycle
    service and Phase 2 engines. Derive the outbound field mask from purpose
    intersection and description policy, use managed-content semantics, block
    conflicts before action construction, and atomically advance snapshot and
    baseline only after verified postconditions. Add default-run tests for
    every purpose, description mode, conflict, and verified baseline advance.
  - Requirement: FR3, FR4, FR6, FR7, FR9, FR11, NFR2, NFR3

- **Production intake and create do not establish the required local/baseline state, and project publication is rejected** (`packages/cli/src/commands/pjm/remote/service.ts:421`)
  - Issue: p03-t12 requires backlog and project-target publication, but the
    public create path rejects every project target. Intake materializes
    metadata/state without creating or enriching the selected backlog file,
    adding its compact association, or establishing the initial inbound
    baseline (`service.ts:1041`). Verified create writes a binding state with
    both `snapshot` and `baseline` null (`service.ts:1223`), despite the
    authoritative read-back having the fields needed for both. The command can
    therefore report verified while leaving reconciliation without the
    last-agreed state required by p03-t05/p03-t12.
  - Fix: Use the explicit project publication projection for project targets,
    implement deliberate local intake create/enrich plus compact association,
    and construct the initial sanitized snapshot and reconciliation baseline
    from the authoritative read. Add production-run tests for backlog/project
    creates and intake create/enrich that assert the full durable state, not
    only the terminal envelope.
  - Requirement: FR4, FR5, FR9, FR14, FR18, NFR3, NFR4

- **Verified create/intake materialization is not restart-safe** (`packages/cli/src/commands/pjm/remote/service.ts:1170`)
  - Issue: Create continuation first transitions the operation to terminal
    `verified`, then separately writes metadata, state, and the compact
    association. A crash at any later write leaves a terminal journal, and
    continuation rejects every terminal operation at `service.ts:822`, so the
    missing materialization cannot resume. Intake likewise writes metadata and
    state in separate steps before the terminal transition; a crash after
    metadata makes the retry fail as "already materialized." The new store
    tests prove append-only primitives in isolation but do not exercise these
    default-run crash boundaries.
  - Fix: Journal materialization as explicit idempotent substeps and make
    continuation resume the first incomplete local substep. Do not mark the
    operation terminal until required metadata, state, baseline/snapshot, and
    association writes are durably complete; diagnose and repair any
    one-sided state. Add filesystem/default-run crash injection after every
    boundary and restart with a new runner/store instance.
  - Requirement: FR5, FR11, FR14, NFR2, NFR3

### Important

- **Suppression evidence has no typed adapter-extension path through the action boundary** (`packages/cli/src/commands/pjm/remote/external-action.ts:373`)
  - Issue: Accepted observations expose only a flat `string[]` of suppressed
    names. The production snapshot handoff filters that list to the four core
    names and provides no extension values, allowlist, or bounded
    core-versus-extension evidence (`packages/cli/src/commands/pjm/remote/service.ts:1036`).
    The Phase 2 sanitizer supports adapter-approved extensions, but an
    extension value already replaced with the suppression marker cannot be
    paired with its redaction evidence through this bridge. Provider adapter
    phases would have to invent a second unsafe convention.
  - Fix: Model suppression evidence as bounded discriminated core/extension
    references, require extension keys to be schema-safe members of the
    adapter allowlist, and consume each marker/evidence pair exactly once at
    snapshot persistence. Add a generic adapter-extension observation-to-
    snapshot integration test.
