- **Initial relink/recreate approval does not bind the capability or exact
  action it authorizes**
  (`packages/cli/src/commands/pjm/remote/service.ts:856`)
  - Issue: Initial resolution preparation persists
    `capabilityEvidenceDigest: 'unprobed'`, and the public capability component
    merely hashes that placeholder (`service.ts:1699`). Apply validates the
    approval against that unchanged preview before reading and selecting the
    live capability (`service.ts:1063`, `service.ts:1148`), then persists the
    selected execution only afterward (`service.ts:1198`). The recreate
    projection component also hashes lifecycle kind, local target, and optional
    provider reference (`service.ts:1704`), while the actual duplicate-search
    action uses the then-current `state.localProjection.title`
    (`service.ts:1173`). Consequently, capability changes and recreate query
    drift are not mismatched preview components and are not rejected before
    action. The JSON/human envelope is inspectable, but its capability and
    projection digests do not describe the exact relink/recreate action that
    follows.
  - Fix: For relink and recreate-search, select and validate the current
    provider-neutral capability before constructing the approval preview, bind
    its evidence digest and the exact sanitized semantic action intent into the
    persisted component digests, and recompute both at apply. Reject absent,
    changed, stale, or mismatched capability/action evidence before writing the
    current action. Represent detach's lack of a host action explicitly rather
    than as an unprobed capability.
  - Requirement: FR13, FR14, FR16, NFR2, NFR6, NFR8; `prev3-t02` items 2-3.

- **Recreate still assumes priority mapping instead of applying current
  priority policy**
  (`packages/cli/src/commands/pjm/remote/service.ts:4221`)
  - Issue: Both create-preview construction and apply-time recomputation pass
    `priorityMapping: true` unconditionally (`service.ts:4221` and
    `service.ts:927`). The new recreate-specific planner then emits priority
    whenever purpose composition permits outbound priority
    (`service.ts:5321`), without evidence that this binding/provider currently
    advertises a safe mapping. This misses the explicit revision requirement to
    intersect the new-record projection with current priority policy and the
    P0 FR6 rule that priority participates only when a safe provider mapping is
    advertised. Existing tests exercise only the hard-coded enabled case.
  - Fix: Resolve the current safe-priority-mapping decision from bounded
    provider/binding evidence, bind that decision into policy/preview evidence,
    pass it to both preview and apply-time recomputation, and add recreate tests
    proving priority is omitted when mapping is absent while title/description
    and anomaly resolution still proceed.
  - Requirement: FR3, FR6, NFR2, NFR5; `prev3-t01` items 2-3.
