## Findings

### Critical

- **Default user-scope installs outside Git mutate successfully and then fail in the project-only post-hook** (`packages/cli/src/commands/init/tools/index.ts:1492`)
  - Issue: The reconciled direct command correctly maps an omitted scope to the
    pack's user default (`index.ts:1374-1383`), and aggregate install correctly
    tolerates an unavailable project root (`index.ts:841-846`) and builds user
    requests (`index.ts:899-919`). Both command paths then call
    `reconcileAfterInstall()` (`index.ts:1534-1537`, `1546-1555`). That hook
    skips project config only when the raw command context is explicitly
    `user`; an omitted scope remains `all`, so it calls
    `resolveProjectRoot()` after the user lifecycle has already written every
    asset and scoped intent (`index.ts:1481-1501`). A real CLI run in a fresh
    non-Git directory printed a JSON `status: ok` docs result, then
    `Unable to resolve project root`, exited 2, and left the complete user pack
    plus declared intent on disk. This fails the required fresh user-default
    no-Git path and presents a failed/partially reported command after durable
    mutation.
  - Fix: Drive the post-hook from the lifecycle's actual affected concrete
    scopes (or the existing run metadata), and skip project reconciliation when
    no project request was applied. Add real command-level direct and aggregate
    default-scope tests outside Git that assert exit 0, one valid JSON value,
    complete user inventory, declared user intent, and no project-root call.
  - Requirement: FR1, FR2, FR3, FR5, NFR1, NFR3

- **Executable asset mode makes docs and workflows permanently non-idempotent** (`packages/cli/src/commands/tools/shared/content-digest.ts:18`)
  - Issue: Static-file drift includes executable bits in the digest
    (`content-digest.ts:14-21`). Every manifest `script()` is declared
    executable (`pack-manifest.ts:79-88`), and the reconcile plan copies it then
    applies mode `0755` (`pack-reconcile.ts:97-113`). The bundled shared
    `packages/cli/assets/scripts/resolve-tracking.sh` is mode `0644`, so a
    successful docs/workflows install necessarily differs from its source as
    soon as the required chmod runs. Real post-install inventory reported that
    script `outdated`, and an immediate real dry-run update for workflows
    planned the same `copy-file` plus `chmod` again. The executor's
    completeness-only assertion (`apply-pack-reconcile.ts:114-126`) does not
    catch drift, and the current lifecycle test checks first-apply completeness
    but never a second no-op (`pack-lifecycle.test.ts:125-152`). This violates
    the P0 requirement that a second install/update against a current pack
    report no changes.
  - Fix: Make source and desired executable mode agree (for example, ship the
    canonical script executable) or compute static drift against the manifest's
    normalized target mode. Add real-filesystem repeat install/update tests for
    every executable manifest asset and require an empty second plan; also fail
    post-apply verification when any managed asset remains drifted.
  - Requirement: FR2, FR5, NFR2

### Important

- **`update --all` still recreates a removed pack from another owner's retained shared asset** (`packages/cli/src/commands/tools/update/update-tools.ts:155`)
  - Issue: The inventory placement fix correctly requires declared intent or a
    present non-shared managed asset (`pack-inventory.ts:243-252`), so a removed
    docs pack with only workflows' retained shared script now reports
    `unavailable`. However, scoped completeness still counts every managed
    asset including shared ones (`pack-inventory.ts:191-200`), leaving the
    removed pack `partial`. Pack/all update treats any non-absent inventory as
    installed even when intent is disabled (`update-tools.ts:147-163`). In a
    real remove-then-dry-run sequence, removing docs while workflows retained
    `resolve-tracking.sh` was followed by `update --all` planning all docs
    assets and `write-intent enabled: true`, which would restore the explicitly
    removed placement. The new tests stop at placement/diagnostic assertions
    (`pack-inventory.test.ts:234-268`, `remove-tools.test.ts:578-615`) and do not
    exercise the update eligibility consumer.
  - Fix: Select legacy update candidates from declared intent or the same
    unambiguous non-shared ownership evidence used by placement, not raw
    completeness. Add remove-owner-A / retain-owner-B / update-all tests in
    both owner orders and assert no plan or intent write for A.

### Medium

- **Lifecycle JSON returns pre-intent inventory as if it were the applied result** (`packages/cli/src/commands/tools/shared/apply-pack-reconcile.ts:198`)
  - Issue: The executor inventories and stores its result before applying queued
    intent operations, then returns that unchanged inventory
    (`apply-pack-reconcile.ts:198-213`). The reconciled direct command exposes
    the complete lifecycle result in JSON (`commands/init/tools/index.ts:1427-1433`).
    A real fresh docs install therefore returned
    `apply.inventory.intent.source: inferred-legacy` even though the subsequent
    intent write had made it `declared`. The filesystem is correct, but the
    structured post-apply evidence is stale and can mislead automation.
  - Fix: Re-inventory after intent persistence for the returned result, or
    return separate filesystem-verification and final-state fields with explicit
    semantics. Add a JSON integration assertion that successful fresh install
    reports declared intent.
