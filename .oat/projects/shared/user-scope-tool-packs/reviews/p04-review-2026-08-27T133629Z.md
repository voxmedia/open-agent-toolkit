  - Issue: `resolvePjmTemplate` falls back to `process.env.HOME` when no `home` is
    injected. Every other user-scope path in the CLI resolves home through
    `CommandContext.home`, which is `os.homedir()`
    (`packages/cli/src/app/command-context.ts:49`) and feeds
    `resolveScopeRoot('user', cwd, home)` (`packages/cli/src/fs/paths.ts:41-43`) — the
    same resolver that decides where `~/.oat/templates/*` is written on install. The
    `home` injection point that `design.md:495-504` calls for exists on the options

    `packages/cli/src/commands/pjm/index.ts:273`, `packages/cli/src/commands/backlog/index.ts:211`,
    and `packages/cli/src/commands/decision/index.ts:250` each pass `templatesRoot` and
    `assetsRoot` but omit `home`.
  - Failure scenario: on a platform or shell where `HOME` is unset but `os.homedir()`
    resolves (notably Windows, where Node derives `homedir()` from `USERPROFILE`), the
    installer writes managed defaults to `<homedir>/.oat/templates/` while
    `resolvePjmTemplate` skips the user tier entirely and silently falls through to the
    bundled tier. The user-scope managed-default tier that Phase 4 introduced disappears
    with no diagnostic; `backlog new --json` would report `templateTier: "bundle"` while
    the user's customized managed default sits unread on disk.
  - Fix: thread `home: context.home` into the four `createBacklogItem` /
    `createDecisionRecord` / `initializeRepoReference` / `migratePjmRepo` call sites listed
    above, and change the `template-source.ts:42` fallback from `process.env.HOME` to
    `homedir()` so the read path and the write path agree by construction. Add a
    `template-source.test.ts` case asserting user-tier resolution still succeeds with
    `process.env.HOME` deleted but `home` injected.
  - Requirement: FR7
