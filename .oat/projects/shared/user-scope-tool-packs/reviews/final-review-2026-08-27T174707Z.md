### Important

- **[I1] `oat tools remove` clears durable scoped intent even when it removed
  nothing, and reports that nothing happened**
  (`packages/cli/src/commands/tools/remove/index.ts:133-150`)
  - Issue: the intent-clearing loop is guarded only by
    `!dryRun && target.kind !== 'name'`. It never inspects `result.removed`.
    For `--all` it clears all eight packs' intent at every resolved scope; for
    `--pack X` it clears X's intent. Reproduced: a repo with
    `.oat/config.json` = `{"version":1,"tools":{"docs":true,"utility":true}}`
    and no assets on disk, then
    `oat tools remove --all --scope project` → exit 0, stdout
    `No tools to remove.`, and `.oat/config.json` is left as `{"version":1}`.
    Both declared intents were silently deleted from a **tracked** file while
    the user was told nothing was removed.
  - Consequence: this destroys exactly the state FR5 depends on —
    "`--pack` and `--all` restore a pack when all files are missing but durable
    intent remains" — and it violates FR5's ordering criterion, "Removal clears
    intent only after selected managed assets are removed **or reports a
    recoverable failure**." Neither happened. It also lands as an unexplained
    diff in a committed config file for the rest of the team. Note the genuine
    _failure_ path is safe: `executeManagedPackRemoval`
    (`remove-tools.ts:197-221`) throws before the intent write, so intent
    correctly survives a partial removal. Only the "nothing removed" path is
    wrong.
  - Fix: clear intent only for packs that had removal evidence, or that had
    intent _and_ were successfully reconciled to absent. Concretely, gate the
    loop on the per-pack removal outcome rather than on `target.kind`, and when
    intent is cleared without any asset removal, say so in the output
    (`Cleared intent for docs (user); no managed assets were present`). Add a
    regression test asserting that
    `remove --all` on a config-only, asset-free scope either preserves intent or
    reports the clear.
  - Requirement: FR5 (P0), NFR1 (P0)

- **[I2] Per-pack install ignores existing placement and defaults to user scope,
  silently creating duplicate-scope installs on upgrade; docs assert the
  opposite** (`packages/cli/src/commands/init/tools/index.ts:1345-1352`;
  `packages/cli/src/commands/tools/shared/pack-manifest.ts:165,182,203,222,272,291,315,326`;
  docs at `apps/oat-docs/docs/cli-utilities/tool-packs.md:34-37,419,421`)
  - Issue: `createReconciledPackCommand` resolves scope as
    `context.scope === 'project' || context.scope === 'user' ? context.scope :
definition.defaultScope` with no lookup of where the pack is already
    installed. Every pack now has `defaultScope: 'user'`. Reproduced: a repo
    with `docs` installed at project scope, then `oat tools install docs` with
    no `--scope` → `Scope: user`, `Reconciled operations: 12`, a second full
    copy at `~/.agents/skills/`, and `~/.oat/config.json` gains
    `{"tools":{"docs":true}}`. `oat doctor` then exits **1** with
    `packs:scope_duplication - docs [duplicate-scope]: installed at project and
user scope; provider precedence is not inferred`.
  - Consequence: this is the standard upgrade path for every existing
    0.2.3x user, because the old default was project scope. Running the same
    install command they have always run now silently doubles their install,
    turns a previously-green `oat doctor` red, and requires
    `oat tools migrate` to undo. Existing-placement precedence _is_ implemented,
    but only in the aggregate resolver
    (`init/tools/index.ts:596-603,633-647`) and in brainstorm
    (`init/tools/brainstorm/index.ts:81-114`) — not in the seven other per-pack
    subcommands. Meanwhile `tool-packs.md:34-37` states "On a **re-install**,
    existing placement wins. A pack already installed at project scope stays at
    project scope", and `:419`/`:421` repeat it. The Final Summary does not
    mention the default-scope flip at all.
  - Fix: either (a) extend the aggregate resolver's existing-placement
    precedence into `createReconciledPackCommand` so a re-install without an
    explicit `--scope` targets the scope the pack already occupies — my
    recommendation, since it matches the documented contract and the spec's
    "Existing project, user, or combined placement is preserved unless the user
    explicitly requests migration"; or (b) keep the behavior and correct
    `tool-packs.md:34-37,419,421`, add the flip to the Final Summary and to
    release notes, and have the per-pack path warn when it is about to create a
    second placement. Do not ship (a)-shaped docs over (b)-shaped code.
  - Requirement: FR1 (P0), NFR3 (P0), FR10 (P1)

## Cross-Phase Coherence

**Is the manifest genuinely the single source of truth by the end?** For asset
_membership_ and per-asset scope/ownership, yes — and this is the project's
strongest result. Every live path (install aggregate and per-pack, update,
remove, migrate, outdated, list, info, has, status, doctor, provider sync) reads
`PACK_MANIFEST` directly or through a derived view. The legacy per-pack
installers are dead in production (`init/tools/index.ts:893` takes the reconcile
branch). `skill-manifest.ts:33-94` reduces every legacy `*_SKILLS` constant from
the manifest. Adding a skill to a pack is genuinely a two-file edit — the
manifest and `bundle-inputs.mjs` — and omitting either fails
`bundle-consistency.test.ts:349`/`:385` in both directions. That bidirectional
bundle guard is the healthiest duplicate in the tree.

The exception is the **pack-name roster**, which survives as roughly ten
independent hardcoded copies (`config/oat-config.ts:882-894` and `:901-910`,
`config/resolve.ts:81`, `commands/config/index.ts:120,242,447`,
`tools/update/index.ts:92`, `tools/remove/index.ts:85`,
`tools/update/update-tools.ts:233,391`, and five inside
`init/tools/index.ts`). `VALID_TOOL_PACKS` uses `as const satisfies readonly
(keyof OatToolsConfig)[]`, which checks each element is a valid key but does not
require exhaustiveness, so a ninth pack added to the type union but missed in
the array would be silently stripped by `normalizeToolsConfig` on every read.
I did not find a test that would catch any of these. This is a latent
maintainability risk rather than a shipped defect — the roster has been eight
for the whole branch and all eight are consistent at head — so I have not raised
it as a finding. It is worth a backlog item before pack nine.

**Does per-scope intent mean the same thing in p01 storage, p02 lifecycle, p03
migration and p05 diagnostics?** Substantially yes, and this is the second
strong result. One accessor pair (`readScopedPackIntent` /
`writeScopedPackIntent`) owns the three-state model
(`declared` / `inferred-legacy` / `none`), and one predicate
(`hasScopedPackPlacementEvidence`, `pack-inventory.ts:287`) answers "is this pack
here" for install, update, remove, migrate, outdated, list, info, status and
doctor alike. Only three call sites touch `tools` state outside the accessor:
`pjm/index.ts:277` (the recorded deferred item), `project-tools-config.ts:43-53`
(**M2**) and `config/index.ts:2228-2234` (**M6**). For a five-phase refactor of
this size, three bypasses is a good number.

Write ordering is coherent _structurally_ rather than by convention, which is
the right design: `apply-pack-reconcile.ts:163-213` buckets every `write-intent`
operation out of the mutation loop, applies filesystem ops, re-inventories,
asserts, and only then writes intent. Install, update and migrate all inherit
this for free. I verified the three orderings the design specifies and all three
hold. The one place ordering is _not_ inherited is `oat tools remove`, whose
intent clearing lives in the command adapter
(`remove/index.ts:133-150`) rather than in the plan — which is exactly why
**I1** exists. That is the clearest single lesson in the diff: the seam is where
a phase re-implemented, outside the shared planner, something the planner
already guaranteed.

The same pattern explains **I2**: p01 set `defaultScope: 'user'` and the
aggregate resolver honored existing placement, but p02's per-pack adapter
re-derived scope from the definition without that lookup. Both phases are
individually defensible; the composition is not. And it explains **m1**: p05
built `formatPackPath` as the single presentation contract, but p02's update
renderer predates it and never adopted it.

Two apparent inconsistencies I checked and concluded are **deliberate and
correct**, not findings:

- Templates are `seed-if-missing` at project scope and `managed` at user scope
  (`pack-manifest.ts:39-42`). This looks asymmetric but is precisely FR7: repo
  customizations are owner data, user templates are managed defaults. Verified
  behaviorally in both directions.
- `oat tools remove --pack X --scope user` removes without confirmation while
  migration refuses source removal non-interactively. Different postures for the
  same underlying deletion, but justified: removal is an explicit primary
  request naming pack and scope; migration's removal is a secondary consequence
  of a move. (The _intent_ half of removal is still wrong — I1.)

**Aggregate risk of the recorded deferred items.** The five bare-path skill
chains, the `destinations.md:79` ratchet gap, the `pjm migrate` project-intent
key, the `user-agent-unmaterialized` under-report and
`SCOPE_CONTENT_TYPES.user = ['skill']` are all correctly characterized in the
Final Summary and I found no evidence any is worse than recorded. Two of them do
compound with findings here: the `user-agent-unmaterialized` under-report and
**M1**'s over-report are the same defect class (an ownership/scope classifier
applied unconditionally where the underlying condition is conditional), now
present in both directions in the same diagnostic surface. And `pjm migrate`'s
project-intent key plus **M2**'s unreported promotion both stem from treating
physical project presence as intent. Neither compounding is blocking, but they
should be closed together rather than as unrelated tickets.
