## Findings

### Critical

- **Pack removal clears declared intent while managed assets still make the pack effectively installed** (`packages/cli/src/commands/tools/remove/index.ts:111`)
  - Issue: After `removeTools()` returns, pack and `--all` removal delete the
    selected scoped intent keys unconditionally. The compatibility remover
    deletes scanned skills/agents, workflow user templates, and manifest
    scripts, but it does not remove other assets that the manifest marks
    `managed`, including core's docs directory, docs template directories, and
    ideas/project-management user templates
    (`packages/cli/src/commands/tools/remove/remove-tools.ts:89`). I directly
    reproduced a declared user-scope docs pack with only a managed
    `docs-app-fuma` template remaining: the removal flow deleted the config
    key, left the template in place, and `readScopedPackIntent()` immediately
    returned `enabled: true, source: "inferred-legacy"`. The command therefore
    reports success without clearing effective scoped intent, and a later
    update can silently re-adopt the supposedly removed pack.
  - Fix: Make pack/all removal enumerate every selected manifest asset whose
    ownership is `managed` at the concrete scope, apply shared-owner retention,
    verify those selected assets are absent, and only then delete the scoped
    intent key. Preserve seed/override assets and unrelated config keys. Add
    real pack and `--all` command tests for every managed asset kind, empty
    physical scans, partial installs, and post-removal intent re-reads.
  - Requirement: FR2, FR3, FR5

### Important

- **The shared script makes a nonexistent second owner look intended, so last-owner removal retains it** (`packages/cli/src/commands/tools/shared/scoped-pack-intent.ts:78`)
  - Issue: Shared-script retention asks `readScopedPackIntent()` whether the
    other owner remains intended
    (`packages/cli/src/commands/tools/remove/remove-tools.ts:112`). Legacy
    inference treats any managed destination as evidence for a pack, including
    the shared `.oat/scripts/resolve-tracking.sh` path. I directly reproduced a
    scope containing only that script and no config: both `docs` and
    `workflows` returned `enabled: true, source: "inferred-legacy"`. Thus a
    docs-only install makes workflows appear to own the same file (and vice
    versa), so removing the actual last owner preserves the orphaned script.
    The existing last-owner test injects `isPackIntended: false`, bypassing the
    production inference that causes the defect; both-owner and `--all` cases
    do not expose it.
  - Fix: Base shared-asset retention on unambiguous remaining-owner evidence:
    declared intent or a non-shared physical managed asset for the other pack,
    with the selected removal set excluded. Add production-path tests for
    docs-only, workflows-only, both-owner declared and legacy installs,
    last-owner removal, and `--all` without stubbing the ownership decision.
  - Requirement: FR2, FR5, FR9

### Medium

- **Dual declared intent with no files is still diagnosed as duplicate canonical assets** (`packages/cli/src/commands/tools/shared/pack-inventory.ts:278`)
  - Issue: The previous review's non-blocking finding is unchanged.
    `scopeHasPlacement()` treats declared intent as placement, and every
    `placement === "both"` result emits `duplicate-scope` even when both scoped
    inventories are absent. The resulting diagnostic claims canonical assets
    exist at both scopes while returning empty paths and versions, obscuring
    the repairable intended-but-missing state.
  - Fix: Preserve `placement: "both"` for dual intent if desired, but emit
    `duplicate-scope` only when each scope has at least one observed canonical
    asset. Add the declared-both/assets-absent matrix case.
  - Requirement: FR4, NFR4

- **Manifest source and generation materialization is not enforced as a complete forward contract** (`packages/cli/src/commands/init/tools/shared/bundle-consistency.test.ts:319`)
  - Issue: The bundle consistency assertion still checks only bundled
    inventory entries against manifest sources; it does not prove that every
    manifest source is bundled and exists. Generation values are validated as
    enum metadata but have no shared materializer or handler-coverage test. The
    workflow installer manually implements them, and only creates the two
    declared `empty-file` seeds when the shared projects directory itself is
    absent (`packages/cli/src/commands/init/tools/workflows/install-workflows.ts:184`),
    so an existing shared directory with missing local/archived `.gitkeep`
    seeds is not repaired. Current fresh user inventory is complete and missing
    scripts fail forward, but the declared forward/generation contract remains
    able to drift silently.
  - Fix: Add manifest-to-staged-bundle/source existence checks for every
    source-backed asset and a generation-handler coverage table for every
    `PackAssetGeneration`. Materialize each seed independently when absent,
    including partial existing project roots, and test fresh plus partial
    project installs.
  - Requirement: FR2, NFR2
