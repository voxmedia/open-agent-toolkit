## Findings

### Critical

- **Migration deletes a shared script still owned by another source-scope pack**
  (`packages/cli/src/commands/tools/migrate/migrate-pack.ts:296`)
  - Issue: Source removal delegates directly to `planPackReconcile()` with the
    remove action. That planner removes every present managed asset in the
    selected pack and has no input for other-pack ownership. Both `docs` and
    `workflows` declare `.oat/scripts/resolve-tracking.sh` with shared owner
    `resolve-tracking`, while the established `tools remove` path explicitly
    checks the other owners' declared or legacy ownership evidence before
    retaining the file. Migration bypasses that retention path. A direct
    planner probe in this review produced a `remove-file` operation for
    `script:resolve-tracking.sh`; therefore migrating either pack can delete the
    script while the other remains intended at the source scope, making that
    remaining pack partial. The migration preview also incorrectly lists the
    shared path as a removal.
  - Fix: Move shared-owner retention into the common reconcile planning
    contract and make both ordinary removal and migration consume it. Supply
    source-scope ownership evidence for every other manifest owner, omit the
    shared path from removal when any other owner remains, and report it in
    `retained`. Adjust remove verification so an intentionally retained shared
    observation does not fail the selected pack's removal postcondition. Add
    project and user migration tests for both directions (`docs` retained by
    `workflows`, and `workflows` retained by `docs`) with declared and inferred
    legacy ownership evidence.
  - Requirement: FR8, NFR1

- **Provider-sync failure leaves migration in a state that rerun cannot safely repair**
  (`packages/cli/src/commands/tools/migrate/migrate-pack.ts:228`)
  - Issue: `applyPackReconcilePlan()` performs provider sync only after file
    changes, verification, and intent persistence. If destination sync throws,
    the command reports a raw system error, but on rerun the destination is
    already current and declared, so `planPackReconcile()` produces no changed
    canonical paths and does not retry sync. The rerun can then verify the
    canonical destination and remove the source even though destination
    provider materialization never succeeded. The source side has the inverse
    problem: if removal sync throws after files and intent were removed,
    `completeMigrationSourceRemoval()` returns `source-removal-failed` with a
    generic "re-run interactively" instruction, but a fresh migration can no
    longer detect the source as installed and cannot retry the failed prune.
    This contradicts the design's exact `oat sync --scope ...` recovery contract
    and can leave missing destination views or stale source views.
  - Fix: Model sync failure separately from canonical filesystem failure. Do not
    allow source removal after a destination-sync failure until the destination
    sync has succeeded, and make a rerun explicitly retry the required
    canonical paths even when the destination files are already current. For a
    source-sync failure, preserve enough completion state to retry pruning or
    return the exact `oat sync --scope <source>` recovery command rather than a
    migration command that can no longer plan. Add injected destination- and
    source-sync failure tests that execute the documented recovery and prove
    convergence.
  - Requirement: FR5, FR8, NFR1, NFR4

### Important

- **The interactive preview is count-only and conflicts never reach the preview model**
  (`packages/cli/src/commands/tools/migrate/index.ts:214`)
  - Issue: Human output renders only five counts, then asks for destructive
    confirmation without showing asset IDs, paths, or statuses. In addition,
    `planPackMigration()` throws immediately for newer or legacy-false
    destination conflicts, so its returned `conflicts` array is always empty.
    FR8 requires additions, duplicates, conflicts, and removals to be previewed,
    and the design calls this an explicit, inspectable transaction. The current
    human path cannot expose the exact shared-script mistake above, while the
    blocked conflict path collapses structured state into prose.
  - Fix: Render the preview entries, including asset ID/type, scope, path, and
    status, before destination apply and source confirmation. Return a typed
    blocked preview containing conflicts instead of throwing before the preview
    exists; prevent execution while conflicts remain. Add human and JSON tests
    that assert concrete removal/conflict paths rather than counts alone.

- **Legacy-false destination installs are blocked instead of adopted by the explicit migration**
  (`packages/cli/src/commands/tools/migrate/migrate-pack.ts:132`)
  - Issue: Scoped intent deliberately treats a bare legacy `false` as
    non-authoritative and reports physical assets as `inferred-legacy`. FR9 and
    the design allow a later explicit mutation at the selected scope to record
    that inferred intent. Migration is exactly such an explicit scoped
    mutation, but it rejects any destination `legacy-false-conflict` before
    planning, so a valid legacy destination cannot be adopted or reconciled by
    the migration command.
  - Fix: Carry the legacy-false diagnostic into the preview, reconcile the
    destination as inferred legacy, and persist declared destination intent only
    after complete verification. If any physical conflict must still block,
    classify that conflict from actual asset status rather than from the
    non-authoritative boolean. Add project-to-user and user-to-project adoption
    coverage.

### Medium

- **The migrate adapter duplicates the canonical pack-name authority**
  (`packages/cli/src/commands/tools/migrate/index.ts:33`)
  - Issue: The command introduces another hard-coded list of all eight packs
    even though the project establishes the manifest as the single canonical
    pack definition. A future manifest pack can be fully shipped yet rejected
    only by `tools migrate`, with no compile-time or consistency check tying
    this array to the manifest.
  - Fix: Derive validation/choices from `PACK_MANIFEST` or reuse a single shared
    manifest-derived `isPackName` helper.
