### Low

- **Same-page fragment links whose id contains a character reference are now stripped** (`packages/cli/src/commands/project/archive/archive-utils.ts:1630`)
  - Issue: p07-t06 decodes attribute values before interpretation (`attributeValue`, line 1597), so `fragment` is now decoded text. The existence check that follows still builds a regex from that fragment and tests it against the raw, still-encoded `html`. For `href="#a&amp;b"` with `id="a&amp;b"`, the decoded fragment `a&b` no longer matches the raw `id="a&amp;b"`, so the link attribute is removed. Before this phase the raw fragment matched the raw id. Verified by reading the code, not by a probe (the function is not exported). Ids containing `&`, quotes, or other encoded characters are rare in generated recaps, so the impact is small.
  - Suggestion: compare against decoded ids — collect `id`/`name` values through the existing `attributes()` reader, or encode the fragment the same way before building the regex — and add one keeper case with an entity-bearing id.

- **Summary-failure rebuild can replace the real cause with a recap-mismatch error** (`packages/cli/src/commands/project/archive/archive-utils.ts:2238`)
  - Issue: p07-t07 re-exports the recap without the summary link inside the summary-export `catch`. When the existing page was adopted rather than created by this attempt and it carries the link, the re-export throws `Existing project recap export … does not match persisted snapshot`. That is the intended refusal (test `preserves an adopted linked recap when summary failure would require different output`), and nothing is overwritten. But the thrown error replaces the just-recorded `Summary export to … failed: …` warning, so the user sees a recap mismatch with no mention of the summary failure that triggered it, and a path that was warning-only for non-synced projects becomes a hard failure after the archive has already moved.
  - Suggestion: wrap the rebuild so the thrown error includes the original summary-export message and says the linked page was preserved, giving a clear next step (repair the summary destination and retry).

- **Repaired recap footer link is pinned to the wave branch** (`.oat/repo/reference/project-recaps/20261005-backlog-wave-5.html:274`)
  - Issue: p07-t10 corrected the path to `apps/oat-docs/docs/reference/project-artifacts.md` (the file exists, and the exported hash `f7eb0f4d…a9bc` matches the summary receipt; the original page hash is unchanged). The URL still points at `blob/wave/2026-10-03-backlog-wave-5/…`, which stops resolving once the branch is deleted after merge. The branch ref predates this task, so this is carry-forward rather than a defect in the repair.
  - Suggestion: decide whether durable recaps should link to `main` or a commit SHA; if so, track it against the exporter rather than hand-editing this derived page again.
