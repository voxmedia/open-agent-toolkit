### High

- **H1 — Helper fails every commit when the repository has a submodule or un-ignored nested Git repository** (`packages/cli/src/commands/shared/exact-path-commit.ts:102`)
  - Issue: The unrelated-path preservation snapshot enumerates `git ls-files --cached --others --exclude-standard` (lines 350–368) and calls `fileIdentity` on each entry. `fileIdentity` handles symlinks and absent files only; a tracked gitlink or an untracked nested repository is listed as a directory, so `readFile` throws `EISDIR` and the whole operation returns `failed` before any commit is attempted. The embedded hook guard at line 398 has the same `lstat`/`readFileSync` shape and would abort the commit the same way. The owned paths are irrelevant: committing a single unrelated Markdown file fails.
  - Evidence (executed, P2a/P2b below): in a disposable repo an untracked nested repo and then a tracked submodule each produced `{"outcome":"failed","error":"EISDIR: illegal operation on a directory, read"}` for `commit-paths -- owned.md`; the accepted control in the same repo before adding them returned `committed`.
  - Impact: all adopted callers (project log, record commits for scaffold/pull/open/prune/migrate, promote, and every skill snippet) route through this helper, and shipped guidance states there is no staged-index or pathspec fallback. A user repo with a submodule, or with an agent worktree directory that is not ignored, loses every OAT lifecycle commit with an error that names neither the path nor the cause. The pre-phase `git add -- <paths>; git commit -- <paths>` form worked in these repositories.
  - Fix: Give directories a stable identity instead of reading them — for example return `gitlink:<mode>` (or the submodule HEAD) when `lstat` reports a directory, in both `fileIdentity` and the generated hook guard — or exclude gitlink (`160000`) entries and trailing-slash `--others` entries from the unrelated set. Add a real-Git control with a submodule and an untracked nested repo to `exact-path-commit.test.ts`.
  - Requirement: C1 (one primitive serves CLI and skill lifecycle commits); p03-t02 adoption without regressing existing callers.

### Medium

- **M1 — Removals and renames staged with `git rm`/`git mv` are rejected** (`packages/cli/src/commands/shared/exact-path-commit.ts:159`)
  - Issue: An absent path is accepted only if `git ls-files --error-unmatch` finds it in the real index. `git rm` and `git mv` remove the entry from the index, so the documented contract ("include tracked removals and both names of a rename") fails with `Absent path is not a tracked removal: <path>` for the idiomatic staged form. Only a filesystem-level delete/rename (unstaged) passes, which is the only form the tests model (`exact-path-commit.test.ts:94-95` use `rm`/`rename` from `node:fs`).
  - Evidence (executed, P9/P9b/P9c): `git rm gitrm.md` then `commit-paths -- gitrm.md` → `failed`; `git mv gitmv-old.md gitmv-new.md` then `commit-paths -- gitmv-old.md gitmv-new.md` → `failed`. Passing only the new side → `committed`, producing a commit that adds the new name while HEAD still carries the old one and the staged deletion is left behind — a silent half-rename.
  - Fix: Treat an absent path as a tracked removal when it exists in `HEAD` (for example `git cat-file -e HEAD:<path>`) as well as when it is in the index. Add staged-removal and staged-rename cases to the helper test. p04 archive consumers are likely to move files, so close this before they adopt.
  - Requirement: p03-t01 ("permit tracked removals/renames by carrying both old and new names"); `cli-reference.md` exact-path section.

- **M2 — Terminating the CLI during a hook orphans OAT's own `index.lock`** (`packages/cli/src/commands/shared/exact-path-commit.ts:227`)
  - Issue: The helper now holds the real `index.lock` itself for the full hook duration, but releases it only in a `finally` block. A SIGTERM/SIGINT to the CLI (Ctrl-C, gate or agent tool timeout while lint-staged runs) skips that block. Git cleans its own lock on signals; this helper does not, and neither `commit-paths.ts` nor the helper installs a handler.
  - Evidence (executed, P3): with a 6-second `pre-commit` hook, SIGTERM to the CLI left a zero-byte `.git/index.lock` and an `oat-commit-*` temp directory; the child `git commit` still completed, so HEAD advanced while the real index stayed stale. `git add` then failed with `index.lock: File exists`, and a helper retry returned `blocked` / `persistent-index-lock` telling the user "its owner must finish" — the owner is the dead OAT process. Recovery is a manual lock deletion that the lock-safety guidance otherwise tells users not to do, followed by a same-identity retry.
  - Fix: Release the owned lock (inode-verified, as `stillOwnLock` already does) and the temp directory from SIGINT/SIGTERM/SIGHUP handlers registered for the duration of the operation. Optionally record the owning pid beside the receipt so a later run can positively identify and report an OAT-owned orphan instead of describing it as a foreign lock.
  - Requirement: C3 (bounded lock handling, resumable result). The "never delete an unverified lock" rule is intact; the gap is that the helper can now be the source of the stuck lock.

### Low

- **L1 — The printed manual recovery command leaves the record-commit pending marker in place** (`packages/cli/src/commands/project/sync/ref-sync.ts:1161`)
  - Issue: On a blocked/failed record commit the error tells the user to run `oat internal commit-paths --identity … -- …` directly. That command settles the commit but never calls `clearPending` (lines 1100–1154), so the marker under `.git/oat-record-commit-pending/` persists with a settled identity. If the same `(message, paths)` operation later recurs with different content — for example prune, re-scaffold, and prune again of the same slug — the adapter reuses that identity and the helper refuses with "use a new identity", which the adapter cannot do. Migration is unaffected because it finalizes through `project migrate`.
  - Evidence: source inspection only; not executed (recurrence needs a synced project lifecycle with a remote). The helper half of the claim was executed (P5: reusing a settled identity with new content → `failed`).
  - Suggestion: Point the recovery text at rerunning the owning command where that is safe, or have `commitRecordChange` replace a marker whose receipt is settled and whose commit no longer matches the worktree with a fresh identity.
