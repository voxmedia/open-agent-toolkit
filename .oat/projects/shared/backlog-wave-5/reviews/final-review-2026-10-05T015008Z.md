### High

- **H1 — A `~`-prefixed `core.hooksPath` silently disables every hook on exact-path commits** (`packages/cli/src/commands/shared/exact-path-commit.ts:534-544`)
  - **What happens:** the primitive reads the hook directory with `git config --get core.hooksPath` and passes the raw value to `resolve(root, configured)`. Git expands `~` for this path-typed setting; `--get` without `--type=path` does not. `~/hooks` therefore resolves to `<repo>/~/hooks`, no executable hook is found there, and the generated wrapper hooks delegate to nothing. The commit succeeds with exit 0 and no warning.
  - **Why it blocks:** `BL-260927-share-one-hook-safe-exact-path` requires the primitive to serve lifecycle commits "with hooks enabled". `git config --global core.hooksPath ~/.githooks` is the usual way to install machine-wide hooks, including secret scanners. Before this wave, project-log, promote, prune, migrate and scaffold commits ran plain `git commit` and honoured those hooks; they now bypass them, as does every skill call to `oat internal commit-paths`.
  - **Reproduction (branch build, scratch repository, isolated `HOME`):** a `pre-commit` hook that exits 1, installed at `$HOME/hooks`.
    - Bad state accepted: `core.hooksPath=~/hooks`, `oat internal commit-paths` returns `outcome: committed`, exit 0, and the commit lands.
    - Same hook, plain `git commit`: rejected with the hook's message, exit 1.
    - Accepted controls: `core.hooksPath` as an absolute path and as a repo-relative path (`.hk`) are both rejected by the primitive with the hook's message, exit 2.
  - **Coverage gap:** `exact-path-commit.test.ts` has no case that sets `core.hooksPath` at all, so neither the working forms nor this one are pinned.
  - **Fix guidance:** resolve the directory the way Git does, for example `git rev-parse --git-path hooks` (which already honours `core.hooksPath`) or `git config --type=path --get core.hooksPath`. Add a real-Git test with a rejecting hook under a `~`-relative `core.hooksPath` and an isolated `HOME`, keep the absolute and relative forms as accepted controls, and show the new test fails with the guard neutralized.

### Low

- **L1 — The promotion commit identity is fixed per project path, so a reused slug can never persist** (`packages/cli/src/commands/project/promote/promote.ts:362`)
  - The identity is `promote:<projectRoot>:lite-to-quick`. The receipt for a completed promotion stays in the Git directory. A later Lite project created at the same path in the same clone, then promoted, reuses that identity; the primitive answers `failed` with "Owned artifact changed since this operation committed; use a new identity", and the printed recovery command repeats the same identity.
  - Reproduced the mechanism through `oat internal commit-paths`: commit with an identity, let a later generation of the same path land, then commit again with that identity. Result: `outcome: failed`, exit 2. I did not drive `oat project promote` itself twice.
  - Suggested fix: include a per-operation component (for example the pre-promotion state hash) in the identity, as `commitRecordChange` does with its reservation UUID.

- **L2 — The scaffold failure message points at a recovery command it does not print itself** (`packages/cli/src/commands/project/new/scaffold.ts:879-882`)
  - The old message spelled out the exact `git add` / `git commit` repair. The new one says "Use the exact identity and paths in the reported recovery command", which depends on `detail` carrying the `PendingRecordCommitError` text. For a non-resumable failure, or any error that is not a `PendingRecordCommitError`, no command is in `detail` and the instruction has no referent.
  - Suggested fix: print the command when one exists and a plain inspect-and-retry instruction otherwise.
