### Medium

- **M1: A malformed blocker record now disappears, so the auto-completion blocker hard stop fails open.**
  `packages/control-plane/src/state/parser.ts:253-298` keeps a record only when
  `task_id`, `reason` and `since` are all nonempty strings and discards every
  other entry. `.agents/skills/oat-project-complete-auto/SKILL.md:216`
  hard-fails completion when `project.blockers` is non-empty, and that skill is
  not in the p02-t02 consumer notes in `implementation.md`.
  Probe with the branch build: a `state.md` whose only blocker is
  `task_id: p01-t03` plus `reason: 'Waiting on API contract'` (no `since`)
  returns `[]` from `--field project.blockers` and prints no `Blocker:` line.
  The released CLI (0.3.13) returns `["[object Object]"]` for the same file, so
  the hard stop fired before this change and does not now. A record using
  other key names and a bare `42` behave the same way (`[]` now,
  `["[object Object]","42"]` before).
  The plan asked for malformed entries to be handled "without silent
  `[object Object]` coercion"; the implementation removed the coercion but made
  the loss silent instead.
  Fix guidance: keep a malformed entry visible rather than dropping it. For
  example, emit a legacy-style string such as
  `malformed blocker entry: <JSON of the entry>` so the list stays non-empty and
  human output names the problem, or keep partial records with the fields they
  have. Add a parser case and a status case asserting a record without `since`
  yields a non-empty list, and update the three documentation statements that
  say such entries are ignored (`apps/oat-docs/docs/reference/project-artifacts.md:99-101`,
  `.agents/skills/oat-project-progress/SKILL.md:191-193`,
  `packages/control-plane/README.md`).
