### Important

- **Helper-written input can violate the heading grammar and disappear from roll-up** (`packages/cli/src/commands/project/log/append.ts:109`)
  - Issue: `validateSingleLine` permits the grammar delimiter `·`, while the parser regex explicitly rejects that character inside `area`, `producer`, and `ref`. The unrestricted multiline body and `versionNote` can also introduce lines beginning with `## ` or `### `; `entriesSection` treats `## ` as the end of the entries region and the parser treats `### ` as another entry. As a result, a successful `oat project log append` can create an entry that `check` reports as invalid or that `rollup` omits, contradicting the CLI-owned “valid by construction” contract and risking observation loss at archive time.
  - Fix: Make append validation and parsing share the same serialization boundary. At minimum, reject `·` in heading fields, reject newline-bearing `versionNote` values, enforce the structural one-line body contract, and either reject/escape body lines that collide with level-two/level-three structural markers or make the parser recognize only unambiguous command-owned entry boundaries. Add append/check/rollup tests for each collision.
  - Requirement: Validated machine-parseable entry grammar; append/check/rollup correctness.

- **Summary commits omit the repository ledger written by roll-up** (`.agents/skills/oat-project-summary/SKILL.md:395`)
  - Issue: Step 6 writes or updates the configured repository ledger, but Step 8 stages only `summary.md` (plus decision records when applicable). A standalone successful summary run can therefore report that observations were durably rolled up while leaving `.oat/repo/reference/project-observations.md` uncommitted. Any append-based promotion made in Step 2.5 can likewise remain outside the summary commit.
  - Fix: Resolve the effective `workflow.projectLogLedgerPath` and stage it whenever roll-up reports `ledgerOutcome: "appended"`; also stage `project-log.md` when Step 2.5 appended a promotion. Add skill-contract assertions that the commit step includes every tracked surface mutated by the summary flow.
  - Requirement: Durable ledger graduation and roll-up before archive.

- **Implement cannot reliably execute its newly required project-log appends under its declared tool contract** (`.agents/skills/oat-project-implement/SKILL.md:9`)
  - Issue: The skill now requires `oat project log append` after dispatches, STOP/park events, phase outcomes, and merge attempts, but its `allowed-tools` still permits only `Bash(git:*)`. Unlike the summary skill, it did not add `Bash(oat project log:*)`. Hosts that enforce or pre-authorize the declared tool patterns can prompt, deny, or skip these appends—especially during non-interactive autonomous execution—breaking default `auto` creation and the primary structural appender contract.
  - Fix: Add `Bash(oat project log:*)` (or the repository-approved narrower equivalent) to the implement skill frontmatter and pin that permission alongside the append-point prose in `review-skill-contracts.test.ts`.
  - Requirement: Automatic implement dispatch/STOP/phase/merge structural entries.

### Medium

- **The first ledger write does not deduplicate duplicate candidates within the same log** (`packages/cli/src/commands/project/log/rollup.ts:217`)
  - Issue: `additions` filters candidates only against keys already present in the ledger. It does not add accepted candidate keys to the set while filtering, so two `general` judgments with the same date and area are both written on the first roll-up. Later runs report `deduplicated`, but the ledger is already duplicated, violating the documented date-plus-area deduplication contract.
  - Fix: Build additions while updating a working key set (preserving the first matching entry), and add a test with two same-date/same-area general entries in one project log.
  - Requirement: Ledger deduplication by entry date and area.
