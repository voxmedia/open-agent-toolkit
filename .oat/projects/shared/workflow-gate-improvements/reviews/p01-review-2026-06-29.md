## Summary

Phase p01 adds the intended parser, review-specific gate command, generic executor preservation, and dev-build warning polish, and the scoped test/type-check commands pass. However, `oat gate review` does not actually pass the resolved project to the child provider, and its artifact discovery can accept non-project review artifacts; both break the project-scoped review gate contract. The parser also has a false-pass risk for partial explicit counts and an inaccurate fallback count for standard nested OAT finding bullets.

### Important

- **Resolved project is not passed to the review provider** (`packages/cli/src/commands/gate/index.ts:1130`)
  - Issue: `runReviewGate` resolves `projectPath`, but the dispatched prompt only includes the gate note, optional type/scope hints, and the user prompt. For `oat gate review --project named ...` with no active project, or when `--project` intentionally differs from the active project, the child provider has no reliable instruction to review the resolved project and may fail to write the expected artifact or review the wrong project.
  - Fix: Include the normalized resolved project path in the gate context sent to the target, for example `Resolved project: ${projectPath}. Run the review for this project path.`, and add tests that assert explicit project name/path values are present in the child argv.
  - Requirement: p01-t02 project resolution and target dispatch

- **Review gate can accept ad-hoc or archived artifacts as the produced project review** (`packages/cli/src/commands/gate/index.ts:1129`)
  - Issue: `runReviewGate` uses `findLatestReview({ repoRoot, projectPath })` before and after dispatch, but that helper also considers archived project reviews and ad-hoc review directories. A gate-originated project review should discover the active top-level artifact under the resolved project; otherwise a child that writes an ad-hoc artifact, or an unrelated newer ad-hoc artifact, can be treated as the gate result and parsed for pass/fail.
  - Fix: Use a project-active-only discovery path for gate reviews, or filter the returned latest review to `kind === 'project'`, `actionable === true`, `archived === false`, and a path under `${projectPath}/reviews/`. Add regression tests for ad-hoc-only and archived-only artifacts after dispatch.
  - Requirement: p01-t02 review artifact discovery and project resolution

- **Partial explicit counts suppress parsed blocking findings** (`packages/cli/src/commands/gate/review-verdict.ts:94`)
  - Issue: `readFrontmatterCounts` returns explicit counts when it finds any one count field, defaulting all missing severities to zero and skipping Findings-section parsing. An artifact with `oat_review_critical_count: 0` plus an Important finding in the body would be treated as non-blocking, which violates the conservative parser requirement.
  - Fix: Prefer explicit counts only when all four severities are present and valid, or parse the Findings sections for missing severities. If partial explicit counts are considered invalid, return an actionable parse error.
  - Requirement: p01-t01 verdict parsing and p01-t02 exit threshold behavior

### Medium

- **Fallback parser overcounts standard nested OAT findings** (`packages/cli/src/commands/gate/review-verdict.ts:113`)
  - Issue: The fallback counter counts any indented markdown bullet, so a normal finding shaped as one top-level bullet with nested `Issue` and `Fix` bullets is reported as multiple findings. This usually does not change blocking status, but it makes the verdict summary counts unreliable.
  - Fix: Count only top-level list items or numbered items within each severity section, and add a regression test using the standard OAT review finding template.
