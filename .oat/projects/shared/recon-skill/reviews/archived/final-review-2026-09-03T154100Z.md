### Important

- **A rejected claim is deleted but the synthesis still asserts it, and the packet publishes as `complete`**
  (`.agents/skills/recon/scripts/reconcile-ledger.mjs:234-242`,
  `.agents/skills/recon/scripts/reconcile-ledger.mjs:261-264`,
  `.agents/skills/recon/scripts/validate-packet.mjs:2261-2263`,
  `.agents/skills/recon/scripts/render-packet.mjs:57-60`)
  - Issue: `prev8-t02` handles a `rejected` semantic disposition by pushing
    the claim onto `removals` and filtering it out of `ledger.claims`. Nothing
    touches `ledger.synthesis`, so `synthesis.answer` and
    `synthesis.keyClaimIds` continue to reference the rejected claim. The
    validator's synthesis check is shape-only
    (`lib/contracts.mjs:1050-1055`); there is no rule that `keyClaimIds` or
    `unresolvedQuestionIds` resolve to existing entries, and
    `renderPacketDocument` silently drops unresolved key-claim IDs with
    `.filter(Boolean)`. Direct probe on the standard fixture: mark the
    semantic disposition for `claim-1` as `rejected`, run `reconcileLedger`,
    write the ledger and reconciliation back, and call `renderPacket`. Result:
    `valid: true`, `publishable: true`, `status: complete`, and the rendered
    `packet.md` reads "## Synthesis / The source contains alpha evidence."
    (the rejected claim's statement) followed by an empty "## Key Claims"
    section. The ledger's `keyClaimIds` is still `["claim-1"]` while
    `claims` no longer contains `claim-1`. This overstates assurance in the
    consumer entry point, contradicting discovery Success Criteria ("The
    packet never overstates assurance when sources are ... contradictory";
    "`packet.md` lets a downstream model understand the major verified,
    contested, and unresolved findings") and design Error Handling, which
    routes failed verification to the `unsupported` claim state
    (`design.md:575`, `design.md:653-661`) rather than silent deletion. The
    `supported:unsupported` transition is legal in `lib/contracts.mjs:66` but
    absent from the reconciler's own `legalReconciliationTransitions`
    (`reconcile-ledger.mjs:16-24`), so the honest downgrade is unreachable
    through the bundled helper. The p-rev8 tests assert only that the claim
    disappears and the run compiles; none inspects the synthesis or the
    rendered packet.
  - Fix: (1) In `validateAssurance` (or the ledger shape validator), add a
    categorical referential-integrity check: every `synthesis.keyClaimIds`
    entry must resolve to a claim in `ledger.claims`, and every
    `synthesis.unresolvedQuestionIds` entry to `ledger.unresolvedQuestions`
    (for example `SYNTHESIS_REFERENCE_MISSING` at `$.synthesis.keyClaimIds`).
    This makes a stale synthesis non-publishable regardless of how the ledger
    was produced. (2) In `reconcileLedger`, prefer the design's state model:
    add `supported:unsupported`, `provisional:unsupported`,
    `verified:unsupported`, and `contested:unsupported` to
    `legalReconciliationTransitions` and transition a `rejected` claim to
    `unsupported` (retaining it, its evidence links, and a transition record)
    instead of deleting it. If wholesale removal is intentionally retained
    for some rejections, the reconciler must also prune the removed IDs from
    `synthesis.keyClaimIds` and record a material gap so the run cannot
    publish as `complete` with a rejected key claim. (3) Tests: a negative
    control reproducing the probe above (rejected key claim → validator
    rejects with the new code), a positive control where the reconciler's
    output passes and `packet.md` no longer states the rejected claim, and a
    render-level assertion on the Synthesis section.
  - Requirement: discovery Success Criteria (assurance honesty), design
    Publication Outcomes and Evidence Drift (`unsupported` state), p-rev8
    `prev8-t02` intent ("contract-legal negative dispositions").

### Medium

- **A valid but non-publishable run still returns a `ValidatedRun` that the exported renderer will publish**
  (`.agents/skills/recon/scripts/validate-packet.mjs:2261-2287`,
  `.agents/skills/recon/scripts/render-packet.mjs:277-280`)
  - Issue: `compileValidatedRun` now computes `publishable` and pushes
    `PACKET_NOT_PUBLISHABLE` into `errors`, but the return still exposes
    `validatedRun` whenever `valid` is true, and `valid` is computed before
    the new issue is appended, so callers receive `valid: true` alongside a
    non-empty `errors` array. `renderPacket` re-checks `publishable`, but
    `renderValidatedPacket` is an exported public function that accepts any
    frozen `ValidatedRun` and never consults run status. Direct probe: quick
    fixture with `run.status = 'running'` → `compileValidatedRun` returned
    `{ valid: true, publishable: false, validatedRun: <object> }`, and
    `renderValidatedPacket(validation.validatedRun)` promoted a `packet.md`
    reading "**Status:** running". The design defines `ValidatedRun` as "the
    only trusted in-memory representation of a publishable run"
    (`design.md:125-126`) and `packet-contract.md:53-55` says rendering
    accepts only `ValidatedRun`; the boundary therefore no longer implies
    publishability. Only tests call `renderValidatedPacket` today, so the
    documented CLI path is safe, but the invariant the design relies on is
    now false and the next internal caller inherits the gap.
  - Fix: Return `validatedRun: publishable ? validatedRun : undefined`, and
    either fold publishability into `createValidatedRun` (refuse to construct
    for non-`complete`/`partial` status) or make `renderValidatedPacket`
    assert `manifest.run.status` is `complete` or `partial` before writing
    the temporary file. Keep `valid` semantically consistent with `errors`:
    either report `valid: false` when `PACKET_NOT_PUBLISHABLE` is present or
    document that `valid` excludes publishability and `errors` may be
    non-empty for a valid run. Add a test that a `running` fixture yields no
    `validatedRun` and that `renderValidatedPacket` on a hand-built
    non-publishable run throws a categorical code.

### Minor

- **The contract does not say what run status an unresolved adversarial challenge carries**
  (`.agents/skills/recon/SKILL.md:214-216`,
  `.agents/skills/recon/references/packet-contract.md:177`,
  `.agents/skills/recon/tests/integrity-contracts.test.mjs:909-918`,
  `.agents/skills/recon/tests/workflow.integration.test.mjs:401-410`)
  - Issue: The validator publishes a standard run as `complete` with every
    claim `contested` and no gap (direct probe: challenge the adversarial
    disposition, reconcile, validate → `valid: true, publishable: true,
status: complete`). The p-rev8 tests instead hand-patch a material
    `UNRESOLVED_CHALLENGE` gap and set `partial`, which the validator then
    requires (`INVALID_PARTIAL_STATUS` fires for `partial` without a gap).
    Neither `SKILL.md` Step 7 nor `packet-contract.md` states which shape the
    controller must produce, so the tests encode a convention the runtime
    does not enforce or document. The current behaviour is defensible
    (contested is a categorical state rendered under "Contradictions and
    Qualifications"), so this is contract clarity rather than a defect.
  - Suggestion: State in `packet-contract.md` (and mirror in `SKILL.md`
    Step 7) whether an unresolved material challenge is a material gap that
    forces `partial`, or whether a `complete` run may carry contested claims.
    Align the two p-rev8 tests with whichever rule is chosen.

- **Docs page does not mention withdrawal of `packet.md` on non-publishable generations**
  (`apps/oat-docs/docs/workflows/skills/recon.md:94`)
  - Issue: The docs page describes the layout of "every structurally
    publishable run" but never states the withdraw-on-failure and
    withdraw-on-non-publishable behaviour now implemented and documented in
    `packet-contract.md:263-270`. A reader of the docs site cannot learn that
    a failed or interrupted generation leaves no consumer entry point.
  - Suggestion: Add one sentence under the layout section mirroring the
    packet-contract wording ("a non-publishable candidate withdraws any
    existing `packet.md`").
