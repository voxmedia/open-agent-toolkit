### Critical

- **User-scope sync feeds bundle-root agents into a scope-root-only plan and fails before materialization** (`packages/cli/src/commands/sync/index.ts:336`)
  - Issue: the user-scope branch appends every result of `scanBundledManagedAgents({ scopeRoot })` to `providerCanonical`, including the two built-in roles whose canonical paths are under `packages/cli/assets/agents`, and passes that entire array to ordinary `computeSyncPlan`. The ordinary executor derives a scope root only from paths containing `/.agents/`, so fresh real integration runs fail with `Cannot infer scope root from canonical path: .../packages/cli/assets/agents/oat-phase-implementer.md`. The isolated existing integration cases for `sync --scope user`, `sync --scope all`, and user-installed pack sync failed 3/3. This breaks the core p03-t03 user materialization path before either built-in or pack-owned agents can be reconciled.
  - Fix: keep extension-only bundled role definitions separate from ordinary provider mapping inputs. Ordinary sync planning must receive only canonical entries whose ownership/root semantics it can execute safely; installed user-materializable pack agents may be included through a separately typed in-scope set or an executor contract that carries the explicit scope root. Continue passing the complete built-in-plus-pack set to Codex/Cursor materialization extensions. Add the three existing real command-integration cases to the focused p03 gate so unit mocks cannot hide this boundary.
  - Requirement: `p03-t03`; installed user-scope pack agents must materialize through supported provider behavior without regressing built-in roles or ordinary user sync.

### Important

- **Mixed remove-then-install batches plan dependency acquisition from stale asset availability** (`packages/cli/src/commands/tools/shared/pack-lifecycle.ts:109`)
  - Issue: the new projection updates only `intent.requiredBy`; every entry's asset statuses still come from the same pre-apply filesystem. In a production-function probe, research was the sole utility consumer, then one batch requested `remove research` followed by `install brainstorm`, with brainstorm declaring the same two utility dependencies. The release plan removed both selected utility skills. The later acquire plan had observed those skills as current before apply, so it planned only the new lease; after the release applied, acquire verification failed because both skills were missing. The batch left utility absent with no leases and neither consumer installed. Reversing root request order avoids the failure, making the result order-dependent. The root/scope key correctly prevents projection bleed across different roots and scopes, but it does not make same-key mixed actions coherent.
  - Fix: narrowly compute the final lease consumers for each dependency owner/scope/root before filesystem planning and retain selected assets whenever that final set is non-empty, while preserving the existing ordered lease writes and one global preflight before mutation. Do not add a generalized inventory simulator. Add both remove-then-install and install-then-remove regressions using two consumers of the same selected assets, and assert identical final leases, files, inventory, and root outcomes.
  - Requirement: `p03-t02`; batched dependency reconciliation must be idempotent and converge safely across mixed lifecycle requests.

- **A root-apply failure after dependency release loses dependency provider-cleanup paths on the advertised retry** (`packages/cli/src/commands/tools/migrate/migrate-pack.ts:510`)
  - Issue: moving `releaseDependencies` before the root apply makes a dependency-release exception retryable, but creates an adjacent loss window. A real-filesystem production probe migrated research project-to-user, let source dependency release succeed, injected failure at source root apply, then followed the advertised full migration retry. The source remained complete/direct and the retry reached `migrated`, but the first attempt had already removed the source utility lease and both utility skills. The retry's idempotent dependency release therefore returned no `changedCanonicalPaths`, and the final source sync received only research-owned paths. It omitted `.agents/skills/oat-dispatch-subagents` and `.agents/skills/subagent-orchestration`, so stale source provider views for the already-removed dependencies are not reconciled.
  - Fix: retain or reconstruct successfully removed dependency canonical paths across a root-apply failure so the exact advertised retry cannot report `migrated` until those provider views are reconciled. This can be a bounded migration cleanup record/derivation or immediate dependency-only cleanup on the failure path; it does not require changing destination-before-source ordering. Add a failure-injection integration test at root apply after successful dependency release and assert both utility canonical paths reach source sync on the exact full-command retry.
  - Requirement: `p03-t02`; destination-first migration and source cleanup must remain recoverable and idempotently convergent after partial failure.
