### Important

- **Non-publishable but valid candidates do not withdraw a prior `packet.md` and yield an empty diagnostic**
  (`.agents/skills/recon/scripts/validate-packet.mjs:2263-2281`,
  `.agents/skills/recon/scripts/render-packet.mjs:260-269`,
  `.agents/skills/recon/scripts/validate-packet.mjs:2313`)
  - Issue: `compileValidatedRun` withdraws `packet.md` only when `valid` is
    false. `publishable` is computed separately as `valid && status in
{complete, partial}`, but nothing in `validateAssurance` binds
    `run.status` to the validated topology, so a manifest that flips
    `run.status` to `failed`, `running`, `preparing`, or `awaiting-approval`
    while keeping every other artifact intact is reported `valid: true,
publishable: false, errors: []`. The CLI (`process.exitCode = result.valid
? 0 : 1`) then exits 0, so the documented Step 7 controller sequence
    ("Only a valid candidate proceeds to `render-packet.mjs`") proceeds to the
    renderer. `renderPacket` throws `Packet validation failed: ` (empty code
    list) _before_ entering `renderValidatedPacket`'s try/catch, so the
    withdrawal path never runs. A direct probe against the standard fixture
    reproduced all three statuses: first publish succeeds, status flip →
    `valid: true, publishable: false`, CLI exit would be 0, renderer message
    `Packet validation failed: `, and `packet.md` still exists reading
    `**Status:** complete` while `manifest.json` says `failed`. This
    contradicts `packet-contract.md:266-269` ("failure withdraws any existing
    `packet.md` … a rejected canonical generation cannot retain a consumer
    entry point from another generation"), `design.md` Publication Outcomes
    (`failed` → "`packet.md` is absent") and the design's "must not leave a
    misleading `packet.md`" rule. It is the same class of split-generation
    defect that Revisions 5–7 closed for the `!valid` path; the
    valid-but-unpublishable path was never covered by a test.
  - Fix: In `compileValidatedRun`, compute `publishable` before the withdrawal
    check and withdraw `packet.md` (through the same `assertUnchangedRoot`
    guard) whenever `!publishable`, not only when `!valid`. Emit a categorical
    issue (e.g. `PACKET_NOT_PUBLISHABLE` with the offending status at
    `$.run.status`) so `errors` is non-empty and `renderPacket`'s message
    carries a code. Make the CLI exit nonzero when `!publishable` (or document
    a distinct exit code) so the controller sequence cannot proceed to the
    renderer. Add tests: (a) valid-then-status-flip for each of the four
    statuses proving `packet.md` is withdrawn and the code is reported,
    (b) `render-packet.mjs` on such a directory withdraws and reports the code,
    (c) a valid `complete`/`partial` replacement control still publishes.
    Align the one sentence in `packet-contract.md` and `SKILL.md` Step 7 that
    currently say "valid candidate" to say "publishable candidate".
  - Requirement: discovery Key Decision 15 / design Publication Outcomes /
    `packet-contract.md` Validation and Publication.

### Medium

- **Bundled reconciler rejects contract-legal negative dispositions, so `contested` is unreachable through it**
  (`.agents/skills/recon/scripts/reconcile-ledger.mjs:4-8`,
  `.agents/skills/recon/scripts/reconcile-ledger.mjs:61-73`,
  `.agents/skills/recon/scripts/lib/contracts.mjs:1667-1670`)
  - Issue: `contracts.mjs` permits `semantic: affirmed|rejected|uncertain` and
    `adversarial: unchallenged|challenged`, and the packet validator accepts
    `rejected` dispositions with typed removals
    (`integrity-contracts.test.mjs:1305-1338`). `reconcileLedger`, however,
    throws `Reconciliation received an invalid <kind> disposition` whenever
    any semantic disposition is not `affirmed` or any adversarial disposition
    is not `unchallenged`. A probe with a schema-valid adversarial result
    carrying `challenged` threw immediately. The `legalReconciliationTransitions`
    set lists `provisional:contested`, `supported:contested`, and
    `verified:contested`, but the only code path reaching `contested` is a
    material coverage gap; a challenge or rejection can never be reconciled.
    This contradicts the p05-t01 plan intent ("preserving honest unresolved,
    unsupported, and contested outcomes") and the design's adversary role.
    The script is not on the documented controller path (SKILL.md routes
    reconciliation to a `reconcile` worker and never references it), so the
    shipped runtime is not broken, but the helper is bundled in the pack,
    exported, and is what the fixture runner uses — meaning no end-to-end
    scenario exercises a contested/unsupported outcome through reconciliation
    into publication.
  - Fix: Accept every disposition value the contract permits. For a
    `challenged`/`rejected` disposition, derive the contract-legal downgrade
    (`→ contested`, or a typed removal with `removalDispositions` when the
    review authorizes removal) instead of throwing; keep `uncertain` as
    no-promotion. Add positive controls for challenged → contested and
    rejected → removal through `compileValidatedRun`, and a
    `workflow.integration` scenario for "genuine contradiction retained as
    contested" as listed in the design's Workflow Integration Tests.
    Alternatively, if the helper is intentionally test-only, move it under
    `tests/helpers/` so it is not shipped as a runtime script.
