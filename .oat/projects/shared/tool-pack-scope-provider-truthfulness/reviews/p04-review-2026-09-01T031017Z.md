## Findings

### Critical

- **A child created after absent-transition revalidation can be deleted by deferred apply**
  (`packages/cli/src/fs/io.ts:110`)
  - Issue: An explicit transition whose collection destination was manually
    cleared re-proves the planned `absent` identity and detaches ownership at
    `packages/cli/src/engine/execute-plan.ts:507`, then awaits manifest
    persistence at line 596 before reporting the detachment `changed` and
    releasing deferred children at lines 606-615 and 796-821. A concurrent
    unmanaged child can appear during that persistence window. Planning has
    already forced deferred entries to `create_symlink` or `create_copy`
    (`packages/cli/src/engine/compute-plan.ts:932`), and the later provider-path
    check validates ancestry but not final-path ownership. For a symlink entry,
    `createSymlink` catches `EEXIST`, recursively removes the destination at
    `packages/cli/src/fs/io.ts:115`, and falls back to a copy. A deterministic
    reproduction injected a user directory after the first real manifest save
    and observed `collection=changed`, `operation=changed`, and
    `userOwned=missing`. This defeats the round-3 requirement that a later
    absent plan allow **safe** convergence and violates P0 unmanaged-content
    preservation.
  - Fix: Give deferred transition creates no-clobber semantics. An apply-time
    `EEXIST` or final-path identity change must preserve the destination, fail
    that child operation, and report actionable recovery; do not route it
    through destructive symlink-to-copy fallback. Apply the same preservation
    boundary to deferred copy creation, and add deterministic symlink/copy
    regressions that insert both a user file and directory after collection
    absence revalidation but before child mutation. Assert the replacement
    bytes/tree survive, the child fails, and manifest evidence does not claim
    the entry changed.
