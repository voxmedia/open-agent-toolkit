## Findings

### Critical

- **Collection creation can be redirected outside the provider root after the apply-time proof** (`packages/cli/src/engine/execute-plan.ts:452`)
  - Issue: The executor proves every collection at lines 419-446, then invokes the mutation hook, and creates the final symlink at lines 454-458 without rechecking ancestry. The creation primitive calls `ensureDir(dirname(linkPath))` before `symlink` (`packages/cli/src/fs/io.ts:117`), so a parent replaced with a symlink during that interval is followed. A diagnostic hook that replaced `.claude` with a link to an external temporary directory observed `createdOutside: true`; rollback later removed it, but the out-of-scope mutation had already occurred and a failed rollback can leave it behind. This violates the P0 NFR1 apply-time ancestry guarantee and the Phase 4 design's immediate pre-mutation recheck.
  - Fix: Run the mutation hook before the final proof, re-prove canonical/provider identity immediately before creation, and harden the creation primitive so it neither creates nor follows a changed/symlinked ancestor. Add a deterministic regression using `beforeFirstMutation` that swaps the parent and asserts the creation primitive is never reached and no path appears outside the scope root.
  - Requirement: FR5, NFR1, NFR2

- **Historical `oat-created` ownership deletes a user-replaced exact alias** (`packages/cli/src/engine/execute-plan.ts:493`)
  - Issue: Manifest collection records retain only paths, ownership, and verification time, not the identity of the alias OAT originally created (`packages/cli/src/manifest/manifest.types.ts:81`; projection at `packages/cli/src/engine/collection-sync.ts:334`). On disablement, planning snapshots the replacement alias's current exact-link proof while carrying forward historical `oat-created` ownership. The executor therefore compares the current replacement only with that same current proof and unlinks it at lines 506-513. An independent fixture removed the OAT-created link, created a new same-target link with a different inode, and observed `proofStatus: exact-link` followed by `exists: false`. The canonical target survived, but user-owned filesystem content was deleted, contrary to the explicit "still-exact OAT-created alias" boundary.
  - Fix: Persist creation-time alias identity/provenance sufficient to distinguish the original link (for example device, inode, and exact link text), and authorize unlink only when current identity matches that stored creation identity. Existing records without durable creation identity must detach ownership while preserving the alias. Add disablement/removal tests for a same-target replacement with a different inode.
  - Requirement: FR5, NFR1, NFR2

### Important

- **Changing `auto` to explicit `symlink` or `copy` cannot transition an owned collection to per-entry mode** (`packages/cli/src/engine/compute-plan.ts:648`)
  - Issue: Collection reconciliation runs only when the configured strategy is `auto`, while the later cleanup loop skips every collection belonging to an active provider (`packages/cli/src/engine/compute-plan.ts:858`). Per-entry planning then descends beneath the still-present collection alias and the ancestry guard throws. An independent reproduction failed with `Unsafe provider parent ".claude/skills": symbolic links are not allowed in provider ancestry.` The fresh explicit-strategy tests do not cover an existing collection. This breaks the documented/configured authority that explicit `symlink` and `copy` remain per-entry strategies.
  - Fix: Detect owned collections that are no longer eligible because strategy changed. Plan a safe detach first; unlink only a still-proven, durably identified OAT-created alias, preserve adopted or changed aliases with an actionable conflict, and perform per-entry reconciliation only after the collection path is safely clear. Add `auto -> symlink` and `auto -> copy` integration tests for OAT-created, adopted, changed, and unverifiable aliases.
  - Requirement: FR5, FR10, NFR2, NFR3

### Medium

- **Manifest V2 accepts non-normalized inherited paths that escape collection ancestry lexically** (`packages/cli/src/manifest/manifest.types.ts:171`)
  - Issue: Collection records use the normalized path schema, but inherited entries still use the weaker base relative-path schema at lines 23-31. The ancestry check uses raw `startsWith`, so `.agents/skills/../../outside` and the analogous provider path parse successfully as children of the collection. The current inherited-entry executor path only detaches manifest ownership, so the review did not reproduce target deletion from this defect, but the persisted ownership graph violates the V2 invariant and can misclassify drift/removal state.
  - Fix: Require normalized POSIX paths for every `strategy: collection` entry before ancestry comparison, then compare by normalized path segments. Add traversal, empty-segment, dot-segment, and backslash rejection fixtures.
  - Requirement: FR5, NFR1, NFR4

- **The planner ignores the registry's `collectionAlias` capability** (`packages/cli/src/commands/sync/index.ts:337`)
  - Issue: Provider registrations carry an explicit per-scope/content `collectionAlias` capability (`packages/cli/src/providers/shared/registry.ts:207`), but sync strips registrations to adapters before planning. The planner gates only on `contentType === 'skill'` and mapping shape (`packages/cli/src/engine/compute-plan.ts:648`). Current bundled skill mappings are mechanically marked supported, so this does not break a bundled provider today, but an unsupported or future/custom capability cannot prevent collection planning and the recovery claim is not enforced at its stated authority boundary.
  - Fix: Thread the resolved capability (or an eligibility set derived from it) into planning and require `collectionAlias === 'supported'`. Add a command/planner test whose active skill mapping is explicitly registered as unsupported and verify per-entry planning.
  - Requirement: FR5, FR10, NFR4
