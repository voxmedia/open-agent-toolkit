### Important

- **Provider-set help rewrite accepts arbitrary scopes and silently writes project config** (`packages/cli/src/commands/providers/set/index.ts:219`)
  - Issue: The round-2 fix replaced `withScopeOption(...).choices(['project', 'user', 'all'])` with a raw `Option` that has a default but no `.choices(['project', 'user'])`. The handler rejects only the exact value `all`; every other string flows through the typed boundary. A live isolated run of `providers set --scope nonsense --enabled claude --json` exited 0, wrote `<cwd>/.oat/sync/config.json`, and returned `scope: "nonsense"`.
  - Impact: A typo or unsupported scope can mutate project configuration while the JSON response claims a different scope. This breaks the selected-scope and scope-isolation guarantees and makes the newly corrected help text more restrictive than actual behavior.
  - Fix: Constrain the Commander option with `.choices(['project', 'user'])` (or validate with the canonical scope schema before resolving any root). Add a command test proving an arbitrary value is rejected before `resolveScopeRoot` or any config write and that no config file is created.
  - Requirement: FR1, FR2, FR10, NFR3.

- **Core human apply output still labels plans as applied instead of rendering operation results** (`packages/cli/src/commands/sync/apply.ts:178`)
  - Issue: Core exact results are normalized and retained in `operationResults`, but `formatAppliedOutput` passes only the immutable plan to `formatSyncPlan(..., true)`. That formatter produces `Sync plan (applied)` and lists every planned named asset with its plan reason; it receives no exact `changed/current/failed/missing` status or redacted failure. The same happens for aggregate-only adapters whose JSON operation status is intentionally `unknown`.
  - Impact: On a mixed core result, human output presents the failed asset beneath an applied heading and gives only a generic partial-failure warning, while JSON identifies the failed asset. On aggregate-only results, named assets appear applied even though the normalized evidence says their outcome is unknown. This violates the Phase 3 per-operation evidence and human/JSON parity contract.
  - Fix: Pass the scope's normalized core operation results into the human formatter and join them to plan entries by stable scope/provider/content/asset/action identity. Render plan reason separately from actual `changed`, `current`, `failed`, `missing`, or `unknown` status and the already-redacted failure. Add human-output tests for exact mixed success/failure and aggregate-only unknown results.
  - Requirement: FR1, FR4, NFR3.
