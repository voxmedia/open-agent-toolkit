### Important

- **Human extension apply output reports plans as applied but omits per-operation results** (`packages/cli/src/commands/sync/apply.ts:212`)
  - Issue: `formatAppliedOutput` renders only immutable planned extension operations and their reasons, then labels the section `extension (applied)` at line 227. Apply-time `operationResults` are correctly stored separately at lines 305-313 for JSON, but they are never passed to or rendered by the human formatter. A mixed extension result can therefore show every planned create/update beneath “applied” while the only failure disclosure is the generic “partial failures” warning.
  - Impact: Human and JSON compatibility surfaces do not expose the same normalized facts, and a user cannot identify which extension-owned role/config operation failed. This leaves round-1 finding 1 only partially fixed and violates the requested per-operation evidence contract.
  - Fix: Pass extension `operationResults` into the human formatter and join each result to its stable planned operation identity (`provider`, `target`, `path`, `action`, and `entryName`). Render the immutable reason and the actual `changed`/`current`/`failed` outcome separately, including a redacted failure. Add a mixed-success/failure human test alongside the JSON preservation test.
  - Requirement: FR1, FR4, NFR3.

### Medium

- **Aggregate-only compatibility results are converted into fabricated per-asset outcomes** (`packages/cli/src/commands/sync/apply.ts:143`)
  - Issue: When a legacy `SyncResult` omits `operations`, `normalizeOperationResults` assigns `changed` to the earliest non-skip planned entries and `failed` to later entries solely from aggregate counts. Counts cannot establish which asset succeeded, so a two-operation result with one success and one failure may publish the inverse of what happened. Extra unmatched counts are also attributed to the first planned asset at lines 166-193.
  - Impact: Legacy or injected execution adapters can produce confident but false per-asset evidence and refresh advice even though the compatibility type explicitly permits aggregate-only results.
  - Fix: Preserve aggregate counts, but mark ambiguous non-skip operations `unknown` (or expose only an aggregate compatibility diagnostic) whenever exact operation records are absent. Never assign a failure or success to a named asset without attributable evidence. Add a two-operation mixed-count test that proves no order-based attribution occurs.
  - Requirement: FR1, NFR3.

### Minor

- **The provider command reference and live help still describe a project-only command** (`apps/oat-docs/docs/provider-sync/commands.md:102`)
  - Issue: The command reference says `oat providers set` enables project providers and lists only `--enabled`/`--disabled`; live help repeats “project providers” in `packages/cli/src/commands/providers/set/index.ts:218`. The command now supports explicit `--scope user`, and the dedicated scope page documents its correct syntax.
  - Impact: Users reading the command reference or help may not discover user-scope configuration even though the fixed examples elsewhere are executable.
  - Suggestion: Describe project as the default, list `--scope project|user`, and say that the selected scope's sync config is updated. Keep the existing `--enabled <providers>` and `--disabled <providers>` forms.

- **The provider overview's user-scope rule omits ordinary user agent mappings** (`apps/oat-docs/docs/provider-sync/providers.md:131`)
  - Issue: The scope summary says user scope is “skills, plus the two bundled managed Codex and Cursor role definitions.” The same page correctly shows Claude, Cursor, Copilot, Gemini, and Codex user agent behavior in the provider-specific rows, so this summary contradicts the implemented capability-selected user-agent surface.
  - Impact: Readers can incorrectly conclude that ordinary canonical user agents do not materialize or native-read outside the two bundled extension roles.
  - Suggestion: State that user scope includes skills and capability-supported agents, then separately note that the two bundled managed roles participate only in Codex/Cursor extension expansion.
