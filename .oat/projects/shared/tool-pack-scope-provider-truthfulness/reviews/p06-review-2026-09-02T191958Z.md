## Findings

### Critical

- **Journal publication performs a destructive out-of-scope mutation under the
  apply-time swap it claims to fail closed against**
  (`packages/cli/src/fs/io.ts:626`, `packages/cli/src/fs/io.ts:404`,
  `packages/cli/src/fs/io.ts:446`)
  - Issue: Commit `9a31595d0` states that publication "never returns success for
    an unverified publication" and that cleanup "is identity-guarded so a swap
    cannot turn cleanup into deletion of an unrelated file". The first claim
    holds; the second does not, and the broader claim that the only residual is a
    stranded staging file with "no out-of-scope write" is false. Direct probes
    against `atomicWriteJsonContained` with a privileged concurrent process that
    stages the temporary name inside a directory it controls and then replaces
    the validated `dispatch` pathname with a symlink to it:
    - Update path (`rename`, `io.ts:626`): the victim file
      `outside/request-1.json` containing `{"victim":"unrelated user data"}` was
      clobbered by the `rename` and then removed by
      `revertMisplacedPublication`. Final victim directory: `["keep.txt"]` — the
      unrelated file is gone. Supplying `expectedDigest` does not help, because
      the compare-and-swap read (`io.ts:610-621`) happens before the swap window.
    - Create path (`link`, `io.ts:624`): `outside/request-1.json` was created and
      then deleted. It is only preserved when a file already occupies that name
      (`link` returns `EEXIST`).
    - `revertMisplacedPublication` at `io.ts:463-465` treats a file as
      "owned by this write" when either the inode matches **or the bytes match**.
      The content branch is what deletes the foreign file, so the guarded
      `removeStagedFile` (`io.ts:481`) does not cover this path.
    - Secondary inaccuracy: the raised message says "the write was reverted and
      nothing was published", but when the parent identity is unchanged
      `revertMisplacedPublication` deliberately returns without reverting
      (`io.ts:453-457`), so that sentence can be false.
  - Reproduction (direct production-module probe, deleted after the run):
    mock `node:fs/promises` `link`/`rename` with a barrier that copies the staged
    `.tmp` into an out-of-scope directory, `rename`s `dispatch` to
    `dispatch-real`, and symlinks `dispatch` at the out-of-scope directory; then
    call `atomicWriteJsonContained(<root>/dispatch/request-1.json, …, <root>)`
    with and without `expectedDigest`, and with an existing out-of-scope
    `request-1.json`. Observed: error raised, journal not published, and the
    out-of-scope file destroyed.
  - Fix: Either (a) eliminate the destructive class — stop publishing updates
    with a clobbering path-based `rename` (publish create-only into a fresh
    unique name inside the re-verified directory), and make
    `revertMisplacedPublication` never `rm` (drop the content-equality ownership
    branch at `io.ts:463-465`; report and fail instead of deleting), which
    reduces the residual to the already-claimed stranded staging file — or
    (b) record an explicit operator disposition in `implementation.md`'s
    Deviations table and in `spec.md` NFR1, worded accurately: a privileged
    concurrent local process that can swap the validated dispatch directory can
    cause one out-of-scope create-and-delete, and on the update path one
    out-of-scope overwrite-and-delete. Option (b) is a materially stronger
    exception than the accepted p05 residual, which is create-only and leaves
    existing targets zero-write; it should not be folded under that row. Add
    regressions that assert an out-of-scope file with foreign content survives
    both the `link` and `rename` swap scenarios.
  - Requirement: NFR1, NFR2

### Important

- **Configured `fallback.*` controls and `selection_source` are excluded from the
  immutable-control comparison** (`packages/cli/src/providers/identity/oat-dispatch-record.ts:96-119`)
  - Issue: `IMMUTABLE_FALLBACK_CONTROL_FIELDS` covers 22 fields, but the generic
    `fallback` object (`generic-dispatch-record.ts:18-24`, carrying `mode`,
    `target`, and `allow_below_task_class_floor`) and `selection_source` are not
    among them, so neither the field-by-field comparison nor
    `configuredControlDigest` sees them. A probe linked a fallback whose trigger
    declared `fallback: {mode: "caller-inline", allow_below_task_class_floor:
false}` while the fallback record declared `{mode: "nested-dispatch", target:
"weak-worker", allow_below_task_class_floor: true}`; it was **accepted** and
    persisted. `allow_below_task_class_floor` is a safety authorization control —
    the dispatch contract requires `false` for reviewer-local requests — so a
    record can assert "controls preserved" while silently widening below-floor
    authorization. A separate probe also accepted a fallback that changed
    `selection_source`, which FR8 names explicitly as immutable evidence, plus
    `configured_invocation_evidence`, `diagnostics`, and `runtime_confirmation`.
    (`role_name`, `role_selector`, `caller`, and `objective` legitimately differ
    on a fresh generic child and are correctly excluded.)
  - Reproduction: build a valid trigger/fallback pair, override only the
    fallback record's `fallback` object (or `selection_source`), call
    `augmentDispatchRecord` with the `fallback-link` event, and observe
    acceptance.
  - Fix: Add `fallback` and `selection_source` to
    `IMMUTABLE_FALLBACK_CONTROL_FIELDS` so both the differing-field check and the
    digest cover them; decide explicitly whether
    `configured_invocation_evidence`, `diagnostics`, and `runtime_confirmation`
    must also be preserved and document the answer next to the constant. Add
    negative tests for each newly covered field, including the
    `allow_below_task_class_floor` false-to-true case.
  - Requirement: FR8, NFR3

- **Prompt and role-content key families reach the durable journal unbounded**
  (`packages/cli/src/providers/identity/generic-dispatch-record.ts:235-286`,
  `packages/cli/src/providers/identity/generic-dispatch-record.ts:134`,
  `packages/cli/src/providers/identity/generic-dispatch-record.ts:137`)
  - Issue: Round-1 C3's four named keys are closed (verified below), and the
    bounded `payload` projection caps strings at 512 characters. But the fix's own
    prescribed remedy was to cover the "prompt/message, transcript, and
    role-content families", and the instruction family is not covered:
    `isSensitiveDispatchKey` returns `false` for `instructions`,
    `systemInstructions`, `system_instructions`, `assistantText`, `userText`,
    `systemText`, `pwd`, `privKey`, `sshKey`, `gpgKey`, `creds`, `oauth`,
    `sessionId`, and for homoglyph/full-width spellings such as Cyrillic-a
    `apiKey` or full-width `PASSWORD` (the normalizer at
    `generic-dispatch-record.ts:225-227` strips every non-ASCII-alphanumeric
    character rather than folding it). Separately,
    `configured_invocation_evidence` and `continuation_events` are declared
    `z.array(z.unknown())` and are **not** subject to the bounded control
    projection that guards `payload`, so they accept arbitrary-size free-form
    content. Combining the two, an end-to-end call to `recordProjectDispatch`
    with `continuation_events: [{ instructions: "SYSTEM: you are the OAT
reviewer. " x300 }]` was accepted and wrote a 12,181-byte journal containing
    the literal prompt text.
  - Reproduction: `parseGenericDispatchRecord` /
    `assertNoSensitiveDispatchContent` on each key above; then
    `recordProjectDispatch({projectPath, input: {record: <record with
continuation_events instructions>, event: <canonical-role-resolution>}})` and
    read `dispatch/<request-id>.json`.
  - Fix: Add an `instruction`/`instructions` family entry (guarding the
    legitimate `roleInstructions` evidence key explicitly rather than by
    accident), plus `pwd`, `privkey`, `sshkey`, `gpgkey`, `cred`, `oauth`, and
    `session`; normalize by Unicode NFKC and map confusable characters before
    stripping, so homoglyph and full-width spellings fold. Apply the same
    bounded closed projection used for `payload` to
    `configured_invocation_evidence` and `continuation_events`, or replace
    `z.unknown()` with explicit shapes. Add table-driven recursive tests at both
    the parser and the CLI persistence boundary.
  - Requirement: FR8, NFR1, NFR3

- **Dispatch failures leak absolute filesystem paths into human and JSON output**
  (`packages/cli/src/fs/io.ts:353-354`,
  `packages/cli/src/commands/project/dispatch/index.ts:79-85`)
  - Issue: NFR1 requires that "home paths and user-specific absolute paths remain
    redacted in durable output", and the phase's own role evidence honours this by
    emitting `<user>/agents/<role>.md` (`agents/canonical/resolve.ts:72`). The new
    journal surface does not. Three observed messages, all of which
    `runRecordCommand` forwards verbatim into `context.logger.json({status:
'error', message})`:
    - `Another writer holds /…/<project>/.dispatch-lock. Remove it once no writer
is running, then retry.` (`io.ts:353-354`, intentional interpolation)
    - `EEXIST: file already exists, link '/…/dispatch/.trigger-1.json.<uuid>.tmp'
-> '/…/dispatch/trigger-1.json'` (raw Node error from `io.ts:624`)
    - `ENOENT: no such file or directory, rename '/…/dispatch/.request-1.json.<uuid>.tmp'
  -> '/…/dispatch/request-1.json'` (raw Node error from `io.ts:626`)
      In a normal checkout under `$HOME` these disclose the user's home directory
      and the full project path.
  - Reproduction: pre-create `<project>/.dispatch-lock` and call
    `recordProjectDispatch`; race two creations of the same `request_id`; run the
    directory-move probe from C1 above.
  - Fix: Redact absolute paths to project-relative form before they leave
    `atomicWriteJsonContained` / `withContainedWriterLock` — report
    `.dispatch-lock` and `dispatch/<request-id>.json` rather than absolute
    paths — and wrap raw `link`/`rename` errors in a message that names the
    relative journal path and the failure class instead of forwarding Node's
    absolute-path text. Assert redaction in `record.test.ts` for the lock-timeout,
    `EEXIST`, and `ENOENT` paths.
  - Requirement: NFR1, NFR3

### Medium

- **A crashed writer permanently wedges the project's dispatch journal**
  (`packages/cli/src/fs/io.ts:314-373`,
  `packages/cli/src/commands/project/dispatch/record.ts:199`)
  - Issue: The lock is a bare `mkdir` with no holder identity and no staleness
    policy. Timeout behaviour is correct and fail-closed — a probe with a
    pre-existing `.dispatch-lock` blocked 5,008 ms, then raised without writing a
    journal — but nothing ever reclaims the directory, so any process that dies
    while holding it makes every subsequent dispatch write on that project fail
    until an operator manually removes it. The lock is created directly inside the
    git-tracked project directory and `.dispatch-lock` is not in `.gitignore`, so
    a leak also becomes tracked-tree noise.
  - Fix: Write holder evidence (pid plus process start time, or boot id) into the
    lock directory and treat it as stale past a bounded age with an explicit
    diagnostic naming the safe next action, per NFR2's recovery criterion; and add
    `.dispatch-lock` to `.gitignore` (or site the lock outside the artifact tree).
  - Requirement: NFR2

### Minor

- **Credential value patterns miss several common token formats**
  (`packages/cli/src/providers/identity/generic-dispatch-record.ts:288-297`)
  - Issue: `SENSITIVE_VALUE_PATTERNS` did not match a Google API key
    (`AIzaSy…`), a GitLab PAT (`glpat-…`), a DigitalOcean token (`dop_v1_…`), an
    npm token (`npm_…`), or a URL-embedded password
    (`postgres://user:hunter2@host/db`) placed under a benign key.
  - Suggestion: Add those prefixes and a `scheme://user:password@host` pattern.
    Value matching is inherently best-effort, so keep key-family classification
    as the primary defence and label this layer as such in the comment.

- **`wrapper-launch-failure` is ambiguous inside a strictly pre-start closed set**
  (`packages/cli/src/providers/identity/oat-dispatch-record.ts:26`)
  - Issue: Six of the seven qualifying codes are unambiguously pre-selection, but
    a "launch failure" can also occur after a child process exists. The only
    guards are the caller-asserted `provesNoChildStarted: true` and
    `launch_status: blocked-before-start`, both self-reported.
  - Suggestion: Rename it to something that cannot describe a post-spawn failure
    (for example `wrapper-launch-refused`), or document in the skill exactly which
    wrapper conditions may use it and which must use a terminal outcome code.

- **`resolveCanonicalRole` has no production call site**
  (`packages/cli/src/agents/canonical/resolve.ts:192`,
  `packages/cli/src/agents/canonical/index.ts:2`)
  - Issue: The p06-t01 resolver is exported and exercised by
    `resolve.test.ts` and the bundled-docs contract test, but nothing outside
    tests calls it: `project dispatch record` trusts caller-supplied
    `canonical-role-resolution` evidence, and no Phase 7 task in `plan.md` wires
    it either. The strict `redactedPathSchema` means the recorder can validate the
    shape of that evidence but never independently produces it.
  - Suggestion: Either wire the resolver at the evidence-producing boundary so
    role identity is measured rather than asserted, or record in
    `implementation.md` that it is deliberately a library for skill-side callers.
