## Findings

### Critical

- **Pack update still promotes declared intent into realized placement**
  (`packages/cli/src/commands/tools/update/update-tools.ts:173`)
  - Issue: The new pack-update selector calls
    `hasScopedPackPlacementEvidence()`, whose first condition is
    `inventory.intent.enabled`. A declared-but-absent pack therefore creates an
    update request and can install missing assets. The newly added test even
    ratifies this by expecting a fully missing, intent-only docs pack to be
    repaired. This contradicts p02-t01's rule that new selectors cannot consume
    the deprecated placement semantics, FR1/FR3, and the phase verification
    that declared intent never becomes realized placement.
  - Fix: Gate pack update on `hasScopedPackRealizationEvidence()` or projected
    `knownRealizedScopes`, report a declared-only pack as not installed (with
    its diagnostic), and replace the intent-only repair test with a regression
    proving zero reconcile requests and zero writes.
  - Requirement: FR1, FR3, FR10

- **Install commands never expose the required lifecycle outcome**
  (`packages/cli/src/commands/init/tools/index.ts:760`)
  - Issue: p02-t04 introduced `PackLifecycleOutcome`, and the design's public
    JSON table requires aggregate install to add `lifecycle[]` and reconciled
    per-pack install to add one `lifecycle`. Aggregate success still emits only
    `status`, `installedPacks`, `syncScopes`, and optional `adoptedPacks`; the
    direct command at line 1584 still emits raw `results` without a lifecycle
    projection. As a result, canonical verification and provider-sync partial
    states cannot be represented through the install surfaces that p02 was
    meant to normalize.
  - Fix: Build lifecycle outcomes from the resolved selection, reconcile
    results, changed-scope auto-sync evidence, and post-apply inventory; add
    them to aggregate and direct human/JSON output while retaining every legacy
    field and existing exit behavior. Add success, canonical failure,
    verification failure, and provider-sync partial tests for both paths.
  - Requirement: FR2, FR3, NFR2, NFR3

### Important

- **ProviderScopeContext is defined but bypassed by every production consumer**
  (`packages/cli/src/commands/sync/index.ts:67`)
  - Issue: p02-t03 requires config/detection to be resolved once per scope and
    a `ProviderScopeContext` to be injected into init, sync, status, doctor, and
    provider commands. Production callers only pull adapter and extension
    arrays from `getProviderRegistrations()` and continue using their existing
    config-aware adapter resolution independently. Repository search finds
    `resolveProviderScopeContext()` only in its definition/export and registry
    unit test, so the new activation evidence and capability rows do not govern
    any consumer. This leaves later materialization/reporting work without the
    shared context boundary the plan depends on.
  - Fix: Add a context dependency at each planned consumer boundary, resolve it
    once for each evaluated scope, and derive active adapters/extensions and
    activation evidence from that context. Add the planned registry-only test
    provider coverage so a registration reaches all consumers without a
    command-private edit, while keeping detection outside canonical inventory.
  - Requirement: FR4, NFR3, NFR5

- **Pack-removal lifecycle fabricates final evidence, especially on dry-run**
  (`packages/cli/src/commands/tools/remove/remove-tools.ts:403`)
  - Issue: `removalLifecycleOutcomes()` constructs every requested scope as
    available and absent without re-inventorying it, even when `dryRun` is true
    and no file was removed. It also puts the scopes selected for removal into
    `retainedRealizedScopes`, reversing that field's additive-selection
    meaning. Thus a dry-run against an installed pack reports
    `finalEvidence.realizedPlacement: none`, and applied removal can claim
    verified absence solely from a plan outcome rather than filesystem proof.
  - Fix: Preserve current evidence for dry-run, re-inventory after applied
    removal before reporting final evidence, and represent retained scopes only
    as scopes proven to remain. If removal needs a different selection model,
    introduce an explicit removal projection rather than overloading retained
    install semantics. Add pack dry-run and partial-removal regression tests.
  - Requirement: FR1, FR3, NFR2, NFR3
