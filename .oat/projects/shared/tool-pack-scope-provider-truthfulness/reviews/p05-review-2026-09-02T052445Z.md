## Findings

### Critical

- **Pre-publication cleanup can delete a foreign replacement at the recovery path**
  (`packages/cli/src/commands/shared/agents-md.ts:513`)
  - Issue: After linking the original inode to the randomized recovery name,
    `writePlannedContent()` records only the boolean `recoveryExists`. If
    validation then fails, the `finally` block unconditionally removes that
    pathname whenever publication did not occur; it does not verify that the
    pathname still names the hard link OAT created. A deterministic injected
    filesystem reproduction replaced the recovery link immediately before its
    first `lstat`. The helper rejected with `AGENTS.md content changed before
mutation.`, the public original remained live, but `recoverySurvived` was
    false because line 514 deleted the foreign replacement. The same common
    path is used for direct and contained-symlink targets. This violates NFR1's
    P0 unmanaged-content preservation and fail-closed requirements.
  - Fix: Bind cleanup to the exact recovery inode created at line 484. If the
    runtime cannot conditionally unlink that identity, preserve the pathname
    and return an explicit recovery-required/blocked result rather than using a
    path-based `rm`. Apply the same identity-safe rule to every temporary or
    recovery cleanup that can race with a replacement.
  - Bounded verification: Add direct-file and contained-symlink tests that
    replace the recovery pathname with a regular file and a symlink at each
    pre-publication validation/cleanup boundary. Assert the foreign bytes and
    public original both survive, the result is blocked/recovery-required, no
    absolute path is emitted, and no subsequent cleanup deletes either object.
  - Requirement: NFR1 (P0), NFR2 (P0)

- **Shared-helper consumers report success after a recovery-required publication**
  (`packages/cli/src/commands/docs/init/index.ts:268`)
  - Issue: The new result variant was handled by aggregate tools and registered
    workflows, but not globally as p05-t01 requires. Docs init logs
    `AGENTS.md docs section recovery-required` only in human mode and then sets
    exit code 0; in JSON mode its `status: ok` payload is emitted before the
    helper call and the recovery result is omitted. PJM init ignores both
    upsert results at `packages/cli/src/commands/pjm/init.ts:205-214`, after
    which the registered command emits `status: ok`. Decision init includes the
    two action strings but still emits top-level `status: ok` and exits 0 at
    `packages/cli/src/commands/decision/index.ts:164-182`. An injected docs
    command reproduction returned `recovery-required` from the real dependency
    seam and observed `exitCode: 0` with only `{status:"ok"}`. These commands
    can therefore mutate the public file and leave hidden retained originals
    while claiming ordinary success, contrary to FR6 and NFR2's partial-failure
    reporting contract.
  - Fix: Make recovery-required a structured, non-success outcome at every
    helper consumer. Delay each command's final JSON/human success report until
    guidance results are known; report the completed scaffold/adoption layer as
    partial, the guidance layer as recovery-required/blocked, and exit nonzero.
    PJM must collect both section outcomes without converting the first recovery
    into an unreported intermediate state.
  - Bounded verification: Add actual registered CLI tests for `oat docs init`,
    `oat pjm init`, and `oat decision init` with an existing direct file and a
    contained symlink. For human and JSON modes, assert nonzero exit, exactly
    one final structured partial outcome, explicit completed versus blocked
    layers, retained recovery evidence, unchanged scope/adoption semantics, and
    no ordinary `status: ok`.
  - Requirement: FR6 (P0), NFR2 (P0)

### Important

- **Recovery evidence is anonymous and an unresolved recovery becomes success on rerun**
  (`packages/cli/src/commands/shared/agents-md.ts:519`)
  - Issue: `UpsertSectionResult` carries only the action string, so callers
    cannot identify the randomized hidden recovery artifact or give a safe next
    action. A temporary-directory reproduction updated an existing file and
    received `recovery-required` with one retained `.recovery` file; an
    immediate identical rerun returned `no-change` while that file remained and
    the result contained no recovery evidence. The aggregate e2e test currently
    codifies exit 1 followed by exit 0 without resolving the retained original.
    For contained symlinks, “preserved beside AGENTS.md” is additionally
    ambiguous because the artifact is beside the resolved target. This is not
    the actionable, convergent recovery state required by NFR2.
  - Fix: Return a redacted repository-relative recovery identifier and a safe
    resolution action, and persist enough identity-bound state to rediscover
    unresolved recoveries. A rerun must remain explicitly recovery-required
    until the retained original is deliberately reconciled or removed; it must
    not silently downgrade to `no-change` merely because the public generated
    bytes are current.
  - Bounded verification: Cover direct and contained-symlink first update,
    repeated run before resolution, explicit recovery resolution, name
    collision, and multiple recoveries. Assert the artifact stays contained,
    its identity/mode/ownership matches the original, output names it only by a
    redacted actionable identifier, and ordinary success occurs only after
    resolution.
  - Requirement: FR6, NFR2

- **Successful publication changes user bytes and permissions outside the managed section**
  (`packages/cli/src/commands/shared/agents-md.ts:566`)
  - Issue: Both upsert branches run a whole-file
    `.replace(/\n{3,}/g, '\n\n')`, so blank-line runs in user prefix,
    interstitial, or suffix content are collapsed even when they are outside
    every managed range. The temporary file is created with `targetMode`, but
    creation mode is masked by the process umask and never restored. A concrete
    update of a mode `0666` file with four user-owned newlines returned
    `recovery-required`; the public version collapsed the user spacing and had
    mode `0644`, while the retained original remained byte-exact at `0666`.
    Thus the original is recoverable, but the live generated version contradicts
    FR6's unrelated-content preservation and the documented promise that
    accepted updates preserve unrelated content.
  - Fix: Splice only the validated managed ranges and add only the minimal
    separator needed at the insertion/removal boundary; never normalize the
    whole document. After exclusive temporary creation, explicitly restore the
    validated target permission bits (and preserve supported ownership/metadata
    or block with recovery guidance when that cannot be done safely) before
    publication.
  - Bounded verification: Add byte-for-byte prefix/interstitial/suffix fixtures
    containing three-plus newlines for update and legacy migration, plus direct
    and contained-symlink mode tests under a restrictive umask. Assert public
    unrelated bytes and intended metadata remain exact and the recovery hard
    link still retains the original identity/mode/ownership.
  - Requirement: FR6 (P0), NFR1 (P0)

- **Recovery filesystem failures leak absolute user paths**
  (`packages/cli/src/commands/init/tools/index.ts:883`)
  - Issue: Filesystem errors from temporary/recovery `writeFile`, `link`,
    `rename`, and cleanup propagate with their absolute source/destination
    paths. Aggregate and workflows guidance append `error.message` verbatim to
    the user-facing blocked reason; docs, PJM, and decision error paths do the
    same. An injected recovery-link `EPERM` reproduced a message containing the
    full temporary repository path and randomized recovery filename. Normal
    recovery output is redacted only because it discards all path evidence, not
    because the error boundary sanitizes it. This violates NFR1's explicit
    redaction requirement.
  - Fix: Convert low-level publisher failures into structured error codes with
    redacted repo-relative targets and safe actions. Sanitize both human and JSON
    error rendering at every helper consumer; do not relay raw Node filesystem
    messages or absolute recovery/temp names.
  - Bounded verification: Inject failures for temporary create, recovery link,
    revalidation, publish, and cleanup through aggregate, registered workflows,
    docs, PJM, and decision commands. Assert human/JSON parity, useful failed
    layer and next action, and absence of repo root, home path, UUID filename,
    or other user-specific absolute path.
  - Requirement: NFR1 (P0), NFR2 (P0)
