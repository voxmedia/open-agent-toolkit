### Assessment of the Three Flagged Bound Consequences

- **(a) The 64 KiB whole-record ceiling.** Right call. A record built with
  deliberately generous but realistic content — 20 diagnostic lines, 40
  candidates, 10 evidence entries, 10 structured continuation events —
  measures **3,751 bytes against 65,536**, roughly 17x headroom. The ceiling
  rejects rather than truncates, and the message names the actual byte count, so
  a Phase 7 caller that somehow reaches it is told exactly what happened. The
  alternative was demonstrably exploitable: round 3 persisted a 2.05 MB journal
  revision through chunking. A dispatch record is provenance metadata, not a
  document, and capping it is the correct contract. Nothing in `spec.md` or
  `design.md` states or implies an unbounded record; `design.md` says nothing
  about record size at all, so the bound fills a gap rather than contradicting
  one. The only residual is that callers cannot read the limit anywhere
  (Minor above).

- **(b) `identifier()` at 256 chars on `model_selector`.** Right call, and the
  concern does not survive contact with the contract. "Preserve opaque
  selectors byte-for-byte" (`record-schema.md:194`) is a prohibition on
  _transforming_ the alias — no normalization, no case folding, no truncation —
  and the code stores it verbatim. A length bound rejects the record whole; it
  never produces a silently altered selector, so the preservation guarantee is
  intact for everything it admits. I probed the longest realistic alias I could
  construct, a 137-character Bedrock provisioned-throughput ARN
  (`anthropic.claude-opus-5-…:provisioned-model/abcdefghij`), and it was
  accepted with ~119 characters to spare. 256 is roughly 2x the worst realistic
  case.

- **(c) The fail-closed normalizer.** Right call, and **the implementer's stated
  consequence is stricter than what shipped**. The claim that it "rejects any
  key containing a non-ASCII character" is not accurate: NFKD plus
  combining-mark removal folds accented Latin cleanly, so
  `naïve_field` → `naivefield` and `schlüssel` → `schlussel` both classify as
  **not sensitive** and pass. What actually fails closed is a key that will not
  fold to Latin at all — `модель` → `moe` and `モデル` → ``are both flagged.
So the real rule is "keys must fold to Latin/ASCII", which is materially
narrower than "reject any non-ASCII character" and is correct for this
surface: the schema is`.strict()`with snake-case ASCII field names, and the
only free-key container is`payload`, which carries provider sandbox and tool
control names. A genuinely internationalized field name in a non-Latin script
would be rejected, but nothing in this contract produces one. Failing closed
is the right posture for a control whose job is catching accidental
well-named secret fields, and the comment at
`generic-dispatch-record.ts:363-372` explains the reasoning honestly.

### `MUTABLE_FALLBACK_CONTROL_FIELDS` — Sound or Dead Weight?

Sound, and load-bearing despite having no production consumer. Two mechanisms
depend on it. First, `as const satisfies readonly (keyof GenericDispatchRecord)[]`
makes every entry compile-time-checked against the schema type, so a renamed or
removed field breaks the build. Second, the completeness test
(`oat-dispatch-record.test.ts:547-557`) asserts
`[...IMMUTABLE, ...MUTABLE].sort()` **equals** the sorted schema key list and
that the union has no duplicates — a partition assertion that is impossible to
write with the immutable list alone, which could only ever prove
`immutable ⊆ schema`. I verified the partition independently: 46 schema fields,
31 immutable, 15 mutable, union 46, zero uncovered, zero overlap, zero entries
not in the schema. Adding a generic field without recording a mutability
decision now fails a test rather than silently defaulting to mutable, which is
exactly the failure mode round 3's M2 described. This is an executable
specification, not dead code, and the comment at
`oat-dispatch-record.ts:169-172` says so.
