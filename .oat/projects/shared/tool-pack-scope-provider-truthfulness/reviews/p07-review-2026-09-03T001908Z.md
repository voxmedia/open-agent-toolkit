**2. The O(1) bound is sound — I attacked it eight ways and could not break it.**
The claim under test is that projection cost is bounded by entry count because
per-entry work is bounded. Measurements, with every large structure built
_outside_ the timer:

```text
attack                                         parser     production   result
5M-element array at read key payload.id          0.1ms            —    typeof gate, rejected
64 MiB string at read key payload.id            13.2ms            —    linear, then length-capped
64 MiB string at read key agent_path             0.1ms            —    length check precedes split
64 MiB whitespace-padded string at payload.id   79.3ms            —    trim() is the only O(n) read
2,000,000 keys on one metadata payload           0.3ms         2.8ms   fixed key reads, unaffected
200k-deep nesting under an unread entry key      0.1ms         1.1ms   never traversed
500k-deep nesting inside entries                    —          0.5ms   never traversed
5,000 maximal session_meta entries              25.1ms            —    bounded
5,001 entries                                    0.0ms            —    degrades, reason names the limit
baseline (2 entries)                             0.0ms         0.5ms
```

The docstring's phrasing ("each value read is length-capped at 256 characters")
is slightly imprecise — `observationIdentifier` calls `value.trim()` _before_ the
length check (`oat-dispatch-record.ts:362-365`), so a huge string at a read key
is scanned once. But the security conclusion holds and is stronger than the
docstring claims: the sum of all read-field lengths is bounded by the input size,
which `JSON.parse` in `runRecordCommand` (`index.ts:111`) has already paid in
full before the bound is ever consulted. Cost is O(input), never amplified.
`agentPathDepth` guards its `split('/')` behind a 1024-char check
(`codex-runtime-observation.ts:136`), and `OBSERVATION_IDENTIFIER_PATTERN` has no
nested quantifier, so there is no ReDoS surface.

**Removing the byte bound reopened nothing** — it strictly reduced work.
`JSON.stringify(entries)` was itself O(input) _in addition to_ the parse already
paid, and it doubled peak memory. Entry count is O(1). The **17 MiB unread field
is genuinely never traversed**: behind a getter that records access, the getter
