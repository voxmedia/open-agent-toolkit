  - Issue: For a manually cleared collection and configured `symlink`, the
    collection transaction re-proves absence, detaches ownership, and persists
    it at lines 580-600 and 663-669. The deferred child then checks provider
    ancestry at line 928, but `applyEntry` calls `createSymlinkNoClobber` after
    that check. That primitive calls recursive `mkdir` and path-based `symlink`
    at `packages/cli/src/fs/io.ts:147-152`; neither operation is bound to the
    identities just checked. A deterministic probe performed the production
    safety check, replaced `.claude` with a symlink to an external directory,
    then invoked the production no-clobber primitive. It returned success and
    created `outside/skills/s` as a symlink (`outsideCreated: true`). In the
    full executor, that success also advances `nextManifest` and can persist a
    false per-entry ownership claim. No-clobber protects only the final child
    name; it does not prevent parent traversal. The integration case at
    `packages/cli/src/engine/engine.integration.test.ts:631-640` asserts the
    symlink release succeeds but does not replace a parent between validation
    and publication.
  - Fix: Treat deferred directory symlink transitions as unavailable unless
    creation is performed relative to an identity-bound, non-following parent
    primitive. On the current runtime, preserve the collection/block evidence
    and fail before detachment/publication, as directory copy now does. Add an
    apply-path regression that swaps both the provider parent and the newly
    created collection directory after safety validation and proves zero
    external/provider writes, zero per-entry ownership, preserved collection
    evidence, and actionable recovery. If an explicit external-ownership
    disposition is the only safe release, expose and document that exact
    disposition instead of recommending `symlink` as safe.
