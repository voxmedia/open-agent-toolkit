- **Apply-time extension evidence overwrites the compatibility plan operations** (`packages/cli/src/commands/sync/apply.ts:309`)
  - Issue: `Object.assign(summary, result)` copies `MaterializationApplyResult.operations` over `MaterializationExtensionSummary.operations`. The former contains result records with `status` and no `reason` (`packages/cli/src/providers/shared/materialization-extension.ts:36`), while the latter is the planned-operation array required by the public summary type (`packages/cli/src/commands/sync/sync.types.ts:95`). Real Codex/Cursor extensions now return result operations, so an apply run loses plan reasons: human extension output renders `undefined` at `apply.ts:225`, and the Codex compatibility JSON maps an absent `reason` at `apply.ts:332`. Current sync tests avoid the defect by returning apply results without `operations` in the compatibility assertions.
  - Impact: Successful runs produce internally inconsistent human/JSON evidence, and adding the required per-operation result evidence breaks the pre-existing compatibility surface.
  - Fix: Keep planned `operations` immutable, store apply evidence under a separate `operationResults` field, and copy only counts plus that evidence into the summary. Add a real apply-result fixture that includes operations and asserts plan reasons and result statuses both survive.
  - Requirement: FR1, FR4, NFR3.

- **Status and doctor still treat Claude user-agent materialization as unavailable** (`packages/cli/src/commands/status/index.ts:1173`)
  - Issue: Status declares user managed-role materialization only when Codex or Cursor is active (`status/index.ts:1173-1182`), and doctor applies the same Codex/Cursor-only extension test (`packages/cli/src/commands/doctor/index.ts:1117-1127`). Phase 3 deliberately materializes Claude reviewer/implementer agents through Claude's core user mapping, but that evidence never reaches the compatibility diagnostic. Status also scans user canonical content through its default scope filter (`status/index.ts:860-865`, `status/index.ts:955-963`), which still excludes user agents, so it cannot report Claude user-agent drift through the ordinary provider report either.
  - Impact: A successfully synced active Claude installation can still receive `user-agent-unmaterialized`, or omit its agent drift entirely. This contradicts the p03-t03 requirement to derive the compatibility summary from richer provider evidence and breaks agreement among sync, status, and doctor.
  - Fix: Replace the provider-name boolean with per-provider/content materialization evidence that includes both core entry-sync and extension-owned roles. Feed capability-selected user agent targets into status scanning, then add active-Claude status/doctor tests alongside the existing Codex/Cursor and unsupported-provider cases.
  - Requirement: FR3, FR4.

- **The sourced Claude refresh policy contradicts the cited official contract** (`packages/cli/src/providers/shared/registry.ts:93`)
  - Issue: The registry assigns every Claude agent change a `manual-refresh` policy, and the adviser recommends `/agents` (`packages/cli/src/providers/shared/restart-adviser.ts:106`). The cited current [official Claude Code subagent documentation](https://code.claude.com/docs/en/sub-agents) instead says existing agents directories are watched and changes load within seconds without restart; a restart is needed only for the first agent in a directory absent at session start, agents under `--add-dir`, or sessions using `--disable-slash-commands`. It also says `/agents` no longer opens the creation wizard as of v2.1.198. The same stale claim is published in `apps/oat-docs/docs/provider-sync/providers.md:16` and `apps/oat-docs/docs/provider-sync/scope-and-surface.md:72`.
  - Impact: Most successful changes receive unnecessary and ineffective `/agents` advice, while the first-new-directory case that truly needs restart receives weaker advice. The dated provenance therefore makes the lifecycle guidance look more authoritative while being false.
  - Fix: Model the documented conditional state (existing watched directory versus first new directory and exceptional launch modes), or keep the policy `unknown` until the current evidence model can represent those facts. Remove `/agents` as refresh recovery, update both docs pages, and test watched-directory and first-directory cases.
  - Requirement: FR1, FR7, NFR3.
