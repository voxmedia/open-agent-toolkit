### Minor

- **The staleness policy reclaims a provably live holder past the hard cap, and
  the constant's comment says the opposite** (`packages/cli/src/fs/io.ts:311-312`,
  `packages/cli/src/fs/io.ts:380-397`)
  - Issue: `WRITER_LOCK_HARD_STALE_MS` is documented as "A lock older than this
    is reclaimed even when liveness **cannot be decided**", but
    `writerLockStaleReason` returns the cap reason whenever the holder is _not_
    provably dead, including when `holderIsRunning` proved it alive. Probed: a
    holder recording this host's token and this process's live pid, aged 20
    minutes, is reclaimed. The behaviour is defensible — a dispatch write is
    sub-second, so a 15-minute holder is effectively hung, and the revision CAS
    keeps the journal correct either way — but the comment under-describes it
    and a reader auditing NFR2 would draw the wrong conclusion.
  - Suggestion: Reword the constant to state that the cap reclaims _any_ lock
    past the bound, including a live one, and name the CAS as the invariant that
    makes that safe. Everything else in the policy probed correct: a live holder
    at 2 s is never reclaimed, a dead pid at 2 s is, a lock below the 1 s
    minimum is not, a missing or garbage holder file is not reclaimed on age
    alone before the cap, `pid 1` (`EPERM`) reads as alive, and a foreign
    `hostId` falls back to the cap rather than to a meaningless pid check.

- **Unmapped non-ASCII characters are silently deleted during key
  normalization, so small-capital and diacritic spellings evade the family
  denylist** (`packages/cli/src/providers/identity/generic-dispatch-record.ts:281-287`)
  - Issue: The comment at line 230-234 correctly identifies the hazard —
    "Stripping non-ASCII characters would silently delete a homoglyph and unmask
    nothing" — but the mitigation is a 34-entry map, so anything outside it is
    still stripped. Every vector round 2 named is now closed (Cyrillic-a
    `apiKey`, full-width `ａｐｉｋｅｙ`, Greek-omicron `passwοrd`, math-bold
    `𝖠𝗉𝗂𝗄𝖾𝗒`, zero-width-joined and separator variants all normalize to the
    denied token), but `ᴘᴀssᴡᴏʀᴅ` normalizes to `ss`, `ᴀᴘɪᴋᴇʏ` to `i`, and
    `pàssword` to `pssword`, all of which pass. Attacker value is low — a caller
    who wants to hide a secret can simply name the key `foo`, which this layer
    cannot catch either — so the practical loss is nil; the control's real job
    is catching _accidental_ well-named fields, and that job is done.
  - Suggestion: Fail closed instead of extending the map: if the NFKC-folded,
    confusable-mapped key still contains any non-`[a-z0-9]` character that is
    not a recognized separator, treat the key as sensitive. Applying NFKD and
    dropping combining marks would additionally fold the diacritic case.

- **`removeStagedFile` can unlink an attacker-created alias to this call's own
  staged inode** (`packages/cli/src/fs/io.ts:616-634`)
  - Issue: Cleanup is bound to inode identity, which is the right primitive and
    is why the round-2 Critical is closed. One residual: if a privileged
    concurrent process hard-links the staged `.tmp` into a directory it controls
    and then swaps the `dispatch` pathname at it, the cleanup's identity check
    passes and it unlinks that alias. No data is destroyed — the inode remains
    linked from the real directory, and no pre-existing foreign file can ever
    match, since a distinct file has a distinct `dev`/`ino` pair — so this does
    not weaken the stated guarantee. It is worth a sentence in the function's
    doc comment so a future reader does not mistake "removes only the inode this
    call created" for "removes only names this call created".
  - Suggestion: Extend the `removeStagedFile` comment, or additionally require
    the parent directory identity to be unchanged before removing.
