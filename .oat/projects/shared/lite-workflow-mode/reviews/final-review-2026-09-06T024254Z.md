- **p06-t08 routing fix never fires for a real promoted project; the test fixture encodes a field the artifact never carries** (`packages/control-plane/src/recommender/router.ts:106`)
  - Issue: the new branch checks `currentArtifact?.readyFor`, and
    `currentArtifact` is the parsed `discovery.md`. The control-plane populates
    artifact `readyFor` only from that file's `oat_ready_for` frontmatter
    (`packages/control-plane/src/state/artifacts.ts:48`); it never reads
    `state.md`'s `oat_ready_for`. Promotion renders `discovery.md` from the
    discovery template without touching that key
    (`packages/cli/src/commands/project/promote/promote.ts:219`), so the file
    carries `oat_ready_for: null`, and the promote suite asserts exactly that
    (`promote.test.ts:97`). Only `renderQuickState` (`promote.ts:245`) sets
    `oat_ready_for: oat-project-quick-start`, on `state.md`, which the
    recommender does not consult. The router test passes because its fixture
    places `readyFor` on the discovery artifact
    (`packages/control-plane/src/recommender/router.test.ts:138`), a state no
    shipped code path produces. The neutralized-branch negative control
    recorded for p06-t08 therefore proves only that the fixture toggles the
    assertion, not that the defect is fixed.
  - Reproduction (built CLI from this head, isolated `HOME`, temp repo):
    `oat project new demo --mode lite --scope shared`, author the five
    sections, commit, `oat project promote .oat/projects/shared/demo --to quick
--json` returns `promoted`; then `oat project status --project-path
.oat/projects/shared/demo --json` reports `recommendation.skill:
"oat-project-discover"` with reason "Route quick discovery work based on
    boundary tier". `discovery.md` frontmatter shows `oat_status: in_progress`
    and `oat_ready_for: null`; `state.md` shows `oat_ready_for:
oat-project-quick-start`. The same result occurs for `--scope local`. The
    dashboard path (`packages/cli/src/commands/state/generate.ts:365`) keys
    on `state.readyFor` and routes to quick-start, so the inconsistency the
    prior gate review reported is unchanged.
  - Why Important rather than Medium: the underlying routing defect was rated
    Medium in the prior gate review, but this pass ships a fix that is inert,
    a regression test that pins a non-existent state, and closeout records
    (`implementation.md:466`, the p06-t08 commit message, and the prior auto
    review's "resolved" verification) that misstate the release. Design §5
    step 6 and §4 ("progress, next, open, and the dashboard know what to run
    next") remain unmet for promoted projects, and future maintainers would
    read the green test as coverage.
  - Fix: make the promoted `discovery.md` carry the readiness signal so the
    parsed artifact matches `state.md`. In `renderDiscovery`, set the rendered
    frontmatter's `oat_ready_for` to `oat-project-quick-start` (keeping
    `oat_status: in_progress` is acceptable because the new router branch
    deliberately does not require `status === 'complete'`). Update the
    promote-suite discovery expectation at `promote.test.ts:97` accordingly.
    Replace the router fixture with one derived from a real promoted
    `discovery.md`, record that provenance in the test, and add one CLI-level
    control that runs promote against a temp repository and then asserts the
    control-plane recommendation is `oat-project-quick-start`. Re-run the
    reproduction above and confirm the neutralized-branch control fails
    through the real artifact path. Alternatively, if the team prefers the
    router to honor `state.md`, expose the state-level `oat_ready_for` through
    the control-plane parser and branch on that; either approach must be
    proven against a real promoted project, not a hand-built fixture.
  - Requirement: Design §5 step 6 (promoted state "ready for quick-start"),
