### Important

- **`oat project promote` mutates a local-scope Lite project and then reports `persistence-failed`** (`packages/cli/src/commands/project/promote/promote.ts:266`)
  - Issue: `persistPromotion` treats every non-synced scope as committable and
    runs `git add -- <project files>` at line 291. Local projects live under
    `.oat/projects/local/**`, which the scaffolder itself adds to `.gitignore`,
    so `git add` exits 1 with "The following paths are ignored by one of your
    .gitignore files". By that point `discovery.md`, `references/lite-plan.md`,
    a fresh quick `plan.md`, and the quick `state.md` have all been written, so
    the command returns `{ status: "refused", reason: "persistence-failed",
files: [four files] }` and exit 1 for a project that is now fully promoted on
    disk. The scaffolder's own convention (`scaffold.ts:916`) commits only for
    `shared` and pushes only for `synced`; local scope skips git entirely. The
    Lite skill's Step 3.5 treats a non-zero promote as failure and continues
    Lite execution against what is now a quick project with a placeholder plan.
  - Reproduction: in a temp repository, `oat project new demo --mode lite
--scope local`, author the five sections, then `oat project promote
.oat/projects/local/demo --to quick --json`. Observed: `persistence-failed`,
    exit 1, all four files present, `state.md` already at `oat_workflow_mode:
quick`. The same steps with `--scope shared` return `promoted` and commit
    `chore(oat): promote demo to quick`.
  - Fix: in `persistPromotion`, return without any git operation when
    `scope === 'local'` (mirroring the scaffolder) and report `promoted`. Add a
    local-scope promote test that asserts no `git add`/`commit` call and a
    `promoted` result, and keep the existing shared/synced positive controls.
    Update the `cli-reference.md` promote paragraph if the JSON contract gains
    a persistence note.
  - Requirement: Design §5 "Commit by scope with the fail-closed resolver" and
    Error Handling "never commits a half-promoted project"; discovery Success
    Criterion "A lite project can be promoted in place to quick without losing
    interview content" (content is preserved, but the reported outcome is
    wrong and the entry skill acts on it).

### Medium

- **Promoted project is routed to `oat-project-discover` by the recommender while state says ready for quick-start** (`packages/control-plane/src/recommender/router.ts:295`)
  - Issue: `renderDiscovery` (`promote.ts:219`) renders `discovery.md` from the
    template with `oat_status: in_progress` and `oat_ready_for: null`, and
    `renderQuickState` sets `state.md` to `discovery`/`complete`/
    `oat_ready_for: oat-project-quick-start`. The recommender computes the
    boundary tier from the artifact (in-progress, no placeholders → tier 2),
    looks up `discovery:complete:2`, finds no quick route, and falls back to
    `CURRENT_PHASE_SKILLS` → `oat-project-discover`. The dashboard
    (`state/generate.ts:368`) special-cases the same state and routes to
    `oat-project-quick-start`. `oat project status`, `oat-project-progress`,
    and `oat-project-next` therefore disagree with `.oat/state.md` and with the
    Lite skill's "point to `oat-project-quick-start`" handoff.
  - Reproduction: after the shared-scope promotion above, `oat project status
--json` reports `recommendation: { skill: "oat-project-discover", reason:
"Route quick discovery work based on boundary tier" }`.
  - Fix: add the same `readyFor === 'oat-project-quick-start'` branch to the
    recommender (the parsed state already exposes `readyFor`,
    `control-plane/src/types.ts:44`) so both next-step surfaces agree, with a
    router test for the promoted state. Alternatively render the promoted
    `discovery.md` as `oat_status: complete`, but that alone routes tier 1 to
    `oat-project-plan`, not quick-start, so the router branch is the smaller
    consistent fix.
  - Requirement: Design §5 step 6 (state "ready for quick-start") and Design
    §4 "progress, next, open, and the dashboard know what to run next".

### Minor

- **The Lite plan template ships a second-phase review row** (`.oat/templates/plan-lite.md:132`)
  - Issue: the Reviews table seeds `p01` and `p02` code rows although a Lite
    plan must have exactly one phase (`validateLitePlan`). Nothing consumes
    the extra pending row, but it invites authors to leave a phantom `p02` row
    or, worse, to add a second phase to match it.
  - Fix: drop the `p02` row from `plan-lite.md` (and the bundled CLI asset
    copy) so the seeded table matches the single-phase invariant.
