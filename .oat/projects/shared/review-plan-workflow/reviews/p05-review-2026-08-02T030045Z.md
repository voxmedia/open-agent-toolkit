### Important

- **Gate launch-attempt correlation is published but never consumed, so
  accounting-invalid translation cannot fire end-to-end**
  (`packages/cli/src/commands/gate/index.ts:3269`)
  - Issue: `runReviewGate` mints `launchAttemptId` and publishes it to the child
    as `OAT_GATE_LAUNCH_ATTEMPT_ID` (`packages/cli/src/commands/gate/index.ts:3269`)
    and as `oat_gate_launch_attempt_id` in the prompt frontmatter
    (`packages/cli/src/commands/gate/index.ts:577`), then queries the private
    index with that exact tuple
    (`packages/cli/src/commands/gate/index.ts:3291-3294`). Nothing consumes
    either channel: a repository-wide search for `OAT_GATE_LAUNCH_ATTEMPT_ID`
    and `oat_gate_launch_attempt_id` outside `gate/index.ts` and its own test
    returns no hits, and `oat review prepare-context` reads `gateRunId` and
    `launchAttemptId` only from JSON stdin
    (`packages/cli/src/commands/review/prepare-context.ts:67-68`). The three
    canonical coordinator skills that p05-t03 just edited tell the coordinator
    to invoke `prepare-context` "for the authoritative range, sink, invocation,
    and already-resolved outer budget"
    (`.agents/skills/oat-project-review-provide/SKILL.md:897-901`) and never say
    that a gate-originated review must forward the two correlation IDs or where
    to obtain them. Because `parsePrepareReviewContextInputV1` rejects
    `invocation: 'gate'` unless both IDs are non-null
    (`packages/cli/src/review/schemas.ts:556-563`), the two reachable outcomes
    are both wrong: the coordinator omits the IDs and downgrades to
    `manual`/`auto`, leaving `preparation.correlation.gateRunId` null so
    `validateStoredReviewOutput` never records a terminal receipt
    (`packages/cli/src/commands/review/validate-output.ts:231-236`) and
    `resolveReviewPlanFailure` always returns null; or it declares
    `invocation: 'gate'` without the attempt ID and preparation throws
    `$/gate correlation does not match invocation`, breaking enforce-mode gate
    review outright. Design assigns the parent half of this handshake
    (`design.md:662-667`) but leaves the child half unassigned, so no phase
    currently owns it.
  - Fix: add the forwarding contract to the canonical coordinator owners — state
    that a gate-originated enforce review must read `oat_gate_run_id` and
    `oat_gate_launch_attempt_id` from the gate prompt frontmatter (or
    `OAT_GATE_RUN_ID`/`OAT_GATE_LAUNCH_ATTEMPT_ID`) and pass both as
    `gateRunId`/`launchAttemptId` with `invocation: "gate"` — or have
    `prepare-context` default them from the environment when `invocation` is
    `gate` and stdin omits them. Either way, add one integration fixture that
    drives gate → `prepare-context` → `validate-output` → gate translation
    against a real `ValidationStore` so the tuple round-trip is pinned rather
    than mocked; today `gate/index.test.ts` only stubs
    `resolveReviewPlanFailure`, and `review-plan-failure.test.ts` only stubs the
    store, so no test crosses the process boundary. If the fix is deferred to
    p06-t06 dogfooding instead, record that decision and the tracking evidence
    explicitly rather than leaving the seam unowned.
  - Requirement: FR9, FR10, NFR3

### Medium

  caller** (`packages/cli/src/review/validation-store.ts:1194`)
  - Issue: `deletePreStartRejectedGateRun` exists with full tests
    (`packages/cli/src/review/validation-store.test.ts:534-600`) but a
    repository-wide search finds no non-test caller. Design states that "a
    pre-start role/launch rejection terminalizes and deletes that pair before a
    fresh attempt receives a new launch-attempt ID" and assigns that to the gate
    parent (`design.md:664-666`), and p05-t04 Step 2 lists "cleanup" among the
    things the tuple must be threaded through (`plan.md:3033-3034`). The gate's
    actual rejection path never calls it: `writeRefusalFailure`
    (`packages/cli/src/commands/gate/index.ts:3312-3337`) reports the refusal and
    returns, and the `finally` block removes only the branch-local CLI and the
    gate run marker (`packages/cli/src/commands/gate/index.ts:3671-3690`).
    Impact is bounded rather than incorrect — a rejected attempt's correlation
    entry and prepared run directory survive until TTL, and the stale pair is
    keyed by a distinct attempt ID so it cannot be confused with the retry — but
    the designed cleanup does not happen.
  - Fix: call `deletePreStartRejectedGateRun(runId, launchAttemptId)` from the
    gate's pre-start rejection path before a replacement attempt is launched,
    tolerating `ENOENT` for legacy mode where no run was ever prepared; or, if
    the gate parent is deliberately not the owner, correct `design.md:662-667`
    to name the actual owner and drop "cleanup" from the p05-t04 step.
  - Requirement: FR9, NFR3

- **`preflightReviewPlan` discards the structured budget diagnostic that
