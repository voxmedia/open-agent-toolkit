## Findings

### Critical

- **C1: Canonical implementation artifacts fail obligation parsing**
  (`packages/cli/src/review/obligations.ts:151`)
  - Issue: `parseDeviationObligations` assumes the first non-empty line after
    `## Deviations from Plan / Design` is a table and requires the obsolete
    `Planned / Expected` seven-column header. The canonical template and this
    project's `implementation.md` include explanatory prose first and use
    `Source Artifact`, `Planned / Documented`, `Reason`, and `Follow-up`
    (`.oat/templates/implementation.md:168`,
    `.oat/projects/shared/review-plan-workflow/implementation.md:604`).
    Direct execution against this project's artifact fails with `Markdown table
rows must begin and end with a pipe`. Because p02-t12 always adds
    implementation obligations when the artifact exists, enforce-mode
    task/phase/final preparation is blocked for canonical projects.
  - Fix: Parse the actual canonical implementation template: locate exactly one
    canonical deviations table within the section, accept its current exact
    headers, preserve placeholder/partial-row fail-closed behavior, and add a
    round-trip test against `.oat/templates/implementation.md` and this
    project's artifact.
  - Requirement / task impact: FR3 (P0), p02-t11, p02-t12, p02-t25, p02-t29.

- **C2: The plan CLI bypasses the strict ReviewPlanV1 parser**
  (`packages/cli/src/commands/review/validate-plan.ts:39`)
  - Issue: The trust boundary checks only that stdin is a non-null object, casts
    it to `ReviewPlanV1`, and passes it to partial semantic validation. It never
    calls the existing strict `parseReviewPlanV1`. Unknown fields and malformed
    nested shapes therefore either reach receipt validation or crash as exit-2
    system errors. The p02-t29 integration fixture itself supplies
    `verificationBoundary.requiredClaims` as `string[]`
    (`packages/cli/src/review/review-lifecycle.integration.test.ts:78`) despite
    the contract requiring `{ kind, mode }[]`, and the lifecycle accepts it.
  - Fix: Run `parseReviewPlanV1` immediately after bounded strict JSON parsing,
    translate schema failures to a stable exit-1 input/contract envelope, and
    add command-level malformed/unknown-field tests plus a spawned lifecycle
    test.
  - Requirement / task impact: FR1 and FR3 (P0), NFR3, p02-t24, p02-t28,
    p02-t29.

- **C3: A denied whole-diff policy does not prevent whole-diff execution**
  (`packages/cli/src/review/plan-validator.ts:227`)
  - Issue: Validation compares only the echoed `plan.wholeDiff` object with the
    sealed eligibility result. It never validates `plan.strategy` or lane
    evidence strategies. A plan can therefore set
    `strategy: whole-diff-inline`, faithfully copy `allowed: false`, obtain a
    receipt, and proceed to evidence. This defeats the central selective-loading
    boundary.
  - Fix: Reject `whole-diff-inline` unless sealed eligibility is allowed and
    require strategy/lane fields to be mutually consistent. Add negative tests
    for every denied eligibility reason.
  - Requirement / task impact: FR4 (P0), NFR4, p02-t16, p02-t23, p02-t24.

- **C4: Gate correlation filenames do not encode an exact tuple**
  (`packages/cli/src/review/validation-store.ts:142`)
  - Issue: The index path concatenates two variable-length, hyphen-permitting
    IDs. `(gateRunId: "a-b", launchAttemptId: "c")` and
    `(gateRunId: "a", launchAttemptId: "b-c")` map to the same file.
    `resolveGateCorrelation` then trusts that path's `runId` without checking
    the loaded run's stored tuple (`validation-store.ts:325`). Independent
    reproduction resolved the second, never-bound tuple to the first run.
  - Fix: Use an injective encoding (for example canonical tuple hashing or
    length-prefixed components), store both IDs in the index record, and verify
    the record and loaded run match the requested tuple before returning.
  - Requirement / task impact: FR1 (P0), NFR3, p02-t18, p02-t25, p02-t29.

- **C5: Repository-local plaintext state bypasses command capabilities**
  (`packages/cli/src/commands/review/prepare-context.ts:39`)
  - Issue: The production command stores validation state at the predictable,
    unignored `$repo/.oat/review-validation` path. The reviewer receives the run
    ID and normally has same-user repository filesystem access. `readRun`
    accepts plaintext JSON after checking only top-level schema/run identity and
    expiry (`packages/cli/src/review/validation-store.ts:221`); it does not
    strictly parse nested state or authenticate transitions. A reviewer or
    injected command can therefore edit phase, accepted-handle, plan, receipt,
    or capability state directly instead of presenting a one-shot token. File
    mode `0600` does not isolate processes running as the same user.
  - Fix: Put authoritative mutation behind a launcher-owned service or
    cryptographically authenticate stored state with a launcher-held secret,
    strictly parse every persisted state load, and keep the store outside the
    repository. Do not claim reviewer non-mutation authorization from same-UID
    file permissions alone.
  - Requirement / task impact: FR1 (P0), NFR3, p02-t17 through p02-t25.

### Important

- **I1: Mutation and lock recovery are not crash-safe**
  (`packages/cli/src/review/review-lifecycle.ts:33`)
  - Issue: Checkpoint and plan validation consume their one-shot capability in
    one store update, then observe/compute and commit the phase/context/receipt
    in a later update (`review-lifecycle.ts:79`, `review-lifecycle.ts:120`,
    `review-lifecycle.ts:142`). A process failure between those updates burns
    the token and leaves an unrecoverable live run. Separately, the global lock
    is an exclusive file removed only in `finally`
    (`packages/cli/src/review/validation-store.ts:106`); a process crash leaves
    `.store.lock` permanently blocking updates, and the reaper ignores it.
  - Fix: Verify-and-consume capabilities in the same atomic mutation that
    commits the checkpoint or receipt, and implement an owner/lease-based stale
    lock recovery protocol with adversarial crash tests.
  - Requirement / task impact: p02-t18, p02-t21, p02-t24, p02-t29; recovery and
    atomic-state milestone.

- **I2: The patch-counting deadline cannot stop a stalled stream**
  (`packages/cli/src/review/patch-estimate.ts:99`)
  - Issue: The deadline is checked only after `for await` receives a chunk. If
    Git or an adapter stops yielding without closing, `next()` can wait forever,
    `stop()` is never called, and preparation exceeds its 5–30 second cap.
    Independent reproduction raced a never-yielding iterator past its deadline
    and returned `deadline-not-enforced`.
  - Fix: Race stream reads/completion against a real timer or abort signal,
    terminate the child at the deadline even when no chunk arrives, await child
    cleanup, and return a lower-bound result.
  - Requirement / task impact: FR2, FR4, NFR4, p02-t05, p02-t06.

- **I3: Lifecycle rejections are emitted as system failures**
  (`packages/cli/src/commands/review/review-json.ts:88`)
  - Issue: Any ordinary `Error` becomes
    `category: system`, `review-json-system-error`, exit 2. Checkpoint replay,
    invalid/consumed tokens, receipt mismatch, pre-validation evidence start,
    expired state, malformed ranges, and budget-floor rejection all currently
    throw ordinary errors. The production commands do not translate these
    expected lifecycle/input cases, contradicting the required deterministic
    0/1/2 envelope contract; raw internal error messages are also copied to
    stdout.
  - Fix: Define typed domain errors at runtime boundaries and translate input,
    contract, and validation rejections to stable safe exit-1 codes/details.
    Reserve exit 2 and sanitized messages for I/O/store corruption/system
    failures.
  - Requirement / task impact: NFR3, p02-t26 through p02-t29.

- **I4: Lane evidence cutoffs are not validated**
  (`packages/cli/src/review/plan-validator.ts:242`)
  - Issue: The validator checks that top-level `timeAllocation` exactly matches
    sealed policy but never reads `lane.deadlineMs`. A lane can be launched
    after the evidence cutoff or even after output deadline while still
    receiving a valid plan receipt.
  - Fix: Validate each lane deadline against the sealed planning/evidence
    interval and require the mode-appropriate null/non-null shape.
  - Requirement / task impact: FR8 (P1), p02-t15, p02-t23.

- **I5: Trusted follow-up commands are pinned to an ambient global binary**
  (`packages/cli/src/commands/review/prepare-context.ts:46`)
  - Issue: The production dependency hard-codes `cli: "oat"`, so a
    branch-local/source `prepare-context` invocation returns commands that may
    execute an older global installation or another PATH entry. The integration
    test only extracts arguments and calls TypeScript functions directly; it
    never spawns the rendered commands.
  - Fix: Carry the exact launcher-owned branch-local executable/argv prefix into
    preparation, render from an argv representation, and add an end-to-end test
    that executes all returned commands against the same candidate build.
  - Requirement / task impact: NFR2, NFR3, p02-t20, p02-t25, p02-t27 through
    p02-t29.

- **I6: The p02-t10 code is correct, but its design grammar is stale**
  (`.oat/projects/shared/review-plan-workflow/design.md:358`)
  - Issue: The design permits only a standalone fully-bold Step line as the
    Files-block terminator, while canonical `plan.md` uses inline prose after
    the bold Step label. The implementation intentionally accepts both and has
    a focused regression test. Reverting the code to the design regex would
    break canonical plan parsing; this is artifact drift, not an implementation
    defect.
  - Fix: Align the design grammar with the implemented
    `^\*\*Step ...\*\*(?: prose)?$` behavior and record the accepted drift in
    the canonical deviation mechanism after C1 is fixed.
  - Requirement / task impact: p02-t10 artifact alignment; no code correction
    required.

### Medium

- **M1: The canonical fixture corpus remains disconnected from its parsers**
  (`packages/cli/src/review/obligation-fixtures.test.ts:23`)
  - Issue: All four parser-dependent corpus checks remain `it.todo` after their
    owning p02-t08 through p02-t11 tasks. The phase's four reported todos are
    exactly these checks. In addition, TypeScript excludes ordinary tests, so
    the malformed `requiredClaims` fixture in the p02-t29 integration test is
    not type-checked. The green suite therefore does not validate the promised
    producer/consumer corpus.
  - Fix: Replace the todos with parser assertions over every source/expectation
    pair and add runtime-schema assertions for integration fixtures (or include
    dedicated compile-time contract fixtures in the TypeScript program).
  - Requirement / task impact: FR3, NFR5, p02-t07 through p02-t11, p02-t29.

- **M2: Requirement Index trailing-content validation stops at one blank line**
  (`packages/cli/src/review/obligations.ts:29`)
  - Issue: If the table is followed by a blank line, then non-heading content,
    the parser accepts it because it checks only `lines[table.endIndex]`. The
    design requires every line through the next level-two heading or EOF to be
    blank, so malformed selected structures can be silently accepted.
  - Fix: Scan the complete post-table interval, permitting only blank lines
    until the next exact level-two heading or EOF, with a regression covering
    blank-then-content.
  - Requirement / task impact: FR3, p02-t09.

- **M3: Command rendering is POSIX-shell-specific**
  (`packages/cli/src/review/command-capabilities.ts:87`)
  - Issue: Single-quote escaping is safe for POSIX shells but not for Windows
    `cmd.exe` or PowerShell, despite the design's platform-safe argv and NFR2
    portability requirements.
  - Fix: Preserve commands as executable plus argv and let the provider adapter
    spawn without a shell, or render with an explicit shell-specific strategy
    selected by the launcher. Add platform contract tests.
  - Requirement / task impact: NFR2, p02-t20, p02-t27 through p02-t29.
