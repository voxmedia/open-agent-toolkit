## Findings

### Critical

- **C1: The reviewer inherits the validation authority key**
  (`packages/cli/src/review/validation-store-authority.ts:82`)
  - Issue: Every production review command reconstructs its
    `ValidationStoreAuthority` from `OAT_REVIEW_AUTHORITY_KEY` in
    `process.env` (`commands/review/prepare-context.ts:47`,
    `checkpoint-artifacts.ts:32`, `validate-plan.ts:36`, and
    `begin-evidence.ts:28`). Returned follow-up commands are executed by the
    reviewer, and `executeCommandInvocation` supplies no scrubbed environment
    by default (`command-invocation.ts:26`), so ordinary child processes inherit
    the same HMAC key. An independent reproduction launched an arbitrary
    shell-free Node child through `executeCommandInvocation`; it read back the
    exact synthetic authority key. A reviewer with the run ID can therefore
    read state, modify phase/capability/plan/receipt fields, recompute the HMAC,
    and replace the authoritative file. If the key is removed from the
    reviewer environment instead, all separate follow-up command processes
    fail at `launcherValidationStoreAuthority`.
  - Fix: Keep the state-authentication key in a launcher-owned service/process
    that is not part of the reviewer execution environment. Route the
    capability-bearing operations through that authority, or use an equivalent
    broker that injects authority only into an isolated trusted command process
    the reviewer cannot repurpose. Add a spawned adversarial test that tries to
    read the authority key and re-sign state from the reviewer environment.
  - Requirement / prior finding: FR1, NFR3, prior C5.

### Important

- **I1: Concurrent stale-lock reclaim can remove a new live owner's lock**
  (`packages/cli/src/review/validation-store.ts:328`)
  - Issue: A contender reads the current lock record, decides it is stale, and
    then unconditionally removes the path at line 344 without verifying that
    the path still names the same inode/nonce. Two contenders can both inspect
    a dead lock; one can remove it and acquire a new lock before the other
    executes `rm`, after which the delayed contender deletes the new live
    owner's lock and enters concurrently. The fixed 30-second lease is also
    never renewed, so a delayed but live owner can be reclaimed. Atomic
    capability transitions and operation-over-cleanup error precedence are
    fixed, but this recovery race still permits concurrent lost updates to
    security-sensitive state.
  - Fix: Reclaim with a compare-and-swap/fencing protocol that proves the stale
    inode and nonce are unchanged at deletion, and reject writes from an owner
    whose fencing token is no longer current. Renew leases or otherwise prevent
    expiration from invalidating a still-active owner. Add deterministic
    concurrent-reclaimer and live-owner-expiry tests.
  - Requirement / prior finding: NFR3, prior I1.

- **I2: Prepare-context input failures still become exit-2 system errors**
  (`packages/cli/src/commands/review/prepare-context.ts:123`)
  - Issue: The command performs only a partial object/budget/correlation check,
    casts the result to `PrepareReviewContextInput`, and calls production
    preparation. Invalid ranges and budget-floor rejection still throw plain
    `Error` values at `review/prepare-context.ts:69` and
    `review/budget.ts:30`. `runReviewJsonCommand` consequently maps them to the
    generic exit-2 `review-json-system-error`. An independent command-boundary
    reproduction with a malformed range returned exactly that system envelope.
    This leaves two cases explicitly named by prior I3 unresolved and also
    permits malformed nested prepare input to reach production code.
  - Fix: Strictly parse the complete prepare input at the CLI boundary and map
    deterministic range, budget, scope, obligation-source, and correlation
    rejections to stable safe exit-1 input/contract codes. Keep exit 2 only for
    actual I/O, corruption, and unexpected runtime failure.
  - Requirement / prior finding: NFR3, prior I3.

- **I3: Source-mode follow-up commands drop the active TypeScript loader**
  (`packages/cli/src/commands/review/prepare-context.ts:43`)
  - Issue: The default launcher identity is only `process.execPath` plus
    `process.argv[1]`; it omits the resolved loader arguments in
    `process.execArgv`. Under the documented `pnpm run cli:source` path this
    renders `node packages/cli/src/index.ts ...`. An independent reproduction
    showed that exact launch fails with `ERR_UNKNOWN_FILE_EXTENSION`, while the
    source CLI succeeds through `tsx`. The new tests spawn synthetic `.cjs`
    candidates, so they do not exercise the production source default. The
    repository already preserves loader arguments in
    `commands/gate/branch-local-cli.ts:34`.
  - Fix: Derive the executable and argv prefix from the existing branch-local
    launch resolver, including resolved `--require`/`--import` loader arguments,
    and add an end-to-end test that obtains commands from the real source CLI
    then spawns every returned command against that same checkout.
  - Requirement / prior finding: NFR2, NFR3, prior I5.

- **I4: Design still specifies shell command strings after the argv migration**
  (`.oat/projects/shared/review-plan-workflow/design.md:742`)
  - Issue: `PrepareReviewContextResultV1.commands` is still documented as three
    strings even though p02-t39 changed the canonical TypeScript contract to
    `ReviewCommandInvocationV1` objects containing executable, argv, and stdin
    mode. This stale interface conflicts with the defensible shell-free
    implementation and can cause later coordinator phases to reintroduce string
    rendering or integrate the wrong shape.
  - Fix: Add `ReviewCommandInvocationV1` to the design data models and update
    `PrepareReviewContextResultV1` plus command-flow prose to use executable,
    argv, and stdin semantics.
  - Requirement / prior finding: NFR2, artifact alignment following prior M3.

### Medium

- **M1: Authenticated persisted state is not fully strictly parsed**
  (`packages/cli/src/review/validation-store.ts:193`)
  - Issue: Persisted telemetry entries are checked only for top-level keys,
    schema version, run ID, phase, and disposition, then cast wholesale at
    lines 247-249. Adapter IDs, timestamps, rejection reason, and the complete
    nested observation schema are not validated. The outer authenticated
    envelope also uses ordinary `JSON.parse` at
    `validation-store-authority.ts:62`, which does not reject duplicate object
    keys. Authentication protects integrity only when the key is secret; it
    does not satisfy the required strict persisted-schema boundary or prevent
    malformed authenticated state from reaching lifecycle code.
  - Fix: Add and use a strict `HostTelemetryEvidenceV1` parser, validate
    phase-dependent state coherence, and parse the authenticated envelope with
    the repository's duplicate-key/trailing-value rejecting JSON boundary.
  - Requirement / prior finding: NFR3, strict-parsing portion of prior C5.
