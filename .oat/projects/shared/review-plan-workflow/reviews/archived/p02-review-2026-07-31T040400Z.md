## Findings

### Critical

- **C1: The production broker cannot complete a bound lifecycle**
  (`packages/cli/src/review/validation-authority-broker.ts:29`)
  - Issue: The broker protocol and dispatch switch expose only `checkpoint`,
    `validate`, and `begin` actions (lines 29-45 and 170-193). No
    launcher-owned route calls `bindAcceptedHandle`, although every checkpoint
    and plan capability rejects while `acceptedHandleDigest` is null
    (`command-capabilities.ts:80-82`). The passing broker integration test
    bypasses this production constraint by constructing another
    `ValidationStore` with the raw key and binding directly
    (`validation-authority-broker.test.ts:90-98`), an authority that production
    intentionally removes. An independent broker request with the genuine
    generated checkpoint token therefore returned a capability-rejected
    response. In addition, the documented source `prepare-context` path
    remained live beyond 60 seconds after spawning the
    broker: `launchValidationAuthorityBroker` ends the startup/key streams but
    leaves those custom child-pipe handles attached while only destroying
    stdout/stderr and unrefing the child (lines 266-277 and 311-313). The CLI
    caller consequently never receives a completed prepare invocation.
  - Fix: Add a distinct launcher-only accepted-continuation binding channel
    that cannot be invoked with reviewer-visible socket data or command
    capabilities, and bind before enabling reviewer mutations. Fully
    close/unref every broker startup pipe after the response so
    `prepare-context` exits while the detached broker remains available. Add a
    real source-CLI integration test that launches preparation, performs
    launcher binding without reconstructing the key/store in the test process,
    then executes checkpoint, validate, and begin as separate keyless
    processes.
  - Requirement / prior finding: FR1, NFR3, prior C1.

### Important

- **I1: Brokered lifecycle rejections are converted to exit-2 system failures**
  (`packages/cli/src/review/validation-authority-broker.ts:107`)
  - Issue: The broker serializes only an error message, and
    `requestValidationAuthorityBroker` reconstructs every rejection as a plain
    `Error` at line 108. `runReviewJsonCommand` therefore cannot recognize the
    original `ReviewDomainError` and emits `review-json-system-error` with exit 2. An independent execution of the generated checkpoint command reproduced
    exit 2 for the deterministic unbound-capability rejection. The direct
    command tests exercise injected lifecycle functions and do not cover this
    production broker branch.
  - Fix: Give broker failures a strict versioned envelope carrying safe
    category, code, message, and details, reconstruct the domain error at the
    client boundary, and add broker-backed command tests for replay, phase,
    expiry, receipt, and capability failures. Keep exit 2 for actual transport,
    corruption, and runtime faults.
  - Requirement: NFR3; regression of the previously resolved lifecycle error
    boundary.

- **I2: Direct broker requests bypass strict ReviewPlan parsing and can commit malformed state**
  (`packages/cli/src/review/validation-authority-broker.ts:168`)
  - Issue: The socket payload is parsed with ordinary `JSON.parse`, cast to
    `BrokerRequest`, and its `plan` is passed directly to
    `validateAndReceiptPlan` (lines 168-185). A reviewer-side child knows the
    broker socket and one-shot plan token from the returned invocation, so it
    can bypass the strict `validate-plan` stdin parser. An independent request
    supplied an otherwise valid plan with an unknown top-level field. The
    broker reported the unknown field only after `updateRun` had renamed the
    newly sealed state; a subsequent authoritative read failed with the same
    schema error, proving malformed authenticated state remained committed and
    the capability transition was lost.
  - Fix: Strictly parse a versioned, exact-key broker request at the authority
    boundary, including `parseReviewPlanV1` before any lifecycle mutation.
    Reject duplicate keys and unknown action fields, and validate the complete
    next state before the atomic rename so a failed post-write read cannot
    leave authoritative state corrupted.
  - Requirement: FR1, NFR3; new regression of the strict ReviewPlan boundary.

### Medium

- **M1: Empty telemetry bypasses all post-checkpoint phase coherence checks**
  (`packages/cli/src/review/validation-store.ts:235`)
  - Issue: Recovery `f179344b` gates post-checkpoint coherence on
    `telemetry.length > 0`. This preserves empty-telemetry compatibility by
    skipping not only telemetry requirements but also context/plan/assignment/
    receipt requirements. An independently authenticated state changed from
    `prepared` to `evidence_started` with empty telemetry and null context,
    plan, assignment, and receipt was accepted by `readRun`. The recovery test
    covers a prepared state containing only post-artifact telemetry; it does
    not test a valid empty-telemetry later phase or this malformed empty case.
  - Fix: Decouple lifecycle phase coherence from telemetry cardinality. Permit
    an empty legacy telemetry array where required, but still enforce context
    for every post-checkpoint phase, no plan/receipt at `artifacts_loaded`, and
    complete plan/assignment/receipt state for later phases. Add positive
    compatibility and negative malformed-state fixtures.
  - Requirement / prior finding: NFR3, prior M1.
