## Findings

### Critical

- **Tier 1 still tells the reviewer to write the discoverable final path**
  (`.agents/skills/oat-project-review-provide/SKILL.md:803`)
  - Issue: The section first says the reviewer receives only the private draft,
    but the dispatch payload instructions then require the “pre-computed
    artifact path” for the subagent to write to. That is the final Step 7 path,
    so a reviewer following the latter instruction can create a discoverable
    artifact before `validate-output`, publication, or acceptance. This directly
    defeats the fail-closed local artifact rail.
  - Fix: Pass only `artifactDraftPath` to the reviewer, retain the final path
    exclusively in the launcher, and add a contract test that rejects any Tier
    1 instruction or payload containing the final discoverable path.
  - Requirement: FR1, FR9, NFR3

- **Output acceptance ignores the validated verification boundary**
  (`packages/cli/src/review/output-validator.ts:318`)
  - Issue: `ReviewOutputValidationContext` carries
    `plan.verificationBoundary`, but validation only iterates claims the
    terminal chose to provide. It never requires the planned direct claim kinds
    or positive-coverage samples. In addition, finding IDs are collected only
    for structured candidates, so artifact findings are invisible to the
    promoted-finding cross-check. I reproduced a complete terminal with an
    empty evidence/verification registry against a plan requiring all four
    direct claim kinds and a positive sample; it returned `valid: true`.
  - Fix: Validate the final claim set against
    `verificationBoundary.requiredClaims` and
    `verificationBoundary.positiveCoverage`, require evidence for every
    required direct/sample claim, and give artifact candidates a typed,
    immutable finding-ID projection so their promoted findings are checked too.
  - Requirement: FR7, FR9, NFR1

- **Duplicate buckets can replace a required lane while exact-set validation passes**
  (`packages/cli/src/review/output-validator.ts:100`)
  - Issue: Bucket counts are compared and each supplied ID is looked up, but
    accounting lane/classification IDs are not required to be unique and the
    expected ID set is never exhausted. I reproduced a two-lane validated
    assignment whose output repeated `lane-a` twice and omitted `lane-b`; the
    validator returned `valid: true`. This loses one path/obligation owner while
    retaining the valid assignment digest.
  - Fix: Build seen-ID sets for output lanes and classifications, reject
    duplicates, and compare the exact output ID sets to the stored projection
    before validating bucket contents or references. Add duplicate/missing
    lane and classification regressions.
  - Requirement: FR3, FR9

- **An uncovered delegated lane can self-declare complete without permitted contingency**
  (`packages/cli/src/review/output-validator.ts:491`)
  - Issue: The outcome matrix accepts `workerOutcome: uncovered` plus
    `primaryCompletion.outcome: complete` and `inspectionCoverage: all`, but it
    never compares completed indexes/obligations to the stored
    `primaryContingency`, never requires contingency to be allowed, and never
    derives final coverage from worker plus primary evidence. I reproduced an
    assignment with `primaryContingency.allowed: false` that returned
    `valid: true` after reporting the worker uncovered and primary completion
    complete.
  - Fix: Pass the stored contingency projection into outcome validation,
    reject primary completion when contingency is not permitted, validate exact
    completed subsets and their evidence, and derive final
    inspected/uninspected coverage instead of trusting `inspectionCoverage`.
  - Requirement: FR6, FR7, FR9

- **The production CLI bypasses immutable same-handle repair enforcement**
  (`packages/cli/src/commands/review/validate-output.ts:103`)
  - Issue: `validate-output` calls `validateReviewOutput` directly.
    `validateAndRepair` and its immutable-substance digest/two-repair cap are
    referenced only by unit tests, while validation state records neither an
    output substance digest nor output attempt counts. I submitted an invalid
    first terminal, then a corrected terminal with changed review summary; the
    second call returned `valid: true`. Repeated calls are likewise unbounded.
    Skill prose cannot mechanically freeze the first terminal or enforce the
    cap.
  - Fix: Wire the accepted continuation through one launcher-owned coordinator
    that records the initial immutable substance digest and validation/repair
    counts, transitions state through `accounting_repair`, and rejects changed
    substance or a fourth submission. Integration tests must exercise the
    actual CLI/coordinator path, not only prose ordering and the isolated helper.
  - Requirement: FR7, FR9, NFR3

- **Artifact validation discards the only validated snapshot**
  (`packages/cli/src/commands/review/validate-output.ts:80`)
  - Issue: The command creates an immutable descriptor snapshot but discards
    the returned bytes and digest; success exposes only the terminal digest.
    Publication therefore has no validated snapshot to consume. I validated an
    artifact, changed its prose while preserving accounting, re-snapshotted it
    through the available API, and published it; the discoverable artifact
    contained the post-validation mutation.
  - Fix: Make artifact validation return or privately persist an opaque accepted
    snapshot identity, atomically bind it to the accepted terminal, and allow
    publication to consume exactly that snapshot once. Never re-snapshot the
    reviewer-controlled draft after validation.
  - Requirement: FR9, NFR3

### Important

- **Publication reopens a temporary pathname and hard-links it instead of atomically renaming the verified descriptor**
  (`packages/cli/src/review/artifact-staging.ts:122`)
  - Issue: After closing the exclusive temporary-file descriptor, publication
    rereads the pathname and later hard-links that pathname to the destination.
    A concurrent replacement between digest verification and `link` can make
    the destination name a link to bytes that were never verified. This
    contradicts the design’s descriptor-safe copy, digest recheck, and atomic
    rename contract.
  - Fix: Keep the temporary descriptor/identity bound through verification,
    reject link/inode drift, then atomically rename that exact temporary file
    within the destination directory. Add an adversarial publication-temp
    replacement test, not only private-draft replacement coverage.
