### Critical

- **`publish-request/v1` bypasses semantic publication-root validation; credential-bearing roots reach disk before `initializeRun` returns** (`.agents/skills/explainer-kit/scripts/lib/contracts.mjs:469-471`)
  - Issue: `validatePublicationRoots` gates its entire semantic check on
    `value.schemaVersion === 'explainer-kit.publish-request/v2'`. A `v1` block matches
    neither that branch nor the receipt branch, so the function returns having
    validated nothing. `v1` remains a fully accepted shape:
    `schemas/run-request.schema.json:48-52` declares `durability.publish` as
    `oneOf: [publish-request/v1, publish-request/v2]`, and v1's own pattern
    `^s3://[^/\s]+(?:/[^\s]*)?$` (`schemas/publish-request.v1.schema.json:20-22`)
    happily matches an authority containing `:` and `@`. `git show 634463e0c --stat`
    confirms p06-t01 tightened only the **v2** schemas.

    Reproduction — two run-requests identical apart from `schemaVersion` and v2's
    required `publicAccess`:

    ```text
    v1 valid=true  []
    v2 valid=false ["one-of","publish-roots"]
    ```

    The harm lands before the connector ever runs. `initializeRun`
    (`scripts/lib/records.mjs:96-103`) writes `canonicalPersistedRunRequest(...)` to
    `run-request.json`; that is `privacySafeRequest` (`records.mjs:857-864`), which
    deletes only `theme.artDirection` and performs no redaction of publication roots.
    Executed end to end against a real temp output root:

    ```text
    initializeRun SUCCEEDED -> <outputRoot>/demo
    <outputRoot>/demo/run-request.json:20:  "s3Uri": "s3://AKIAV1LEAK:supersecret@example-bucket/p",
    <outputRoot>/demo/run-request.json:21:  "publicBaseUrl": "https://user:pass@cdn.example.com/p",
    ```

    `run-request.json` is a permissible member of the retained run package
    (`package-coverage.mjs:32-38`) and is hash-covered as an immutable package path,
    so a leaked credential is durably retained and archivable — and a caller-supplied
    publisher callback receives the unvalidated request. This is precisely the failure
    the handoff criterion "No credentials enter requests, manifests, logs, or
    receipts" exists to prevent, and it defeats the p06-t01 acceptance contract
    "Require rejection before run initialization or process launch"
    (`plan.md:1086-1088`). The connector check at `s3-static.mjs:68-75` is real and
    does protect process launch, but it executes after initialization, after the full
    build, and after persistence — so it cannot satisfy that contract.

  - Fix: drop the `schemaVersion === '.../v2'` condition so `validatePublicationRoots`
    runs `normalizePublishRoots` for **every** `publish-request` kind, v1 included.
    v1 replay is not a valid reason to exempt it: replay concerns tolerating
    historical _non-canonical_ forms (trailing slashes, doubled separators), which the
    request branch already tolerates because — unlike the receipt branch — it asserts
    only that normalization succeeds, not that the input was already canonical. If
    genuine v1 replay fixtures do break, exempt only the specific non-canonical
    tolerances, never credential/userinfo screening. Add a v1 case to every p06-t01
    parity test, and redact publication roots in `privacySafeRequest` as defense in
    depth.
  - Requirement: handoff acceptance "No credentials enter requests, manifests, logs, or
    receipts"; `design.md` Safety Invariants; `plan.md` p06-t01.

### Medium

- **Publication-root validator does not screen C0/C1 control characters or backslashes** (`.agents/skills/explainer-kit/scripts/lib/s3-roots.mjs:41-42,58-63,127`)
  - Issue: both parsers screen with `/\s/`, which in JS matches only space, `\t`,
    `\n`, `\r`, `\f`, `\v` — not the remaining C0 range or `DEL`. Probed against the
    **hardened v2** path via `normalizePublishRoots` directly, so this is not v1-only:

    ```text
    NUL in s3Uri path        ACCEPT -> "s3://example-bucket/p\x00x"
    SOH in s3Uri path        ACCEPT -> "s3://example-bucket/p\x01x"
    ESC in s3Uri path        ACCEPT -> "s3://example-bucket/p\x1bx"
    DEL in s3Uri path        ACCEPT -> "s3://example-bucket/p\x7fx"
    NUL in publicBaseUrl     ACCEPT -> "https://cdn.example.com/p\x00x"
    newline / tab / CR       REJECT (E_PUBLISH_ROOTS)
    ```

    Accepted control bytes flow into the S3 object key, the composed public URL, the
    catalog, the receipt, and `aws` argv. There is no shell (`execFile`, not `exec`),
    so this is not command injection. NUL specifically fails closed but badly: Node
    throws `ERR_INVALID_ARG_VALUE` at spawn, an uncoded crash rather than a clean
    `E_PUBLISH_ROOTS`. `ESC`/`DEL`/`SOH` pass through spawn cleanly and reach terminal
    output and durable records — a terminal-escape injection vector that sits oddly
    against this project's otherwise strict "no uncontrolled bytes in output" posture.
    Related and same-class: `parseS3Root` rejects `\` (`:42`) but `parsePublicRoot`
    does not, so `https://ex.com\evil/p` is accepted and silently normalized to
    `https://ex.com/p` (the segment is dropped because the raw regex captures it into
    the authority while WHATWG `URL` treats `\` as a separator). The host still
    resolves correctly, so there is no hijack.

  - Fix: reject any codepoint `< 0x20`, `0x7f`, and `\` in both `parseS3Root` and
    `parsePublicRoot` — e.g. screen with `/[\x00-\x1f\x7f\\]/` alongside the
    existing `\s` test — and add these cases to the p06-t01 parity tests.

- **S3 root and public root are validated independently with no correspondence check; divergence is unverifiable in `protected` mode** (`.agents/skills/explainer-kit/scripts/lib/s3-roots.mjs:13-24`)
  - Issue: `normalizePublishRoots` parses the two roots in isolation and never relates
    them. Probed: `s3://example-bucket/private/a` paired with
    `https://cdn.example.com/unrelated/b` is accepted, as is any same-host/divergent-path
    combination. A _host_ correspondence check would be wrong — the handoff's own
    production example pairs `s3://vox-media-open-agent-toolkit/repositories/duet`
    with `https://open-agent-toolkit.voxops.net/repositories/duet`, deliberately
    different hosts — but the _path suffix_ corresponds in every legitimate example,
    and nothing enforces it. In `public` mode the divergence self-detects, because
    `httpGet(target.publicUrl)` 404s and raises `E_PUBLISH_VERIFY`
    (`s3-static.mjs:257-263`). In `protected` mode the fetch is skipped entirely
    (`publicVerification = { status: 'skipped-protected' }`, `:256-257`) while
    `catalogFromManifest(manifest, roots.publicBaseUrl)` (`:113`) and
    `composePublicationTarget` still stamp that unverified host into the catalog and
    into every receipt entry's `publicUrl`. So in exactly the mode the handoff added
    for protected destinations, every advertised public URL can point somewhere that
    was never checked and never uploaded to, and the receipt still reads `verified`
    for the object.
  - Fix: require the public root's path suffix to equal the S3 key prefix (allowing
    the documented host difference), or — at minimum — record an explicit
    `rootCorrespondence` fact in the receipt so a reviewer can see the two roots were
    never cross-checked. Add a protected-mode divergent-root case to

    tested".

- **Loopback, link-local, and private-network public roots are accepted, and public verification follows redirects** (`.agents/skills/explainer-kit/scripts/lib/s3-roots.mjs:58-91`, `s3-static.mjs:692-702`)
  - Issue: `parsePublicRoot` enforces HTTPS and absence of userinfo/query/fragment but
    applies no address policy. Probed as accepted: `https://127.0.0.1:8443/p`,
    `https://169.254.169.254/p` (the AWS IMDS address), `https://localhost/p`,
    `https://10.0.0.5/p`, `https://[::1]/p`, `https://vault.internal/p`. In `public`
    mode `defaultHttpGet` then issues `fetch(url, { redirect: 'follow', ... })`
    against that host for the sentinel and for every artifact. Exploitability is
    genuinely bounded — it requires a change to committed shared repo config
    (`.oat/config.json`), it runs only after the explicit human publication gate, and
    the response body is hashed and compared so a mismatch fails rather than
    exfiltrating anything. But it is still an attacker-influenced outbound GET
    primitive with redirect following aimed at internal addresses, and pass/fail
    timing discloses internal reachability. `redirect: 'follow'` also means an
    operator-legitimate external root can be bounced inward by a third party.
  - Fix: reject loopback, link-local (`169.254.0.0/16`, `fe80::/10`), and unique-local
    /private ranges in `parsePublicRoot` unless an explicit opt-in is configured, and
    set `redirect: 'error'` (or `'manual'` with an explicit same-origin check) in
    `defaultHttpGet` — a canonical public artifact URL should never legitimately
    redirect.

  - Issue: `await enforceRetainedRunPackage(state, manifest, { includeTerminalEvidence: true }).catch(() => {})`.
    Removal still happens — `package-coverage.mjs:87-89` deletes unexpected entries

    swallowing, so the failure is at least visible in terminal evidence.

  - Issue: any throw inside the publish `try` sets `providerFailed = true`, including

    failure. This is the only residue of deferred finding m2 (see below).
