### Assessment of the Strict-Signature Design

The dispatch asked me to assess the design, not merely its correctness.

**The absent-key / explicit-undefined distinction is coherent, and it is not a
quiet default under a new name.** The distinction is drawn against the _call
site's syntax_ (`'publicAccess' in options`), not against a runtime value. The
defect class being closed was "an author added an options parameter and four
call sites never learned about it" — and a syntactic key requirement is exactly
the right instrument for that class, because it is unsatisfiable by accident of
data flow. Reading `{ publicAccess: undefined }` as `public` is semantically
correct and consistent with the rest of the system rather than a convenience:
`publish-request/v1` and `publish-receipt/v1` have no such field, and both other
resolution points independently agree — `s3-static.mjs:118-121` forces v1
requests to `'public'`, and `run.mjs:1998-2000` resolves a v1 publish config to
`undefined → public`.

**Correcting the dispatch's premise about the guard test.** The dispatch relayed
that `contracts.test.mjs:758-772` "skips the explicit-undefined case rather than
asserting it." That is not what it does. It skips it _inside the throw loop_,
which is correct, since explicit-undefined must not throw — and then asserts it
separately at `:786-790`, where
`catalogFromManifest(finalized, base, { publicAccess: undefined }).publicVerification`
must equal `'required'`. The scoping is deliberate and correct; only the loop's
construction is awkward, which I recorded as a Minor.

**No new failure mode on any previously-working path.** I traced this rather
than assumed it. The v1 records that legitimately have no `publicAccess` never
reach either function: `durability.mjs:380` calls it only inside
`if (receipt.schemaVersion === 'explainer-kit.publish-receipt/v2')`, leaving a
v1 receipt's `catalogArtifact` undefined at `:403`; and
`run.mjs:2876-2877` returns `{ manifest }` for any non-v2 receipt before the
call. On the v2 branches the field is schema-`required` with
`enum: ["public","protected"]`, so it can never be structurally undefined.
Resume, replay, export, and the CLI publish path all route through these same
five production sites.

**The 30-call-site audit, independently verified.** I confirm 30 unique
executable call sites (22 `catalogFromManifest` + 8 `validateInitiativeCatalog`)
and that no accidental omission exists. Two corrections to the count's framing:
there are **two** deliberate guard-test omissions, not one —
`contracts.test.mjs:767` and `:773` — so the tally is 28 threaded + 2
deliberate; and the cited range `758-772` stops one line short of the second.
Neither changes the conclusion. I also checked the harder question the count
does not answer: whether any site threads the key with a _wrong value_, which
would satisfy the guard while still producing a wrong hash. None does.

**Net judgment.** Trading a silent wrong hash for a loud throw is the right
trade here, and the throw is genuinely unreachable on shipped paths. The one
honest caveat is recorded as a Minor: the guard converts "forgot the argument"
into a hard error but leaves "threaded an expression that evaluates to
undefined" silently permissive. No call site is exposed to that today.
