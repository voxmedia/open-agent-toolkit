### Critical

- **`protected`-mode publication can never be recorded durable: the `p07-t03` catalog policy option is not propagated to the durability verifier** (`.agents/skills/explainer-kit/scripts/lib/durability.mjs:381`)
  - Issue: `p07-t03` made the generated catalog carry a public-verification
    **policy** marker — `catalogFromManifest(manifest, publicBaseUrl, { publicAccess })`
    embeds `resolvePublicVerificationPolicy(options.publicAccess).catalogMarker`
    (`catalog.mjs:81-82`), which is `"skipped-by-policy"` for `protected` and
    `"required"` otherwise, **including when `publicAccess` is `undefined`**
    (`catalog.mjs:21-34`). Three of the four production call sites pass it —
    `s3-static.mjs:131`, `run.mjs:2005`, `run.mjs:2883`. `durability.mjs:381`
    does not:

    ```js
    const catalog = catalogFromManifest(manifest, receipt.roots?.publicBaseUrl);
    ```

    `receipt.publicAccess` is available on the same object and is already used
    eleven lines below at `durability.mjs:459`.

    Consequence: for a `protected` run the connector publishes a catalog
    containing `"skipped-by-policy"` and records that catalog's hash in the
    receipt; `verifyPublishEvidence` then rebuilds the catalog with `"required"`,
    derives a different hash, and rejects the receipt with `cross-record-mismatch`
    (`contracts.mjs:1155-1163`).

    Reproduced **end to end** through the real `publishS3Static` producer (fake
    S3 destination only; every explainer-kit code path shipped) into the real
    `recordDurability` consumer, using the real in-flight `incomplete` manifest /
    `publish: running` build-record transition:

    ```text
    === publicAccess=public ===
      uploaded catalog publicVerification : required
      receipt.publicAccess                : public
      recordDurability durable            : true
      manifest.outcome after              : built-durable

    === publicAccess=protected ===
      uploaded catalog publicVerification : skipped-by-policy
      receipt.publicAccess                : protected
      recordDurability durable            : false
      error: cross-record-mismatch - Publish receipt artifact does not match the manifest.
      manifest.outcome after              : built-not-durable
    ```

    Cause isolated to the marker, not to anything else in the catalog:

    ```text
    public     required           sha256:a6b94dc4…
    protected  skipped-by-policy  sha256:5e230a9c…
    undefined  required           sha256:a6b94dc4…
    durability.mjs recompute (no options): sha256:a6b94dc4…
    ```

    This is not a corner case. `references/contracts.md:303-305` states that for
    `durability.strategy: publish`, "A verified receipt is subsequently recorded
    as durability evidence," and `run.mjs:1951-1955` leaves the run
    `built-not-durable` with warning `publish-receipt-evidence-required`
    precisely so that step must follow. So the mandated terminal step of every
    protected publication now fails closed, and the run is never archivable or
    exportable as durable.

    It is invisible to the suite because the fixture is self-consistent with the
    bug: `publishReceiptV2` at `tests/durability.test.mjs:630` builds the
    receipt's catalog hash the same defaulted way —
    `catalogFromManifest(manifest, roots.publicBaseUrl)` — despite receiving
    `publicAccess` as a parameter and using it for `verificationFor`. Verifier
    and fixture agree with each other and both disagree with the real producer,
    so `accepts complete public and protected connector-shaped v2 receipts`
    (`tests/durability.test.mjs:249`) passes vacuously. Passing `{ publicAccess }`
    in that one fixture line turns the test red immediately:

    ```text
    not ok 1 - accepts complete public and protected connector-shaped v2 receipts
        protected
        false !== true
    ```

    The full skill glob is 562/562 green at this HEAD, so nothing in the gates
    catches it.

  - Fix: pass `{ publicAccess: receipt.publicAccess }` at `durability.mjs:381`.
    Then de-vacuum the fixture: `tests/durability.test.mjs:630` must build the
    catalog under the same policy it declares in the receipt, exactly as
    `run.integration.test.mjs:4986` and `publish-boundary.test.mjs:228` already
    do. Strongly consider making the policy argument **required** rather than an
    options bag that silently defaults to the `public` marker — the silent
    default is the sole reason a missing argument produced a plausible-looking
    catalog instead of a loud failure, and it is what makes this class of miss
    repeatable. Add a `protected` case to the durability suite that is driven
    from a receipt the real connector produced.
  - Requirement: handoff acceptance "Protected-public-root behavior is explicit
    and tested"; `references/contracts.md:303-305`; `plan.md` p07-t03 Step 2.3
    ("Derive the catalog marker and the receipt status from one internal result").
