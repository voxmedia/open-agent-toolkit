### Important

**I1. Singleton-mode waves are now unbounded in every profile; the documented
hard cap no longer bounds worker fan-out**

- `.agents/skills/recon/scripts/lib/contracts.mjs:85-94,95-123,124-158` —
  each profile's `countedLaneModes` excludes `map`, `compile`, and
  `reconciliation`.
- `.agents/skills/recon/scripts/lib/contracts.mjs:624-641` — `laneCount`
  sums only `countedLaneModes` lanes before comparing against `policy.lanes`.
- No other check bounds lanes on the excluded modes: the singleton checks at
  `contracts.mjs:896` and `:939` enforce one _wave_ per mode and their order,
  not one _lane_; `PROFILE_CONCURRENCY_CAP_EXCEEDED` compares the declared
  `maxConcurrency` field, not lane counts.

Before `be329458b`, the reduce counted every lane, so 42 lanes in `quick`
tripped `PROFILE_LANE_CAP_EXCEEDED` at `lanes: 4`. After it, the following
probe returns `[]` from `validateV2ProfileTopology()` for `quick` `map`×40,
`quick` `compile`×40, and `standard` `reconciliation`×40 (42/42/46 total
lanes):

```js
import { validateV2ProfileTopology } from '.agents/skills/recon/scripts/lib/contracts.mjs';
import { createV2ExecutionApproval } from '.agents/skills/recon/tests/fixtures/packet-fixture.mjs';
const laneIdForMode = (mode) =>
  mode === 'semantic-verification' ? 'lane-semantic' : `lane-${mode}`;
const execution = createV2ExecutionApproval({
  modes: ['map', 'gather', 'compile'],
  laneIdForMode,
});
const map = execution.waves.find((w) => w.mode === 'map');
for (let i = 2; i <= 40; i += 1)
  map.lanes.push({
    laneId: `lane-map-${i}`,
    scope: `packet/map-${i}`,
    writeRoot: `raw/dossiers/map-${i}.json`,
  });
console.log(
  validateV2ProfileTopology({
    schemaVersion: 2,
    run: { requestedProfile: 'quick' },
    execution,
  }),
); // []
```

This contradicts the shipped contract and the design intent: `profiles.md:4-5`
("never exceeds the approved hard cap"), `profiles.md:14-16` ("one mapping
wave ... one compile lane"), and `packet-contract.md:132-133` ("All possible
lanes count against the profile's 4/10/20 worker-lane cap"). The plan's task
`prev2-t01` also describes the permitted quick topology as "map plus up to four
gather lanes plus compile", i.e. single-lane map and compile. The approval
preview still shows the true total, so a human approver can catch it, but the
validator is documented and designed as the hard fail-closed bound and it no
longer is one. The same shape of defect — validator admitting a topology the
contract forbids — was rated Important in the `p02` and 2026-09-10 final
reviews.

**Fix guidance:** keep `countedLaneModes` for the 4/10/20 adaptive cap and add
a second rule in `validateV2ProfileTopology()` requiring exactly one lane for
every wave whose mode is not in `countedLaneModes` (new code, e.g.
`SINGLETON_WAVE_LANE_COUNT`), or fold the singleton lanes back into the count
and raise the caps by the singleton count per profile (`quick` 4→6, `standard`
10→13, `thorough` 20→23). Either choice must be applied to both preview and
finalized packet validation through the shared validator, pinned in
`routing-contracts.test.mjs` and `packet-validation.test.mjs` with the probe
above as the negative control, and reflected in `profiles.md` and
`packet-contract.md` (see M1).

### Minor

**m1. Approval preview prints total lanes beside an adaptive-only cap without
saying so**

- `.agents/skills/recon/scripts/lib/routing.mjs:418-420,504-518` —
  `## Worst-case limits` prints `Lanes: {total}` and `Profile lane cap:
{policy.lanes}`; the first is every lane, the second applies only to
  `countedLaneModes`.
- `.agents/skills/recon/tests/routing-preview.test.mjs:321-335` — the new test

lanes: 4 of 6 total)`, or equivalent, and pin it in the preview CLI test.
