### Medium

- **Any manifest shape error still cascades into spurious lane and condition diagnostics** (`.agents/skills/recon/scripts/validate-packet.mjs:2139`)
  - Issue: `routing` is assigned only when `manifestShape?.valid` is true
    (`validate-packet.mjs:2139-2140`). When any manifest shape issue exists,
    `validateConditionalRouting` (`:2256`) and `validateApprovedLanes` (`:2263`)
    run against `routing === null`, so every artifact is reported as
    `UNAPPROVED_LANE` and every recorded outcome as
    `UNKNOWN_CONDITION_OUTCOME`. Reproduced at the reviewed head with the v2
    standard fixture plus `configureConditionalContradiction`: setting one
    wave's `selectionReason` to `''` yields `MISSING_REQUIRED_FIELD: 1,
UNKNOWN_CONDITION_OUTCOME: 1, UNAPPROVED_LANE: 7`; adding one unknown
    `execution` key yields `UNKNOWN_FIELD: 1` plus the same eight cascade
    errors. Prior gate finding M1 was scoped to fingerprint drift, and retro
    RP-01 records "skip dependent checks when routing is unavailable" as
    implemented directly in `p05-t01`; the fingerprint trigger is gone but the
    skip was not implemented, so the RP-01 disposition note overstates closure.
    The packet remains correctly unpublishable; `design.md` § Error Handling and
    § API Design still require output that distinguishes invalid schema from
    conditional-evidence and lane errors.
  - Fix: In `compileValidatedRun`, skip `validateConditionalRouting` and
    `validateApprovedLanes` (and the dependent `collectCompletePasses`
    withholding path) when `routing` is null, or normalize routing whenever the
    `$.execution` subtree itself has no shape issues while still withholding
    `ValidatedRun` on any error. Add a control asserting that a single
    non-execution manifest shape error produces exactly that one error without
    `UNAPPROVED_LANE` or `UNKNOWN_CONDITION_OUTCOME`. Correct the RP-01
    disposition note in `references/project-retro.md:237-254` to reflect the
    remaining work if it is deferred instead.

- **Conditional non-contradiction waves without a binding condition are now accepted and publishable** (`.agents/skills/recon/scripts/lib/contracts.mjs:781`)
  - Issue: The removed `validateExecutionV2` condition block included a
    `MISSING_WAVE_CONDITION` check that rejected any `conditional: true` wave
    lacking exactly one activating condition (pre-image
    `contracts.mjs:857-871` at `ad1d8ae9`). The surviving
    `validateV2ProfileTopology` only covers the reverse direction: it rejects
    `contradiction-resolution` waves that are not condition-bound
    (`UNCONDITIONAL_CONTRADICTION_RESOLUTION`, `:781-794`) and required
    singleton modes marked conditional (`:826-837`). A `conditional: true` wave
    whose mode is neither (for example `redundant-gather` in a `standard`
    manifest, or any non-required mode) with no condition now passes.
    Reproduced at the reviewed head: `validateArtifactShape` valid,
    `createRoutingPreview` accepted, and `validatePacket` returned
    `valid: true, publishable: true` for a standard packet containing such a
    wave. The wave can never activate, consumes lane cap, and is shown to the
    user for approval as conditional work that has no trigger;
    `packet-contract.md:123-127` still describes conditions and destinations as
    a one-to-one binding. This is a rule dropped during consolidation, not an
    approved contract change.
  - Fix: In `validateV2ProfileTopology`, after computing
    `conditionDestinations`, iterate `waves` and emit one issue (reuse
    `MISSING_WAVE_CONDITION`, or fold into `INVALID_CONDITION_DESTINATION`
    semantics) for every `conditional === true` wave not in
    `conditionDestinations`; also decide whether conditional waves are limited
    to `contradiction-resolution` and enforce it in the same place. Add the
    dead-conditional-wave control to `routing-contracts.test.mjs` and
    `packet-validation.test.mjs`, and state the reverse-direction rule in
    `packet-contract.md` next to line 127.
