### Medium

- **Approval drift cascades into spurious lane and condition diagnostics** (`.agents/skills/recon/scripts/validate-packet.mjs:2152`)
  - Issue: `routing` is populated only when `manifestShape.valid` is true and the
    approval fingerprint matches (`validate-packet.mjs:2118-2154`). When either
    fails, `validateConditionalRouting` (`:781`) and `validateApprovedLanes`
    (`:916-921`) run against `routing === null`, so every approved lane becomes
    `UNAPPROVED_LANE` and every recorded outcome becomes
    `UNKNOWN_CONDITION_OUTCOME`. Reproduced with a v2 standard fixture whose
    `maxConcurrency` was changed after approval: the result was
    `APPROVAL_FINGERPRINT_MISMATCH` plus `UNKNOWN_CONDITION_OUTCOME` and seven
    `UNAPPROVED_LANE` errors. The pre-branch code resolved lanes from
    `manifest.execution.waves` and emitted only the drift error. The packet is
    still correctly unpublishable, but `design.md` § Error Handling requires
    output that distinguishes approval drift from conditional-evidence and lane
    errors, and this regression conflates them.
  - Fix: Either skip `validateConditionalRouting`/`validateApprovedLanes` when
    `routing` is null (the manifest is already invalid), or normalize routing
    whenever the `$.execution` subtree has no shape issues regardless of the
    fingerprint outcome and unrelated manifest errors, while continuing to
    withhold `ValidatedRun` on any error. Add a test asserting that
    single-axis approval drift yields `APPROVAL_FINGERPRINT_MISMATCH` without
    `UNAPPROVED_LANE` or `UNKNOWN_CONDITION_OUTCOME`.

- **Two parallel v2 condition validators emit duplicated and divergent errors** (`.agents/skills/recon/scripts/lib/contracts.mjs:676`)
  - Issue: `validateExecutionV2` (`contracts.mjs:676-871`) and
    `validateV2ProfileTopology` (`contracts.mjs:981-1120`) both re-implement
    condition shape, predicate, `maxActivations`, duplicate-ID,
    destination-binding, forward-only, and terminal-ordering checks, and both run
    from `validateManifest` (`contracts.mjs:1323-1329`). Probes show an unknown
    predicate yields two `INVALID_CONDITION_PREDICATE` issues at the same path,
    and a duplicated condition yields `DUPLICATE_ID`, `DUPLICATE_ROUTING_ID`, and
    two `DUPLICATE_CONDITION_DESTINATION` issues for one defect. The codes also
    diverge (`DUPLICATE_ID` vs `DUPLICATE_ROUTING_ID`; `INVALID_CONDITION` vs
    `INVALID_ROUTING_CONDITION`). Task `p04-t03` extracted one shared topology
    validator for preview and packet validation, but the older per-condition
    rules in `validateExecutionV2` were left in place, so two implementations
    must now be kept in sync.
  - Fix: Make `validateExecutionV2` responsible only for closed-shape and field
    typing of `conditions`, and delegate every semantic condition rule to
    `validateV2ProfileTopology` (or move the shape checks into the shared
    validator and call it once). Normalize the duplicated codes to one name per
    defect and add a control asserting exactly one issue per injected defect.

- **Activated conditional-lane gap format is enforced but undocumented** (`.agents/skills/recon/scripts/validate-packet.mjs:701`)
  - Issue: `gapNamesConditionalLane` requires the gap message to contain the
    literal backticked substrings `` wave `<waveId>` `` and `` lane `<laneId>` ``
    (`validate-packet.mjs:701-709`); otherwise an activated conditional lane
    without a result fails with `MISSING_LANE_OUTCOME`. `packet-contract.md`
    only says a triggered destination needs "a material
    `PASS_FAILED`/`PASS_OMITTED` gap" (`references/packet-contract.md:170-172`)
    and documents the wave-mode token rule for non-conditional lanes
    (`:229-234`); `SKILL.md` Step 5 (`SKILL.md:249-253`) does not mention the
    format either. The error text ("naming both exact identities") does not
    reveal the required syntax, so a controller following the published
    contract cannot produce an accepted honest partial without reading source.
  - Fix: Document the exact message form (or, preferably, match structured
    `waveId`/`laneId` fields on the gap instead of message substrings) in
    `packet-contract.md` next to the `MISSING_LANE_OUTCOME` rule and reference
    it from `SKILL.md` Step 5 item 5. Pin the documented sentence in
    `skill-contract.test.mjs` alongside the existing contract pins.

### Minor

- **Inactive-conditional artifact check omits the same-run filter used by lane checks** (`.agents/skills/recon/scripts/validate-packet.mjs:889`)
  - Issue: The `INACTIVE_CONDITIONAL_ARTIFACT` loop iterates every entry in
    `artifactsById` without the `value.runId !== manifest.run.id` guard that
    `validateApprovedLanes` applies (`validate-packet.mjs:925`) and
    `collectCompletePasses` applies (`:1006`). A foreign-run dossier sitting in a
    conditional lane path is reported with a conditional-routing code instead of
    being handled by the run-identity rules that own it.
  - Suggestion: Add the same `runId` guard for consistency so each artifact
    defect is attributed to one owning rule.
