### Important

- **Thorough runs with two triggered contradiction waves cannot reconcile**
  (`.agents/skills/recon/scripts/lib/contracts.mjs:745`)
  - Issue: The closed reconciliation declaration pins `conditionalReviews` to
    exactly `reviews/redundant-verification.json` and
    `reviews/contradiction-resolution.json`
    (`contracts.mjs:731-768`), and the controller CLI accepts only
    manifest-declared review paths, rejecting any other supplied review with
    "review set drifts" (`reconcile-ledger.mjs:448-484`). Thorough policy still
    permits two conditions (`contracts.mjs:151`, `conditions: 2`) and
    `references/profiles.md:62-65` documents "up to two condition-bound
    `contradiction-resolution` evidence waves". Every lane write root must be
    unique (`contracts.mjs:595-606`), so a second approved contradiction wave
    necessarily writes elsewhere (the conditional-routing test uses
    `reviews/contradiction-resolution-second.json`). When both conditions
    trigger, the second result is a complete assurance review
    (`validate-packet.mjs:685-691`, `1225-1238`) that the CLI cannot
    incorporate; packet validation then fails with
    `RECONCILIATION_REVIEW_MISMATCH` because the incorporated set must equal
    the complete assurance-review set (`validate-packet.mjs:1817-1829`).
    The failure is fail-closed, but an approvable, documented topology becomes
    structurally unpublishable after all its worker cost is spent. The prior
    worker-owned reconciliation had no such fixed input list, so this is a
    regression introduced by the p01-t04 closed contract; no test exercises a
    thorough run with two triggered conditions end to end.
  - Fix: Choose one and make the docs, policy, and validator agree. Either
    (a) derive the accepted conditional review set from the approved
    manifest: allow `conditionalReviews` to enumerate the exact `writeRoot` of
    every approved conditional `contradiction-resolution` wave plus
    `reviews/redundant-verification.json`, validate that enumeration against
    the manifest's conditional waves in `validateV2ProfileTopology`, and keep
    the CLI's exact-set rule; or (b) cap thorough at one condition
    (`conditions: 1`) and update `profiles.md`, `packet-contract.md`, the
    routing preview test (`maxConditions: 2`), and the conditional-routing
    two-lane test. Add an end-to-end control in
    `workflow.integration.test.mjs` for whichever behavior is chosen.

### Minor

- **Entry-detection helper mutates the importing process's exit code**
  (`.agents/skills/recon/scripts/lib/cli-entry.mjs:12`)
  - Issue: `isDirectExecution` is a predicate used at module import time by
    every CLI, but on a realpath failure it writes to stderr and sets
    `process.exitCode = 2` as a side effect. A library consumer that imports
    one of these modules from a process whose `argv[1]` is not a resolvable
    file (for example a bundler or stdin entry) would exit nonzero without
    running any CLI. The plan's "exit nonzero with a diagnostic" outcome is
    intended for direct execution, not imports.
  - Suggestion: Return a structured result or throw, and let each CLI's guard
    own the exit policy; or only set the exit code when the module URL itself
    resolves to `argv[1]` lexically.
- **Controller CLI treats thorough-required redundant verification as optional**
  (`.agents/skills/recon/scripts/reconcile-ledger.mjs:450`)
  - Issue: `reviews/redundant-verification.json` sits in `conditionalReviews`
    and is included only when present in `manifest.artifacts`. For a thorough
    run, redundant verification is a required pass, so a missing result
    silently produces a reconciliation that omits it; downstream packet
    validation catches the missing pass, but the CLI could have failed earlier
    with a specific diagnostic.
  - Suggestion: When `manifest.run.requestedProfile` is `thorough`, require
    `reviews/redundant-verification.json` in the declared review set.
