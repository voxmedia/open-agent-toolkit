### Important

- **An archived review can hide an older active review event** (`packages/cli/src/commands/review/latest.ts:163`)
  - Issue: `sortReviewCandidates` orders all project candidates by `oat_generated_at` before considering active/archived priority. `oat-project-review-receive` uses this resolver, rejects an archived result as non-actionable, and reports that no active review is waiting. With the new append-ordered model, multiple active artifacts are legitimate: after receive archives the newest artifact, any older active artifact remains in `reviews/`, but the newer archived artifact still wins forever. A disposable reproduction with an active artifact at `2026-07-15T00:00:00Z` and an archived artifact at `2026-07-15T01:00:00Z` returned the archived path with `actionable: false`. This checkout already has `reviews/final-review-2026-07-15T004643Z.md` active, so receiving this newer artifact creates the exact stranded-artifact state.
  - Fix: Add an actionable/active-only project resolution mode (or make project review-receive enumerate top-level active artifacts first), update `oat-project-review-receive` to use it, and add a regression test proving an older active project artifact is selected when a newer archived artifact exists. Preserve the existing all-history behavior for callers that genuinely ask for the newest historical review.
  - Requirement: Distinct, monotonic Reviews events and local receive routing.

- **Final-state readers search the whole plan instead of the Reviews ledger** (`.agents/skills/oat-project-complete/SKILL.md:161`)
  - Issue: `oat-project-complete`, `oat-project-pr-final`, and the implementation closeout reference changed from first-match to `grep ... | tail -1`, but all three grep the entire `plan.md`. Their prose claims to select the latest appended event in `## Reviews`; a later matching table row or example outside that section can instead override the real ledger status. Canonical plan sections may appear in different orders, so this can either bypass a pending final review or falsely block a passed one.
  - Fix: Extract only the `## Reviews` section through the next level-two heading before selecting the last `final | code` row, or route these readers through the existing parsed project-state/control-plane surface. Add fixtures where a later non-ledger example conflicts with the actual latest Reviews event and assert all three readers honor the ledger.
  - Requirement: Distinct, monotonic Reviews events and latest-event lifecycle routing.
