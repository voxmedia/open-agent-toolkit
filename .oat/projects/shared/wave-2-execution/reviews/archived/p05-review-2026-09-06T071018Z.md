### Medium

- **The continuation is never told to reconcile the artifact's recorded `HEAD`
  with its own base before applying**
  (`.agents/skills/oat-project-implement/references/phase-execution.md:255-271`;
  `.agents/agents/oat-phase-implementer.md:493-503`;
  `scripts/capture-dirty-tree.mjs:885`)
  - Issue: the manifest records `head` and `verifyArtifact` returns it, but the
    `recovered_patch` brief carries only
    `{ artifact, manifest_digest, size, stat, components }` — no head — and
    neither contract instructs the child to compare `manifest.head` against the
    HEAD it is about to patch. `--verify` proves artifact integrity, not base
    agreement. `git apply --index` is not a reliable base check for text hunks:
    a small hunk whose context happens to match at a different commit applies
    cleanly and silently produces wrong content. In the happy path the root's
    restore leaves the tree at the capture HEAD, so the invariant holds by
    construction — which is precisely why it should be asserted rather than
    assumed, especially for a same-target `implement` continuation where HEAD
    may legitimately be ahead of `phase_base_head`.
  - Fix: have the child compare `verifyArtifact`'s returned `head` with its own
    `git rev-parse HEAD` before applying and stop with the
    `artifact-verification-failed` reason on mismatch; optionally surface `head`
    in the `recovered_patch` field set (kept identical in both contracts).

### Minor

- **Containment path reconstruction is off by one when the nearest existing
  ancestor is the filesystem root**
  (`scripts/capture-dirty-tree.mjs:578-581`)
  - Issue: `join(realAncestor, artifactRoot.slice(ancestor.length + 1))` assumes
    the ancestor is not `/`. For `ancestor === '/'` the `+ 1` eats the first
    character of the next component: `/nonexistent-top/sub/art` reconstructs as
    `/onexistent-top/sub/art` (reproduced directly with `node -e`). No false
    accept is reachable — any artifact path that truly resolves inside the
    worktree has an existing ancestor at or inside the worktree, and the
    non-recursive `mkdir` at `:694` rejects such a path anyway — but this is a
    latent correctness bug inside a security check.
  - Suggestion: use `resolve(realAncestor, relative(ancestor, artifactRoot))`.

- **`--verify` cannot detect files added to the artifact directory that the
  manifest does not list** (`scripts/capture-dirty-tree.mjs:835-875`)
  - Issue: the aggregate size check sums only manifest-listed files plus the
    manifest, so an extra file dropped into the artifact directory passes
    verification (probe P6). Impact is low: the applier reads only
    `index.patch`, `worktree.patch`, and `manifest.untrackedPaths`, so the extra
    file is inert. It is nonetheless weaker than the "the artifact is immutable
    between the verification and the application" claim at
    `phase-execution.md:269-271`.
  - Suggestion: enumerate the artifact directory during `--verify` and reject
    any entry that is neither `manifest.json`, `round-trip.proof`, nor a
    manifest-listed file.

- **Staged-rename classification depends on Git's rename-detection config**
  (`scripts/capture-dirty-tree.mjs:318-323`)

    than a safety hole.
  - Suggestion: either note the config dependence in the script comment or set
    `-c status.renames=true` on the status call so classification is
