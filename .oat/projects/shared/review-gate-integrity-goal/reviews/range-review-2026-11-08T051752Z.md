### Medium

- **M1: Exclude blocked plan carriers from amendment approval boundaries** (`packages/cli/src/commands/gate/convergence.ts:607`)
  - Issue: `readPlanApprovals` collects every plan carrier with a timestamp, without checking whether it represents approval, and adds an unmatched carrier as an approval at lines 640–646. The goal workflow explicitly persists a `status: blocked, disposition: null` carrier when a plan gate stops; it also explicitly says that carrier is never approval (`oat-project-goal/SKILL.md:554`). On a resumed rerun of that same amendment, the first review precedes the blocked carrier's `decided_at`, while the rerun follows it. They therefore receive different `amendmentAfter` values, and `computeGateConvergence` returns `null`: the second run loses all carried-over/resolved reporting. The branch-build reproduction below confirms this; removing only the blocked carrier restores run 2 with both findings carried over.
  - Requirement: Outcome 5 and p08 require successive runs of the same configured gate on one amendment, including reruns after fixes, to remain one sequence. Brief contract section 12.4 says a carrier written before user approval is not approval.
  - Fix: Treat only actual approval evidence as an amendment boundary. Keep the blocked carrier out of both carrier-based approval matching and the unmatched-carrier fallback. Add the resumed-blocked-plan case at the convergence boundary, retaining a valid approved-carrier control and the existing different-amendment separation.

- **M2: Preserve milestone identity when final resolves to a single phase** (`packages/cli/src/commands/gate/convergence.ts:461`)
  - Issue: A goal code run becomes a milestone sequence only when its resolved scope is literally `final` or it has more than one phase. p15 explicitly resolves a state-selected `final` to a single phase token when the active milestone has one phase, preserving `oat_review_requested_scope: final`. Convergence discards that requested-scope evidence: `SequenceRun` does not carry it, and the current/prior-run readers never pass it. The result is a `scope:p02` sequence for the same exit gate previously reported as `milestone:m02`. Replaying the same captured findings with only `oat_review_scope` changed from `final` to `p02` (requested scope still `final`, phase set still `[p02]`) returns no convergence, while `final` → `final` returns run 2 with two carried-over findings. This affects supported single-phase milestones, including the brief's planned m04.
  - Requirement: Outcome 5 gives a goal milestone exit gate the milestone as its subject whatever scope token it used. Outcome 7 and review-provide's milestone-exit rule explicitly select the single-phase token for a singleton milestone.
  - Fix: Preserve and consult the existing original-hint/exit evidence when resolving the sequence subject, so a singleton state-selected exit retains its milestone identity. Keep ordinary single-phase review gates in their separate scope sequence. Cover the real p15-produced frontmatter at the convergence boundary alongside the existing ordinary-phase and literal-final controls.
