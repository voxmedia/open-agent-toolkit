### Medium

- **`unset` reports a false "already unset" success when the stored value is invalid, and cannot clean it** (`packages/cli/src/commands/config/index.ts:2629-2665`)
  - Issue: `unsetConfigValue` reads the surface through the normalizing readers
    (`readOatConfig` et al.), which silently **drop** an invalid value rather
    than throwing. `removeConfigPath` then finds nothing and returns
    `removed: false`, so the command prints
    `explainers.defaults.style is already unset in shared config` and exits 0 —
    while the key is still physically present in `.oat/config.json`. Probe:
    with `{"explainers":{"defaults":{"style":"totally-bogus-style"}}}`,
    `oat config unset explainers.defaults.style --shared` exited 0 claiming
    already-unset and left the file byte-identical; `oat config set
explainers.defaults.style dark-edgy --shared` on the same file succeeded and
    repaired it. So `set` can clean a corrupt file and `unset` cannot, while
    reporting success.
  - The implementer was aware of this class — the code special-cases
    `documentation.excludes` and `projects.defaultScope` with
    `readOatConfigFor*Repair` readers "otherwise a strict read would reject the
    very value being removed" (`:2650-2655`). That covers only the keys whose
    read _throws_; keys whose invalid value is silently _dropped_ are unhandled.
  - Impact is bounded: the normalizer already excludes the bad value from
    resolution, so no wrong value is ever used. The defect is the false success
    message plus the inability to clean the file.
  - Fix: when `removed` is false, re-read the surface raw (unnormalized) and, if
    the path is physically present, either remove it or report a distinct
    outcome (e.g. "present but not readable as a valid value") instead of
    "already unset". At minimum, do not claim already-unset for a key that
    exists on disk.

- **Env-override refusal over-blocks a surface-targeted removal and its remediation message is inaccurate** (`packages/cli/src/commands/config/index.ts:2589-2594`)
  - Issue: the guard tests the **effective resolved** source
    (`resolved.resolved[key]?.source === 'env'`), not the targeted surface. With
    `OAT_PROJECTS_ROOT=envval` set, `oat config unset projects.root --shared`
    exits 1 with `Cannot unset 'projects.root': ... Unset the environment
variable instead.` and the stored `.oat/config.json` value survives — even
    though removing the shared value is a legitimate, well-defined operation.
    The message is misleading: unsetting the env var does **not** remove the
    stored value; the user must unset the env var _and then re-run_ `unset`.
  - Asymmetry with `set`: in the identical env-override state,
    `oat config set projects.root .oat/projects/other --shared` **succeeds**
    (exit 0) and rewrites the shared file. So `set` may modify the stored value
    under an env override but `unset` may not remove it.
  - This is fail-closed (a refusal, not a bypass), so it is not weaker-anywhere,
    and it satisfies the plan's literal wording ("env-sourced values are
    reported as not unsettable"). The defect is the inaccurate guidance and the
    effective-vs-surface scoping.
  - Only three keys have env aliases (`packages/cli/src/config/resolve.ts` —
    `OAT_PROJECTS_ROOT`, `OAT_PROJECTS_DEFAULT_SCOPE`, `OAT_WORKTREES_ROOT`), so
    blast radius is small.
  - Fix: either scope the guard to the targeted surface (refuse only when the
    surface holds nothing and env is what the user is seeing), or amend the
    message to state that a stored value remains and must be removed after
    clearing the env var.

- **The aggregate-key refusal is undocumented on all three pages, behind a sentence phrased as an exhaustive count** (`apps/oat-docs/docs/reference/cli-reference.md:172`)
  - Issue: `unsetConfigValue` refuses **four** classes — env-sourced, lifecycle
