### Important

- **Docs promise a "never quietly dropped" guarantee the code does not provide** (`apps/oat-docs/docs/cli-utilities/configuration.md:94`)
  - Issue: the page states "A malformed value is rejected with an error rather than
    silently ignored, so an exclusion you asked for is never quietly dropped." That is
    false for path-shaped entries. `normalizeExcludedPaths`
    (`packages/cli/src/commands/instructions/instructions.utils.ts:187-199`) `continue`s
    past absolute paths and `..`-escaping entries with no error and no trace. Probe on
    the built CLI: `instructionPointerExcludes: ["/etc"]` → exit 0, 3 `CLAUDE.md`
    written, and the entry is absent from `excludedPaths`; `["../outside"]`, `[".."]`,
    and `["."]` behave identically. An operator who believes this sentence can think a
    tree is protected while sync writes pointers into it — the fail-open direction the
    key exists to prevent. The sibling page
    `apps/oat-docs/docs/provider-sync/instruction-sync.md:69-70` states the behavior
    correctly ("absolute paths and paths escaping the repository are ignored"), so the
    two pages also contradict each other.
  - Fix: replace the clause with the accurate contract — a _structurally_ malformed
    value (non-array, or an empty/non-string entry) is rejected with exit 2; absolute
    and repo-escaping entries are ignored. This is an artifact-alignment fix; the
    implementation behavior is defensible and deliberately documented in code.

- **A configured exclusion that matches nothing is silently inert and still reported as applied** (`packages/cli/src/commands/instructions/instructions.utils.ts:161-233`, `packages/cli/src/config/oat-config.ts:1506-1553`)
  - Issue: there is no feedback anywhere when an exclusion resolves to a directory that
    does not exist or can never match. The `excludedPaths` payload field reports
    configured intent, so it actively asserts the exclusion is in force. Four
    manifestations, three probed:
    (a) absolute entries dropped (above);
    (b) `..`-escaping entries dropped (above);
    (c) **case-mismatched `documentation.root` on a case-insensitive filesystem** —
    with `root: "Apps/Docsapp"` on APFS, `dirExists` succeeds so the derived content
    root is `Apps/Docsapp/docs`, but the scan compares against
    `relative(repoRoot, entryPath)` which yields `apps/docsapp/docs`. Probe result:
    `excludedPaths: ["Apps/Docsapp/docs"]` while `apps/docsapp/docs/guide/AGENTS.md`
    reverts to `missing`. Issue #238 silently recurs on the default developer platform
    while the JSON output claims the tree is excluded;
    (d) Windows drive-absolute entries fall in the same class (see Ruling 5).
  - Fix: emit a warning when a normalized exclusion entry names no existing directory,
    or when the derived content root does not resolve to a real directory. That single
    diagnostic closes (a) through (d) at once and makes `excludedPaths` trustworthy.
    Alternatively, rename the payload field to `configuredExcludes` and document the
    gap; the field's own doc comment already concedes it is "not a record of
    directories actually skipped".
