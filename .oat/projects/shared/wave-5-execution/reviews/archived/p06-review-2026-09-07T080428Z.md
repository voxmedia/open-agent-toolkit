**Is skipping a bare unpaired trailing `**`acceptable? Yes.** The alternative
the question raises — reporting unpaired trailing runs verbatim — is worse, and
for the same reason.`_`is simultaneously an emphasis delimiter and glob
syntax, and with no opening run there is no local evidence to tell them apart.
Reporting verbatim would flag`.oat/scripts/generate-_`and`.oat/scripts/resolve-tracking.sh\*`as violations, breaking correct glob
documentation, in exchange for catching a reference whose author wrote
unbalanced emphasis that renders as a literal`\*\*` on the page — visibly wrong
to anyone reading the rendered doc. The paired rule uses the only evidence
available (an opening run actually paired the trailing one) and, in its absence,
falls back to the module's standing and plan-endorsed policy that glob syntax
names no concrete file. That is the conservative, consistent reading.

The asymmetry between the delimiters is also right. `_` is a legal filename
character, so requiring an opening run is what keeps the typo
`resolve-tracking.sh_` failing instead of being normalized into the shipped
name — I confirmed it still fails, live and in fixture. And the budget is
per-delimiter, so `**.oat/scripts/resolve-tracking.sh_**` correctly peels two
asterisks, keeps the underscore, and still reports the typo.

Two design details deserve credit. The peel loop interleaves rather than running
an ordered pass, which is what makes `**x.sh**.` (emphasis closing outside a
sentence period) resolve correctly to `x.sh`. And moving the glued-identifier
rejection out of the lookbehind into `readOpeningEmphasis` is a strict
improvement: a lookbehind cannot distinguish an emphasis delimiter at a word
boundary from an underscore inside a name, and the Unicode-aware
`IDENTIFIER_CHARACTER` correctly rejects `café_.oat/scripts/…`, which the old
ASCII lookbehind would have mishandled.
