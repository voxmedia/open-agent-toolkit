## Required Rulings

**Ruling A — the `effective` semantics ("is this tree protected", not "did the predicate fire") is CORRECT; the rejection of Codex's false-positive claim is JUSTIFIED.**

My probe matrix establishes the invariant empirically, with no false positives and no false
negatives:

| Configured entry                                 | Warned? | Tree actually protected?               | Correct? |
| ------------------------------------------------ | ------- | -------------------------------------- | -------- |
| `/etc` (absolute)                                | yes     | n/a — never reaches `configured`       | yes      |
| `../outside` (escape)                            | yes     | n/a — never reaches `configured`       | yes      |
| `Apps/Docsapp/docs` (case mismatch)              | yes     | **no** — docs pages scanned            | yes      |
| `nonexistent-dir`                                | yes     | **no** — nothing to protect            | yes      |
| `.oat/repo` (carve-in root)                      | yes     | **no** — `.oat/repo/AGENTS.md` scanned | yes      |
| `apps/docsapp/docs/guide` (shadowed by ancestor) | no      | **yes** — pruned via the ancestor      | yes      |
| `node_modules` (built-in skipped)                | no      | **yes** — pruned by the global rule    | yes      |
| `.oat/repo/pjm` (carve-in descendant)            | no      | **yes** — genuinely pruned             | yes      |

Warned ⟺ the named tree is unprotected. Codex's framing would have required warning on the last
three rows, where the operator's intent _is_ satisfied — training operators to ignore warnings on
correct configurations, which is strictly worse than the status quo. Listing a subtree explicitly
so it stays protected if the docs root later changes is a sensible defensive config that would
have been warned under Codex's reading. The implementer's rejection is well-founded and the tests
pinning both directions are the right control.

One imprecision, folded into Minor #4 rather than raised separately: the type doc calls
`effective` the subset "the scan can actually prune", which for `node_modules` is true only via a
different mechanism. Accurate enough as written.

**Ruling B — `.oat/repo` descendants SHOULD be excludable; the plan's carve-in intent is not violated, and Codex's false-negative finding was correct.**

The plan constrains the carve-in three times, and every constraint is about _collateral_
suppression, never about refusing a deliberate opt-out:

- Outcome: "the `.oat/repo` carve-in keeps working."
- STOP condition: "excluding a docs root would leave `.oat/repo/**` unscanned."
- Step 1: the predicate is "evaluated after the carve-in check so `.oat/repo/**` is still
  scanned."
- Done criterion: "The `.oat/repo` carve-in still produces pointers."

All four hold at this head. Probed: excluding `.oat` (implicitly, as a root-excluded directory)
and excluding `.oat/repo` explicitly both leave the carve-in fully scanned, and the round-1
ordering control still goes red when the predicate is moved ahead of the carve-in. The Done
criterion also holds under a descendant exclusion: with `.oat/repo/pjm` excluded,
`.oat/repo/AGENTS.md` still receives its pointer.

Treating descendants as unexcludable would have been a _false_ warning about an exclusion that
demonstrably works — probe evidence: `.oat/repo/pjm/AGENTS.md` is genuinely pruned and
`.oat/repo/AGENTS.md` is not. So the exact-match fix (`UNEXCLUDABLE_PATHS` holding only the
carve-in root) is right, and Codex's finding was a real defect worth fixing.

The residual is documentation, not design: the guarantee is "the carve-in _root_ is always
scanned", not "everything under `.oat/repo` is always scanned", and the docs still assert the
latter. That is Medium #3. Weaker-anywhere is unaffected because reaching the new behavior
requires an explicit opt-out naming the exact path, which then appears in
`effectiveExcludedPaths`.
