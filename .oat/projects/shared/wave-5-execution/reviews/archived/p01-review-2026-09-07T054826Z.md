### Minor

- **Docs and decision record say recovery "never re-reads the artifact path"; the shared parser does read it as an immutability assertion**
  (`apps/oat-docs/docs/cli-utilities/workflow-gates.md:410`,
  `.oat/repo/reference/decisions/DR-260907-additive-post-selection.md:17`)
  - Issue: recovery never _sources content_ from the path, which is the intended
    claim, but `assertArtifactContentCurrent`
    (`packages/cli/src/commands/gate/review-verdict.ts:539,584`) does read it, so
    a deleted or modified artifact makes re-validation fail. My probe P-B
    (artifact deleted between snapshot and recovery) returned `review_failed`,
    not a recovered pass. The adjacent sentence covers replacement bytes but not
    deletion, so a reader could infer the path is irrelevant.
  - Suggestion: say "re-validates the immutable snapshot rather than re-parsing
    whatever the path now holds; the artifact must still be present and unchanged
    for re-validation to succeed." This direction of drift is strictly safe (the
    code is stricter than the prose), so it is prose precision only.

- **Plan Test-plan bullet expecting `postSelection.step: 'verdict-parse'` is unreachable under the plan's own step-4 rule**
  (`.oat/repo/reference/external-plans/2026-09-02-recover-committed-review-artifacts-after-post-selection-failures.md:289-290`)
  - Issue: step 4 says the envelope names the _thrown_ sub-step, and a
    verdict-parse failure on the normal path returns an eligibility envelope
    instead of throwing, so `verdict-parse` can never be the thrown step for
    "committed artifact does not validate". The shipped test asserts step
    `invocation-corroboration` with code `artifact_verdict_unparsable`; my live
    probes returned step `artifact-correlation` with the same code, i.e. whatever
    segment actually threw. Behavior matches step 4 exactly.
  - Suggestion: reword the bullet to assert the eligibility cause in
    `postSelection.code` and leave `step` unpinned. No code change.

- **Recovery re-validation swallows unexpected errors with no diagnostic**
  (`packages/cli/src/commands/gate/index.ts:4054-4063`)
  - Issue: `try { disposition = await disposeValidatedReviewArtifact(...) } catch
{ disposition = undefined; }`. If re-validation itself throws (a programming
    error inside `corroborateGateInvocation` / `reviewBlocksAtThreshold` /
    `join`), the run still fails closed to `review_failed`, but
    `postSelection.code` reports the _original_ error while the actual blocker
    was the recovery attempt, and nothing is logged.
  - Suggestion: emit a `dependencies.writeDiagnostic` line or set a distinct
    sentinel cause (e.g. `recovery_revalidation_failed`) so a persistent
    non-recovery is distinguishable from the transient failure that triggered it.

- **Recovery emission fallthrough can double-print in non-JSON mode**
  (`packages/cli/src/commands/gate/index.ts:4070-4110`)
  - Issue: the `recoveryEmitted` guard is correct and desirable in `--json` mode
    (`context.logger.json` is one call: it either emits or throws). In human mode
    `writeReviewGateResult` makes several `logger.info` calls; if one after the
    first throws, the partially printed result is followed by the full
    `review_failed` error line.
  - Suggestion: low priority and strictly fail-closed — optionally buffer the
    human-mode lines before writing. Documenting the intent in the existing
    comment would also be enough.
