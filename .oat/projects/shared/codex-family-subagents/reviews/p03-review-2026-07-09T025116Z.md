### Important

- **Cursor subagent validation trusts parent CLI success without proving the Task probe succeeded** (`packages/cli/src/providers/identity/availability.ts:439`)
  - Issue: `validateCursorSubagentModel` returns `valid` whenever the `cursor-agent -p ...` process exits successfully. It ignores whether the subagent actually returned the sentinel `OAT_CURSOR_SUBAGENT_MODEL_VALID`, so a successful parent run that failed to launch the requested Task model, declined the tool call, or returned fallback prose can falsely validate an unsupported subagent model. This undercuts p03-t01's requirement to validate Cursor subagent eligibility rather than the broad catalog or parent CLI success.
  - Fix: Treat the probe as valid only when the expected sentinel is present in the appropriate output. If the process exits successfully without the sentinel, fall through to allowed-list parsing or report `unvalidated`; add a regression test for `ok: true` with non-sentinel output.
  - Requirement: p03-t01

- **Doctor reports unvalidated dispatch matrix cells with a passing status** (`packages/cli/src/commands/doctor/index.ts:479`)
  - Issue: `createDispatchMatrixDoctorCheck` sets `status: hasUnknown ? 'warn' : 'pass'`, so cells with `availability: 'unvalidated'` produce a green doctor check and exit code `0`. p03-t04 requires unavailable or unparsable provider catalogs to produce an explicit warning state rather than implying the configured matrix is proven runnable.
  - Fix: Track `hasUnvalidated` separately and return `status: 'warn'` when unknown or unvalidated cells exist, while keeping the current message detail. Update the doctor regression that currently expects unvalidated cells to have exit code `0`, or explicitly update the project artifact if non-warning unvalidated output is now the intended contract.
  - Requirement: p03-t04

- **Human-facing dispatch guidance still labels the OAT tier as `Dispatch policy`** (`.agents/skills/oat-project-implement/SKILL.md:462`)
  - Issue: The p03-t05 plan and dispatch UX supplement require human-facing output to use `OAT Dispatch Tier` for OAT abstraction values such as `high`, `frontier`, `uncapped`, and `inherit host defaults`. The updated structured log and examples still render `Dispatch policy: ...` in the primary human-facing block, leaving the ambiguity that p03-t05 was added to remove. The tests also miss this because they assert generic "policy" wording rather than the required label.
  - Fix: Change the human-facing template and examples to `OAT Dispatch Tier: ...`; keep `dispatch_policy=` only in the formal `Dispatch stamp` and keep any lower-level enforcement log wording if it is intentionally machine/debug oriented. Add contract tests that assert `OAT Dispatch Tier` appears in the bundled implement skill and that the primary display examples do not use `Dispatch policy:` for the tier field.
  - Requirement: p03-t05
