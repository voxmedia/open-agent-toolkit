### Minor

- **No resolver test exercises the unknown/advisory provider path end-to-end** (`packages/cli/src/commands/project/dispatch-ceiling/index.ts:121`)
  - Issue: The registry's advisory fallback (`getCeilingAdapter('cursor')` → `mode: 'unsupported'`,
    `dispatchArgs: null`) is well covered at the adapter unit level (`registry.test.ts:104-122`).
    But the resolver itself rejects any provider other than `codex`/`claude` in
    `normalizeProvider` (`index.ts:121-126`), so the resolver can never surface a
    `mode: 'unsupported'` result today. This is consistent with design ("internal
    registry, exactly codex + claude today") — the unsupported mode is reachable only
    through the adapter, which `buildProviderResolution` faithfully threads. Not a defect;
    just note that the `unsupported` branch in `buildProviderResolution` (`index.ts:319`)
    is currently dead from the resolver's entry point and is forward-looking for a future
    Cursor adapter.
  - Suggestion: When a third provider adapter is added (future phase), add a resolver-level
    test asserting `mode: 'unsupported'` + `dispatchArgs: null` for that provider. No action
    required this phase.

- **Advisory branch in `buildProviderResolution` is unreachable for codex/claude with a resolved value** (`packages/cli/src/commands/project/dispatch-ceiling/index.ts:321-324`)
  - Issue: When `value !== null`, `mode` falls to `'advisory'` only if `supportsCeiling`
    is true but `compileToDispatchArgs` returns null. For codex/claude, the resolver only
    passes values that already passed `isValidProviderValue` (same allowlist the adapter
    checks), so `compileToDispatchArgs` cannot return null on that path — the advisory
    branch is defensively correct but never taken. This is sound (single allowlist source),
    not a bug.
  - Suggestion: Optional — none needed. The defensive branch is cheap and correct.
