### Important

- **Page→ledger claim check is fail-open for tokens outside `h`/`tr`/`li`/`p` blocks**
  (`.agents/skills/explainer-kit/scripts/verify.mjs:50`)
  - Issue: `extractRenderedClaims` iterates only
    `/<(h[1-6]|tr|li|p)\b[^>]*>([\s\S]*?)<\/\1>/gi` per `<section>`. Any
    number, ISO date, or closed-vocabulary status rendered in another element
    that is not nested inside one of those four tags — `<div>`, `<dd>`,
    `<span>`, `<blockquote>`, `<figcaption>`, `<strong>` at section level, and
    so on — is never harvested, so `pageToLedger` cannot fail on it.
    `spec.md` FR4 requires that "every number, date, and status the page
    states traces to the fact bundle by subject and value", and `design.md`
    § `scripts/verify.mjs` (line 65) specifies a helper that "harvests every
    term, number, date, and status token from the rendered text with its
    nearest heading or label as subject" and falls back to "the enclosing
    `<section id>`" as subject. The design's risk row ("Both passes fail
    closed with the token named") is therefore not true for this case: the
    miss is a silent pass. Because the subject-bound claim check is the
    spec's stated mitigation for removing the critic seam (spec § Risks), a
    silent bypass on a common HTML pattern (stat strips, wave-map nodes such
    as the program recap's `<div class="map-node">…<span>` at
    `.oat/repo/reference/explainers/2026-08-31-execution-program-recap/site/index.html:431`)
    undermines the guarantee the `built` outcome carries.
  - Reproduction (run against a copy of the shipped project-explainer
    package with `verifyRun({ recipe: 'project-explainer', rung: 'none' })`):
    - unchanged page → `pageToLedger: pass`
    - `<p>Delivered 9999 tasks.</p>` injected → `pageToLedger: fail`
      (`verify-claim-untraced:planned-architecture:9999`)
    - `<div class="stat"><strong>9999</strong> tasks, status failed, shipped 2031-01-01</div>`
      injected → `pageToLedger: pass` (fabricated number, status, and date
      all untraced and all accepted)
  - Fix: after the block pass, strip the matched `h`/`tr`/`li`/`p` blocks
    from each section's HTML and run the same number/date/status harvest over
    the residual text with `sectionId` as subject (the design's declared
    fallback), pushing those claims into `claims` so `pageToLedger` fails
    with `verify-claim-untraced:<section>:<value>`. Add a red-then-green
    control in `.agents/skills/explainer-kit/tests/verify.test.mjs` next to
    the `extractRenderedClaims` case (line 125): a fabricated token inside a
    `<div>` (and one inside `<dd>`) must fail `pageToLedger`, and the shipped
    fixture pages must still pass. If instead the project deliberately scopes
    the check to those four blocks, amend `spec.md` FR4, `design.md` line 65
    and the risk row, and `references/recap-authoring.md:62-64` to say so
    explicitly (the brief currently says only to keep a value "in the same
    sentence, list item, or table row as its subject"; it does not tell the
    author that values elsewhere are unverified) — but the implementation
    route is the smaller, requirement-preserving change.
  - Requirement: FR4 (partial); design § `scripts/verify.mjs`

### Minor

- **Design wording drift: "dates (ISO and long form)"**
  (`.oat/projects/shared/agent-authored-recap/design.md:65`)
  - Issue: Both `bundle.mjs#indexClaims` (line 171) and
    `verify.mjs#extractRenderedClaims` (line 72) match only ISO
    `\d{4}-\d{2}-\d{2}` dates. Long-form dates are neither indexed nor
    harvested, so the design overstates coverage. Behaviour is internally
    consistent (a long-form date on the page is never traced, and the brief
    tells authors to spell dates as the fact base does), so this is artifact
    alignment, not a code defect.
  - Suggestion: Change the design sentence to "dates (ISO `YYYY-MM-DD`)" when
    the artifact is next touched, or extend both regexes together with a
    fixture if long-form dates are wanted.

- **Length-only environment redaction can over-redact structural diagnostics**
  (`.agents/skills/explainer-kit/scripts/lib/sanitize.mjs:19`)
  - Issue: Every environment value of 12 or more characters is replaced with
    `<env>` regardless of variable name. Under `pnpm`/`npm` scripts this
    includes values such as `npm_package_name` (`open-agent-toolkit`) and
    `npm_lifecycle_script`, so a bundle cause that legitimately names a
    locator containing that string (for example a document-collision message)
    is rendered less actionable than FR6's "sanitized actionable cause"
    intends. The direction of the trade-off is safe and the p06-t04/p06-t09
    controls pass; impact is limited to diagnostics.
  - Suggestion: Skip the length-only rule for names matching a small
    structural allowlist (`npm_*`, `PWD`, `TERM*`, `SHELL`) or raise the
    distinctive-length threshold, keeping the name-based
    `SENSITIVE_ENVIRONMENT_NAME` rule unchanged; add one control that a
    locator containing the `npm_package_name` value survives in the cause.
