- **Gate and legacy marker lineage cannot round-trip through the named canonical helpers** (`.agents/skills/oat-project-review-provide-remote/SKILL.md:194`)
  - Issue: The changed skill requires legacy markers without usable lineage to be ineligible and gate markers to match the exact `oat_gate_target`, then identifies `marker-parser.ts` and `body-builder.ts` as the canonical mirrored marker implementation. That implementation cannot preserve the new contract: `ReviewInvocation` permits only `manual | auto`, `parseMarkerBlock` defaults every omitted or unknown invocation—including `gate`—to `manual` (`packages/cli/src/review-remote/marker-parser.ts:29`, `packages/cli/src/review-remote/marker-parser.ts:108`), and `BuildInput` cannot emit a gate invocation or target (`packages/cli/src/review-remote/body-builder.ts:47`). A direct probe confirmed that both an invocation-less legacy marker and a `gate` marker parse as lifecycle `manual`; the gate target is only an untyped extra. Following the repository's named helper contract can therefore make legacy provenance eligible and collapse a gate marker into lifecycle lineage, violating exact gate-target isolation.
  - Fix: Extend the marker model, parser, and body builder to represent `gate` plus a required non-empty `oat_gate_target`; preserve omitted invocation only as legacy/unknown rather than silently converting it to lifecycle; and add parser, builder, narrowing-composition, and project integration tests for same-target gate matching, different-target rejection, gate/lifecycle isolation, and invocation-less legacy rejection.
  - Requirement: Project markers must be target-qualified for the same project/scope/lineage; gate target isolation must be exact; legacy markers without usable lineage must fail open.

- **Prior-review enumeration failures have no defined automatic fail-open path** (`.agents/skills/oat-project-review-provide-remote/SKILL.md:197`)
  - Issue: Both changed rails run `gh api .../pulls/$PR/reviews` as candidate discovery (`.agents/skills/oat-review-provide-remote/SKILL.md:149`) but define fallback only after a candidate list exists. An API/network/rate-limit/parsing failure has no resolution reason or instruction to continue over the full PR diff, despite the new assertion that every automatic candidate failure fails open with an explicit reason. A conforming executor can stop the review at candidate discovery instead of safely reviewing full scope.
  - Fix: Capture candidate-enumeration status and stderr. When automatic narrowing is active and reviews cannot be listed or parsed, continue with full PR scope and a stable explicit reason such as `prior-reviews-unavailable` plus diagnostic detail. Define the forced-`--narrow` behavior separately, and add contract coverage for both project and ad-hoc rails.
  - Requirement: Automatic candidate failures must fail open to full scope with explicit reasons.
