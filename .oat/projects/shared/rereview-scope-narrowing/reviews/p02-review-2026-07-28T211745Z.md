### Important

- **Invalid durable heads can still authorize a narrowed range** (`packages/cli/src/review-remote/narrowing.ts:63`)
  - Issue: `priorReviewFromLedger` copies any string into `PriorReview.headSha`, and `matchesTuple` checks only project, scope, and lineage. The guard then passes that value to Git, whose object lookup accepts unambiguous abbreviated SHAs. A direct probe with `reviewedHead: "abc1234"` and successful existence/ancestry responses returned `kind: "narrow-range"` with `priorSha: "abc1234"`. The control-plane parser filters malformed rows, but this exported normalization/narrowing boundary does not enforce that precondition, so callers that construct candidates from raw ledger or artifact data can trust invalid provenance instead of failing open.
  - Fix: Require a full 40-character hexadecimal SHA before any candidate can match, ideally in the shared candidate predicate so both artifact- and row-sourced candidates are covered. Treat an invalid head as no eligible prior review. Add regression cases for abbreviated, symbolic, non-hex, and valid full heads.
  - Requirement: Full SHA validation and fail-open narrowing.

### Medium

- **Known provenance columns are parsed by position rather than header name** (`packages/control-plane/src/state/reviews.ts:94`)
  - Issue: The parser destructures cells 6–8 as reviewed head, invocation, and gate target. Writers are explicitly required to preserve unknown trailing columns and mutate known fields by header name, so a valid extended table such as `Artifact | Notes | Reviewed Head | Invocation | Gate Target` is misread. A direct probe omitted the valid reviewed head, exposed the SHA as `invocation`, and exposed `gate` as `gateTarget`. This breaks the documented public `ReviewStatus` shape and disables durable narrowing for extensible ledgers.
  - Fix: Resolve known column indices from the table header and parse each row against those indices while retaining five-column compatibility and row order. Add tests with an unknown column before/between lineage columns and with reordered known provenance columns.

- **The clean remote-receive branch does not carry the ledger migration/preservation rule** (`.agents/skills/oat-project-review-receive-remote/SKILL.md:131`)
  - Issue: The no-unresolved-comments path populates the three provenance fields and then explicitly stops, but the instructions to widen legacy tables, mutate by header name, and preserve unknown cells appear only later in Step 6. On a legacy or custom widened ledger, this early branch can omit the cells or rebuild the row without the preservation guarantees required of every writer.
  - Fix: Move the ledger write/migration contract before the branch or explicitly apply it in the clean path. Add a skill-contract assertion covering both clean and findings-bearing remote receive paths.
