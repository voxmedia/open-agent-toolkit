## Findings

### Critical

- **Child discovery revalidation is not enforced on the real completion path** (`packages/cli/src/validation/project-state.ts:194`)
  - Issue: `validateInheritedContextGate` rejects `oat_status: complete` with `oat_inherited_context_revalidated: false`, but the phase did not wire any actual discovery-completion path to call it. The implementation commit audit says no TypeScript command currently mutates `discovery.md` to complete, and the live `oat-project-discover` skill still marks discovery complete directly in prose. That means a split-created child can still be advanced past discovery without revalidating inherited context, contrary to `plan.md` p01-t02 and the design's mandatory gate.
  - Fix: Add an enforceable discovery-completion boundary before Phase 2 depends on this invariant. Practical options: introduce a CLI helper/command that completes discovery only after validating the child discovery frontmatter, then update the relevant lifecycle skills to use it; or update the skills to explicitly invoke an existing validation command before changing `discovery.md` to complete. Add a call-site test that fails when a child discovery has `oat_parent` and `oat_inherited_context_revalidated: false`.
  - Requirement: p01-t02

### Important

- **`oat_parent` does not have to resolve to an existing coordination parent** (`packages/cli/src/validation/project-state.ts:125`)
  - Issue: `validateChildLinkage` only errors when a matching parent snapshot is supplied and that snapshot is not coordination. If `oat_parent` points to a missing project, or if callers use `assertValidProjectStateContent` without `relatedProjects`, validation passes. This misses the design rule that `oat_parent` must reference an existing project directory with `oat_kind: coordination`.
  - Fix: Add an explicit missing-parent error when `oat_parent` is set and the available related-project set does not contain it, and provide a file-system-aware validation helper for write boundaries that need to validate real project state. Cover both missing-parent and non-coordination-parent cases in tests.
  - Requirement: p01-t02

- **Split plan validation does not prevent existing project slug collisions** (`packages/cli/src/commands/project/split/validate-plan.ts:151`)
  - Issue: `oat project split validate-plan` calls `validateChildPlan(..., new Set())`, so it can never report `slug-collision-existing` for already existing projects. Separately, `validateChildPlan` only checks existing slugs against child slugs and never checks whether `plan.parentSlug` already exists. This weakens the design's single pre-write checkpoint for slug collisions and can allow a parent or child collision to reach the write phase.
  - Fix: Make `validate-plan` resolve the project root/scope and pass the existing project slug set into `validateChildPlan` (or accept an explicit testable dependency for that lookup). Update `validateChildPlan` to reject `plan.parentSlug` when it is present in `existingSlugs`. Add tests for both existing child and existing parent collisions through the CLI command.
  - Requirement: p01-t05, p01-t06

### Minor

- **Duplicate fired signals can falsely cross the split threshold** (`packages/cli/src/projects/split/signals.ts:19`)
  - Issue: `evaluateSignals` counts the raw `fired` array length and raw load-bearing count. A duplicated CLI value such as `independently-shippable,independently-shippable` is treated as two fired signals and can even return `confidence: high`, even though only one unique signal fired.
  - Suggestion: Dedupe `input.fired` before evaluating, or reject duplicates in the CLI parser. Add a unit test for duplicate input so threshold semantics remain tied to unique signals.
