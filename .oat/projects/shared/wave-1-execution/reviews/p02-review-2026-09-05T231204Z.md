  - Fix: extend that bullet list with the structural requirement (all seven

    (`2026-08-30-make-assets-errors-override-aware.md`) rewrites this same error

  - Requirement: plan `## Done criteria` are all met; this is downstream artifact

- **Four of the seven newly-required directories have no packaging guarantee**
  (`packages/cli/src/release/public-package-contract.ts:70-78`,
  `packages/cli/scripts/bundle-assets.sh:42,104-121`)
  - Issue: this change converts "a bundle directory is absent" from graceful
    degradation into a hard, total failure of the installed CLI (verified
    end-to-end below: exit code 2 on `oat tools list`). npm tarballs do not carry
    empty directories — I confirmed this empirically with a minimal
    `npm pack --dry-run` fixture. Three of the seven directories are populated
    conditionally or from an inventory list that could be empty: `docs/` only
    `if [ -d "${DOCS_SOURCE}" ]` (`apps/oat-docs/docs`), and `agents/` and
    `scripts/` from `bundle-inputs.mjs` lists (currently 5 and 3 entries). If any
    of them ever becomes empty, `pnpm build` still creates the directory on disk,
    so every local gate and the entire 5480-test suite stays green, while the
    published tarball silently omits it and every command in the installed
    package aborts with exit 2. `requiredPackedPaths` guards
    `assets/bundle-metadata.json`, `assets/migration/…`, `assets/templates/…`,
    `assets/skills/…` and `assets/NOTICES.md` — but not `agents/`, `scripts/`,
    `docs/`, or `config/`. The plan's own STOP conditions name "a supported
    distribution intentionally omits one of those directories", so distribution
    integrity is inside this change's declared risk frame even though the fix is
    outside its file scope.
  - Fix: in a follow-up (or at the wave fan-in), add one representative packed
    path per newly-required directory to `requiredPackedPaths` in
    `packages/cli/src/release/public-package-contract.ts` — e.g.
    `assets/config/dispatch-matrix-recommendation.json`, one `assets/agents/*`
    file, one `assets/scripts/*` file, and one `assets/docs/*` file — so the
    existing packed-payload test fails before a broken tarball can be published.
    A producer-side alternative (writing a placeholder file into each of the seven
    directories) would also work but touches `bundle-assets.sh`, which this plan
    puts explicitly out of scope. Not a defect in the committed code; it is a
    missing guard for a failure mode this code newly makes fatal.

### Minor

- **The new "unreadable" family discards the underlying errno**
  (`packages/cli/src/fs/assets.ts:90-93`)
  - Issue: the non-`ENOENT` branch is the one path that can abort every CLI
    command for a reason the operator cannot see. The thrown message —
    "Bundled assets are unreadable: required directory could not be read:
    `<path>`" — drops the caught error entirely, so `EACCES`, `ELOOP`, `EIO`, and
    a stale NFS handle are indistinguishable, and the remedy sentence ("reinstall
    or rebuild") is actively misleading for a permission fault. `CliError`
    (`packages/cli/src/errors/cli-error.ts:1-9`) takes no `cause`, so the
    error is not recoverable from the exception object either.
  - Suggestion: append the errno to the message, e.g.
    `… could not be read (${(error as NodeJS.ErrnoException).code ?? 'unknown'}): ${directoryPath}.`
    — a single-line change inside `assets.ts` that stays within the lane's file
    scope and does not touch the remedy prose the downstream plan owns. Widening
    `CliError` to accept `{ cause }` would be a separate, larger change.
