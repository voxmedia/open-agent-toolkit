### Important

- **Active-consumer coverage does not enforce one matching provider pair in
  loading order** (`packages/cli/src/validation/skills.test.ts:3784`)
  - Issue: The shared consumer loop checks only that each file contains the
    principles path, some `subagent-orchestration/references/` path, and some
    `oat-dispatch-subagents/references/` path. It does not prove that principles
    are loaded first, exactly one active-provider selection reference is chosen,
    or the mechanics reference matches that provider. The new test at line 4013
    checks ordering only for `oat-repo-improve`, so any other declared consumer
    could load all provider references, reverse selection/mechanics order, or
    pair different providers while the suite remains green.
  - Fix: For every active consumer, isolate its dispatch-loading block and
    assert the semantic sequence: principles, exactly one provider-selected
    guidance reference, then the matching mechanics reference. Preserve valid
    mechanics-only pointers outside the selection block rather than globally
    banning dispatch references.
  - Requirement: Phase p02 active-consumer loading contract; design Consumer
    Migration responsibilities.

- **Task-class assertions pin labels but not durable classification semantics**
  (`packages/cli/src/validation/skills.test.ts:3832`)
  - Issue: The test proves that all five row labels occur in the principles file
    and that provider matrices list them in order. It does not pin the durable
    classification order (deterministic verifiability, silent-miss risk,
    dispersed context, ambiguity/novelty, consequence), qualification meanings,
    stronger-class uncertainty rule, or escalation boundaries. Those semantics
    can be removed or materially inverted while all new assertions still pass.
  - Fix: Parse the principles task-class table as one ordered structure and
    assert focused semantic markers for each qualification. Add targeted
    assertions for the classification order, stronger-class uncertainty rule,
    and the four escalation boundaries without snapshotting unrelated prose.
  - Requirement: Phase p02 five-task-class and durable classification/order
    contract; design Skill Contract Tests.

### Medium

- **Claude routing test omits the root-versus-subagent cost rationale**
  (`packages/cli/src/validation/skills.test.ts:3907`)
  - Issue: The assertions protect Opus-first rows, Fable escalation triggers,
    and cyber-classifier framing, but they do not protect the rationale that
    root calls are low-volume and coherence-critical while routine savings
    belong in high-volume bounded subagents. Removing the complete canonical
    “Root and Subagent Cost Posture” rationale at
    `.agents/skills/subagent-orchestration/references/provider-claude.md:58`
    would not fail this test.
  - Fix: Add a focused assertion tying low-volume/coherence-critical root
    orchestration to routine savings in higher-volume bounded subagents. Avoid
    pinning exact model versions beyond the existing durable Opus/Fable policy.

- **Legacy-record compatibility is constructed by the test rather than
  validated from a contract fixture** (`packages/cli/src/validation/skills.test.ts:3978`)
  - Issue: `legacyRecord` is produced by programmatically deleting every
    optional guidance field from the enriched record and then asserting that
    those deleted fields are absent. Those absence checks are tautological and
    cannot establish that a real legacy record remains accepted or
    contract-valid. The prose assertion that fields are optional is useful, but
    it does not detect a contradictory required-field example or schema change.
  - Fix: Validate a dedicated legacy request/record example that omits the
    optional fields, alongside the enriched example containing all six fields.
    If the repository has no executable record parser, make the two canonical
    fenced examples explicit and assert their required baseline fields and
    guidance-field presence/absence directly.

- **Mechanics ownership guard misses plausible named-recommendation forms**
  (`packages/cli/src/validation/skills.test.ts:3925`)
  - Issue: The Claude marker requires a family name followed by a digit, and the
    matrix checks recognize only two exact headings and one exact four-column
    header. An unversioned recommendation such as `hard-reasoning: Opus`, or a
    named-model table with different headings, can reintroduce selection policy
    into mechanics without failing. This is a false-negative risk in the
    ownership boundary the phase is meant to harden.
  - Fix: Detect known provider-family names when they occur in recommendation
    rows, lists, or task-class mappings, plus broader recommendation-table
    structure. Keep the check context-sensitive so generic model selectors and
    class-floor terminology remain explicitly allowed.
