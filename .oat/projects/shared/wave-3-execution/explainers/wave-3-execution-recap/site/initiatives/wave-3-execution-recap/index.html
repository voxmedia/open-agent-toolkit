Wave 3: giving the CLI an explicit assets root

The CLI reads its bundled skills, agents and templates from one directory. Nothing could point it anywhere else, so the test that proved those bundles reach every consumer had to reach into the working repository to do it.

Implementation Complete 1 of 1 lanes, both review rounds closed

Reviews Passed plan gate, phase, final and exit gate
Remaining Wave PR not yet opened or merged

What was asked for

Wave 3 of the 2026-08-19 execution program carried a single bounded change, so the wrapper OAT project has exactly one lane. The CLI resolves its assets root — the bundled skills, agents, templates and scripts it installs into a repository — from a fixed packaged location. Only the build script that produces that bundle ever consulted an environment variable; the runtime resolver ignored one entirely.

Before

A test that wanted its own bundle could not have one. The package-coverage smoke test built into the repository's own assets directory and read back from it, so the thing under test and the thing being tested shared a directory.

After

OAT_ASSETS_DIR selects the assets root at runtime, validated exactly as the packaged one is. The smoke test builds into a private temporary directory, points the built CLI at it, and proves the built code reads that directory and not the shared one.

The override is not a fallback switch. A value that is set but wrong — a missing directory, a file where a directory belongs, a bundle with no metadata, a bundle stamped for a different version — must fail closed with the error the CLI already raises, never quietly reverting to the packaged bundle. Unset and blank values keep the packaged root untouched.

The constraints the wrapper accepted

  1. The lane's entire implementation contract is its immutable external plan. The wrapper adds ordering, gates, review mapping and bookkeeping, and restates none of it.
  2. Run the source plan's drift check in the worktree before editing, extended by the wrapper to cover the release surfaces the plan writes, every call site of the resolver, and the way the smoke runner isolates processes.
  3. Honour every source-plan STOP condition verbatim; a tripped STOP parks the lane instead of weakening the plan.
  4. Confirm the source plan's own done criteria, then run the full definition of done, invoking each gate literally and capturing every exit code to a log — including the two gates continuous integration never runs, because this wave writes into the smoke tree.
  5. Obtain an independent cross-model review of the uncommitted work before committing, and keep reviewed history append-only: fix rounds land as new commits and no reviewed SHA is amended.

Success meant the source plan's done criteria confirmed and recorded, every review row passed, and the full definition of done green on the wave branch.

Decisions that shaped the result

Four choices changed what shipped or how it got there. Each is recorded with the reason it was made and the consequence it carried.

  1. Close the ambient-environment class at the runner seam

    Reason
    Making the resolver read an environment variable made every test that resolves an assets root sensitive to the machine running it. The first review round named one call site; sweeping the class showed the real exposure was production code correctly following the new override through seven command paths.
    Consequence
    One line in the CLI's test-runner config pins the variable to empty for the whole suite, taking it from 52 failures under a partial ambient bundle to 3695 green. The two explicit call-site fixes stayed as defence in depth, and two reviewers separately confirmed the line masks nothing: removed under a complete ambient bundle, the suite still passes.

  2. Keep the error messages the plan mandated, and file the wording

    Reason
    The fail-closed errors tell the reader to rebuild the packaged bundle. For someone who set an override by hand that remedy points at the wrong thing entirely, and the reviewer said so.
    Consequence
    The wording was left exactly as the source plan required rather than widened mid-lane, and an override-aware message was filed as a backlog candidate. The same call sent a second observation — that a bundle carrying only metadata passes validation and degrades later — to the backlog rather than into the change.

  3. Pre-plan the version bump, then re-check it after committing

    Reason
    Earlier waves established that any change under the CLI source tree is a publishable change. Separately, the release version gate reads committed state only, so a green run before the commit says nothing about the commit itself.
    Consequence
    The lockstep bump was planned into the lane instead of patched on afterwards, and re-running the version gate after committing became a standing rule for the remaining waves rather than a one-off.

  4. Prove isolation against the built CLI, not the injection seam

    Reason
    The change adds an injectable environment argument, which makes unit tests easy and proves nothing about the shipped binary. A smoke test that only injected would have restated the unit tests in a slower medium.
    Consequence
    The smoke file imports the built output and asserts the resolved root is its own temporary directory, with a negative control that moves the shared assets aside entirely. The final review then drove the same behaviour through real commands on the built CLI.

How the wave was built

With one lane there is no fan-out to manage, so the structure worth drawing is vertical: the loops a change had to survive before it counted as done. Three fired, and each one sent work back to a different owner.

What the wrapper owns

  • Ordering, the drift-check addendum and the concurrency ceiling
  • The wrapper-level definition-of-done sequence and its captured exit codes
  • Review mapping, gate targets and dispatch policy
  • Commit scope naming, backlog archival and all bookkeeping

What the external plan owns

  • Its drift check and STOP conditions
  • Its implementation steps and embedded verify gates
  • Its done criteria, review focus and test plan
  • The files it is allowed to write

What changed

The lane landed as one task commit of nine files plus one append-only fix commit of six, so every SHA a review cites still resolves. Three of the fix commit's files sit outside the source plan's declared scope; each is a test-hermeticity consequence of the change itself, and each was declared and accepted rather than absorbed.

How it was checked

Ten green gates did not find the defects that mattered here. Reviewer-designed probes did: a conditional skip that quietly removed the only coverage of the production default, a whole class of environment sensitivity nobody had swept, and cleanup code that was correct but unasserted, so two mutations of it survived.

The pattern worth carrying forward: a test that passes because it was skipped, and cleanup that works but is never checked, both read as green. Only a mutation or a removal tells them apart from the real thing.

Where this leaves the repository

Works now

  • One environment variable points the published CLI at a different assets root, and that directory is validated exactly as the packaged one is.
  • An override that is set but invalid must fail closed, with the same actionable error and the offending path named; no route falls back silently.
  • The package-coverage smoke test builds its own bundle in a temporary directory, proves the built CLI reads it, and leaves neither the variable nor the directory behind.
  • The CLI suite no longer inherits an operator's own override, and the five public packages sit at 0.2.35 with the tracked backlog item closed.

Did not ship

  • The fail-closed message still tells the reader to rebuild the packaged bundle, which is the wrong remedy for someone who set the override by hand. The source plan mandated the existing wording; a better one is a backlog candidate.
  • A bundle carrying only metadata satisfies validation and then comes up short at read time. That matches the plan's validation bar exactly, and a structural check is the second backlog candidate.
  • No documentation landed inside the lane — the source plan's scope excludes docs — so the entry for the new variable was written afterwards, at the post-implement documentation step.
  • The wave PR has not been opened or merged; the recorded closeout stops at the completed pre-approval steps.

For the next reader

  • Treat the variable as a public runtime knob now. It decides which bundled skills, agents and templates the CLI writes into someone's repository, which is a wider blast radius than a test fixture.
  • Take the two backlog candidates together: an override-aware remedy message and a structural check for partial bundles are the same conversation.
  • Re-run the release version gate after committing, not only before. It reads committed state, so a pre-commit pass is not evidence about the commit.
  • The sync manifest still records 0.2.34 while the packages read 0.2.35. That is a pre-existing repository pattern with its own tracked item, not something this wave introduced.
