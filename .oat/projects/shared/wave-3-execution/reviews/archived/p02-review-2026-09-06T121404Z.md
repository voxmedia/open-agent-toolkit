### (b) The three Codex dispositions

**1. REJECTED — recursive run-directory removal. Disposition upheld; the
argument is sound, and stronger than the one recorded.** No reserved child can
ever lie outside `createdPaths`: `createdPaths` is seeded with the run
directory itself (`provision.mjs:226`), and a reservation is structurally
forced to be a _direct child_ of that run directory both when written
(`journal.mjs:551-560`) and again when read (`cleanup.mjs:247-255`). So the
brief's question — is there a window where a reserved child outside
`createdPaths` gets removed — resolves to no, by construction. The real
question is the inverse: a reserved child that materializes _after_ validation
would have its directory removed by `cleanup.mjs:1120` while its Git
registration survived. That window is closed by the runner, not by cleanup:
`run-smoke.mjs:182-194` waits for the in-flight stage promise (which contains
`createPhaseWorktree`) to settle, and on non-quiescence sets
`context.cleanupSafe = false`, which gates `shouldCleanup` at
`run-smoke.mjs:326-333`. Cleanup therefore does not run while a phase-creation
promise is outstanding. The window is also identical at base, where the same
recursive removal existed (`cleanup.mjs:837` at base) and an unjournaled child
would equally have escaped the snapshot-based descendant refusal.

### Important

- **The probe-to-`worktree add -b` residual is mis-described in code and absent
  from the contract, and deletion is possible inside it**
  (`tools/smoke/runner/journal.mjs:631-638`)
  - Issue: the comment states "The remaining window between this probe and
    `git worktree add -b` is closed by Git itself: `add -b` refuses an existing
    branch, and cleanup only deletes a branch-only reservation whose tip still
    equals the reserved baseline exactly." Probe P14 falsifies the conclusion.
    After a reservation is durable, a foreign actor creating that exact branch
    name at the exact reserved baseline is subsequently **deleted** by cleanup
    (`actions` contained `branch:smoke-automated-…-p01`, foreign branch
    `DELETED`). `add -b` refusing protects _this run from adopting_ the branch;
    it does not stop cleanup from deleting it, because the reservation — made
    before the branch existed — is the deletion authority. Separately,
    `CONTRACT.md` contains no statement of this residual at all; searching for
    `residual|race|probe|add -b|window|already exists|closed by Git` yields
    only `CONTRACT.md:316`, which describes the unrelated _interruption_
    window. On the program's dedicated deletion-safety surface, a knowingly
    accepted residual that is documented as "closed" and omitted from the
    normative contract is a defect in the safety model's documentation, even
    though the collision requires guessing a UUID-bearing branch name and
    landing it on the exact run baseline.
  - Fix: rewrite the comment to state the residual honestly — creation is
    refused by `add -b`, but a colliding foreign branch sitting at exactly the
    reserved baseline remains deletable — and add one sentence to the
    reservation paragraph in `tools/smoke/CONTRACT.md` (near `:342-357`)
    recording the same. Plan step 6 requires the contract to explain
    reservation semantics; an accepted deletion residual belongs there.
  - Requirement: external plan `## Review focus` — "Audit every new cleanup
    path as an ownership/security boundary"; `## Implementation steps` step 6.

### Medium

- **The manifest-tamper guard can be shed by omitting one optional field**
  (`tools/smoke/runner/cleanup.mjs:247-261`)
  - Issue: the comment above the guard states the goal precisely — "Cleanup
    must not trust a manifest to have been written by that writer: an entry
    that named a resource outside the run directory, or a baseline other than
    the run's own, would otherwise enter the owned sets and skip the
    unjournaled-run-descendant refusal" — and explains that binding to reserved
    origin prevents a forged `registered` transition from shedding it. That
    holds only for entries that retain `reservedAt`. A forged v2 entry with
    `state: 'registered'` and **no** `reservedAt` skips both re-derivations.
    Probe P9 proves the consequence: such an entry naming a worktree outside
    the run directory was accepted and the victim worktree registration and
    branch were both deleted. The matched control with `reservedAt` present was
    refused (`reserves a worktree outside the manifest run directory`).
  - **Not a regression**, and this is why it is not Critical: the equivalent
    base-commit forgery (a v1 entry, which is all base accepted) produced the
    identical outcome — accepted, victim deleted — when run against base
    `cleanup.mjs`. The trust boundary is unchanged; only the comment's claim
    outruns it.
  - Fix: either extend the containment and run-baseline re-derivation to every
    schema-v2 entry, with an explicit and documented exemption for the direct
    registration path that `scripts/worktree/init.sh` depends on, or narrow the
    comment to say the invariants are re-derived for reservation-origin entries
    only and that direct registration retains base-level trust.

- **Operator docs overstate what the transaction guarantees**
  (`apps/oat-docs/docs/contributing/smoke-testing.md:254-257`)
  - Issue: two claims exceed the code. (1) "an interruption cannot leave one of
    them as a child cleanup has to refuse" — an interruption inside
    `git worktree add` can still leave a path with no Git registration, which
    `cleanup.mjs:666-670` and `:705-709` refuse by design. What the transaction
    actually guarantees is that no child is left _unjournaled_. (2) "their
    entries are read exactly the same way" (of other nested creators) is
    contradicted by `cleanup.mjs:247`: a directly-registered entry carries no
    `reservedAt` (`journal.mjs:929-938`) and so is _not_ subject to the
    containment and run-baseline re-derivation a finalized reservation gets.
    This is the same asymmetry as M1, and the sentence actively conceals it.
  - Fix: replace (1) with "an interruption can no longer leave an _unjournaled_
    child", and replace (2) with an explicit statement that direct registration
    is validated more loosely because its creation transaction has not been
    migrated.

- **The evidence bundle advertises schema v2 but drops every v2 discriminator**
  (`tools/smoke/evidence/collect.mjs:1594-1610`)
  - Issue: `normalizeManifest` projects journal resources as
    `{baselineCommitSha, branch, runIdentity, worktree}` while passing
    `schemaVersion` through verbatim from the manifest, which is now 2
    (`provision.mjs:247`). `state`, `markerPath`, `reservedAt`, `registeredAt`,
    and `commonGitDir` are all dropped. A bundle from an interrupted run
    therefore reports a never-materialized reserved child as an ownership
    resource indistinguishable from a corroborated one, and the
    `implement-parallel-isolation` whitelist at `assertions.mjs:542` silently
    widens. No deletion or ownership decision depends on it today — `state` is
    read only in `cleanup.mjs` — so this is evidence fidelity, not a safety
    defect, and declining it as out of the plan's enumerated scope was
    reasonable.
  - Fix: track as a follow-up backlog item — project `state` (and ideally
    `markerPath`) into the bundle, or pin the projected `schemaVersion` to the
    shape actually emitted so a bundle cannot claim v2 fidelity it does not
    carry.
