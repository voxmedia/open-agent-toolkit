- **Repo-relative symlinks bypass declared-project and active-project containment** (`packages/cli/src/commands/gate/index.ts:1446`)
  - Issue: gate project normalization rejects only lexical `..` escapes (`index.ts:1446-1464`), then `assertProjectPath` accepts the path when `stat` reports a directory and `state.md` (`index.ts:1536-1555`). The shared `dirExists`/`fileExists` helpers use `stat`, which follows symlinks (`packages/cli/src/fs/io.ts:13-28`). A repo-relative path such as `.oat/projects/shared/external` can therefore be a symlink to a project outside the repository and still be accepted by `--project`; review discovery then reads that external `reviews` directory while reporting the lexical in-repo path as the declared project. The parallel active-project guard has the same gap: `normalizeProjectPath` performs only `path.resolve`/`relative` lexical containment (`packages/cli/src/config/oat-config.ts:785-813`), after which project sync reads `state.md` through the symlink and materializes its targets as `project-config` (`packages/cli/src/providers/codex/codec/sync-extension.ts:332-386`). This restores the external-state injection class that p04-t16 claims to close and weakens the declared-subject guarantee.
  - Suggestion: containment-check the real path of the resolved project directory (and reject symlink escapes) before reading state or reviews. Use one shared realpath-aware helper for explicit gate projects, active projects, and Codex materialization, and add symlink-to-external regressions for all three paths.

- **User-scope status omits the managed base agents required to compute Codex drift** (`packages/cli/src/commands/status/index.ts:428`)
  - Issue: user sync deliberately augments generic user canonical entries with `scanBundledManagedCodexAgents()` before computing the Codex extension (`packages/cli/src/commands/sync/index.ts:277-290`), because generic user scanning excludes agents. The new user-status path passes only `canonicalEntries` from `scanCanonical` (`packages/cli/src/commands/status/index.ts:320-325`, `:428-435`). When user config contains any custom Codex target, `computeCodexProjectExtensionPlan` requires both managed base roles and throws if they are absent (`packages/cli/src/providers/codex/codec/sync-extension.ts:567-584`), so `oat status --scope user` fails instead of reporting drift. With no custom target, it still cannot compare the installed base-role files against bundled canonical content. The added test locks in the empty input rather than exercising the real custom-target path (`packages/cli/src/commands/status/index.test.ts:659-674`).
  - Suggestion: give status the same narrowly scoped bundled-agent dependency and input composition as sync, then cover a real user custom target plus drift in each managed base role.

### Medium

- **Ownership markers are recognized and rewritten anywhere in generated TOML content** (`packages/cli/src/providers/codex/codec/shared.ts:78`)
  - Issue: managed-role and owner detection use unrestricted `content.includes`, and owner insertion replaces the first line beginning `# oat-owner:` anywhere in the file (`shared.ts:78-90`, `:100-133`). Canonical developer instructions are embedded in a TOML multiline string, so an instruction example containing one of these markers can be mistaken for the authoritative header. Owner precedence can then classify a project-owned role as user- or catalogue-owned, and stale cleanup trusts that result when selecting removals (`packages/cli/src/providers/codex/codec/sync-extension.ts:474-550`). Materialization may also rewrite the instruction line instead of adding a header owner, silently changing canonical agent content.
  - Suggestion: parse only the contiguous leading OAT header comment block, require exactly one well-formed role/owner marker there, and add body-marker and conflicting-marker tests before using ownership for deletion.

- **Dispatch parsing accepts incompatible action/role pairs and aggregation trusts only the role** (`packages/cli/src/providers/identity/stamp.ts:141`)
  - Issue: `parseModernStamp` validates `action` and `role` independently but never enforces the canonical pairs `implementation/implementer`, `fix/fix`, and `review/reviewer` (`stamp.ts:141-177`). Producer resolution then filters solely on `role === implementer || fix` (`packages/cli/src/commands/gate/index.ts:973-1007`). Consequently `action=review role=implementer` is counted as producer work, while `action=implementation role=reviewer` is silently excluded, allowing malformed bookkeeping to corrupt exact and final/range provenance. The current project still contains `action=fix role=implementer` at `implementation.md:377`, demonstrating that incompatible grammar is accepted even after p04-t19 repaired three other records.
  - Suggestion: reject incompatible modern action/role pairs in the parser (or filter by a validated producer action/role predicate), warn consistently, and add exact/range regressions proving malformed review stamps cannot enter producer aggregation.

- **Interrupted quick plans cannot resume their required review disposition** (`.agents/skills/oat-project-next/SKILL.md:221`)

  - Suggestion: route quick tier-3 plan recovery back to `oat-project-quick-start` (or add a mode-aware review-resumption path), and add a table-to-skill contract test that proves a pre-review quick plan cannot point at implementation.
