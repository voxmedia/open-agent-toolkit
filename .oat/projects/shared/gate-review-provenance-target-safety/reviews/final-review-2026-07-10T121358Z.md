### Important

- **Correlation and verdict evaluation use different artifact snapshots** (`packages/cli/src/commands/gate/index.ts:1669`)
  - Issue: candidate discovery reads and hashes the artifact while extracting run/project identity (`index.ts:1669-1705`), then `parseReviewGateVerdict` rereads the path independently (`review-verdict.ts:477-528`). The second-read invocation fields are checked, but project corroboration remains the first-read result and the candidate signature is never compared before the verdict is emitted (`index.ts:2592-2696`). A concurrent writer can therefore retain the expected run/invocation values while changing the project or findings counts between reads, combining previously corroborated identity with a different verdict and allowing a false-green gate.
  - Suggestion: parse and corroborate one immutable content snapshot, or reject a signature change before outcome evaluation. Preserve the parser's controlled empty-section normalization without accepting unrelated concurrent mutations, and add a race regression.

- **Relative active-project paths can escape the repository during project-scoped materialization** (`packages/cli/src/config/oat-config.ts:798`)
  - Issue: absolute active-project paths are containment-checked, but relative paths are returned after lexical normalization without resolving them against the repo (`oat-config.ts:798-821`). `resolveActiveProject` then joins that value to the repo root (`oat-config.ts:1074-1093`), and project sync reads the resulting external `state.md` and imports its Codex targets as `project-config` (`packages/cli/src/providers/codex/codec/sync-extension.ts:331-374`). A value such as `../other-repo/.oat/projects/shared/demo` can contaminate the current repository's tracked `.codex` view with another project's targets.
  - Suggestion: resolve every relative candidate against the repository root, reject it unless the result is contained by that root, and add traversal tests covering local-config resolution and project-state materialization.

- **Managed Claude and Cursor reviewer models are resolved but not bound to shared review dispatch** (`.agents/skills/oat-project-plan-writing/SKILL.md:28`)
  - Issue: the shared contract promises all active providers, but its target-preserving procedure is Codex-specific (`oat-project-plan-writing/SKILL.md:28-75`, `:212-216`). The project review dispatcher likewise invokes base Claude/Cursor agents without requiring the resolver-returned `dispatchArgs.model` (`.agents/skills/oat-project-review-provide/SKILL.md:513-578`). Per-phase implementation review binds Claude but has no equivalent Cursor rule (`.agents/skills/oat-project-implement/SKILL.md:1083-1116`). Managed Claude/Cursor artifact, phase, or final reviews can therefore run at host defaults even though the resolver reports an enforced target; the configured opaque Cursor string may never reach the invocation.
  - Suggestion: make target consumption provider-neutral. Require `providers.<provider>.dispatchArgs.model` on Claude/Cursor review calls, preserve it through timeout retries, fail closed when the host cannot apply it, and add payload-level tests for every configured Cursor string.

- **Quick and imported plans can advertise completion before readiness and artifact review finish** (`.agents/skills/oat-project-quick-start/SKILL.md:455`)
  - Issue: quick-start writes `oat_status: complete` and `oat_ready_for: oat-project-implement` before dispatch resolution, phase-review setup, and artifact review (`oat-project-quick-start/SKILL.md:455-470`, `:496-646`). The router treats both complete/non-null and complete/null artifacts as phase-advance signals (`.agents/skills/oat-project-next/SKILL.md:139-147`), so interruption or unresolved non-interactive dispatch can expose an unreviewed plan to implementation.
  - Suggestion: keep both workflows `in_progress` with `oat_ready_for: null` until dispatch readiness and the artifact-review outcome are recorded, then atomically mark complete/ready. Add interruption-state contract tests for quick-start, import-plan, and provider-plan-via-import.
