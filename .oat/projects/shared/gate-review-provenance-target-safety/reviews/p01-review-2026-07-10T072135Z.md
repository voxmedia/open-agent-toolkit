### Important

- **Updating invocation metadata can silently reset target priority** (`packages/cli/src/commands/gate/index.ts:597`)
  - Issue: `parseExecTargetConfig` always materializes `priority`, defaulting an omitted `--priority` to `0`. `setExecTarget` then merges that value over the existing same-layer target, so an operator adding or changing only invocation metadata (while repeating the required runtime/base command) silently drops an existing nonzero priority and can change which reviewer is selected. The preservation test starts from priority `0`, so it cannot detect this regression.
  - Fix: Omit `priority` from the partial mutation when the flag is absent, preserve the existing same-layer value during merge, and let resolution default a genuinely new target to `0`. Add a test that updates one invocation field on a target with nonzero priority and asserts priority plus the other invocation field remain unchanged.
  - Requirement: p01-t02

- **One missing availability executable aborts the entire target list** (`packages/cli/src/commands/gate/index.ts:2022`)
  - Issue: `runTargetList` calls `dependencies.runProcess` directly for each enabled availability probe. A spawn error such as `ENOENT` rejects `Promise.all`, so `oat gate target list --json` returns a top-level error instead of marking only that target unavailable. This is common when one built-in provider CLI is not installed and can hide a different explicitly configured, enabled, available target from the phase-review setup consumer. The selection path already uses `checkArgv`, which catches probe errors and returns `false`; the list path does not.
  - Fix: Reuse `checkArgv` (or catch per-target probe failures) so each failed or missing availability command yields `available: false` without aborting other entries. Add coverage with a rejected availability probe alongside a successful configured target and assert no execute calls occur.
  - Requirement: p01-t02

- **A manual or auto artifact can be accepted as a successful gate artifact** (`packages/cli/src/commands/gate/index.ts:2201`)
  - Issue: Gate corroboration compares the six gate-only fields but never requires `verdict.invocation === 'gate'`. An artifact stamped `oat_review_invocation: manual` or `auto` with matching run/target/runtime/model/effort/source proceeds to severity evaluation and can pass; the success envelope merely echoes the wrong marker later. That loses the workflow provenance used by review-receive to choose gate-specific autonomous disposition and cycle handling.
  - Fix: In the gate execution path, reject a missing or non-`gate` invocation marker before severity evaluation while keeping `parseReviewGateVerdict` backward-compatible for standalone manual/auto artifacts. Add gate integration tests for missing, manual, and auto markers with otherwise matching gate fields.
  - Requirement: p01-t04

- **Unexpected post-selection failures lose the immutable invocation record** (`packages/cli/src/commands/gate/index.ts:2256`)
  - Issue: The record is created after selection, but exceptions after that point still fall through to the generic `writeError`, whose JSON contains only `status` and `message`. A realistic launch rejection from `executeTarget` (for example, the selected executable disappears or cannot spawn), a review-directory I/O error, or another unexpected post-selection exception therefore omits `runId`, target/project, and `gateInvocation`, contrary to the every-post-selection-outcome contract and the documented structured completion envelope.
  - Fix: Keep the selected invocation record in scope for the outer failure handler or wrap all post-selection operations in a structured failure branch that emits it. Add a launch-rejection test and at least one post-selection filesystem-error test asserting the same record is reused in JSON.
  - Requirement: p01-t03

### Medium

- **Raw prompt scalars are not YAML-safe for the YAML-aware parser** (`packages/cli/src/commands/gate/index.ts:304`)
  - Issue: Prompt assembly emits configured strings as unquoted YAML scalars, while `stringOrNull` accepts only parsed strings. Valid non-empty configuration values such as `123`, `true`, `null`, or `model # canary` are parsed by YAML as a number, boolean, null, or truncated comment value, so an exact-copy artifact is rejected as missing/mismatched even though the configured value was preserved. Current tests cover only YAML-safe model slugs.
  - Fix: Render every prompt-provided frontmatter value with YAML-safe scalar quoting (or provide a complete fenced YAML block generated by the YAML library) and keep corroboration string-exact after parsing. Add parameterized parser/gate tests for numeric-, boolean-, null-, colon-, hash-, and quote-containing target/runtime/model/effort values.
  - Requirement: p01-t04
