### Medium

- **No-op/order preservation silently fails for trailing-comma configs that every reader accepts** (`packages/cli/src/config/oat-config.ts:2084`)
  - Issue: `readRawJsonForWrite` uses `JSON.parse`. The shared readers (`readOatConfigWithWarnings` at `oat-config.ts:1881` and the repair readers) parse through `parseJsonConfig` (`packages/cli/src/config/json.ts`), which accepts trailing commas (`allowTrailingComma: true`). A config file that `oat config get` reads cleanly is therefore treated as "unparsable" at write time: `existing` is `undefined`, the output falls back to the normalizer's fixed order, and the skip never applies. I reproduced this against commit 9541287ad with a `tsx` probe that ran `writeOatConfig(root, await readOatConfig(root))` on `{"version":1,"git":{...},"projects":{...},}`. The file was rewritten and `git` moved below `projects`, which is the exact #329 symptom. This violates the BL-260927-preserve-oat-config-json-key criteria ("no semantic change leaves `.oat/config.json` byte-identical"; "a real change preserves the existing order of untouched keys") for a reader-accepted file shape. Hand-edited files are the likeliest to carry a trailing comma, and `configuration.md` now tells users to repair `pjm.remote` by hand. The implementer disclosed that "unparsable/JSONC files" are rewritten, but this file shape is not unparsable by the repository's own contract. The same probe on the repository's real `.oat/config.json` was byte-identical, so the defect is limited to this file shape.
  - Fix: Parse with `parseJsonConfig(raw, filePath)` inside the existing `try/catch` rather than with `JSON.parse`. It is the repository's single parse chokepoint, is `__proto__`-safe, and does not run the normalizer, so the plan's "never through the normalizer" constraint still holds. Truly invalid files still throw and are still rewritten. Add a test in the `writeOatConfig key order and no-op writes` block: a trailing-comma file with `git` before `projects` stays byte-identical on a no-op write and keeps its key order on a real change. Confirm the test fails with the current `JSON.parse`.

- **New configuration.md paragraph misstates the exit code for `oat config get`/`unset`** (`apps/oat-docs/docs/cli-utilities/configuration.md:131`)
  - Issue: The paragraph added in p02-t04 says a wrong-typed or unknown `pjm.remote` leaf "makes every shared config read fail closed with exit code `2`". It adds that this "includes ordinary reads such as `oat config get` and `oat config unset`". The config command catches the `CliError(…, 2)` and sets `process.exitCode = 1` (`packages/cli/src/commands/config/index.ts:3707-3714` and the sibling handlers). The phase's own negative control asserts `expect(process.exitCode).toBe(1)` for `oat config unset` (`packages/cli/src/commands/config/index.test.ts:6340`). The paragraph also says the error "names each offending field path and its structure type". Unknown-key findings name only the path (`collectUnknownPjmRemoteKeys`, `oat-config.ts:1311-1321`); only the new leaf findings carry a type.
  - Fix: Change the docs to match the code. `oat config` subcommands exit `1` with the `Invalid PJM remote policy structure` message, and exit `2` applies where the `CliError` propagates to the top-level handler. Alternatively, drop the exit-code claim. Say that wrong-typed leaves are reported with their structure type and unknown keys by path. Do not change the command's exit code unless that is a deliberate decision.

### Low

- **The "failed === 0 conjunct" test cannot fail when that conjunct is removed** (`packages/cli/src/commands/sync/index.test.ts:1778`)
  - Issue: `restampOnly` (`packages/cli/src/commands/sync/apply.ts:591`) has only two consumers. One is `formatCoreResults`, which now strips the suffix when `restampOnly || runFailed`. The other is the trailing message, which tests `summary.failed > 0` first. When `failed > 0`, both consumers produce identical output whether or not the `summary.failed === 0` conjunct is present, so deleting the conjunct leaves this test green. The test does fail against the pre-fix code, but because of the `runFailed` strip, not the conjunct. The existing code comment at `apply.ts:583-586` already concedes that branch order enforces the outcome. The backlog criterion "A test pins the `failed === 0` conjunct across scopes" would be claimed at closeout on a test that does not pin it.
  - Suggestion: Rename the test to describe what it actually pins: a failed multi-scope run with zero planned operations reads as failed, not restamp-only or no-op. Record in the backlog closeout (p04-t02) that after this fix the conjunct no longer changes observable output. Optionally, make the conjunct observable (for example by exporting `restampOnly` into the JSON summary) or delete it.

- **`pjm.remote.schemaVersion` is not type-checked by the closed-structure guard** (`packages/cli/src/config/oat-config.ts:1136-1141`)
  - Issue: The new leaf checks cover every string leaf, but `schemaVersion` is only allowed as a key. A wrong-typed value (for example `"1"` or `true`) passes the guard, and `normalizePjmRemoteSharedConfig` then silently drops the entire remote tree (`value.schemaVersion !== 1 … return undefined`, `oat-config.ts:1075`). It does not fail closed with the categorical error. This matches the plan's leaf enumeration, but `schemaVersion` is a leaf too, so the backlog's "wrong-typed sibling" class is not fully closed. I did not probe the `unset` interaction for this case.
  - Suggestion: Add a type finding for a present `schemaVersion` that is not a number (for example `pjm.remote.schemaVersion (expected number, received string)`), with a matching row in the `it.each` table. Alternatively, record in the backlog closeout that it is deliberately out of scope.

- **Refresh-provenance kinds and checks duplicated from the registry with weaker rules** (`packages/cli/src/commands/tools/shared/sync-evidence.ts:76`)
  - Issue: `REFRESH_PROVENANCE_KINDS` copies the private set at `packages/cli/src/providers/shared/registry.ts:103`. `asRefreshPolicy` also skips the registry's non-empty `reference` check and its `YYYY-MM-DD` `verifiedAt` validation (`registry.ts:117-151`). Throw safety is unaffected, because `visibilityFor` switches only on `state`. However, the two copies can drift when a provenance kind is added.
  - Suggestion: Export the set, or a `isValidCatalogRefreshPolicy` predicate, from `@providers/shared/registry` and reuse it in `normalizeSyncEvidence`.
