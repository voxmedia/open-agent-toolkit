OAT's independent layers and workflow choices are understandable. I could choose a workflow, identify an appropriate skill, distinguish personal from repository configuration, and find the resume/readiness concepts. Turning that understanding into a safe first accomplishment took substantially more navigation than the opening pages suggest, and two reference-page contradictions reduce confidence about writes.

- Search for `install` led with a specialized installation-boundary result and then Tool Packs; `npm` led with Markdown Features and documentation-related material rather than a beginner installation answer in the sampled results. ## Findings

### Medium

- **M1 — The tested first-run route does not provide a self-contained, no-home-write first success.** Action: followed Home → Quickstart → CLI Bootstrap, used `install`/`npm` search, then read Tool Packs. Outcome: I could choose a safe diagnostic only after deeper reference reading, but could not establish an end-to-end install-and-inspect recipe from the opening route. [Quickstart](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/quickstart/) calls itself “intentionally lightweight”; [Bootstrap](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/bootstrap/) prominently lists `oat init --scope project`, while later explaining that fresh init offers guided setup and core “always installs at user scope.” The caveat exists; it is not a missing warning or a claim that project scope itself writes home. A novice must distinguish initialization scope from pack scope before accepting prompts. Improvement: add one short “first success, no home assets changed” path with obtain-the-CLI prerequisites, explicit prompt choices, writes/no-writes, and expected diagnostic output. Link to full setup afterward; do not imply `--scope project` alone constrains every accepted setup step.

- **M2 — Copyable preference examples recommend the scope later described as unsafe.** Action: read and re-open both preference sections of Configuration. Outcome: the first example sets `workflow.archiveOnComplete`, `workflow.createPrOnComplete`, and `workflow.postImplementSequence` with `--user`; the following section recommends per-repository scope for those same preferences. [Setting preferences](http://<tailnet-host>:65263/open-agent-toolkit/reference/configuration/#setting-preferences) says “User-level: applies to all repos”; [Choosing the right surface](http://<tailnet-host>:65263/open-agent-toolkit/reference/configuration/#choosing-the-right-surface-personal-vs-per-repo) says “Prefer shared scope, or omit it entirely” for PR creation, and describes a cross-repo stuck-completion scenario. A junior copying the plausible first block may adopt precisely the behavior the next block warns against. Improvement: make the safer personal/per-repo split the primary copyable example; remove or clearly label the conflicting lines as an anti-example before the code block. No runtime consequence was tested.

- **M3 — Tool Packs gives incompatible descriptions of whether PJM adoption appends existing root guidance.** Action: read and re-open Install vs Initialize and the tools-install guidance section. Outcome: the same `oat pjm init` command is described as both leaving an existing root file unchanged and appending managed sections to it. [Install vs Initialize](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/tool-packs/#install-vs-initialize) says “without changing that file”; [oat tools install](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/tool-packs/#oat-tools-install) says it “appends the absent” project-management and decision sections. This prevents a source-blind reader from confidently predicting a repository write. Improvement: have the owner verify the actual behavior and reconcile the two descriptions, including existing-file and differing-section cases. I cannot determine which description is correct from these permitted surfaces.

- **M4 — Baseline README Quick Start is source-development-shaped while the docs speak to adoption.** **Main README only, not the new draft.** Action: opened the corrected GitHub URL and read the rendered Quick Start. Outcome: its `pnpm install` and `pnpm run cli -- init --scope project` sequence presumes an OAT source checkout, without making that starting context clear in the block. [Root README](https://github.com/voxmedia/open-agent-toolkit#quick-start) uses “pnpm run cli -- help”; [CLI Bootstrap](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/bootstrap/) instead assumes `oat` is available. As a developer adopting OAT in my own repository, I cannot treat those as interchangeable setup instructions. Improvement: explicitly label the source-checkout path and separately route ordinary CLI adoption to its installation/first-success guide. This is a baseline comparison, not evidence that the proposed README draft retains the problem.

### Low

- **L1 — Task-to-skill selection is stronger than the bridge to invoking the selected skill.** Action: selected a docs-maintenance skill from Skills, then read Core Concepts and Docs Workflows; selected resume skills through search. Outcome: I found the right names, but the inspected task entries were mostly code-styled names rather than direct launch guidance. [Core Concepts](http://<tailnet-host>:65263/open-agent-toolkit/getting-started/concepts/) distinguishes CLI actions from skills; [Docs Workflows](http://<tailnet-host>:65263/open-agent-toolkit/docs-tooling/workflows/) says `oat docs analyze`/`apply` “expose the workflow surface in CLI help.” Improvement: add one provider-neutral example prompt, label agent invocation versus terminal helper, and link the main task choices to their owning guide. For resume, place open → read-only progress → next together. This is friction in the inspected pages, not a site-wide claim that invocation guidance is absent.

- **L2 — The homepage interrupts adopter guidance with contributor/migration language.** Action: read the Home page top-to-bottom and followed its adoption routes. Outcome: the independent-capability framing is strong, but reader attention is also spent on source ownership and retirement of a documentation bucket. [Home](http://<tailnet-host>:65263/open-agent-toolkit/) says “This guide bucket is being retired” and lists `packages/cli/src/**` as a source of truth. Improvement: move contributor migration rationale to contributor guidance and use that space for three concrete outcomes, each with an entrypoint and expected first result. This is editorial prioritization, not incorrect content.

- **L3 — Dispatch guidance explains ceilings more clearly than a newcomer's choice among them.** Action: read the policy table, scope adoption, and exact-target explanations. Outcome: I could explain managed versus inherited dispatch and avoid confusing High with a fixed effort, but could not justify a policy tier for the bug-fix example from workload tradeoffs alone. [Dispatch Policy](http://<tailnet-host>:65263/open-agent-toolkit/workflows/advanced/dispatch-ceiling/) lists Economy, Balanced, High, Frontier, Uncapped, and Inherit; its useful clarification is that High “does not pin” an exact target. Improvement: add a small illustrative decision table covering routine bounded work, ambiguous work, and consequential review, with cost/control implications and a reminder that the ceiling is not the target. Keep provider catalogs and enforcement details in the reference.

## Bounded editorial priorities

1. Put a safe, observable first accomplishment before the broad adoption lanes; distinguish acquiring OAT, installing packs, initializing a repository, and running a skill.
2. Reconcile the two write/scope contradictions before polishing prose. Reference accuracy matters more than shortening those passages.
3. Give the highest-frequency workflow and skill choices a concrete invocation and an owning-guide link, including ordinary same-machine resume.
4. Keep beginner pages outcome-oriented; retain detailed scope, approval, readiness, and dependency material behind progressive links.
5. Align the eventual README adoption path with the docs while explicitly retaining a separate contributor/source-checkout path.

## Limitations and verification

- This was one bounded desktop reader pass, not a whole-site crawl, source audit, CLI validation, accessibility audit, or final visual acceptance. No content was fixed.
- Actions were browser reads/searches/navigation. Success means the reader reached an evidenced decision, not that an OAT command, skill, installation, approval, or resume operation succeeded.
- Absence claims are limited to the named routes and sampled search results. Navigation failures, content discovery friction, and contradictory visible content are distinguished above.
- The site SHA is caller-supplied. The public README was inspected on main and may change independently of the frozen site; it must not be treated as the unreviewed new README draft.
- Recheck editorial fixes by repeating Home → first success as a new adopter with a no-home-write constraint; reading both configuration scope examples; comparing both PJM write descriptions; selecting and invoking the docs-analysis example; and locating ordinary resume with the actual rendered search.
- No repository format discovery or test suite was performed because source/local-file access was outside this review's boundary. The report is the only file written.
