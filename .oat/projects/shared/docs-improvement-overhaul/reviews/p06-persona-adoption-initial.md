## Task 1: README in 60 seconds, and the image

**What I took away in 60 seconds:** OAT is a CLI plus a skill library plus an optional workflow system. It is explicitly "not another agent runtime." My team would get skills and rules kept in one place and synced to Claude, Cursor and Codex. The smallest adoption looks like `oat init --scope project` followed by `oat status`, which the README says "does not create a tracked OAT project." That is a good opening.

**The image helps more than it confuses.** Four boxes, each with its commands, under the line "Start with any one. Each works on its own." It shows at a glance that Provider Sync needs no workflows. One small confusion: the "Reusable Skills" box says "Research, review and idea skills," but the docs say a default install includes every pack (finding F-23). The `skill` chip relies on the README text to explain that `/name` is typed in the agent, not the shell. The text does explain it.

## Verdicts

- **Clear? Partly.** The README, Choose a Workflow, the "Choosing …" tables and the Research skills page are clear. Most deep pages read as implementation contracts, and a manager cannot get the decision-level answer from them in the time available.
- **Well written? Partly.** Sentences are precise and honest, but pages mix three audiences (adopter, operator, maintainer). Internal IDs, contributor commands and raw admonitions leak through, and several key facts sit in the last section of 30–60k-character pages.
- **Helpful? Partly.** I answered about 60% of my questions with citations. The commit/ignore policy, plan approval, new-teammate onboarding, cost and exit were not answered.
- **Compelling (would I pilot it)? Partly.** I would pilot Provider Sync alone, with one team, for a fixed period. Its scope is stated, overwrite behavior is explicit, and the docs are candid about limits. I would not pilot the workflow layer yet: I cannot show where humans approve the plan, how much it costs, or how to back out.

## Three things that would most increase my confidence

1. **A one-page "Pilot OAT with one team" guide for Provider Sync.** Cover what to commit and what to gitignore, what each teammate runs after cloning, the `--scope project` habit and why, and a full exit procedure for the repo, `~/` and origin refs.
2. **A governance summary table.** List every human checkpoint and automatic review, with its default, config key and layer, which layers can override team policy, and a least-privilege recipe for "independent model reviews the final code" that does not require `--dangerously-skip-permissions`.
3. **A status, scope and cost page.** Cover maturity and stability per area, non-goals, who maintains it, a changelog link, and a worked example of the agent runs a typical quick project triggers at Economy vs High.

## Single biggest reason I might say no

The workflow layer cannot be defended to a security-minded staff engineer from these docs. Default tracked projects push refs to our shared remote. An unattended cross-model review effectively requires agents to run with all permission prompts bypassed. And I cannot find a clear point where a human approves the plan.
