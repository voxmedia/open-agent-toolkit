## Sibling-page contradictions

1. **execution-skills.md lists the final review as automatic: CONFIRMED.** `execution-skills.md:107-109` says it dispatches an `oat-reviewer` "to review each phase and the finished work, without a prompt per launch", and `:120` says it "runs … the final code review". The contract supports the new page: `completion-and-closeout.md:273-293` prompts for the route when `reviewExecutionModel` is unset, and in that path the user runs `oat-project-review-receive`. Fix execution-skills.md, for example: "runs final verification, then the final code review (an interactive run first asks how to run it unless `workflow.reviewExecutionModel` is set) and, if one is configured, the implementation exit gate".
2. **hill-checkpoints.md example uses `spec`: CONFIRMED as misleading, but not false.** `hill-checkpoints.md:24-26` shows `['discovery', 'spec', 'design']`. New projects scaffold `['discovery','design']` (`scaffold.ts:157`), and `oat-project-next/SKILL.md:222` calls `spec` legacy. The design skill still honors `spec` (`oat-project-design/SKILL.md` Step 6c/6d). The new page agrees with the contracts. Fix: change the example to `['discovery', 'design']`.
3. **workflow-gates.md omits that local beats shared: CONFIRMED, and slightly worse than an omission.** `workflow-gates.md:1072-1074` says a shared gate "applies to everyone, and wins over a user-level gate". A gitignored local layer overrides it (`resolve.ts:262-283`; reproduced by running). "Applies to everyone" is therefore overstated. The contract supports the new page. Fix: "…is committed with the repository and wins over a user-level gate for the same skill, but a developer's gitignored `.oat/config.local.json` wins over it (see [Approvals and Automation](../approvals-and-automation.md#can-a-teammate-weaken-a-team-rule))."
4. **New: autonomy.md vs the new page on push timing.** `autonomy.md` (oat-project-autonomous warning) says it pushes "after every lifecycle phase", and the skill (`SKILL.md:437-441`) supports that. The new page's "after every phase" is the weaker side (finding #7).
5. **New, tension rather than contradiction:** `workflow-gates.md:1142-1144` advises "add your own target with the permissions it needs" on a trusted machine, while the new page "recommends none". The two can coexist, since the new page already says a team may choose bypass. No change is needed beyond finding #14.
6. **No contradiction found** with `choose-workflow.md:78-84`, `lifecycle.md:112-115` (lite PR only), `starting-projects.md:51-70`, or the warning in `hill-checkpoints.md:114-139`.
