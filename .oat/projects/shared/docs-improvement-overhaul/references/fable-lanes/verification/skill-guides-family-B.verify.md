## Applicability disagreements

There are none. The docs and ALL-blind-applicability.md agree on all 11 skills: new, quick-start, lite, import-plan, capture and split are `none`; discover, spec, design, plan and promote-spec-driven are `required`.

What each entry skill does when a project is already active:

- **new:** switches the active project. Covered only generically, at SP:34-36.
- **quick-start and lite:** resume an active project of their own mode. The page understates this; see #10.
- **import:** takes over any active project. Understated; see #11.
- **capture:** creates a new project and switches to it. It does not check for an active project. The page is silent; acceptable.
- **split:** activates the first child. Stated at SP:255-256.

The table's open question about what quick-start does when the active project is not a quick project (Batch 3, :94) is not addressed by the page, and the contract has no answer either.

## Treatment of the three known contract defects

1. **promote `--project`:** handled truthfully. PS:231-232 tells the reader to select the active project and invoke without a selector flag. It never names the ignored flag, so a reader who sees the skill's argument hint could still try it (#19, nit).
2. **split takes only `--plan-file`:** the invocation is truthful (SP:232-243). The example scenario and the discover section imply a handoff that works on its own, and neither page says how to produce the file (#5, #6, should-fix).
3. **spec readiness mismatch:** acknowledged on both pages (PS:91-92, PS:113-116). The workaround is not actionable (#4, should-fix). Recommending design, which writes `spec.md` itself, is correct.

## Fresh-repo traps

- **Synced scope needs `origin`:** not warned anywhere (#7). This is the most likely first-run failure, and quick-start, lite, import and capture cannot avoid it per call.
- **Synced scope pushes to `origin`:** not stated (#7, #8, #17).
- **`oat init` and the workflows pack:** only a vague "OAT-initialized … relevant skills installed" (#16).
- **Knowledge index before discovery:** stated only on PS:67-70. It is missing from the oat-project-new next step on SP, which is where a newcomer is sent (#9).
- **Default HiLL approvals on spec-driven projects:** not stated (#3).

## Weakest three sections (junior-to-mid reader)

1. **oat-project-split (SP:226-270):** the reader cannot act on it. It requires a `SplitPlanDocument` but never says what that is, where its schema lives, or how to create one. The scenario suggests discovery hands you one, which it does not.
2. **oat-project-import-plan (SP:150-189):** the most dangerous behavior, writing into whatever project is active, is buried as "Check the active project first". The worked example probably fails in the default scope (#12). The output paragraph is dense with unexplained process terms ("resolves dispatch, records import-aware plan review").
3. **oat-project-new (SP:43-74):** this is the reader's first contact. It omits the `origin` requirement, the push and commit it makes, and the knowledge-index prerequisite of the very next step. A newcomer in a fresh local repo will hit a CLI error or a blocked discovery.

The chooser table (SP:12-19) is good. From it, a reader can tell new, quick-start, lite, import and capture apart. They cannot yet start correctly, because of #7, #9 and #16. Undefined terms ("applicability", "dispatch", "exit gate", "artifact review", "HiLL" on SP) add friction throughout.
