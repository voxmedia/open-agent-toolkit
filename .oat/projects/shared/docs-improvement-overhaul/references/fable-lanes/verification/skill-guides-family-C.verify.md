## Applicability disagreements (vs `ALL-blind-applicability.md` plus the agreed clear-active correction)

None material. Every "requires active project" statement matches the table and the contract:

- open: none.
- progress: optional.
- clear-active: optional (prints a message and exits 0).
- next: required in practice; without a pointer it hands off to open and stops.
- implement and reconcile: required; each asks for a name.
- project-review-provide: active or explicit target.
- project-review-provide-remote: resolved from the PR diff or `--project`, not the pointer.
- project-review-receive: without a project it only hands off ad-hoc reviews.
- project-review-receive-remote: active required.
- the four oat-review-\* skills: none.

Minor: the table lists "at least one completed task" as a project-review-provide prerequisite for every review. RF:332-333 narrows that to code review. The contract's own Step 1 inference proposes artifact reviews of discovery, spec and design before any task exists, so the doc's narrower reading is the more coherent one. No change needed.

## Safety omissions (things that commit, push, post or dispatch without a further prompt)

1. **implement → auto PR (blocking, above).** Lite projects always end by pushing the branch and opening a PR. So do `pr`/`docs-pr` preferences and autonomous runs. The doc currently says the opposite.
2. **implement** dispatches phase-implementer and reviewer subagents with no per-launch prompt (except Codex authorization). It commits after every task and boundary, creates and merges parallel worktrees, and runs `oat project push` for synced projects. None of this is stated.
3. **next** invokes its target with no confirmation, including pr-final and complete. Not stated.
4. **open** (synced) can commit an adoption record on the current branch and push a resume commit. Not stated.
5. **project-review-provide** commits review bookkeeping by default (or pushes for synced). The doc says only "persists".
6. **project-review-receive** and **project-review-receive-remote** have required commits (pushes for synced). Not stated.
7. **reconcile** makes one commit, or a push for synced. Stated only as "one bookkeeping operation" (nit).

Correctly stated: approval before posting for both remote provides; explicit approval for replies on both remote receives; ad-hoc remote receive's optional fix → commit → `git push` flow needs explicit confirmation (RF:307-310). Remote provides make no local commits.

## Weakest three sections (junior-to-mid reader who has never used OAT)

1. **oat-project-implement (EX:23-70).** This is the most consequential skill and the least concrete section. Phrases like "phase producers", "dispatch/review handles", "bookkeeping boundaries" and "implementation exit gate" go undefined. The scenario ("executes the pending work, verifies it and routes blocking review findings…") never shows what the user will see or answer: the dispatch policy choice, the checkpoint question, or Codex authorization. The section then wrongly reassures that nothing is published.
2. **oat-project-next (PU:171-206).** The scenario's routing order is wrong for a completed implementation. "Read reported blocker warnings: they are not, by themselves, a promise that the router will refuse to invoke another skill" is a double negative that hides the plain fact (blockers never stop it). And it never says that next skips confirmation.
3. **oat-project-review-receive (RF:354-389).** The text is dense with internal vocabulary ("review event", "collision-safe identity", "gate-originated", "sub-threshold"). It leaves out the two things a user hits in practice: the bookkeeping commit and the 3-cycle cap.

**Can a newcomer pick among the eight review skills?** Mostly yes. The provide/receive, ad-hoc/project and local/remote explanation (RF:146-153) plus the 2×2 table (RF:155-160) is clear, and each section's scenario states why that variant fits. The weak point is placement: the chooser comes after 140 lines of reviewer-independence machinery (flavors, ceilings, gates), which a newcomer must wade through or skip. Moving "Choosing a Review Skill" to the top, or linking it from Quick Look, would fix that. A second gap: nothing tells the reader that the two project remote skills form a pair across machines, with provide on the reviewer's machine and receive on the author's. That is only implied by the scenarios.
