An engineer's tour · Identity Store Split

The identity sync plane, end to end

Vox Media is splitting its one shared Firebase identity project in two: one company keeps it, the other stands up a new one. Until cutover, the source project stays the truth — and a new sync plane inside identity-cloud-functions keeps the destination continuously current. This is how it captures every write, survives every failure, seeds the baseline, repairs the drift, and proves it's safe to flip.

Read time ~15 min Audience engineers Status design complete · implementation in progress Last touched 2026-06-09
Section 01

Why this exists

Vox Media is splitting. The brands can share a company history — they can't share a Firebase project.

Today, every Vox Media brand authenticates against one shared Firebase project, vox-media-identity: one Auth pool of roughly 4.7 million users, plus named Firestore databases (identity, nymag, eater, games) holding profile metadata, login history, entitlements, and operational queues. Two groupings are splitting apart: SpinCo — New York Magazine (nymag.com, The Cut, Vulture, Curbed, Grub Street, Strategist, Intelligencer) plus Vox.com and their apps — and PubCo — Eater, The Verge, and SB Nation plus their apps (now PMX, a PMC subsidiary). One grouping keeps vox-media-identity; the other stands up a new Firebase project. Which company stays and which moves is not yet decided — this explainer walks one open direction, SpinCo moves, as a worked example; the mirror case (PubCo moves) is symmetric, swapping which side's clients flip.

A bulk export/import alone can't do this. Users keep logging in, changing emails, buying subscriptions, and deleting accounts between any snapshot and the actual cutover. So this project builds a live, one-way sync plane: every SpinCo-applicable write to the source project mirrors into the destination, continuously, until cutover day. The non-negotiables, fixed during discovery:

  • UIDs are preserved exactly. Duet sessions, Coral, Jukebox, Supporting Cast, and every Firestore document ID key off the Firebase UID. A changed UID breaks everything downstream.
  • Sync is one-way, source → destination. The old project remains the source of truth until cutover. There is no reverse sync — not even as a rollback mechanism.
  • Sync failures never block source writes. A destination outage must be invisible to a user logging in to nymag.com.
  • But every failure is observable. Non-blocking must not mean silent. Every failed mirror lands somewhere an operator can inspect and replay it.
Scope boundary This workstream owns the sync plane in identity-cloud-functions: capture, policy, queues, ledger, backfill tooling, reconciliation, pruning, and readiness checks. Destination project provisioning, Duet's env swap, NYMag's app release, and legal sign-off are gates the same operator satisfies — but they're not code in this repo.
Section 02

The shape of the problem

Three facts make this harder than "add a hook to the login handler" — and each one shaped the architecture.

Fact 1Most identity writes don't come from this repo

Research across the codebases found that Duet (the web platform behind vox.com and the network sites) writes user_metadata, user_profiles, fcm_tokens, promotions, and entitlement grants directly into the identity database with its own Admin SDK credentials — never passing through a handler here. NYMag web (a separate Amphora stack, not Duet) calls this repo's processLogin and sendEmail functions. And the NYMag mobile app writes delete_users/{uid} into the named nymag database straight from the device via the client Firestore SDK. Any design that only instruments this repo's handlers silently misses most of the data.

Fact 2Users aren't labeled by brand

A user_metadata document is keyed by UID, not brand. One document can carry vox.com membership entitlements and SB Nation community data. Vox's paying members are identifiable (entitlements.vox_memberships) — but that signal covers members only, not the full vox.com population, and NYMag users aren't attributable either (Chorus-era web accounts have no per-site login attribution). No brand's full population is positively filterable, so "sync only SpinCo users" is partly impossible: the design has to treat filtering as policy with fallbacks — broad copy plus best-effort prune — not as a clean predicate.

Fact 3Auth changes can be invisible

Firebase offers no second-gen trigger for Auth record updates. A user changing their password or email through the client SDK touches no code this repo controls and no Firestore document. Whatever the design does, some class of change can only be caught by periodically comparing source and destination — there is no incremental Auth export.

The forcing function Fact 1 forces database-level capture (triggers, not handler hooks). Fact 2 forces an explicit, auditable policy layer. Fact 3 forces a reconciliation backstop. The whole architecture falls out of these three.
Section 03

Architecture at a glance

A trigger-first hybrid: broad Firestore triggers for what triggers can see, queued write-through for what they can't, reconciliation for what nothing can see live.

The design splits the world into three durable planes:

  • Source data plane — the existing project's Auth pool and named Firestore databases. Untouched semantics; still the truth. (Beyond Auth + the named DBs, two adjacent surfaces sit out of this sync's scope: SB Nation's separate Firebase Data Connect SQL database for sports data, on the PubCo/SBN side, and a standing BigQuery export of user_metadata — see Section 08.)
  • Destination data plane — the new destination project's Auth and Firestore, treated as a passive sink during the sync window.
  • Control plane — sync policy, the failure ledger, watermarks, tombstones, manifests, and readiness records. It lives in a separate sync-control datastore, deliberately outside the captured databases — because a trigger that can see its own bookkeeping writes is a feedback loop.

The moving parts, in build order (the plan's six phases): the policy layer and control plane first (one policy authority consulted by everything, plus the ledger and bookkeeping models), then the queue/worker layer (Firebase task queue functions backed by Cloud Tasks), then the capture layer (broad onDocumentWritten triggers on identity and nymag, plus enqueue hooks in repo-owned handlers) together with the destination writer (idempotent, UID-preserving), then backfill tooling, the reconciliation & pruning layer, and finally readiness/cutover controls.

Why trigger-first? Because it was proven before it was chosen. A staging spike (T0.1) deployed a v2 trigger bound to the named identity database, observed live events with correct context at ~1.2s steady-state latency, and — usefully — watched a 10-write burst arrive complete but out of order. That single observation is why idempotency keys and source-event-time conflict resolution are load-bearing requirements, not nice-to-haves.

Queue choice Cloud Tasks won over Pub/Sub deliberately: per-queue rate/concurrency limits fit the per-provider throttling needs, and nothing here needs fan-out. Cloud Tasks' one gap — it deletes tasks after retry exhaustion, leaving no failure inventory — is closed by the ledger rule in Section 07.
Section 04

Policy: who syncs, what travels

Filtering has two independent axes — and conflating them was an early design bug that discovery caught and fixed.

Axis 1 — user/record selection: which documents and Auth records sync at all. Axis 2 — field-level redaction: which fields inside a selected document travel. They're separate because of the mixed-document hazard: even under the narrowest selection, a SpinCo user's user_metadata doc can carry siteData.sbnation_com — PubCo data that shouldn't leak into the destination project unexamined.

Every surface (a database/path/operation family) gets exactly one mode in the active policy:

Mode Meaning
selective Sync only records matching the brand predicate (e.g. Vox paying members via entitlements — a member-only signal, not a full-population filter).
mirror_time_redact Sync the record, strip named fields at write time.
broad Sync everything — requires a recorded legal approval reference.
copy_then_prune Copy broadly now, prune over-copy in the destination before cutover. Also legal-gated.
excluded Never copy. Games, Eater data, Chorus migration collections. Static — never relies on pruning.
expected_drift Differences here are known and accepted (deliberately unsynced state); parity checks record them instead of flagging failures.

Three rules give the policy teeth. First, exactly one policy version is active per source/destination pair, and broad modes require a recorded legalApprovalRef wherever PubCo PII can enter the destination. Second, workers re-resolve the active policy at execution time — a task captured under a looser policy cannot mirror a field the policy has since forbidden. Third, unknown surfaces fail closed: when the broad trigger sees a collection nobody classified (say, Duet ships a new one next quarter), it records policy_unknown and production readiness blocks until someone classifies it. 

interface SyncPolicyVersion {
  policyId: string;
  sourceProjectId: string;
  destinationProjectId: string;
  status: "draft" | "active" | "retired";
  legalApprovalRef?: string;
  surfaces: SyncSurfacePolicy[];
}

interface SyncSurfacePolicy {
  surfaceId: string;
  database?: string;
  pathPattern?: string;
  mode: "selective" | "broad" | "copy_then_prune"
      | "mirror_time_redact" | "excluded" | "expected_drift";
  selectionPredicate?: BrandPredicate;
  redactionRules?: RedactionRule[];
  pruneRules?: PruneRule[];
  legalApprovalRef?: string;  // required for broad / copy_then_prune
}
Why copy-then-prune is a mode, not a failure NYMag's unattributable residual population makes perfect mirror-time filtering impossible for some surfaces. The accepted stance: prefer selective sync where the predicate is clean, fall back to broad copy + destination-side pruning where it isn't — provided the over-copy is legally approved, visible, bounded, and pruned before cutover. Reconciliation's over-copy detection feeds the prune list.
Section 05

Life of a Firestore write

The mainline flow — and the one that catches Duet's writes without Duet knowing the sync plane exists.

A write lands in the source identity database. Maybe processLogin stamped a login origin; maybe Duet granted an entitlement; maybe the NYMag app queued a deletion in nymag. The writer doesn't matter — that's the point. The flow:

  1. The broad trigger for that database fires (onDocumentWritten, catch-all path, one trigger per in-scope named DB: identity and nymag). It normalizes the event into a SourceMutation — database, path, operation, event ID, source event time, before/after existence.
  2. The policy layer classifies the path. excluded → drop. Unknown → policy_unknown record, no destination write. In-scope → apply selection and redaction.
  3. The destination writer applies an idempotent write: compare source event time / write version, check tombstones (Section 09), then last-writer-wins. Simple mirrors happen in the trigger path; anything heavier is enqueued.
  4. Any failure produces a ledger record (Section 07). 
import { onDocumentWritten } from "firebase-functions/v2/firestore";

// One broad trigger per in-scope named database.
// Catches EVERY writer: this repo, Duet, the NYMag app, anything.
// T0.1 proved the database binding (on a single test collection);
// the broad document pattern below is validated during implementation.
export default onDocumentWritten(
  { database: "identity", document: "{collection}/{docId=**}" },
  async (event) => {
    const mutation = normalize(event);   // → SourceMutation
    const verdict  = classify(mutation); // → policy decision
    // mirror | enqueue | record policy_unknown | drop
  }
);

Two design decisions here deserve their reasoning spelled out. Broad capture beat enumerated collections because an enumerated list reintroduces the original gap: when Duet adds another fcm_tokens-style collection, an enumerated trigger never sees it, but a catch-all forces it through classification. And the trigger handler stays thin — normalize, classify, mirror-or-enqueue. No Auth calls, no external side effects, no scans. Login traffic alone writes ~4 documents per login (user_metadata, login_origins, email_ips, ip_emails), so this path runs hot; a SyncVolumeEstimate with real invocation counts is a required gate before production enablement. The provisional production targets are deliberately looser than the staging sample suggests: p95 mirror enqueue under 60 seconds, alerting at 5 minutes of sustained lag — to be recalibrated after staging volume tests.

Delivery semantics are evidence, not assumption The T0.1 burst test delivered 10/10 events with no duplicates — but out of write order. Design therefore assumes at-least-once, unordered delivery everywhere: deterministic idempotency keys per mutation, conflict resolution by source event time, never by arrival order. A clean sample doesn't soften a platform contract.
Section 06

Life of an Auth mutation

Firestore triggers can't see Firebase Auth. So Auth gets a three-layer model, ordered by how much we can observe.

Layer 1Write-through for repo-owned mutations

Where this repo performs the Auth change itself — importUsers in the Memberful and Chorus flows, updateUser in Chorus sync, the onDelete cleanup — the same handler enqueues destination Auth work after the source operation succeeds. The worker imports/updates/deletes the destination record with the UID, password hash, provider links, and custom claims preserved. The handler never waits on the destination; enqueue-and-return.

Layer 2The metadata-create signal for normal signups

A normal client signup creates the Auth record inside the platform — no repo code performs it. But beforeUserCreated (a blocking hook that must never do cross-project I/O) writes identity/user_metadata/{uid} for every platform-native signup (imports bypass it — that's Layer 1's job). That Firestore create is visible to the broad trigger — so it doubles as the async signal to enqueue a destination Auth import for the new user. Indirect, but it turns the most common create path into a captured one.

Layer 3Daily reconciliation for everything invisible

Client-SDK email and password changes, bulk deletes (which skip the v1 onDelete trigger entirely), metadata writes that failed, and destination over-copies — none of these emit any capturable event. A scheduled job does a full Auth export and diff (there is no incremental export at ~4.7M users) using the same selection policy as live sync, then enqueues repairs through the same queue/ledger path. One mechanism closes four gaps at once.

Reconciliation's cost sets an honest ceiling: it's hours-to-daily work, not live capture. The accepted staleness windows are explicit: 24–48h provisional drift for password hashes, emailVerified, and provider links. Email changes carry the same window but are flagged as the class most likely to need tightening — and if product tolerance demands a tighter window than reconciliation can deliver, the named consequence is a write-through dependency in Duet or the client Auth paths. A recorded fork, not a surprise.

Why not just hook beforeUserCreated for everything? Two reasons: importUsers deliberately bypasses blocking hooks (so Memberful/Chorus users would be invisible), and blocking hooks run inside the signup latency budget — the design forbids any inline cross-project I/O there, even if T0.1's spike had failed and made inline writes tempting.
Section 07

Life of a failure

The system's central promise — "non-blocking but fully observable" — is enforced by one rule and one datastore.

The rule: a queued task returns terminal success only after the destination work succeeded, was intentionally dispositioned, or a ledger record has been persisted. Cloud Tasks deletes tasks after retry exhaustion — queue state is transport, not memory — so the worker must write the ledger before acking a terminal failure. Silent loss becomes structurally impossible rather than procedurally avoided.

The failure taxonomy covers every link in the chain, including the meta-failures:

  • Enqueue failure — the handler couldn't even queue the work. That's a sync failure too; it writes the ledger directly.
  • Destination write failure — transient ones retry via Cloud Tasks; terminal ones ledger-then-ack.
  • Policy mismatch — policy tightened while a task waited; the worker applies the tighter policy and records the divergence.
  • Ledger write failure — the failure record itself failed. A dedicated high-signal metric, LEDGER_WRITE_FAILED, alerts on the one case the ledger can't cover itself. 
interface FailureLedgerRecord {
  idempotencyKey: string;
  status: "pending" | "retrying" | "terminal_failed" | "replayed"
        | "resolved" | "ignored_expected_drift"
        | "policy_unknown" | "policy_mismatch" | "pruned";
  failureClass: "enqueue_failed" | "destination_write_failed"
        | "terminal_queue_failed" | "ledger_write_failed" | /* … */;
  // searchable by: user/record, path, operation, project, status
  database?: string;  path?: string;  uid?: string;
  errorCode?: string;  attemptCount: number;
  firstSeenAt: string;  replayedAt?: string;
  payloadPointer?: string;  // pointer, not payload — re-read source on replay
}
// Firestore
firestore:${database}:${path}:set
firestore:${database}:${path}:delete
// Auth (UID-keyed; importUsers is idempotent by uid)
auth:${uid}:import · auth:${uid}:update · auth:${uid}:delete
// External side effects (hashes — no raw PII in identifiers)
side_effect:jukebox:${uid}
side_effect:supporting_cast:${uid}:remove:${priceId}
side_effect:mongo:${emailHash}:delete

Replay is an audited operator action: look up the ledger record by key, re-read the current source state where available (never prefer a stale payload over a possible re-read), and enqueue again — with requestedBy and reason recorded. External side effects get one extra guard: a SideEffectExecutionRecord checked before every provider call, because Supporting Cast and Jukebox won't deduplicate retries for you.

Section 08

The seed: backfill & the no-gap invariant

Live sync is the delta layer around a bulk seed — and one ordering rule decides whether the combination is correct.

Nobody mirrors 4.7M users through triggers. The destination baseline comes from backfill tooling, in scope for this project (single operator — there's no separate migration team): a documented runbook of gcloud/Firebase CLI commands for broad surfaces, plus repo-resident scripts where native tooling can't do the job — Auth seeding via Admin SDK importUsers batches (the CLI drops custom claims), policy-aware Firestore copy for selective/redacted surfaces, and parity checks.

The correctness of "seed + live delta" hangs on a single invariant, schema-validated in the handoff record:

The no-gap invariant liveCaptureEnabledAt ≤ seedSnapshotTime. Enable capture first, then take the seed snapshot (PITR's --snapshot-time can even snapshot the past). Writes landing during the overlap apply twice — harmlessly, because destination writes are idempotent and last-writer-wins by source time. The reverse order leaves a window where writes are captured by nothing: invisible until some future reconciliation maybe finds them. 
interface BackfillHandoff {
  handoffId: string;
  policyId: string;            // MUST match live sync's policy
  liveCaptureEnabledAt: string;
  seedSnapshotTime: string;     // validated: capture ≤ snapshot
  includedSurfaces: string[];
  excludedSurfaces: string[];
  expectedDrift: string[];
  parityResults: ParityResult[];
  status: "running" | "passed" | "failed" | "blocked";
}

The seed consumes the same SyncPolicyVersion as live sync — same selection, same redaction, same exclusions. That's not tidiness; it's what makes the parity gate meaningful. If seed and live sync filtered differently, every count comparison would drown in expected mismatches and real drift would hide in the noise. The one operational hazard the tooling treats with special care: Auth export files contain 4.7M emails plus password hashes. They are GCS-only — no local copies — with tight IAM, access logging, and lifecycle auto-deletion after import verification. A second, standing PII copy lives outside the seed entirely: an ongoing BigQuery export of user_metadata (the analytics feed — distinct from the BigQuery parity-diff tooling) is a live downstream mirror of the identity store, and cutover has to decide whether it gets repointed or re-pinned so it doesn't keep mirroring the source after the flip.

Section 09

Reconciliation & pruning

Two halves of the same loop: find what live sync missed, and remove what broad copy brought along.

Reconciliation runs daily: export source Auth, diff against the destination for in-scope users, and enqueue repairs — Auth field drift, missed signups whose metadata write failed, bulk deletes that fired no trigger, and records the predicate says shouldn't be in the destination at all. Repairs flow through the same queues and ledger as live sync; there is deliberately no second, quieter repair path that could disagree with the first.

Pruning is the cleanup half of the copy_then_prune bargain. Reconciliation and policy evaluation generate an over-copy inventory; the inventory generates a prune manifest; and destructive pruning runs only from a generated manifest — never from an ad-hoc query an operator types at 2am. Manifests support dry-run and resume, record who ran them and why, and a pre-cutover prune gate blocks readiness until remaining over-copy is removed or explicitly dispositioned. 

interface DestinationTombstone {
  key: string;
  targetType: "auth_user" | "firestore_doc";
  deletedAtSourceTime: string;
  sourceEventId: string;
}
// Every destination create/update checks for a newer tombstone first.
// A stale retry arriving after a delete is ignored or ledgered as stale —
// unordered delivery must never resurrect a deleted user.
Safety stack for destructive tooling Explicit --source-project / --destination-project / --policy-id flags · dry-run required before execute · manifests generated from policy output only · audited operator reason. Single-operator migrations don't get code review at run time; the guardrails have to live in the tools.
Section 10

Readiness gates & passivity

Sync cannot be enabled by enthusiasm. It fails closed until the destination provably satisfies a readiness contract.

The readiness check is an IAM-protected entrypoint that verifies 15 gates:

  • Destination Auth import/hash/provider readiness · the named Firestore databases and their locations · cross-project IAM
  • Secrets and config — including the project-literal replacement work · the control store and ledger location · Cloud Tasks queues · GCS export bucket controls
  • Destination sendEmail/processLogin deployed before NYMag web's env flip · FIREBASE_CLOUD_FUNCTION_SECRET continuity for its JWT-authed function calls · authorized domains for the full NYMag brand-domain family (nymag, thecut, vulture, grubstreet, intelligencer, curbed, strategist)
  • Destination passivity · the backfill handoff invariant · the SyncVolumeEstimate · the prune gate
  • The (default)-database recount — a legacy relic classified stale on read-only evidence (17 documents untouched since mid-2024), with owner confirmation and the pre-cutover recount as the residual controls

Any failure blocks enablement. The same fail-closed posture applies at cutover: readiness isn't claimed until representative client paths resolve against the destination (Section 11).

Destination passivity is the other standing rule. During the sync window, the destination project is a data sink: its scheduled jobs, webhooks, and side-effect triggers stay disabled or gated. The hazard is concrete — if reconcilePatreonMembers ever ran in both projects, the shared Patreon refresh-token rotation would produce mutual invalid_grant failures and double entitlement revocations; Memberful can only point its webhook at one project; Mailgun would double-send. Each external side effect gets exactly one owning project at a time, and ownership transfers are explicit cutover steps — enforced by deploy gating and config flags, not operator memory.

One repo, two projects, different behavior This repo's code historically gated behavior on project literals — GCLOUD_PROJECT === "vox-media-identity" controls the NYMag Mongo cleanup and Mailgun validation; the tenant ID rides on another literal. Deployed unmodified to the destination, those branches silently no-op. Replacing them with destination-aware config is in-scope implementation work, and the cutover smoke tests exercise exactly these behaviors.
Section 11

Cutover day

When the gates are green, cutover is three client flips of the moving company's clients — each with a different shape, all validated against the destination first.

This walks the SpinCo-moves direction, so the clients that flip are Duet, NYMag web, and the NYMag app; the inventory below is deliberately scoped to those moving clients. In the mirror direction (PubCo moves), the flipping clients would instead be Eater — whose React Native app superseded an earlier native Swift iOS app — The Verge, and SB Nation, and the staying side becomes a no-op.

Three clients consume the identity project, and each was investigated in its own codebase rather than assumed:

Client What it is The flip
Duet (vox.com + network sites) Web platform; Redis-backed sessions; reads destination Auth + Firestore on account pages and session refresh. Env swap. Regular pages survive on Duet-signed sessions; account paths need destination data present — which is the whole point of the sync.
NYMag web (nymag/sites) Separate Amphora stack — not Duet. Own Redis sessions + Mongo profile store; calls this repo's processLogin/sendEmail. One env change. Its function URLs derive from FIREBASE_AUTH_PROJECT_ID, so auth config and function targets flip atomically — provided the destination has those functions deployed first.
NYMag mobile Expo/React Native app; routes identity through nymag/sites; writes nymag/delete_users client-side. Forced-update release with new Firebase config files. Config-only — no app code changes.

Cutover readiness is proven by representative client paths against the destination: Duet session refresh, email check/change, auth-link sending, entitlement and metadata reads; NYMag web login across all four providers, /oauth/user/profile, and function round-trips; the mobile /mobile/* chain. Users should expect one re-login — refresh tokens are project-bound and die at the flip; that cost was accepted explicitly. Then side effects activate one owner at a time, and the sequencing follows the program's de-risking order: vox.com first (reversible, proves the runbook), NYMag web second, NYMag apps last (the irreversible forced update, on a proven path).

Rollback, before and after Before cutover: trivially safe — disable destination writes; the source was never not the truth; repair or reseed the destination at leisure. After cutover: a separate explicit decision, because reverse sync is out of scope by design. The gates exist precisely so that the "after" case starts from proven parity.
