Bird's-eye deck · Identity Store Split

Splitting one shared identity
platform into two

Every Vox Media brand shares one Firebase identity project. SpinCo (NYMag + Vox.com) and PubCo are splitting it in two — one company stays on the shared project, the other stands up its own — and the moving company's users' logins, profiles, and entitlements have to travel with them, without anyone noticing. This is the plan: seed a copy, mirror every change live, repair the drift, and prove it's safe before anything flips.

~4.7M shared users one-way sync until cutover UIDs preserved exactly 51 implementation tasks
Why this exists

One identity pool, two companies

The split runs along two groupings: SpinCo (NYMag + Vox.com) and PubCo (The Verge, Eater, SB Nation — now PMX, a PMC subsidiary). One company keeps the existing Firebase project; the other stands up its own. Which way the move runs isn't decided yet — this deck walks it through with SpinCo as the worked example, and the mirror case (PubCo moving) holds symmetrically.

The shared platform
One Firebase Auth pool (~4.7M users) plus named Firestore databases hold logins, profiles, login history, and entitlements for every brand at once.
The non-negotiable
Firebase UIDs must survive the move byte-for-byte. Sessions, comments, podcasts, subscriptions — every downstream system keys off the UID.
Source of truth
Until cutover, the old project stays authoritative. Sync is strictly one-way — there is no reverse sync, not even for rollback.
Invisible to users
A destination outage must never break a login on nymag.com. Sync failures are non-blocking — but every one is recorded where an operator can see and replay it.
Why a snapshot isn't enough Users keep logging in, changing emails, and buying subscriptions between any copy and the actual cutover. The copy has to stay continuously current — that's the whole project.
The three hard facts

Why this isn't "add a hook to login"

Fact 1Writers everywhere
Most identity writes don't come from the identity codebase. Duet writes profiles and entitlements directly; the NYMag app writes deletion requests straight from the phone. Hooking our own handlers would miss most of the data.
Fact 2No brand labels
User records aren't tagged by brand. Vox members are cleanly identifiable; NYMag's older web accounts are not. "Just sync the SpinCo users" is partly impossible — filtering has to be policy with fallbacks.
Fact 3Invisible changes
A user changing their password touches no code we control and no document we can watch. Some changes can only be caught by periodically comparing the two projects.
Each fact forces a piece of the design Writers-everywhere forces database-level capture. No-labels forces an explicit policy layer. Invisible-changes forces a reconciliation backstop. The architecture is these three answers, assembled.
The strategy

Seed it, mirror it, repair it, prove it

Live sync doesn't replace the bulk copy — it wraps around it. Four layers, each covering the last one's blind spot.

1 · Seed
Bulk export/import establishes the destination baseline — native gcloud tooling for broad surfaces, custom scripts where filtering or Auth custom claims demand it. ~4.7M users don't flow through triggers
2 · Mirror
Live capture mirrors in-scope Firestore changes fast (~1.2s in staging; production target sub-minute p95) — including writes from systems that don't know the sync exists. Auth-only changes ride the daily repair loop. staging-proven trigger path
3 · Repair
Daily reconciliation diffs the two projects and fixes what live capture can't see: password changes, bulk deletes, failed writes. plus pruning of approved over-copy
4 · Prove
Fail-closed gates: parity counts, a drained failure ledger, real client paths resolving against the destination — before cutover readiness can be claimed. green gates, then flip
Capture

Watch the database, not the code

Broad Firestore triggers observe every write to the database itself — so Duet, the NYMag app, and any future writer are captured without changing a line of their code.

provenDe-risked before chosen
A staging spike deployed a trigger against the named database before the design committed: verdict GO, ~1.2s delivery, and a 10-write burst arrived complete but out of order — which is why every mirror write is idempotent and resolves conflicts by source timestamp, never arrival order.
Unknowns can't slip through
If a new, unclassified collection ever appears, the catch-all still sees it — it's recorded as policy_unknown and production readiness blocks until someone classifies it. Coverage degrades into a visible question, never a silent gap.
Policy

One policy decides what travels

Two separate questions for every surface: which records sync, and which fields inside them travel. One versioned policy answers both — for live sync, the seed, reconciliation, and pruning alike.

Mode Used when Example
Selective The brand predicate is clean Vox members via membership entitlements
Redact at mirror time The record syncs but carries other brands' fields Strip SB Nation data from a SpinCo user's profile
Broad copy legal-gated Clean filtering is impossible NYMag's unattributable older accounts
Copy, then prune legal-gated Broad copy now, clean up in the destination before cutover Over-copy is inventoried, then removed via audited manifests
Excluded Never applicable to SpinCo Games data, Eater data, Chorus migration collections
Expected drift Differences are known and accepted Parity checks record them instead of flagging failures
Pruning is a feature, not a failure No brand's full population is cleanly filterable — entitlement and membership signals cover only paying members — so where a residual can't be filtered, the accepted model is broad copy plus destination-side pruning, provided the over-copy is legally approved, visible, bounded, and pruned before cutover. The exposure is symmetric: whichever company stays is the one whose PII gets over-copied, so broad modes require a recorded legal approval reference wherever the staying company's PII can enter the destination.
Observability

No failure is silent

"Non-blocking" without observability would just be drift with extra steps. One rule makes silent loss structurally impossible:

The ledger rule A sync task may only leave the retry queue after its work succeeded, was intentionally dispositioned, or a failure-ledger record was durably written. The queue is transport; the ledger is memory.
Every failure class covered
Couldn't enqueue? Ledger. Destination write exhausted retries? Ledger first, then ack. Policy changed mid-flight? Recorded. Even the ledger failing has its own dedicated alert (LEDGER_WRITE_FAILED).
Replayable, searchable, audited
Operators can search failures by user, path, operation, or status — and replay by key. Replays re-read current source state (never stale payloads) and record who ran them and why.
Seeding

The seed has one rule: no gap

Bulk copy and live sync only combine correctly in one order — and the design enforces it as schema, not advice.

liveCaptureEnabledAt ≤ seedSnapshotTime — capture first, then snapshot. Writes landing during the overlap apply twice, harmlessly, because every destination write is idempotent. The reverse order leaves a window where changes are captured by nothing. The invariant is validated in the seed-handoff record itself: a handoff that violates it cannot pass readiness.

The one truly sensitive artifact Auth export files contain 4.7M emails plus password hashes. They live in GCS only — no local copies — with tight IAM, access logging, and automatic deletion after import verification.
Drift & cleanup

The repair loop: reconcile, then prune

Reconciliation — find what capture can't see

  • Daily full Auth export + diff against the destination
  • Catches client-side password/email changes, bulk deletes, failed writes, and records that shouldn't be there
  • Repairs flow through the same queue and ledger as live sync — no second, quieter path
  • Accepted staleness: 24–48h for Auth-only fields, with email changes flagged as the window most likely to tighten

Pruning — clean up the approved over-copy

  • Reconciliation's over-copy inventory generates prune manifests
  • Destructive pruning runs only from manifests — dry-run first, resumable, with operator and reason recorded
  • A pre-cutover prune gate blocks readiness until over-copy is removed or explicitly dispositioned
  • Deleted users stay deleted: tombstones stop late-arriving writes from resurrecting anything
Safety rails

Fail closed, stay passive

enablement12 readiness gates
Twelve gates: Auth import capability, the named databases, IAM, secrets, queues, the control store, volume/cost estimates, the seed handoff, destination functions deployed for NYMag web, its JWT-secret continuity, the seven-brand authorized-domain family — and more. Any missing gate blocks enablement. Enthusiasm is not a gate.
split-brainDestination passivity
During the sync window the destination is a data sink: its scheduled jobs, webhooks, and side effects stay off. If the Patreon job ever ran in both projects, the shared token rotation would lock both out and double-revoke subscriptions. Each integration has one owning project at a time — transfers are explicit cutover steps, enforced by config, not memory.
Also in scope: the repo's own assumptions Code that gates behavior on GCLOUD_PROJECT === "vox-media-identity" silently no-ops in the new project. Replacing these hardcoded project checks with destination-aware config is tracked implementation work — and cutover smoke tests exercise exactly those paths.
Cutover

Three client flips, in de-risking order

Every consumer of the identity project was investigated in its own codebase. Cutover readiness means real client paths resolve against the destination — then the flips happen one at a time.

Order Client The flip Why this order
1 vox.com (Duet) Environment swap Reversible — proves the runbook with the lowest stakes
2 NYMag web (own stack — not Duet) One env change; its function URLs derive from the project ID, so auth config and functions flip atomically Still reversible (redeploy); runs on the runbook vox.com proved. Hard prerequisite: destination functions deployed first
3 NYMag apps (iOS + Android) Forced-update release with new Firebase config — config only, no code Irreversible and slowest to roll out — goes last, on a proven path
The accepted user cost One re-login. Refresh tokens are bound to the old project and die at the flip. Web sessions otherwise survive; account pages work because the destination data is already there — which is the entire point of the sync.
