An engineer's tour

Honeypot Engagement

How a rec, a reply, or a WordPress publish becomes a number a public reader sees — and what's actually doing the work between Cyclone, Honeypot, and Duet.

Read time ~12 min Audience Cyclone / Honeycomb / Duet adjacent eng Last touched 2026-05-11
Section 01

The big picture

One narrow projection moves between three systems. The diagram on the right shows it.

Three things own engagement in our world. Cyclone is the source of truth for content (FanPosts, reply threads, WordPress-backed roots) and for the user actions that change a counter — recs, replies, moderation, deletion. Honeypot is the read-side database that powers public content cards and feed pages. Duet is the public serving layer in front of Honeypot — feed renders and the cached hydration endpoint that keeps counters fresh on a page.

Before this project, the engagement story was uneven. content.recs already lived on Cyclone's content row as a real counter, but reply count was only ever derived — counted on demand from rows in the QuickPost tree. Worse, Duet couldn't get either number without either calling Cyclone or doing expensive joins. So we cut a narrow projection: a single replicated table, content_engagement_stats, that Cyclone writes and Honeypot mirrors. Six columns, one job — serve public counters fast.

A note on timing By the time you're reading this, the Cyclone and Honeycomb pieces are in PR or merged. The WP-to-Cyclone Lambda and Duet's public hydration endpoint should be landing within days — they're designed alongside this work and described here as part of the system.

Everything that follows is a slice of the system on the right. Five "life of …" walks show what happens when a single thing changes; the last few sections cover operations, the trade-offs we made, and how to dig deeper.

Section 02

Identity model & vocabulary

Three identifiers carry the whole projection. Get these right and the rest falls into place.

Every row in content_engagement_stats answers two questions simultaneously: who is this counter for on the public internet? and which Cyclone content does it belong to? Those are different questions, so the row uses different identifiers for each.

Public key (source, source_id)

The primary key. source is one of cyclone or wordpress — a namespace. source_id is the public lookup value in that namespace: a Cyclone shortID for Cyclone-native FanPosts, or the WordPress EventBridge detail.subject.id (the same node ID Duet uses) for WordPress-backed roots. This pair is stable across systems, replicates cleanly, and matches the join key Honeypot's content_cards already uses.

Internal anchor content_id

The Cyclone Postgres UUID for the canonical content row. Unique on the stats table. This is how Cyclone's write hooks recognize "the stats row for this content," and how Cyclone reconciliation can sample-check against canonical state. Duet does not use it. 

type EngagementSource = "cyclone" | "wordpress";

interface ContentEngagementStats {
  source: EngagementSource;
  sourceId: string;   // shortID or WP node ID
  contentId: string;  // Cyclone UUID, unique
  recs: number;
  replyCount: number;
  updatedAt: Date;
}

The gatekeeper the eligibility predicate

Not all content gets a stats row. Only public, top-level, hydratable content qualifies: Cyclone-native FanPost rows that are not deleted and are in a published moderation state, plus WordPress-backed ExternalRoot rows that decode to a supported resource type and have no active tombstone. QuickPost replies do not get their own stats rows — they contribute to a parent's reply_count, nothing more.

A single helper, the engagement eligibility predicate, encodes this rule. Live write hooks call it. The WordPress sync route calls it. Backfill calls it. Validation calls it. Anywhere we have to decide "should this content have an active stats row?", it's the same function. If you remember one thing from this section, remember that.

Section 03

Life of a rec on a FanPost

The simpler of the two count stories. content.recs already existed; we mirror it into the projection.

A reader hits the rec button on a Cyclone-native FanPost. The mutation lands on Cyclone's GraphQL recContent resolver. ContentObjectRepository creates the reaction row and bumps content.recs. So far, nothing new — that's Cyclone's existing rec write path, untouched by this project.

What's new is a writer hook colocated with the rec mutation. After the canonical write commits, the hook runs the engagement eligibility predicate against the target content. For an eligible FanPost the hook calls EngagementStatsWriter.upsertForContent(contentId), which recomputes the public counter values from canonical state and upserts the matching row in content_engagement_stats. The write is synchronous; the user's mutation latency includes it. For v1 we chose correctness over deferred maintenance — the projection is narrow enough that synchronous writes are not the bottleneck. 

interface EngagementStatsWriter {
  upsertForContent(contentId: string): Promise<void>;
  removeForContent(contentId: string): Promise<void>;
  refreshReplyCount(rootContentId: string): Promise<void>;
}

The transaction commits. Cyclone's Postgres publication picks up the change in the stats table and ships it. Honeypot's logical replication subscription receives it and the row appears in Honeypot's content_engagement_stats with the same shape and the same updated_at value Cyclone wrote — the replica preserves source freshness, not receive time. End-to-end from rec-click to public visibility is roughly Cyclone write + replication lag + Fastly's s-maxage=15 window.

Unrec follows the same path. The reaction row is removed, content.recs drops, the hook recomputes and upserts. The stats row never disappears for an unrec — only the count moves.

Why recompute, not increment? Even though rec is a "single +1," the writer reads content.recs from canonical Cyclone state and upserts that value. Blind increments diverge whenever a moderation or deletion path moves the underlying number out of band. Recomputing is dull, deterministic, and self-healing.
Section 04

Life of a reply on a FanPost

The novel projection. Before this project, no one stored reply_count; it was a SELECT COUNT(*) waiting to happen.

A reader posts a reply to a FanPost. Cyclone's createQuickPost resolver runs, the new QuickPost row is created, moderation routing decides whether it's published, rejected, or held pending. Once moderation has resolved into a final state, a writer hook walks up to the root contentId and calls refreshReplyCount(rootContentId).

This is where the story diverges from rec. refreshReplyCount does not increment. It re-queries the canonical state — "give me the count of QuickPost children of this root where the moderation status is published and deletedAt is null" — and upserts that exact number into the stats row's reply_count. Every reply create, delete, or moderation transition under the root triggers the same recomputation. 

-- refreshReplyCount, conceptually:
update content_engagement_stats s
set reply_count = (
  select count(*)
  from content q
  where q.parent_root_id = s.content_id
    and q.kind = 'QuickPost'
    and q.deleted_at is null
    and q.moderation_status in ('approved', 'none')
),
    updated_at = now()
where s.content_id = $1;

Why pay the recompute cost on every reply event? Because reply_count has many ways to change that aren't "user clicks reply." Modinator moves a reply between queues. Implio flags a reply hours later. A moderator deletes a reply. A QuickPost author deletes their own post. Each of those flips a single child's countable state, and a blind delta is easy to get wrong in five places. One recompute, one source of truth.

The hook fires from several mutation paths — createQuickPost, deleteContent for reply deletions, rejectContent when a reply is moderated, and the Modinator/Implio queue handlers we'll cover next. The eligibility predicate decides whether the root is still eligible to have a stats row in the first place; if the root has been tombstoned or removed, refreshReplyCount is a no-op against a row that doesn't exist.

After the upsert, replication carries the new reply_count to Honeypot the same way it carried recs in section 3. Public visibility is bound by the same replication lag plus the Fastly TTL on the hydration endpoint.

Section 05

Life of a WordPress publish

The cross-system write path. WordPress is the source, Cyclone is the system of record, and the Lambda is the strict boundary between them.

A WordPress editor publishes a post on one of the Vox properties. WordPress emits an EventBridge event onto the shared bus — post.published, post.updated, or post.unpublished — carrying the canonical detail.subject.id (the same node ID Duet uses to address that resource) plus event metadata: id, type, timestamp.

The Honeycomb-owned wp-to-cyclone Lambda is the only consumer of that event for the engagement lane. It translates the event into a Cyclone-facing sync call: POST /services/wordpress-content-sync, authenticated with x-wordpress-sync-key. This is a dedicated service auth surface — not a GraphQL mutation, not a user-facing route, not the Modinator or Implio webhook credentials. The Lambda is the only authorized caller. 

interface WordPressContentSyncRequest {
  action: "upsert" | "tombstone";
  source: "wordpress";
  sourceId: string;
  communityId: string;
  resourceType: string;
  event: {
    id: string;
    type: "post.published" | "post.updated" | "post.unpublished";
    timestamp: string;
  };
  content?: {
    title?: string;
    url?: string;
    friendlyId?: string;
    metadata?: Record<string, unknown>;
  };
}

Cyclone's route does four things, in order. First, it validates the auth header and the request shape. Second, it consults wordpress_content_sync_state — a Cyclone-local table keyed by (source, source_id, community_id) — to enforce event ordering. An incoming event whose timestamp is older than the row's last_event_timestamp is rejected with 409; a replay of the same event.id returns the previous terminal status idempotently. Third, the WordPress identity classifier decodes the friendlyID (or accepts an explicit identity if implemented) and verifies that the decoded resource type is on the supported list: linkPost, package, post, stream, videoPost, customStory. embedStory is explicitly excluded for v1.

Fourth, Cyclone upserts (or tombstones) the matching ExternalRoot content row and updates wordpress_content_sync_state. The engagement eligibility predicate runs against the updated ExternalRoot; if eligible, an engagement stats row is upserted just like for a FanPost. If the action is tombstone, the stats row is removed — but the sync state is preserved, so a future republish can recreate the row against the same Cyclone UUID without churn.

From here on the flow is identical to a Cyclone-native rec: the stats row replicates to Honeypot, and Duet sees the new counters on its next read.

Idempotency, in one line Same event delivered twice converges on the same row. Newer events win; equal timestamps with different event IDs use deterministic precedence (tombstone > upsert) so unpublish cannot be silently undone by a same-time publish replay.
Section 06

Life of a moderation change

Eligibility isn't static. A queue change in Modinator can make a stats row appear, disappear, or stay put — same code path either way.

Cyclone hands user-generated content to Modinator (the in-monorepo moderation server at apps/mod-server) on creation. Modinator's rules engine and human moderators move content between named queues; each queue maps to a ContentModerationStatus on the Cyclone side. When a moderator moves something — say, from a "needs review" queue to "approved" — Modinator POSTs a ContentQueueChanged webhook back to Cyclone, authenticated with x-webhook-key.

Cyclone's handleContentQueueChanged resolves the queue name to a moderation status, compares it with the content's previous status, and updates content.moderation_status. If visibility changed, the same writer hooks that fire on user actions fire here too: re-evaluate eligibility, upsert or remove the stats row, refresh reply count on the parent if the content was a reply. 

function isPublishedForStats(status: ContentModerationStatus | null): boolean {
  // approved + none (no moderation needed) are public.
  // pending, rejected, deleted are not.
  return status === ContentModerationStatus.Approved || status === ContentModerationStatus.None;
}

Three concrete cases:

  • Pending → Approved on a FanPost. Eligibility flips from false to true; the writer hook upserts a fresh stats row with current recs/replyCount.
  • Approved → Rejected on a FanPost. Eligibility flips from true to false; the writer hook removes the stats row. Replication carries the delete to Honeypot, Duet stops returning a counter for that token (the hydration endpoint returns status: "missing").
  • Approved → Rejected on a QuickPost reply. The reply itself never had its own stats row, but its parent's reply_count drops by one. refreshReplyCount(rootContentId) handles that.

Implio, our third-party moderation service, drives a similar path — Cyclone consumes Implio's transition events and lands them through the same writer hooks. The shape is different, but the destination is the same: re-evaluate eligibility, recompute counters, upsert or remove.

WordPress tombstones (a post.unpublished event from section 5) are technically a moderation-shaped change too: the ExternalRoot becomes ineligible, the stats row is removed, but the sync state survives so the row can be brought back if WordPress republishes.

Section 07

Life of a Duet hydration request

The read side. Public, anonymous, batched, cacheable for fifteen seconds, and strict about its input format.

A reader loads a page that contains, say, twelve cards — a mix of FanPosts and WordPress-backed roots. The page wants current rec/reply counters for all of them in one request. Official Duet callers build a canonical URL: one c= query parameter per item, prefixes uppercase (CY: for Cyclone-native, WP: for WordPress), payloads case-preserved, the whole set deduplicated and sorted in ASCII order, chunked under 2048 characters and 100 tokens. 

GET /api/honeypot/v1/engagement
    ?c=CY:abc123
    &c=CY:zzz999
    &c=WP:ZXQ5OnBvc3Q6NTY3OA

The request hits Fastly first. Cache-Control: public, s-maxage=15 means that for any given canonical URL, Fastly will absorb up to fifteen seconds of traffic into a single origin call (and Fastly request collapsing absorbs concurrent misses). The canonical URL ordering is doing a lot of work here: identical token sets sorted differently would generate different cache keys and tank the hit ratio. v1 intentionally rejects non-canonical orderings with 400 rather than normalizing at origin, because the cache key is already locked in by the time the request reaches us.

On a cache miss, Duet parses and validates the tokens, then queries the Honeypot replica with a VALUES list of (source, source_id) pairs left-joined against content_engagement_stats. Each token gets exactly one result row — found rows return counters and the Cyclone-source updated_at; valid tokens with no matching stats row return status: "missing" rather than a zero counter. 

interface EngagementHydrationResponse {
  data: {
    generatedAt: string;           // response build time
    items: EngagementHydrationItem[];
  };
}

type EngagementHydrationItem =
  | { token: string; status: "found";
      source: EngagementSource;
      sourceId: string;
      contentId: string;
      recs: number;
      replyCount: number;
      updatedAt: string; }
  | { token: string; status: "missing"; };

The found/missing distinction is doing important work. A "missing" row is not the same as a zero counter. Server-rendered HTML on the same page may already display a number — maybe the page was rendered from a feed-anchored left join where missing stats coalesced to zero for display, or maybe the row is just lagging replication. Clients are told explicitly when there is no replicated stats row yet, so they can choose to keep the server-rendered number rather than overwrite it with zero.

Feed-anchored reads work differently from hydration. Feed pages query content_cards left joined to content_engagement_stats on (source, source_id); missing stats rows are not errors and counters coalesce to zero for card display. That's the right default when the surrounding query already exists and missing stats look the same as "no engagement yet." It's the wrong default for hydration, which is updating a counter that's already visible on screen.

Section 08

Operations

Two things you'll do by hand at least once: backfill the projection, and set up logical replication.

Backfill One CLI, two modes

The backfill/reconciliation path is a Cyclone-side service plus CLI. It scans canonical content state, runs the engagement eligibility predicate row by row, computes recs and reply_count the same way the live writer does, and either reports what would change (--dry-run) or applies the changes (mutating mode). Mutating runs only touch rows within the explicit scope (community, source, etc.) — they will not garbage-collect stats rows you didn't ask them to. 

interface EngagementBackfillReport {
  dryRun: boolean;
  scanned: number;
  inserted: number;
  updated: number;
  unchanged: number;
  removed: number;
  skipped: number;
  errored: number;
  bySource: Record<string, number>;
  byContentType: Record<string, number>;
  byWordPressResourceType: Record<string, number>;
  skippedReasons: Record<string, number>;
}

The standard rollout pattern: dry-run scoped by environment and community, review the report (especially the skippedReasons map for surprises like unsupported WP resource types or undecodable friendlyIDs), then run mutating with the same scope. Repeat in production after staging acceptance. Backfill is idempotent — safe to rerun.

Replication Operations-owned, not application-owned

The PostgreSQL publication on Cyclone and the subscription on Honeypot are not managed from application code. Cyclone's migration creates the source table; Honeypot's migration creates the target table; everything else — the publication, the subscription, the replication slot, network paths, replication-user credentials — is operations/runbook work, with Terraform owning the prerequisites (RDS logical-replication parameters, security groups, managed secrets).

The runbook lives in apps/honeycomb-docs/docs/operations/honeypot-engagement-replication.md on the Honeycomb side. It covers publisher readiness checks, subscriber setup, staging validation SQL (row counts by source, sample joins, orphan rows, freshness distribution, subscription health), and the disable/rollback path. Staging always goes first; production repeats only after staging signoff and Duet coordination on package version.

Validation What to look at first

The most useful staging checks, in priority order: subscription is alive and lag is bounded; row counts by source roughly match canonical Cyclone counts; sampled recs and reply_count match canonical state on the same content; orphan stats (rows on Honeypot with no matching content_cards) and missing stats (cards without rows) trend toward zero as replication catches up.

Section 09

Why these choices

A few decisions look obvious in hindsight. They weren't.

Narrow projection over content denormalization

The replicated table is six columns. It does not carry content_type, author data, body, card fields, or feed-ranking signals. Anything richer lives behind content_cards on the Honeypot side, anchored by the same (source, source_id) pair. That separation lets the public counter contract stay small and stable, replication stays cheap, and "what is this content?" stays a single Honeypot question rather than two systems trying to agree on a denormalized card shape.

(source, source_id) as the primary key

We chose a composite text PK over a surrogate UUID for the public identity. Surrogate IDs would have meant minting them on the Cyclone side and shipping them to Honeypot, which is fragile under replication and makes Duet lookups awkward. The composite key is what Honeypot's content_cards already uses, so feed-anchored left joins work without a translation step. content_id is kept as a unique secondary identifier purely for Cyclone-internal anchoring.

No foreign key between stats and content_cards

Logical replication can deliver a stats row before content_cards sees the matching card, or vice versa. A foreign key would have turned that ordering into a hard error. We chose to tolerate temporary orphans at the application level: feed reads left-join and coalesce, hydration distinguishes found from missing, and reconciliation surfaces orphan rows operationally rather than blocking writes.

One eligibility predicate, called everywhere

The single biggest correctness lever in this design. If live writer hooks, the WordPress sync route, and backfill all encoded eligibility differently, the projection would drift the instant anyone forgot to update one of them. Centralizing the rule means there are five places that mutate stats rows, but only one place that decides "should a row exist?"

WordPress sync state outside the replicated table

wordpress_content_sync_state tracks last_event_id, last_event_timestamp, last_action, and tombstone state for idempotency and event ordering. It is intentionally a Cyclone-only table — Honeypot doesn't need it, Duet doesn't need it, and shipping it through replication would have polluted the public contract with implementation details of one specific source's sync lane.

Dedicated service auth for the WordPress route

The WordPress sync route lives at POST /services/wordpress-content-sync with its own x-wordpress-sync-key. Not GraphQL. Not a user mutation under a service token. Not the Modinator or Implio webhook credentials. The boundary is explicit: only the Honeycomb Lambda can call this route, and only this route can write WordPress-backed content. If we ever need a second source (Forum imports, internal CMS, anything), it gets its own route, its own credential, and its own sync state — not a generalized "any service can mutate any content" surface.

Synchronous writes over queued maintenance for v1

The writer hooks update the stats table inside the same Postgres transaction as the canonical write. That's slower per-mutation than queueing the work, but it makes correctness easier to reason about and removes a class of "stats lag behind canonical state" bugs from launch. BullMQ/deferred maintenance is on the table if staging shows real write-pressure problems; the projection is narrow enough that it probably won't.

Section 10

Glossary

Quick reference for terms that show up everywhere in this system.

Term Definition
FanPost A Cyclone-native top-level post. Eligible for a stats row when published and not deleted.
QuickPost A Cyclone-native reply. Never has its own stats row; contributes to a parent root's reply_count.
ExternalRoot A Cyclone content row that represents an externally-sourced root. For v1, "externally-sourced" means WordPress.
friendlyID A field on ExternalRoot encoding the WordPress/Duet node ID as {siteKey}:{resourceType}:{numericId}. The v1 source-identity bridge.
Modinator Vox's in-monorepo moderation server (apps/mod-server). Posts ContentQueueChanged webhooks to Cyclone when content moves between queues.
Implio Third-party moderation service. Drives similar Cyclone updates via its own transition events.
Honeypot The read-side database that powers public content cards and feed pages. Hosts the replicated content_engagement_stats table.
Honeycomb The monorepo that ships @voxmedia/honeypot-db, the replication runbook, and the WP-to-Cyclone Lambda.
Duet The public-facing serving layer. Renders feeds and pages, and exposes /api/honeypot/v1/engagement.
content_cards Honeypot's content card projection. The feed-and-card anchor; remains the visibility filter even when stats are missing.
source_id Public lookup ID inside a source namespace. Cyclone shortID or WordPress node ID.
content_id Cyclone canonical UUID. Unique on the stats table. Used for Cyclone-internal write hooks and reconciliation.
shortID The compact public identifier for a Cyclone FanPost.
