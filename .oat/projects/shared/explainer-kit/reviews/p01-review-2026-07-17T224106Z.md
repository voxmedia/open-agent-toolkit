## Findings

### Critical

- **Default project-scoped adapter cannot find the required user-scoped core** (`.agents/skills/oat-explainer-kit/scripts/check-core.mjs:16`)
  - Issue: `checkCoreCompatibility` derives the core only as a sibling of the
    adapter. The workflows installer defaults to project scope, while the
    adapter's own recovery guidance and design require the utility core at user
    scope. A probe with the adapter under
    `<project>/.agents/skills/oat-explainer-kit` and a valid 1.0.0 core under
    `<home>/.agents/skills/explainer-kit` returns `code: missing`. The tests only
    construct a same-root sibling layout, so they do not exercise the intended
    package boundary.
  - Fix: Pass or resolve the canonical user-scope skills root independently of
    `adapterRoot`, check only that installed canonical location, and add an
    integration case with project-scoped workflows plus user-scoped utility.
    Retain the no-source-checkout-fallback guarantee.
  - Requirement: FR11

### Important

- **Contract validation accepts non-POSIX path values** (`.agents/skills/explainer-kit/scripts/lib/contracts.mjs:60`)
  - Issue: Schema validation is the only validation used by `validate.mjs`, but
    its `safeRelativePath` patterns accept backslashes. A manifest with
    `source.factBasePath: "source\\facts.json"` validates successfully even
    though the design requires POSIX-form paths and `safe-paths.mjs` explicitly
    rejects backslashes. Root confinement is not integrated into the contract
    entry point either, so callers can mistake schema validity for path safety.
  - Fix: Centralize lexical safe-relative-path checks in `validateContract` for
    every path-bearing contract field and reject backslashes, NULs, absolute
    paths, and traversal consistently. Add context-aware root/symlink checks
    where filesystem existence is required, plus negative tests through the
    public validation CLI.
  - Requirement: FR1, NFR2

- **Run-request cross-field invariants are incomplete** (`.agents/skills/explainer-kit/scripts/lib/contracts.mjs:292`)
  - Issue: Runtime validation only checks that publish strategy has a publish
    object. It accepts a supplied fact-base binding containing both `path` and
    `sources`, and it accepts `privacy.retainRawArtDirection: true` when no
    `theme.artDirection` exists. These contradict the documented mutually
    exclusive input contract and the design's explicit privacy validation rule.
    Both cases were reproduced against `validateContract`.
  - Fix: Make supplied/federated fact-base fields mutually exclusive in the
    schema/runtime validator, reject irrelevant `publish` data for non-publish
    strategies, and enforce the retain-raw-direction dependency. Add direct
    negative fixtures for every cross-field branch.
  - Requirement: FR1, NFR2

### Medium

- **Project-state validation permits impossible source/product combinations** (`packages/cli/src/validation/project-state.ts:176`)
  - Issue: Validation rejects only `autonomous_policy + skip`, regardless of
    which product is being validated. It therefore accepts
    `oat_project_explainer: {decision: generate, source: autonomous_policy}` and
    `kickoff_prompt + skip`, although the lifecycle contract permits autonomous
    explainer generation only when explicitly requested (`kickoff_prompt`) and
    does not persist a kickoff skip. The control-plane parser repeats the same
    permissive rule.
  - Fix: Define the allowed decision/source matrix per state field, share or
    mirror it deliberately in CLI and control-plane validation, and add
    table-driven rejection cases for unsupported combinations.
  - Requirement: FR9
